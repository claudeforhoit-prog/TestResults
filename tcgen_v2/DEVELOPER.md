# 개발 지침 (이 생성기를 고치거나 다시 만드는 사람과 AI 용)

이 문서는 테스트 실행 명령 생성기(tcgen) v2 를 고치는 사람과 AI 코딩 도구가 맨 먼저 읽는 문서다.
사용 방법은 `README.md` 에 있다. 이 문서는 구조, 요청 없이 고치면 안 되는 설계 규칙, plan 형식, 시험 방법, 고치는 절차를 적는다.

## 1. AI 에게 시킬 때

```
DEVELOPER.md 와 README.md 를 먼저 읽어라.
0절의 사용자 결정 목록과 3절의 설계 규칙은 사용자가 정한 것이므로 요청 없이 바꾸거나 없애지 마라. 바꿔야 하면 고치기 전에 사용자에게 물어라.
jump/ 의 파일을 고쳤으면 python tools/make_payload.py 를 실행해라.
고친 뒤 python -m unittest discover -s tests -v 가 통과하는지 확인하고, 규칙을 바꿨으면 DEVELOPER.md 와 README.md 와 시험을 같이 고쳐라.
```

## 2. 구조

### 2.1 파일

| 파일 | 하는 일 |
| :-- | :-- |
| `tcgen_core.py` | 화면과 무관한 계산 전부. 앞부분은 v1.4 에서 이어지는 코드(시각 지정 방식의 시각 계산, crontab 줄, 블록 A, B, C, D, 기록 CSV, 리포트용 CSV, 데이터 폴더)이고, 뒷부분이 v2 의 코드다: 설정 프로파일, 시작 시각 계산(`table_starts`), 검증과 plan(`build_seq`, `plan_text`), 타임라인(`timeline_table`), 블록 A, P, S. 버전은 `VERSION` |
| `tcgen_app.py` | 화면(tkinter). 탭 1 실행 명령, 탭 2 모니터링 명령, 탭 3 설정 프로파일, 탭 4 테스트 케이스, 탭 5 생성 결과. 진행 방식은 하나다(v2.12). v1.4 와 같은 시각 지정 화면의 코드는 남아 있으나 화면에서 고를 수 없다(`MODE_LABELS` 의 `time`, `apply_mode`). `load_settings` 는 언제나 `run_mode` 를 `seq` 로 읽는다 |
| `jump/tcrun.sh` | 점프 VM 의 진행 스크립트(POSIX sh). 설치되면 `<작업 폴더>/tcrun`(기본 `~/.tcgen/tcrun`). 자기 위치를 작업 폴더(`D`)로 쓴다 |
| `jump/tcgen_apply.py` | ESX 호스트에서 실행하는 설정 적용 스크립트(Python 3.5 문법, 표준 라이브러리만) |
| `tcgen_payload.py` | 위 두 파일의 내용을 담은 모듈. `tools/make_payload.py` 가 만든다. 직접 고치지 않는다. exe 로 빌드해도 두 파일의 내용이 함께 들어가게 하려고 모듈로 둔다 |
| `tools/make_payload.py` | `jump/` 의 두 파일을 `tcgen_payload.py` 로 옮긴다. `--check` 는 같은지만 확인한다 |
| `tools/release_diff.py` | 올리기 전에 이전 판과 비교해 빠진 화면 칸, 화면 글자, 설정 키, plan 줄 종류, 0절의 결정 번호를 보인다(7절 8번) |
| `run_gui.bat`, `build_windows.bat` | 실행, Windows 실행 파일 빌드(PyInstaller). ASCII, CR+LF 로 저장한다 |
| `tests/` | 6절 |

Python 표준 라이브러리만 쓴다. 추가 패키지를 넣지 않는다. PC 쪽 코드(`tcgen_core.py`, `tcgen_app.py`, `tcgen_payload.py`)는 Python 3.8 에서 동작해야 한다.

### 2.2 세 곳에서 실행되는 코드

| 실행되는 곳 | 코드 | 하는 일 |
| :-- | :-- | :-- |
| PC | `tcgen_core.py`, `tcgen_app.py` | 입력을 검증하고 블록과 plan 을 만든다. ssh 를 호출하지 않는다 |
| 점프 VM | `<작업 폴더>/tcrun` | plan 을 읽어 ESX 호스트별로 케이스를 순서대로 진행한다. VM 에는 `vmssh` 와 같은 방법(비밀번호는 `vmpw`, `SSH_ASKPASS`, `setsid`)으로, ESX 에는 `esxssh`(키)로 접속한다 |
| ESX 호스트 | `/tmp/tcgen/tcgen_apply.py` | 설정 비교와 적용, VM 종료와 켜기, 이전 값으로 복원. `tcrun` 이 호출할 때마다 전송해 저장한다 |

VM 에는 파일을 만들지 않는다. `tcrun` 이 ssh 표준 입력으로 셸 글을 보내 crontab 을 고치고 구성을 읽는다.

### 2.3 자료 흐름

1. `table_starts` 가 표의 줄마다 잡 시작 시각을 계산한다(날짜 시각, `+간격` 은 바로 윗줄 기준). 화면의 `잡 시작 (환산)` 칸, 생성, 리포트용 CSV 가 같은 함수를 쓴다.
2. `build_seq` 가 입력을 검증하고 케이스별 내용(등록할 명령 글, 설정 항목, 잡 시작, `seg`, 모니터링 중지 시각 `mstop`, 잡이 없는 케이스의 `applyat`)을 만든다.
3. `plan_text` 가 그것을 plan(5절)으로 쓴다. `plan_view` 는 같은 내용을 사람이 읽는 글로 쓰고, `timeline_table` 은 탭 5 의 타임라인 표를 만든다.
4. `seq_check_block`, `seq_run_block` 이 plan 을 gzip 뒤 base64 로 블록에 넣는다. 블록은 plan 을 `<작업 폴더>/runs/<실행 ID>/plan` 에 풀고 sha256 을 확인한 뒤 `tcrun check` 또는 `tcrun start` 를 부른다.
5. `tcrun start` 가 ESX 호스트마다 `setsid sh tcrun run <plan> <호스트>` 를 백그라운드로 시작한다.
6. `tcrun run` 은 케이스마다 `run_case` 를 부른다. `SEG 1` 케이스에서 호스트와 비교(`need_change`)하고, 다르면 잡 시작 `PREP_LEAD_MIN` 전까지 기다린 뒤 `apply_settings`, `power_vms` 를 하고, `register_part` 로 그 케이스와 뒤의 `SEG 0` 케이스를 한꺼번에 등록한다. 그 뒤 케이스마다 잡 시작 `SNAP_LEAD_MIN` 전에 `snapshot` 을 부른다.

`tcrun` 과 `tcgen_apply.py` 가 주고받는 줄은 `TCGEN-` 로 시작한다. `TCGEN-RESULT <낱말>` 이 결과다(`nochange`, `changed`, `wouldchange`, `poweredon`, `rolledback`, `nothing`, `error <이유>`). VM 과 ESX 에서 보낸 셸 글의 답도 같은 방식이다(`TCGEN-CLOCK`, `TCGEN-CRON`, `TCGEN-LINE`).

## 3. 설계 규칙 (사용자가 정한 것. 요청 없이 바꾸지 않는다)

### 3.1 동작 방식 (v1.4 에서 이어지는 규칙)

- PC 의 생성기는 글자만 만든다. PC 에서 ssh 를 호출하지 않는다. 사용자가 블록을 복사해 붙여넣는다.
- 엑셀 파일을 입력이나 저장 형식으로 쓰지 않는다(문서 보안 프로그램이 암호화한다). CSV 와 JSON 만 쓴다.
- 등록한 명령은 고치지 않고 crontab 한 줄로 그대로 등록한다. 시작용, 중지용 실행 파일을 VM 에 만들지 않는다.
- 자동으로 추가하는 것은 세 가지뿐이다: 변수를 쓴 명령 앞의 `TC_HOST=…; TC_START=…;`, VM 줄의 `%` 를 `\%` 로, 줄 끝 표식 ` # tcgen <케이스> <호스트>`.
- ESX 줄의 시각은 UTC 다. ESX 줄은 `%` 를 고치지 않는다.
- 모니터링(0절 D1, D2, D3): 잡 시작 5분 전에 시작한다. 중지는 케이스마다 자동(다음 케이스 잡 시작 10분 전), 직접 입력, 중지 없음 가운데 고른다. 중지 명령이 없는 모니터링은 중지하지 않는다.
- 붙여넣기 블록은 ASCII 만 쓰고 csh, tcsh, bash 공통이어야 한다: here-document 끝 줄은 따옴표 없이 쓰고 본문의 `\`, `$`, `` ` `` 앞에 역슬래시. `!` 와 탭을 쓰지 않는다. 줄 끝을 역슬래시로 끝내지 않는다. CR+LF 로 붙여넣어도 동작해야 한다.
- VM 비밀번호는 점프 VM 의 `~/.tcgen/vmpw`(권한 600)에만 둔다. 생성기 파일, CSV, 블록, plan 에 비밀번호를 넣지 않는다. ESX 비밀번호는 저장하지 않는다.
- 블록 D(VM crontab 전체 삭제)는 삭제 전에 VM 에 백업 파일을 남기고, 복사 전에 확인을 받는다. ESX 는 대상이 아니다.

### 3.2 판 구분 (사용자 2026-11-16 "이전 버전하고 구분되도록 저장")

- v2 는 v1.x 와 이름이 다르다: 실행 파일 `tcgen2`, 데이터 폴더 `tcgen2_data`, 설정 폴더 `tcgen2`. v1 의 `tcgen_data` 와 설정 폴더 `tcgen` 은 읽기만 한다(`import_from_v1`).
- 점프 VM 의 `~/.tcgen/vmssh`, `askpass`, `setpw` 는 v1.4 와 글자 하나까지 같게 둔다. v1.4 를 다시 쓸 때 그대로 쓰게 하기 위해서다(`test_v14_compat.py` 가 확인).
- 시각 지정 방식은 v1.4 와 같은 결과를 낸다. 같은 입력이면 블록 A, B, C, D 가 바이트 단위로 같다. `tcgen_core.py` 의 v1.4 부분(`build_entries`, `vm_block`, `esx_block`, `wipe_block`, `setup_block`)을 고치면 이 규칙이 깨진다.
- 저장소에 올릴 때마다 판 번호를 올리고 그 커밋에 태그 `tcgen-v<판 번호>` 를 등록한다(사용자 2026-11-18 "git 에 업로드할 떄 업데이트 할때마다의 버전관리가 되었으면"). 같은 판 번호로 다시 올리지 않는다. 등록한 태그는 옮기지 않는다. 문구나 문서만 고쳐 올릴 때도 번호를 올린다(문서만 고칠 내용은 다음 판에 함께 올리는 것을 먼저 생각한다). 태그는 이름을 지정해 올린다(`git push origin tcgen-v<판 번호>`). 받는 방법은 README 15절.

### 3.3 진행 방식 (사용자 결정 2026-11-18. 업무기록 W-20261118-08)

v2.11 까지의 규칙(프로세스 확인, 변경 작업 뒤 대기, 스냅샷 뒤 대기, 케이스 사이 간격, 시작 시각 준비 60분)은 v2.12 에서 없어졌다. 그 판의 규칙은 태그 `tcgen-v2.11` 의 이 문서에 있다.

- 진행 방식은 하나다. 설정 영역에 `진행 방식` 칸을 두지 않는다("진행방식 순서 실행 / 시각지정 설정이 필요함? 불필요해").
- 잡이 끝났는지 확인하지 않는다. 프로세스를 찾는 기능, 그 설정 칸(케이스 사이 간격, 잡 종료 확인 간격), 탭 1 의 프로세스 이름 열을 두지 않는다("자동 프로세스확인기능은 그냥 빼줘 안하는게낫겠음", "자동으로 감지하는 기능이 주력이 아니라고했잖아 모든게 이 걸로 맞춰져있어"). 시작 시각의 `자동` 은 받지 않는다.
- 잡은 표에 적은 시작 시각에 등록한다. `tcrun` 은 시작 시각을 변경하지 않는다("시작시간이정의가되어있으면 잡 등록은 시작시간으로 해야해 임의로 바꾸면 안됨"). 등록할 수 없으면 등록하지 않고 기록에 이유를 남긴다.
- 시작 시각은 날짜 시각 또는 `+간격` 이다. `+간격` 의 기준은 표의 바로 윗줄 케이스다. ESX 호스트가 달라도, 윗줄이 적용 체크한 케이스여도 같다("그냥 헤깔리니까 바로 윗줄로할래"). 옆 칸 `잡 시작 (환산)` 에 계산한 시각을 보인다("시작시간 +10 +8 등으로 입력하면 옆칸에 시작 시각 환산되어서 나오면 좋겠고").
- 설정 변경이 없는 케이스의 잡은 S 블록 직후에 crontab 에 한꺼번에 등록한다("VM 설정 변경을 안해도 되면 안해도 되는건 crontab 에 한번에 넣어서 불필요한 통신이 중간에 발생하지 않았으면 함").
- 설정 변경이 있는 케이스는 잡 시작 30분 전에 VM 종료, 설정 적용, VM 전원 ON 을 하고 그 케이스부터 다음 설정 변경 전까지의 잡을 등록한다("60분전에 설정 적용이 아니고 30분으로 바꿔줘", "작업 시작전 30분 전에 최소한 설정 바꾸는것이야", "(설정 변경 케이스) : VM 종료 -> 설정 적용 -> VM 전원 ON 후 Crontab 잡 등록 나머진는 동일"). 설정값 `seq_prep_lead_min`, plan 의 `PREP_LEAD_MIN`. 변경 뒤에 따로 기다리는 시간은 없다.
- 구성 스냅샷은 모든 케이스에서 잡 시작 10분 전에 읽는다("config 스냅샷은 잡 시작전 10분에 해줘 모든 케이스에 대해"). 설정값 `seq_snap_lead_min`, plan 의 `SNAP_LEAD_MIN`. 생성기가 값을 조정하지 않는다.
- 등록 기록을 csv 로 남긴다("tcrun에서 테스트케이스명, 실행 VM, 시작시간 찍히고 crontab 등록 여부 만나오는 로그가 따로찎혔으면 좋겠어 csv 형태로"). `<로그 폴더>/tcrun-<실행 ID>-jobs.csv`, 열은 `case,esx,vm,job_start,crontab`.
- 탭 5 에 타임라인을 보인다. 케이스별이 아니라 전체 한 번이고, 설정 변경이 없는 케이스와 있는 케이스로 나눈다("생성 결과 에서 ... 타임라인 요약해서 작성해줘 ... 케이스 별로 할 필요 없고 오버롤하게", "(설정 변경 x) (설정 변경 케이스) ... 나눠서 설명"). `timeline_table`.
- [리포트용 CSV 저장] 의 잡 시작은 환산한 시각이다("+10:00 헀으면 리포트용 csv 저장하면 +10 시간 반영해서 적용이 되어야"). `seq_report_sched`.
- 스냅샷 때 VM 에서 실행할 명령은 칸 하나다. VM 과 BM 서버가 같은 경로의 같은 파일을 쓴다(`--target auto`). 폴더와 파일 이름으로 칸을 나누지 않는다("그냥 guest config 실행ㅇ하는 명령어로 넣을꼐").
- 오류와 경고는 한 줄로 쓰고 화면의 칸 이름을 쓴다. 대상이 없는 경고는 내지 않는다(3.7절).
- VCF Operations 기록(v2.13. 사용자 결정 2026-11-18 "ops 주소 랑 계정 암호 등은 guest config 에 방식하고 똑같이하고싶은데 암호화해서... 생성기에서입력하고 싶어", "설정 프로파일에 있는 내용 을 ops 에 등록하고싶어 경로 config snashopt 내용과 동일하게", "Host 의 vm config 는 A로 해야하고 Guest config 는 B로 해야지"): 설정 영역의 Operations 주소, 계정, 암호. 구성 스냅샷 때 `tcrun` 이 점프 VM 에서 VM 설정(`Custom Configuration|VM|<키>`: config_snapshot 의 11개 키와 설정 프로파일의 키)과 케이스의 호스트 옵션(`Custom Configuration|Host|<구역.옵션>`)을 기록한다. Guest OS 설정은 게스트와 BM 서버 안에서 guest_config_push 가 기록한다(스냅샷 때 VM 에서 실행할 명령). 암호는 guest_config_push 와 같은 방식(`openssl enc -aes-256-cbc -pbkdf2 -iter 100000`, 암호화한 글과 키를 함께 보관)으로 저장한다. 암호 자체는 저장하지 않는다. 기록하지 못해도 케이스는 진행한다.

v2.11 에서 이어지는 규칙은 다음과 같다.

- 케이스는 ESX 호스트별로 표의 순서대로 처리한다. 호스트끼리는 서로 기다리지 않는다.
- VM 전원(사용자 2026-11-16 "VM 이 다 꺼져있으면 VM 둘다 완전히 킨다음에 잡 수행해야되는데 ... 순차적으로 (lpage backing 완료되어야해서 다 올라온거 확인한다음) 킨다음 수행", "VM off 해놓고 테스트할때도있어서 테스트 케이스 등록할 때 off 설정도 필요함"): ESX 호스트가 있는 케이스는 이름이 있는 VM 행이 모두 그 케이스의 VM 이다. 끔인 VM 은 끄고, 켬인 VM 은 표의 순서대로 하나씩 켠다. VM 마다 켜기 작업, 1GB page backing 완료, ssh 로그인을 확인한 뒤 다음 VM 으로 넘어간다.
- 설정 값이 하나라도 다르면 케이스의 VM 을 모두 끄고 변경한 뒤 표의 순서대로 하나씩 켠다(사용자 2026-11-16 "설정변경 한다고 VM 을 끄면 VM1만 끄는게 아니라 전부끄고 설정 적용 한다음 순차적으로 켜야돼"). 값이 모두 같으면 VM 을 끄지 않는다.
- 설정은 값이 이미 다른 값으로 들어 있어도 오류 없이 적용한다: vmx 에서 같은 키(대소문자 무시)의 줄을 모두 지우고 한 줄을 추가한다.
- 한 케이스에서 잡이 있는 모든 VM 은 같은 분에 잡을 시작한다.
- 잡 시작 최소 간격(사용자 2026-11-16 "모든 잡들은 분단위로 다른시각에 시작되어야하거든? 겹치면 안됨"): 생성기는 서로 `seq_start_spacing_min`(기본 5)분보다 가까운 시작 시각을 오류로 알린다. `tcrun` 은 이 점프 VM 의 다른 실행과 가까우면 WARN 만 남기고 적은 시각에 등록한다(시작 시각을 변경하지 않는 규칙이 우선이다).
- 잡이 실행되는 동안 시험 대상 VM 에 접속하지 않는다(사용자 2026-11-16, 2026-11-17 "체크할 때 부하가 꽤 되는거같음").
- 같은 ESX 호스트의 실행 대기(사용자 2026-11-17): ESX 호스트 하나에는 한 번에 한 진행만 일한다. 진행 중에 붙여넣은 실행은 대기(`queued`)했다가 앞 진행이 `done` 으로 끝나면 시작한다. 다른 상태로 끝나면 대기하던 실행은 `paused` 로 끝난다.
- paused 등으로 끝난 실행이 crontab 줄을 남겼으면 그 ESX 호스트의 새 실행을 시작하지 않는다(`host_block`). `tcrun stop` 뒤에 시작한다.
- stop 은 실행 중인 잡을 다루지 않는다. stop 은 진행을 끝내고 줄을 지우고 시작된 모니터링을 중지한 뒤 점프 VM 의 실행 기록을 지운다(0절 D15, D36). v2.14 까지는 stop(진행만 끝냄)과 cancel(줄 삭제, 모니터링 중지)이 나뉘어 있었다.
- stop 은 VM 을 켜고 기다리는 동안에도 바로 적용한다(사용자 2026-11-17 "tcrun stop 으로 stop 도 안되는거같고").
- CPU affinity 같은 값을 계산하지 않는다. 재부팅해야 적용되는 호스트 설정은 다루지 않는다.
- 점프 VM 에서 ESX 로는 ssh 키로 접속한다. 로그는 사용자가 화면에 적은 점프 VM 폴더에 남긴다.
- 기본 프로파일은 `DEFAULT_PROFILES` 에 있다. 데이터 폴더에 `profiles.json` 이 없을 때만 넣고, 사용자가 고친 행을 덮어쓰지 않는다. 이름이나 내용을 고치면 `README.md` 5.4절의 표와 `tests/test_seq.py` 를 같이 고친다.
- 적용 체크한 케이스의 시작 시각은 날짜 시각으로 고정한다(사용자 2026-11-17). 다른 행의 추가, 수정, 삭제, 순서 변경으로 값이 달라지지 않아야 한다(`gui_fuzz_applied.py`).

이 판을 만들 때 정한 것은 다음과 같다(사용자가 정한 규칙이 아니다. 고치려면 시험과 README 7절을 함께 고친다).

- `SEG`: ESX 호스트의 첫 케이스와, 설정 항목, VM 전원, VM 목록이 바로 앞 케이스와 다른 케이스가 1 이다. `tcrun` 은 `SEG 1` 케이스에서만 호스트와 비교한다. ESX 호스트가 없는 케이스는 첫 케이스만 1 이다.
- 설정이 호스트와 다른데 설정을 변경할 시각이 이미 지났으면 바로 변경하고 잡은 적은 시각에 등록한다. 로그에 WARN, 등록 기록에 몇 분 전에 변경했는지를 남긴다. P 블록은 첫 케이스가 이 경우이면 `[PROBLEM]` 으로 알린다. 그 설정을 쓰는 케이스의 잡 시작이 모두 지났으면 변경하지 않는다.
- 잡 시작이 지났거나 1분이 남지 않은 케이스는 등록하지 않는다. 진행은 다음 케이스로 계속되고 상태는 `done` 이다(등록하지 못한 수를 상태 글에 적는다).
- 모니터링 시작 시각이 지났으면 1분 이상 남은 가장 이른 분에 시작하게 등록한다(잡 시작보다 늦지 않게). 잡 시작은 그대로다.
- 모니터링 중지(v2.15): 규칙은 사용자 결정 D2, D3 이다. 이 판에서 정한 세부는 다음과 같다. 다음 케이스는 같은 ESX 호스트의 다음 잡 케이스다(ESX 호스트가 없는 케이스끼리는 그 묶음 안의 다음 케이스). 최대 대기를 적었으면 자동 시각과 잡 시작 + 최대 대기 가운데 이른 쪽. 마지막 케이스의 자동은 최대 대기가 있을 때만 정해진다. 규칙 함수는 `seq_stop_at` 이고 탭 4 의 표시(`seq_stop_view`)와 생성(`build_seq`)이 같이 쓴다. 다음 케이스가 설정 변경 케이스이면 그 케이스의 VM 종료와 설정 적용(잡 시작 30분 전)이 앞 케이스의 중지(10분 전)보다 먼저다. 앞 케이스의 중지 줄은 다음 케이스의 설정 변경 때 지우지 않으므로 VM 이 다시 켜진 뒤 실행된다(`StopRuleTests`). v2.12 ~ v2.14 는 D2, D3 을 빠뜨리고 다음 잡 케이스의 잡 시작 `PREP_LEAD_MIN + 2` 분 전에 중지했다. 그때의 나머지 규칙: 마지막 케이스는 최대 대기가 있을 때만. crontab 줄(`MSTOP`)로 잡과 함께 등록한다. 마지막 케이스에 중지 시각이 없는 것은 경고가 아니라 결과의 `알림:` 한 줄이다(사용자 2026-11-18 "이 경고가필요해?").
- 진행은 마지막 잡 시작 1분 뒤에 끝나고 줄은 남는다(`<호스트>.work/times`). 같은 ESX 호스트의 다음 실행은 설정 변경이 없는 케이스를 시작하자마자 등록하고, 앞 실행이 남긴 줄은 첫 잡 시작 `PREP_LEAD_MIN` 전에 지운다(`take_over`). 앞 실행의 줄을 바로 지우지 않는 이유는 앞 실행의 마지막 잡이 실행 중일 수 있어서다(VM 접속과 모니터링 중지를 피한다). 이름이 같은 케이스의 줄만 시작할 때 지운다(`take_over names`. 새 줄과 표식이 같다).
- 같은 ESX 호스트에 진행 중인 실행이 있으면 새 실행은 그 실행이 끝난 뒤(마지막 잡 시작 1분 뒤. `run_end`)에 시작한다. 그 전에 시작해야 하는 케이스는 대기하는 동안 시작 시각이 지나 등록되지 않으므로, P 블록이 잡 시작이 그 시각의 2분 뒤보다 이른 케이스를 `[PROBLEM]` 으로 알린다. 대기 상태의 글과 S 블록 출력에도 그 시각을 적는다.
- `'설정 적용 N분 전'` 은 `'구성 스냅샷 N분 전'` 보다 커야 하고, 모니터링이 있으면 `'모니터링 시작 N분 전'` 보다도 커야 한다(생성기의 오류).
- 중지 명령이 있는 모니터링이 있으면 `'모니터링 중지 N분 전'` 은 `'모니터링 시작 N분 전'` 보다 커야 한다(생성기의 오류). 같거나 작으면 앞 케이스의 중지 명령이 다음 케이스의 모니터링 시작 뒤에 실행된다.
- S 블록의 확인(D34, D35): plan 의 `LIST` 줄(`confirm_lines`)을 `tcrun start` 가 보이고 `/dev/tty` 에서 yes 를 받은 뒤에만 시작한다(`confirm_start`). 빈 줄과 다른 답이면 다시 묻고, 터미널이 없거나 답이 없으면 아무것도 등록하지 않는다(종료 코드 4). 이미 시작한 실행은 묻지 않는다. 블록은 tcrun 에 입력을 주지 않으므로(`< /dev/null`) 붙여넣은 글이 답으로 읽히지 않는다. VM 이름의 색은 `vm_color` 가 터미널일 때만 넣고(`say`, P 블록의 출력), 파일과 파이프로 가는 글(로그, 점검 로그)에는 넣지 않는다. 시험 전용 환경 변수: `TCRUN_TEST_TTY`(답을 읽을 파일), `TCRUN_COLOR`(always, never), `TCRUN_STOP_GRACE`(`tcrun stop` 이 진행의 다음 확인을 기다리는 초. 기본 60. 강제 종료 경로를 시험할 때 줄인다).
- 실행 계획(`plan_view`)은 타임라인을 맨 위에 한 번 적고, 케이스마다 그 케이스의 값을 항목별 짧은 줄로 적는다(사용자 2026-11-16 "실행계획 너무 읽기어려워 가독성떨어짐"). 탭 5 의 칸이 낮으면 실행 계획 칸을 숨기고 [실행 계획 보기] 로 본다(`fit_plan`).

### 3.4 tcrun 과 tcgen_apply.py 의 구현 규칙 (고치려면 시험을 함께 고친다)

- `tcrun` 은 plan 의 글을 `eval` 하지 않고 이 장비의 셸에 넘기지 않는다. `grep`, `sed`, `cut` 으로 꺼내 파일에 쓰고, 원격에서는 따옴표로 감싼 here-document 로 넘긴다(`test_tcrun_does_not_eval_the_plan`).
- `tcrun` 과 `tcgen_apply.py` 에 시험용 코드를 넣지 않는다. 시험은 가짜 `date`, `sleep` 과 경로 환경 변수(`TCGEN_TMP`, `TCGEN_CRON_DIR`, `TCGEN_VMFS_ROOT`)만 쓴다. 이 변수들은 실제 장비에서는 설정되지 않는다.
- `tcrun` 은 POSIX sh 로 쓴다. `local`, 배열, `[[ ]]` 를 쓰지 않는다. dash 에서도 실행한다.
- Operations 암호의 암호화는 `tcgen_core.py` 의 `ops_encrypt` 에 있다(표준 라이브러리에 AES 가 없어 FIPS 197 의 암호화를 직접 구현했다. `test_aes_block_matches_fips197`, `test_encrypted_password_is_decrypted_by_openssl` 이 확인한다). PC 에는 푸는 코드를 두지 않는다. `tcrun` 은 키와 요청 본문을 작업 폴더의 파일(권한 600)로 넘기고 바로 지운다. 토큰은 curl 설정 파일(`ops.cfg`, `curl -K`)로 넘겨 명령줄 인자에 싣지 않는다(다른 계정이 `ps` 로 볼 수 없게. `OpsTests` 가 curl 의 인자를 기록해 확인한다). 암호와 토큰을 로그에 쓰지 않는다. 호스트 옵션의 값은 plan 의 목표 값이 아니라 스냅샷 때 `tcgen_apply.py snapshot` 이 읽은 값이다(스냅샷 spec 의 `host </구역/옵션>` 줄, 출력 `TCGEN-HOPT </구역/옵션>|<값>`). Operations 주소를 적지 않은 실행은 호스트 옵션을 읽지 않는다.
- `tcgen_apply.py` 는 Python 3.5 문법으로 쓴다. f-string, 변수 주석, `subprocess.run` 을 쓰지 않는다.
- `tcgen_apply.py` 는 무엇이든 바꾸기 전에 대상을 모두 확인한다(VM 을 찾고, vmx 를 읽고, 호스트 옵션을 읽는다). 하나라도 안 되면 아무것도 바꾸지 않는다.
- crontab 등록은 v1.4 의 B 블록, C 블록과 같은 방법이다: 그 케이스의 표식 줄을 지우고 새 줄을 넣는다.
- 한 케이스의 줄은 모든 호스트에 첫 실행 시각 15초 전까지 들어가거나, 어느 호스트에도 없어야 한다(`register_case`). 시각을 뒤로 옮겨 다시 등록하지 않는다. 구현은 다음과 같다(2026-11-18. 느린 VM 하나 때문에 다른 VM 의 잡만 시작된 뒤에 줄을 지우던 결함을 시험으로 재현하고 고침).
  - 접속 하나의 시간 제한은 첫 실행 시각 15초 전까지 남은 시간이다(최대 60초, 5초가 남지 않으면 접속하지 않는다). `guard` 는 초 수 제한에 더해 그 시각(시계 기준)이 되면 접속을 끝낸다.
  - 등록 셸 글은 줄을 넣기 직전에 그 호스트의 시계가 `CRON_DL`(첫 실행 시각 15초 전)을 지났으면 넣지 않고 `TCGEN-CRON late` 를 낸다. 접속이 느린 VM 과 시계가 빠른 VM 이 이 경우다.
  - 등록 셸 글과 삭제 셸 글은 `TCGEN-HAD <수>`(그 호스트에 있던 그 케이스의 줄 수)를 맨 먼저 낸다. 이 줄이 출력에 있으면 셸 글이 실행되기 시작한 것이다.
  - 실패하면 줄을 받은 VM(`RG_HAVE`), 늦게 받은 VM(`RG_SLOW`), 결과가 없는 VM(`RG_UNK`) 순서로 지운다. 줄을 받지 않았다고 답한 VM 과 접속이 안 된 VM 에는 다시 접속하지 않는다.
  - 호스트마다 결과를 나눠 등록 기록의 그 VM 행에 적는다(`$W/jobs.note`): 지우지 못함(`UR_BAD`), 지운 때가 첫 실행 시각 뒤이고 줄이 있었음(`RG_HALF`. 모니터링이 있으면 그 호스트에 중지 명령을 실행), 셸 글이 실행되던 중에 결과가 없었고 지울 때 줄이 없었음(`RG_LATER`. 멈춘 `crontab` 명령이 뒤늦게 줄을 넣을 수 있다).
  - `UR_BAD` 와 `RG_LATER` 의 호스트는 `times` 의 넷째 칸에 적어 케이스를 줄 목록에 남긴다. `close_case` 는 넷째 칸이 있으면 그 호스트의 줄만 지운다.
  - 케이스는 첫 접속 전에 `times` 에 적는다. 등록 중에 진행이 끝나면(stop, 점프 VM 재부팅) stop 이 그 케이스의 줄을 지운다.
- 일부 VM 에만 줄이 들어간 채로 멈추지 않는다. 등록 중에 실패하면 그 케이스의 줄을 모두 지운다.
- 진행이 신호로 끝날 때(`on_signal`): 하던 접속(`G_P`)을 끝내고, 등록 중이던 케이스(`RP_NOW`)와 아직 등록하지 않은 케이스의 행을 등록 기록에 쓴다. `stop_chain` 은 진행이 stop 요청 파일을 보고 다음 확인 시점에 스스로 끝나기를 기다린다(설정 적용, VM 종료, 되돌리기 단계는 그 작업이 끝날 때까지, 그 밖의 단계는 60초). 끝나지 않으면 `<호스트>.stopping` 파일을 만들어 끝난 이유를 알리고 프로세스 그룹에 TERM 을 보내고, 30초 뒤에도 남아 있으면 KILL 을 보낸다.
- `close_case` 는 지우지 못한 호스트가 있으면 그 케이스를 `times` 에 남기고(`CC_BAD`) 지운 것으로 출력하지 않는다. `stop` 을 다시 실행하면 남은 호스트만 처리한다. 다음 실행의 `take_over` 도 같다.
- 잡 시작 간격 경고를 내고 유지한 시작 시각도 `minutes/` 에 기록한다(`claim_keep`). `claim_start` 는 이미 기록한 시각도 매번 다른 기록과 다시 비교한다.
- `tcrun` 은 plan 의 이름(케이스, VM, ssh 대상, ESX 주소)에 명령줄에서 뜻이 달라지는 글자가 없는지 다시 확인한다(`names_ok`, `addr_ok`). 생성기의 검증과 같은 규칙이다.
- 구성 스냅샷(사용자 요청 2026-11-17 "vm 설정, guest os 설정 둘다 기록하고싶음", "잡 시작전 마다 config snapshot 하도록 해줘"): 등록한 케이스마다 `run_case` 가 잡 시작 `SNAP_LEAD_MIN` 전에 `snapshot` 을 부른다. 줄은 그 전에 등록돼 있으므로 스냅샷이 잡 시작 시각에 영향을 주지 않는다. 읽기만 하고, 읽지 못하면 WARN 만 남긴다. `GCMD` 명령은 Guest OS 값을 읽은 뒤 켜져 있는 VM 마다 `( 명령 ) < /dev/null` 로 실행한다(150초 제한, 잡 시작 2분 전이 지나면 실행하지 않음).

### 3.5 테스트 케이스 표

- 케이스 행 아래 VM 행. VM 마다 잡, 모니터링, 설정 프로파일을 지정한다. VM 역할 구분(이름)은 두지 않는다.
- VM 이름 자동 입력 = ESX 호스트 + `vm_prefix` + 두 자리 번호.
- 시작 시각 칸(`seq_start`)과 `잡 시작 (환산)` 칸(`seq_at`, 읽기 전용): `table_starts` 가 계산한다. 표를 그릴 때마다 한 번 계산해 `App.seq_ats` 에 둔다. 시:분만 적으면 화면이 날짜를 붙여 저장한다.
- '적용' 을 체크한 케이스는 생성에서 빠진다. `+간격` 의 기준으로는 쓰인다.
- [명령어 생성] 은 넣을 케이스를 고르는 창을 거친다(사용자 요청 2026-11-16 "명령어 생성 하면 넣을 테스트케이스 선택하는 화면이 안나옴"). 처음 상태는 적용 체크하지 않은 케이스. 화면의 `generate_picked` 가 케이스 표의 사본에서 고르지 않은 케이스를 `applied=True` 로 바꿔 core 에 넘긴다(core 의 생성 함수는 바꾸지 않는다). 시각 지정의 D 블록 주의(`wipe_conflicts`)는 실제 적용 체크로 다시 계산한다. 탭 4 의 적용 체크는 바꾸지 않는다.
- [+ 케이스 추가] 는 새 케이스의 이름 칸을 바로 연다(복사한 케이스는 자동 이름이 골라진 채로). 이름 규칙은 `NAME_RE` 이고, 어기면 이유(crontab 줄과 진행 파일에 들어감)와 설명 칸을 알린다.
- 리포트용 CSV 에서 비교 기준 케이스를 정하지 않는다. [리포트용 CSV 저장] 은 고른 케이스를 탭 4 의 표 순서대로 저장한다(사용자 결정 2026-11-16. v1.4 의 `비교 기준 (첫 줄)` 칸은 v2.2 에서 뺐다). 비교에 쓰는 기준은 성능 리포트 생성기에서 정한다.
- 테스트 케이스 파일(사용자 결정 2026-11-16): 탭 4 의 표는 [불러오기], [다른 이름으로 저장] 으로 사용자가 정한 파일에 저장하고 불러온다. [새로 만들기](사용자 결정 2026-11-20 "새로 만들기 버튼 추가")는 새 파일을 빈 표로 만들고 그 파일로 바꾼다(`new_case_file`. `use_case_file` 에 빈 표를 넘긴다). 이미 있는 파일은 새로 만들지 않는다(그 파일의 표를 지우지 않기 위해서다). 정한 파일이 있으면 자동 저장도 그 파일에 한다. 정하지 않으면 데이터 폴더의 `test_cases.json` 을 쓴다. 실행 명령, 모니터링 명령, 설정 프로파일과 그 밖의 설정은 어느 파일을 쓰든 같이 쓴다. '테스트 종류' 를 만들어 고르는 방식은 쓰지 않는다(사용자가 불편하다고 뺀 방식). 설정의 `case_file` 이 정한 파일의 경로이고, `case_file_paths` 가 파일별로 기억하는 기록 CSV 와 로그 폴더다. `settings.json` 의 맨 위 `record_csv`, `log_dir` 는 기본 파일을 쓸 때의 값이다. 메모리의 설정에서 `record_csv`, `log_dir` 는 항상 지금 쓰는 파일의 값이다(`load_settings` 가 넣고 `save_settings` 가 나눠 적는다). 파일을 바꾸는 순서는 화면의 `use_case_file` 에 있다: 지금 표 저장(실패하면 바꾸지 않음), 새 파일 쓰기 또는 읽기, 설정 저장, 표 바꾸기, 탭 5 결과 지우기. 사용자가 정한 파일을 읽지 못해도 그 파일의 이름을 바꾸거나 지우지 않는다.
- 테스트 케이스 CSV 의 형식은 `CASE_CSV_HEADER` 와 `cases_to_csv`, `cases_from_csv` 에 있다. 열을 더하면 README 4.3절의 표와 `tests/test_seq.py` 의 `CaseFileTests` 를 같이 고친다. 읽을 때는 머리글 이름으로 열을 찾으므로 열이 없는 예전 파일도 읽힌다. 열 이름 `시작 시각 (순서 실행)` 과 테스트 기록 CSV 의 `진행 방식` 값 `순서 실행` 은 파일 형식이라 그대로 둔다.
- 자동 백업(사용자 결정 2026-11-16, 하루 두 번): `auto_backup` 이 오전과 오후에 한 번씩 `backup/auto/<년월일>_<AM|PM>/` 을 만든다. 화면은 켤 때와 30분마다 `auto_backup_tick` 으로 확인한다. 최근 60개만 남긴다.
- 리포트용 CSV 의 머리글(`REPORT_HEADER`)은 성능 리포트 생성기의 케이스 정보 파일 형식과 같아야 한다. 한쪽을 고치면 다른 쪽도 같이 고친다. 점프 VM 의 리포트용 CSV 는 `tcrun` 이 plan 의 `RPTH`, `RPTA`, `RPTB` 줄로 만든다.
- 적용 체크한 케이스는 고정된 기록이다(사용자 요청 2026-11-17 "테스트 명령 실행기에서 적용완료된거 순서를 바꾸거나 하면 잡 시작 시간 다 꼬이면서 기록이 엉키는거같아 이미 적용한 테스트 기록은 시작 시간 안바뀌게할수있어?"). 시각 지정에서 그 케이스의 간격, 잡 시작, 모니터링 중지, 잡 종료 (리포트) 는 그 케이스의 칸을 직접 고칠 때만 바뀌어야 한다. 2026-11-17 재현(v2.7): [위로], [아래로] 가 이 값들을 자리에 남겨 적용 체크한 케이스끼리 값이 서로 바뀌었고, 중간에 케이스를 추가해 잡 시작을 적으면 `recalc_starts` 가 아래의 적용 체크한 케이스를 다시 계산했다. 지키는 곳: `recalc_starts` 와 `interval_from_starts` 는 적용 체크한 행을 바꾸지 않는다. `swap_cases` 는 둘 중 하나라도 적용 체크한 케이스이면 값을 케이스와 함께 옮기고 적용 체크하지 않은 행의 잡 시작도 그대로 둔다(둘 다 적용 체크하지 않은 케이스이면 v1.4 와 같이 시각이 자리에 남는다). 윗줄이 적용 체크한 케이스인 행은 윗줄과 이어지지 않는 행으로 다룬다: `recalc_starts` 는 그 행을 다시 계산하지 않고(방금 추가하거나 간격을 고친 `from_index` 행만 예외), 윗줄이 달라졌을 때의 간격 맞추기(`fit_interval`: 순서 바꾸기, 삭제, 잡 시작 직접 입력)는 그 행과 윗줄이 모두 적용 체크하지 않은 케이스일 때만 한다. 지난 케이스와의 차이(며칠)를 간격에 넣으면 마지막 케이스의 자동 중지 시각(잡 시작 + 간격)이 오류 없이 며칠 뒤가 되기 때문이다(2026-11-17 화면 재현: 새 케이스를 적용 체크한 케이스 위로 옮기자 맨 아래 케이스의 간격이 8:00 에서 184:00 으로 바뀌고 자동 중지가 11-19 01:50 에서 11-26 09:50 이 됨. 이 규칙을 넣기 전 구현에서 확인). 자동 모니터링 중지 시각은 다음 행의 잡 시작으로 계산하므로 `freeze_applied` 가 적용 체크한 케이스의 계산값을 `applied_stop` 에 적어 두고 `case_schedule` 이 그 값을 쓴다(화면의 `calc_schedule` 이 시각 지정에서 표를 그리기 전에 부른다. 적용 체크를 끄면 지운다. 직접 입력 시각 칸 `stop_time` 은 자동으로 바꿔도 예전 값이 남으므로 이 용도로 쓰지 않는다). 화면은 적용 체크한 케이스의 간격, 잡 시작, 모니터링 중지 칸을 고치지 못하게 하고 안내를 보인다(`is_locked`, `locked_notice`). 순서 실행의 칸(시작 시각, 최대 대기)은 다른 행에 영향을 주지 않으므로 고정하지 않는다. 자동 중지의 '다음 케이스' 규칙(바로 아랫줄)은 바꾸지 않았다: 지난 적용 체크한 케이스를 건너뛰게 하면 새 케이스가 마지막 케이스 규칙(잡 시작 + 간격)으로 계산되는데, 잡 시작을 직접 적은 케이스의 간격은 윗줄과의 차이라서 며칠 뒤의 중지 시각이 오류 없이 만들어진다.
- 적용 체크한 케이스의 시작 시각(사용자 결정 2026-11-17: `+8:00` 을 적은 케이스를 적용 체크할 때 칸의 값을 날짜 시각으로 고정 "네"): `toggle_applied` 가 체크할 때 `fix_seq_start` 를 부른다. 값을 찾는 순서는 (1) 이 창에서 방금 만든 결과(`self.result` 의 `start_at`. 그 케이스의 `seq_start` 글이 지금 칸과 같을 때) (2) 테스트 기록 CSV 의 마지막 생성 기록(`seq_start_from_record`. 순서 실행으로 만든 행이고 간격 열이 지금 칸의 `+간격` 과 같을 때) (3) 지금 표로 계산(`seq_start_by_table`. 바로 윗줄 케이스의 시작 시각 + 간격)이다. (1), (2) 는 생성한 계획이라 선택 창에서 일부 케이스만 넣어 생성한 경우에도 맞다. 그래서 `write_records_seq` 가 간격 열에 `+간격`(`start_rel`)을 적는다. 계산할 수 없으면 칸을 그대로 두고 알린다. 적용 체크한 케이스의 시작 시각 칸은 고칠 수 없다(`seq_locked`, 시각 지정의 `is_locked` 와 같은 방식). 적용 체크를 꺼도 날짜 시각을 `+간격` 으로 되돌리지 않는다.
- 기록 대조(사용자 결정 2026-11-17: 이미 변경된 기록을 대조해 되돌리는 기능 "네 정합성안맞는경유필요 함"): 탭 4 의 [기록 대조](`compare_records`)는 적용 체크한 케이스의 시각 값을 기준과 대조하고 고른 케이스를 기준 값으로 되돌린다. 기준은 테스트 기록 CSV 의 마지막 생성 기록(`read_record_rows`, `latest_records`, `record_diffs`) 또는 사용자가 고른 예전 표 파일(`load_cases`, `table_diffs`)이다. 규칙: 적용 체크한 케이스만 본다. 기록의 칸이 비어 있으면 그 칸은 대조하지 않는다(잡 종료는 생성 뒤에 적는 값이다). 시각 지정과 순서 실행의 기록 행을 섞지 않는다(`진행 방식` 열). 되돌리기는 사용자가 고른 케이스만 하고(`restore_cases`), 그 전에 지금 표를 `backup/<시각>_before_record_restore.json` 으로 남긴다(`keep_cases_copy`). 자동으로 되돌리지 않는다: 어느 쪽이 맞는지는 사용자가 정한다.

### 3.6 저장

- 설정, 명령 목록, 설정 프로파일, 케이스 표는 값이 달라질 때마다 자동 저장한다. 저장 버튼을 두지 않는다.
- 데이터는 생성기 폴더가 아니라 데이터 폴더에 둔다. 다시 빌드해도 데이터가 지워지지 않아야 한다.
- 백업에는 탭 4 의 표가 들어 있어야 한다. 사용자가 정한 테스트 케이스 파일은 데이터 폴더 밖에 있으므로 [설정 백업](`backup_to`)과 자동 백업(`auto_backup`)이 `case_file_<파일 이름>` 으로 함께 복사한다(`copy_case_file`). [백업 불러오기](`restore_from`)는 백업의 설정이 가리키는 파일을 그 사본으로 바꾸고, 바꾸기 전 내용을 `before_restore` 폴더에 남긴다(2026-11-17 확인: v2.6 까지는 [설정 백업] 에 사본이 없어 백업을 불러와도 표가 돌아오지 않았음).
- 읽지 못한 데이터 파일은 지우지 않고 이름을 바꿔 보관한다. 형식을 고치면 이전 형식을 읽어 변환하고 원본을 `backup` 에 남긴다.
- 새 값은 선택 항목으로 더한다. v1.4 가 만든 `settings.json`, `run_commands.csv`, `test_cases.json` 을 그대로 읽을 수 있어야 한다.

### 3.7 화면

- 테마는 clam, 색은 `COLORS` 사전 한 곳에서 정한다. 선택한 탭은 파란 바탕 흰 굵은 글씨.
- 쓸 수 없는 글자(`!`, 탭, 한글 등)는 생성 전에 오류로 알린다.
- 오류와 경고 문구(사용자 지적 2026-11-18 "뭔말인지도모르겠따", "이해도안되는말이고 너무 길고"): 한 줄로 쓴다. 무엇이 문제인지와 무엇을 하면 되는지만 적고, 동작 원리는 넣지 않는다. 화면의 칸 이름을 그대로 쓴다. 같은 칸을 변경하라는 글이 여럿이면 하나로 합친다. 생성기가 스스로 맞출 수 있는 값은 오류로 막지 않고 맞춘 뒤 `알림:` 한 줄로 적는다.
- 경고는 그 경고의 대상이 실제로 있을 때만 낸다(사용자 지적 2026-11-18 "모니터링 걸지도않았는데 왜띄우는거야"). 문구를 고치면 `test_seq.py` 의 글 비교와 README 11절의 표를 같이 고친다.
- 표에서 숨긴 열이 있을 때는 `EditableTable.set_visible` 을 쓴다. 누른 좌표의 열 순번은 화면의 순번이므로 `_double` 이 `columns` 의 순번으로 바꾼다.

## 4. 점프 VM 의 파일과 tcrun

| 파일 | 만드는 곳 | 비고 |
| :-- | :-- | :-- |
| `askpass`, `vmssh`, `setpw` | `vmssh_lines`, `setpw_lines`(v1.4 의 `VMSSH_LINES`, `SETPW_LINES` 에서 폴더 경로만 바꾼 것) | 기본 작업 폴더이면 v1.4 와 글자까지 같다. 시각 지정의 A 블록은 v1.4 의 것을 그대로 쓴다 |
| `esxssh`, `postsetup` | `esxssh_lines`, `postsetup_lines` | 짧은 파일. 블록에 `printf` 줄로 넣는다. `esxssh` 는 `-o LogLevel=ERROR` 와 작업 폴더의 `known_hosts` 를 쓴다 |
| `tcrun`, `tcgen_apply.py` | `tcgen_payload.py` | 긴 파일. gzip 뒤 base64 로 넣고 설치 뒤 sha256 을 확인한다 |

`tcrun` 의 하위 명령은 `check <plan>`, `start <plan>`, `run <plan> <esx>`, `status [-a]`, `stop [esx]`, `key`, `version` 이다. `start` 는 S 블록이 쓴다. `cancel` 은 v2.15 에서 없앴다(입력하면 stop 안내를 출력하고 끝 코드 2).

`run` 의 순서: 대기(`queue_wait`), 시작 조건 확인(`host_block`), 앞 실행이 남긴 줄 목록(`open_runs done` → `TAKE`), 케이스마다 `run_case`, 마지막 잡 시작 1분 뒤까지 대기. `run_case` 의 순서: `SEG 1` 이면 `need_change`(비교만), 다르면 잡 시작 `PREP_LEAD_MIN` 전까지 대기 뒤 `take_over`, `apply_settings`, `power_vms`. 같으면 `take_over names`. 이어서 `register_part`(그 케이스와 뒤의 `SEG 0` 케이스를 `register_case` 로 등록하고 `jobs_rows` 로 기록), 남은 `TAKE` 가 있으면 `PREP_LEAD_MIN` 전에 `take_over`. 그 뒤 잡 시작 `SNAP_LEAD_MIN` 전에 `snapshot`.

작업 폴더(사용자 요청 2026-11-16 "tcgen 실행 위치 바꿔야되겠어.. 계정홈폴더로하니까 홈폴더 용량제한있음"): 설정 `jump_dir`(비우면 `~/.tcgen`). `jump_dir`, `sh_path` 가 화면의 글과 셸 글(`~/` → `$HOME/`)을 만든다. A 블록은 그 폴더에 설치하고, 폴더가 `~/.tcgen` 이 아니면 `~/.tcgen` 의 `id_esx`, `id_esx.pub`, `vmpw` 를 복사한다(ESX 키 재등록과 비밀번호 재입력을 피함). P, S 블록과 순서 실행의 D 블록도 그 폴더를 쓴다. `tcrun` 은 `$0` 의 폴더를 작업 폴더로 쓰므로 plan 에 폴더를 적지 않는다. 시각 지정(v1.4 방식)은 `~/.tcgen` 그대로다.

쓰기 확인: `tcrun start`, `run`, `check` 는 작업 폴더(실행 폴더)와 로그 폴더에 1 MB 를 `dd` 로 써 보고(`can_write`), 쓸 수 없으면 시작하지 않거나 `[PROBLEM]` 으로 알린다. 홈 폴더 quota 가 차면 접속 스크립트와 상태 파일이 비어 ssh 출력에 배너만 남는 일이 있었다(사용자 보고 2026-11-16, 원인은 정황).

ssh: `tcrun` 의 VM 접속과 `esxssh` 는 `-o LogLevel=ERROR`(로그인 배너와 `Permanently added` 안내를 출력하지 않음)와 `-o UserKnownHostsFile=<작업 폴더>/known_hosts` 를 쓴다. 실패 이유는 `first` 가 출력에서 ssh 의 오류 줄(denied, refused, timed out 등)을 먼저 고른다. VM 을 켠 뒤 ssh 로그인을 기다리는 동안 `Permission denied` 가 나오면 다시 시도하지 않는다(10초마다 30분 동안 다시 시도하면 계정 잠금 정책에 걸릴 수 있음).

`status`: 마지막 실행(상태 파일이 있는 가장 늦은 실행 ID)의 plan 에 있는 ESX 호스트를 모두 보인다. 상태 파일이 없는 호스트는 `not started` 와 `<호스트>.out` 의 끝 다섯 줄을 보인다. `tcrun stop` 으로 지운 호스트(`stopped_runs` 에 있는 것)는 `not started` 로 보이지 않는다.

`status` 는 대기 중인 진행(`queued`)과 줄이 남은 케이스가 있는 진행도 보인다(`crontab lines on the hosts: case ...` 줄).

`stop`(0절 D15, D36. 사용자 요청 2026-11-16 "잘못수행했을때 취소도 용이하지않은거같아", 2026-11-20 "Stop으로 멈추고 cancle작업까지 둘다 허고 cancle 없애줘", "삭제하면 trunk status에 없어져야지"): 먼저 프로세스가 남아 있는 진행(진행 중, 대기 중)마다 stop 요청 파일을 만든다(사용자 보고 2026-11-16 "tcrun status tcrun stop 이 호스트 1에만 적용되는거같아"). 이어서 실행 ID 가 늦은 것부터(대기 중인 진행을 먼저 끝내야, 앞 진행이 끝난 직후에 그 진행이 시작하지 않는다) 상태 파일이 있는 실행의 호스트마다 처리한다. 프로세스가 남아 있거나 줄이 남은 케이스가 있으면 `stop_chain` 이 한다. 진행이 끝나기를 기다리고(위 `on_signal` 항목), 남은 줄을 지우고 모니터링을 중지한다. 이 부분은 `close_case` 이고 `take_over` 도 같은 함수를 쓴다(`close_open` 은 앞 실행의 plan 을 읽어야 하므로 subshell 에서 실행한다). `<호스트>.work/times`(`register_case` 가 첫 접속 전에 '번호 첫실행시각 잡시작' 을 쓰고, 등록하지 못해 줄을 모두 지웠거나 나중에 줄을 지우면 그 줄을 뺌)에 적힌 케이스의 줄을 `unregister` 로 지운다. 모니터링 시작 시각이 지났고 등록한 중지 시각이 아직 오지 않았으면 MX 줄(`\%` → `%`)과 EMX 줄을 ssh 로 바로 실행한다. 잡 프로세스는 끝내지 않는다(3.3절). 잡 시작 전에 줄을 지운 케이스는 등록 기록에 `removed before the job start (sh tcrun stop)` 행을 더한다. 이 실행과 호스트의 앞으로의 잡 시작 기록을 지운다. 설정은 되돌리지 않는다. 줄을 모두 지운 호스트와 이미 끝난 호스트는 `forget_chain` 이 실행 폴더의 그 호스트 파일을 지우고 `stopped_runs` 에 `<실행 ID> <호스트>` 를 적는다(S 블록을 다시 붙여넣어도 시작하지 않는다). 남은 호스트가 없으면 `forget_run` 이 실행 폴더를 지운다. 로그 폴더의 파일은 지우지 않는다. 접속하지 못한 호스트에 줄이 남으면 그 호스트는 상태 `stopped` 로 남고 다시 stop 하라고 출력한다.

실행 자료는 `~/.tcgen/runs/<실행 ID>/` 에 둔다.

| 파일 | 내용 |
| :-- | :-- |
| `plan` | 블록이 푼 plan |
| `<호스트>.pid` | 진행 프로세스의 pid. 끝나면 지운다 |
| `<호스트>.state` | `state=`, `time=`, `case=`, `pos=`, `step=`, `text=` 줄. `tcrun status` 가 읽는다 |
| `<호스트>.stop` | `tcrun stop` 이 만드는 stop 요청 파일. 진행이 이 파일이 있는지 확인하고 멈춘다 |
| `<호스트>.stopping` | `tcrun stop` 이 TERM 을 보내기 전에 만드는 파일. 진행의 `on_signal` 이 끝난 이유를 `sh tcrun stop` 으로 적는다 |
| `<호스트>.out` | 진행 프로세스의 표준 출력(정상일 때는 비어 있다) |
| `<호스트>.work/` | 원격에 보낸 셸 글과 받은 출력, 이 진행이 켠 VM 의 준비 완료 시각(`on.<VM>`), `times`(줄이 호스트에 남아 있는 케이스마다 `<케이스 번호> <첫 실행 시각> <잡 시작>`. 줄을 지우지 못한 호스트만 남았으면 넷째 칸에 `vm1,vm2,@esx` 처럼 적는다. 다음 실행과 stop 이 읽는다), `reg.ok`(등록한 케이스 번호), `jobs.done`(등록 기록에 행을 쓴 케이스 번호) |

`~/.tcgen/stopped_runs` 는 `tcrun stop` 이 지운 `<실행 ID> <호스트>` 의 목록이다. `tcrun start` 는 여기 있는 호스트를 시작하지 않는다.

잡 시작 시각의 기록은 `~/.tcgen/minutes/<분의 epoch>/` 폴더이고 `who`(실행, ESX 호스트, 케이스)와 `reg`(줄 등록을 마침) 파일이 들어간다. `~/.tcgen/minutes/.lock/pid` 는 기록하는 동안의 잠금이다(3.3절).

호스트 자리의 이름은 ESX 호스트 이름이고, ESX 호스트를 적지 않은 케이스는 `noesx` 다.

등록 시각은 `register_case` 에 있다. 잡 = plan 의 `START` 를 분으로 내린 값, 모니터링 시작 = 잡 - `MON_LEAD_MIN`, 모니터링 중지 = plan 의 `MSTOP`. 시각을 계산해 옮기지 않는다. VM 의 crontab 줄은 그 VM 의 현지 시각, ESX 줄은 UTC 로 쓴다(`mk_vmcron`, `mk_esxcron`).

ESX 호스트의 `tcgen_apply.py` 명령은 `check`, `prepare <tag>`, `poweron <vm> [초]`, `poweroff <vm> [초]`, `lpage <vm>`, `lpagewait <vm> [초]`, `rollback <tag>`, `snapshot`(읽기만 함. 표준 입력의 `vm <이름>`, `key <vmx 키>` 줄을 받아 VM 설정을 `TCGEN-CFG` 줄로 낸다) 이다. `prepare` 는 값이 다를 때 VM 을 끄고 값을 바꾸기만 한다(켜지 않는다). 켜기는 `tcrun` 의 `power_vms` 가 `poweron`, `lpagewait`, ssh 로그인 확인 순서로 VM 마다 한다. spec 의 `off <vm>` 줄은 `check` 가 전원 비교(`TCGEN-POWER`)에 쓴다. VM 의 crontab 시각 칸은 VM 에서 `date -d @<초>` 로, ESX 의 시각 칸은 점프 VM 에서 UTC 로 만든다.

## 5. plan 형식

plan 은 UTF-8 글 파일이고 줄 단위다. 첫 낱말이 종류, 둘째 낱말이 케이스 번호(세 자리)다. 낱말 사이는 빈칸 하나다. `tcrun` 은 `grep "^<종류> <번호> "` 와 `cut -d' ' -f<N>-` 로 읽는다. 줄의 나머지는 글자 그대로 쓴다.

머리 부분은 다음과 같다.

| 줄 | 내용 |
| :-- | :-- |
| `TCGEN-PLAN 2` | 형식 번호. 첫 줄 |
| `VER <판>` | plan 을 만든 생성기의 판. `tcrun` 의 판과 다르면 시작하지 않는다 |
| `RUNID <실행 ID>` | `년월일-시분초`. 로그 파일 이름과 실행 폴더 이름에 쓴다 |
| `LOGDIR <경로>` | 점프 VM 로그 폴더. `~/` 로 시작하면 홈 폴더 |
| `GEN <시각>` | 생성 시각(참고용) |
| `SET <이름> <정수>` | `MON_LEAD_MIN`, `SNAP_LEAD_MIN`, `SPACING_MIN`, `PREP_LEAD_MIN`, `POWERON_WAIT_MIN`, `BOOT_WAIT_MIN`, `SHUTDOWN_WAIT_MIN`. plan 에 없는 이름은 `tcrun` 의 기본값을 쓴다 |
| `ADDR <ESX 호스트> <주소>` | ESX 접속 주소. 없으면 호스트 이름으로 접속 |
| `CHAIN <ESX 호스트>` | 진행 하나. ESX 호스트를 적지 않은 케이스는 `-` |
| `RPTH <CSV 한 줄>` | 리포트용 CSV 의 머리글 |
| `CFGL <이름> <글>` | 구성 스냅샷 csv 의 머리글과 구간 이름(`h1`, `h2`, `time`, `basic`, `adv`, `guest`, `aff`, `ref_esx`, `ref_guest`, `none`). 없으면 `tcrun` 이 영어 글을 쓴다 |
| `OPS HOST <주소>`, `OPS USER <계정>`, `OPS ENC <암호화한 암호>`, `OPS KEY <키>`, `OPS TLS <0 또는 1>` | VCF Operations 기록(설정값 `ops_host`, `ops_user`, `ops_pass_enc`, `ops_enc_key`, `ops_verify_tls`). 주소를 적었을 때만 있다. `tcrun` 의 `ops_login`, `ops_find`, `ops_put`, `ops_snapshot` 이 쓴다 |
| `LIST <글>` | S 블록의 확인 목록 한 줄(v2.15. `confirm_lines`). ASCII 영어. VM 이름은 `vm <이름>` 으로 적는다. `tcrun start` 가 그대로 보인다 |
| `GCMD <명령>` | 구성 스냅샷 때 케이스의 켜져 있는 VM 마다 실행할 명령(설정값 `seq_guest_cmd`). 줄 끝까지가 명령이다. 없으면 실행하지 않는다 |

케이스 부분은 `CASE` 줄로 시작하고 `END` 줄로 끝난다.

| 줄 | 내용 |
| :-- | :-- |
| `CASE <번호> <ESX 호스트 또는 -> <케이스 이름>` | 케이스 시작. plan 의 순서가 실행 순서 |
| `SEG <번호> <1 또는 0>` | 1: 설정이나 VM 전원이 호스트와 다를 수 있는 케이스(호스트와 비교한다). 0: 바로 앞 케이스와 같다(앞의 1 케이스와 함께 등록한다) |
| `MSTOP <번호> <초> <년-월-일 시:분>` | 모니터링 중지 줄을 실행할 시각. 없으면 중지 줄을 등록하지 않는다 |
| `APPLYAT <번호> <초> <년-월-일 시:분>` | 잡이 없는 케이스에서 설정과 VM 전원을 맞출 시각 |
| `START <번호> <초> <년-월-일 시:분>` | 잡을 시작할 시각. 잡이 있는 케이스에 반드시 있다. `<초>` 는 생성한 PC 의 시간대로 바꾼 epoch 이고 뒤의 글은 로그와 등록 기록에 적는다 |
| `RPTA <번호> <CSV 조각>` | 리포트용 CSV 한 행의 앞부분: 테스트 그룹, 케이스명, 설명, 호스트 이름 |
| `RPTB <번호> <CSV 조각>` | 뒷부분: VM, 종료 기준 VM. `tcrun` 은 `RPTA,잡 시작,잡 종료,RPTB` 로 한 행을 쓴다 |
| `VM <번호> <VM 이름> <ssh 대상>` | 그 케이스의 VM. 순서가 켜는 순서. ssh 대상은 `계정@VM` 또는 `VM` |
| `OFF <번호> <VM 이름>` | 그 케이스 동안 끌 VM. 같은 이름의 `VM` 줄이 있어야 한다. 없는 VM 은 켠다 |
| `AH <번호> </구역/옵션>=<값>` | ESX 호스트 옵션 |
| `AV <번호> <VM 이름> <키>=<값>` | vmx 키. 값이 비면 삭제 |
| `PAT <번호> <VM 이름> <정규식>` | 그 VM 에서 이 케이스의 줄을 찾는 `grep` 패턴(표식 + `$`) |
| `MS <번호> <VM 이름> <명령 글>` | 모니터링 시작. 명령 글 = `render_command` 결과 + 표식. 시각 칸은 `tcrun` 이 추가 |
| `JOB <번호> <VM 이름> <명령 글>` | 잡 |
| `MX <번호> <VM 이름> <명령 글>` | 모니터링 중지 |
| `EPAT <번호> <정규식>`, `EMS <번호> <명령 글>`, `EMX <번호> <명령 글>` | ESX 호스트의 패턴, 모니터링 시작, 모니터링 중지 |
| `END <번호>` | 케이스 끝 |

- 케이스에 `JOB` 줄이 없으면 잡이 없는 케이스다(설정과 VM 전원만 맞춤).
- `MS` 나 `EMS` 줄이 있으면 모니터링이 있는 케이스다.
- 형식을 고치면 `PLAN_FORMAT`, `tcrun` 의 `PLAN_FMT`, 이 절, `test_plan_text` 를 함께 고친다. `tcrun start` 와 `run` 은 `VER` 이 같은 plan 만 실행한다. 그러나 `tcrun stop` 과 다음 실행의 줄 삭제(`take_over`, `host_block`)는 같은 점프 VM 에서 앞 판으로 시작한 실행의 plan 도 읽는다. 그래서 줄 종류의 뜻을 바꾸지 않고 줄을 더하기만 할 때는 형식 번호를 올리지 않는다. v2.15 는 `LIST` 줄을 더했고 형식 번호는 2 그대로다(번호를 3으로 올린 초안에서 v2.15 의 tcrun 이 v2.14 실행의 줄을 지우지 못하는 것을 2026-11-20 에 발견해 되돌렸다). `test_tcrun` 의 v2.14 plan 시험이 이것을 확인한다.

가짜 환경(`fakeenv.py`)은 시험 폴더 하나에 점프 VM, VM, ESX 호스트를 폴더로 만들고 가짜 명령을 `PATH` 앞에 둔다.

- 가짜 `ssh`: VM 대상은 제어 터미널이 없는지와 askpass 비밀번호를 확인한다. ESX 대상(`-i`, `-l root`)은 키 파일과 `authorized` 파일이 있을 때만 접속한다. VM 이 꺼져 있으면 접속을 거절한다.
- 가짜 `date`, `sleep`: 가상 시계. 시험에서는 시간이 30배 빨리 간다(`TCGEN_TEST_SPEED`). 장비가 느리거나 다른 작업이 함께 실행 중이면 시점을 보는 시험이 틀릴 수 있다. 그때는 `TCGEN_TEST_SPEED=20` 처럼 배속을 낮춰 실행한다(시험 시간은 그만큼 늘어난다). `tcrun` 은 시간을 `date` 와 `sleep` 으로만 다루므로 시험용 코드가 필요 없다.
- `CronSim`: 등록된 crontab 줄을 가상 시계의 그 분에 실행한다. VM 은 cronie 의 `%` 처리를, ESX 는 `cron.update` 가 있을 때만 다시 읽는 동작을 흉내 낸다.
- 가짜 `vim-cmd`, `esxcli`: Broadcom KB 343248, 320877, 310338 의 출력 형식을 따른다. 실제 ESX 의 출력이 이 가짜와 다르면 시험으로는 찾지 못한다. `README.md` 12절의 '실제 장비에서 확인할 것' 을 참조한다.
- dash 시험(`DashTests`): `PATH` 앞에 `sh` 를 dash 로 두어 `tcrun`, VM 과 ESX 에 보내는 글, cron 이 실행하는 줄을 모두 dash 로 실행한다.

화면 글자가 잘리는지는 `gui_smoke.py <그림 폴더>` 로 창을 PNG 로 저장해 확인한다(macOS). 창 크기는 환경 변수 `TCGEN_W`, `TCGEN_H` 로 정한다.

## 7. 고치는 절차

1. 고치기 전에 고칠 파일을 복사해 둔다. 0절의 사용자 결정 목록에서 이번 변경과 닿는 항목을 찾아 둔다.
2. 고친다. 0절의 항목을 바꾸거나 없애야 하면 고치기 전에 사용자에게 묻는다. 동작이 달라지면 `tcgen_core.py` 의 `VERSION`, `jump/tcrun.sh` 의 `TCRUN_VERSION`, `jump/tcgen_apply.py` 의 `VERSION` 을 같은 새 값으로 고치고 `README.md` 를 같이 고친다. 세 값이 다르면 `test_versions_match` 가 실패한다.
3. `jump/` 의 파일을 고쳤으면 `python tools/make_payload.py` 를 실행한다. 실행하지 않으면 `test_payload_is_in_sync_with_sources` 가 실패한다.
4. `python -m unittest discover -s tests -v` 가 전부 통과하는지 본다. 블록이나 `jump/` 를 고쳤으면 tcsh, dash, perl 이 있는 Linux 나 macOS 에서 실행한다.
5. 화면을 고쳤으면 `python tests/gui_smoke.py` 를 실행한다.
6. Windows 실행 파일은 `build_windows.bat` 으로 만든다.
7. 저장소에 올릴 때는 문구나 문서만 고쳤어도 2번의 세 값을 같은 새 값으로 고치고, 올린 커밋에 태그 `tcgen-v<판 번호>` 를 등록한다(3.2절).
8. 올리기 전에 `python tools/release_diff.py tcgen-v<이전 판> <저장소 폴더>` 를 실행한다. 탭 4 의 칸(고를 수 있는 화면 전체), 탭 1~3 의 칸, 화면의 글자, 설정 키, plan 의 줄 종류, 0절의 결정 번호 가운데 빠진 것을 보인다. 사용자가 요청하지 않은 항목이 빠졌으면 올리기 전에 사용자에게 묻는다. 이 도구는 v2.11 에서 v2.12 로 갈 때 빠진 모니터링 중지 칸을 보인다.
