# 개발 지침 (이 생성기를 고치거나 다시 만드는 사람과 AI 용)

이 문서는 테스트 실행 명령 생성기(tcgen) v2 를 고치는 사람과 AI 코딩 도구가 맨 먼저 읽는 문서다.
사용 방법은 `README.md` 에 있다. 이 문서는 구조, 요청 없이 고치면 안 되는 설계 규칙, plan 형식, 시험 방법, 고치는 절차를 적는다.

## 1. AI 에게 시킬 때

```
DEVELOPER.md 와 README.md 를 먼저 읽어라.
3절의 설계 규칙은 사용자가 정한 것이므로 요청 없이 바꾸지 마라.
jump/ 의 파일을 고쳤으면 python tools/make_payload.py 를 실행해라.
고친 뒤 python -m unittest discover -s tests -v 가 통과하는지 확인하고, 규칙을 바꿨으면 DEVELOPER.md 와 README.md 와 시험을 같이 고쳐라.
```

## 2. 구조

### 2.1 파일

| 파일 | 하는 일 |
| :-- | :-- |
| `tcgen_core.py` | 화면과 무관한 계산 전부. 앞부분은 v1.4 에서 이어지는 코드(시각 계산, crontab 줄, 블록 A, B, C, D, 기록 CSV, 리포트용 CSV, 데이터 폴더)이고, 뒷부분의 '설정 프로파일' 과 '순서 실행' 절이 v2 에서 더한 코드다. 버전은 `VERSION` |
| `tcgen_app.py` | 화면(tkinter). 탭 1 실행 명령, 탭 2 모니터링 명령, 탭 3 설정 프로파일, 탭 4 테스트 케이스, 탭 5 생성 결과. 진행 방식에 따라 `apply_mode` 가 열과 칸을 보이거나 숨긴다 |
| `jump/tcrun.sh` | 점프 VM 의 진행 스크립트(POSIX sh). 설치되면 `<작업 폴더>/tcrun`(기본 `~/.tcgen/tcrun`). 자기 위치를 작업 폴더(`D`)로 쓴다 |
| `jump/tcgen_apply.py` | ESX 호스트에서 실행하는 설정 적용 스크립트(Python 3.5 문법, 표준 라이브러리만) |
| `tcgen_payload.py` | 위 두 파일의 내용을 담은 모듈. `tools/make_payload.py` 가 만든다. 직접 고치지 않는다. exe 로 빌드해도 두 파일의 내용이 함께 들어가게 하려고 모듈로 둔다 |
| `tools/make_payload.py` | `jump/` 의 두 파일을 `tcgen_payload.py` 로 옮긴다. `--check` 는 같은지만 확인한다 |
| `run_gui.bat`, `build_windows.bat` | 실행, Windows 실행 파일 빌드(PyInstaller). ASCII, CR+LF 로 저장한다 |
| `tests/` | 6절 |

Python 표준 라이브러리만 쓴다. 추가 패키지를 넣지 않는다. PC 쪽 코드(`tcgen_core.py`, `tcgen_app.py`, `tcgen_payload.py`)는 Python 3.8 에서 동작해야 한다.

### 2.2 세 곳에서 실행되는 코드

| 실행되는 곳 | 코드 | 하는 일 |
| :-- | :-- | :-- |
| PC | `tcgen_core.py`, `tcgen_app.py` | 입력을 검증하고 블록과 plan 을 만든다. ssh 를 호출하지 않는다 |
| 점프 VM | `<작업 폴더>/tcrun` | plan 을 읽어 ESX 호스트별로 케이스를 순서대로 진행한다. VM 에는 `vmssh` 와 같은 방법(비밀번호는 `vmpw`, `SSH_ASKPASS`, `setsid`)으로, ESX 에는 `esxssh`(키)로 접속한다 |
| ESX 호스트 | `/tmp/tcgen/tcgen_apply.py` | 설정 비교와 적용, VM 종료와 켜기, 이전 값으로 복원. `tcrun` 이 호출할 때마다 전송해 저장한다 |

VM 에는 파일을 만들지 않는다. `tcrun` 이 ssh 표준 입력으로 셸 글을 보내 crontab 을 고치고 프로세스를 찾는다.

### 2.3 순서 실행의 자료 흐름

1. `build_seq` 가 입력을 검증하고 케이스별 내용(등록할 명령 글, 설정 항목, 프로세스 이름 패턴)을 만든다.
2. `plan_text` 가 그것을 plan(5절)으로 쓴다. `plan_view` 는 같은 내용을 사람이 읽는 글로 쓴다.
3. `seq_check_block`, `seq_run_block` 이 plan 을 gzip 뒤 base64 로 블록에 넣는다. 블록은 plan 을 `<작업 폴더>/runs/<실행 ID>/plan` 에 풀고 sha256 을 확인한 뒤 `tcrun check` 또는 `tcrun start` 를 부른다.
4. `tcrun start` 가 ESX 호스트마다 `setsid sh tcrun run <plan> <호스트>` 를 백그라운드로 시작한다.
5. `tcrun run` 은 케이스마다 준비 시각 대기, `apply_settings`, `power_vms`, `register`, `wait_job`, `stop_mon` 을 차례로 부르고 로그 폴더에 기록한다.

`tcrun` 과 `tcgen_apply.py` 가 주고받는 줄은 `TCGEN-` 로 시작한다. `TCGEN-RESULT <낱말>` 이 결과다(`nochange`, `changed`, `wouldchange`, `poweredon`, `rolledback`, `nothing`, `error <이유>`). VM 과 ESX 에서 보낸 셸 글의 답도 같은 방식이다(`TCGEN-CLOCK`, `TCGEN-CRON`, `TCGEN-PROC`, `TCGEN-LINE`).

## 3. 설계 규칙 (사용자가 정한 것. 요청 없이 바꾸지 않는다)

### 3.1 동작 방식 (v1.4 에서 이어지는 규칙)

- PC 의 생성기는 글자만 만든다. PC 에서 ssh 를 호출하지 않는다. 사용자가 블록을 복사해 붙여넣는다.
- 엑셀 파일을 입력이나 저장 형식으로 쓰지 않는다(문서 보안 프로그램이 암호화한다). CSV 와 JSON 만 쓴다.
- 등록한 명령은 고치지 않고 crontab 한 줄로 그대로 등록한다. 시작용, 중지용 실행 파일을 VM 에 만들지 않는다.
- 자동으로 추가하는 것은 세 가지뿐이다: 변수를 쓴 명령 앞의 `TC_HOST=…; TC_START=…;`, VM 줄의 `%` 를 `\%` 로, 줄 끝 표식 ` # tcgen <케이스> <호스트>`.
- ESX 줄의 시각은 UTC 다. ESX 줄은 `%` 를 고치지 않는다.
- 붙여넣기 블록은 ASCII 만 쓰고 csh, tcsh, bash 공통이어야 한다: here-document 끝 줄은 따옴표 없이 쓰고 본문의 `\`, `$`, `` ` `` 앞에 역슬래시. `!` 와 탭을 쓰지 않는다. 줄 끝을 역슬래시로 끝내지 않는다. CR+LF 로 붙여넣어도 동작해야 한다.
- VM 비밀번호는 점프 VM 의 `~/.tcgen/vmpw`(권한 600)에만 둔다. 생성기 파일, CSV, 블록, plan 에 비밀번호를 넣지 않는다. ESX 비밀번호는 저장하지 않는다.
- 블록 D(VM crontab 전체 삭제)는 삭제 전에 VM 에 백업 파일을 남기고, 복사 전에 확인을 받는다. ESX 는 대상이 아니다.

### 3.2 판 구분 (사용자 2026-11-16 "이전 버전하고 구분되도록 저장")

- v2 는 v1.x 와 이름이 다르다: 실행 파일 `tcgen2`, 데이터 폴더 `tcgen2_data`, 설정 폴더 `tcgen2`. v1 의 `tcgen_data` 와 설정 폴더 `tcgen` 은 읽기만 한다(`import_from_v1`).
- 점프 VM 의 `~/.tcgen/vmssh`, `askpass`, `setpw` 는 v1.4 와 글자 하나까지 같게 둔다. v1.4 를 다시 쓸 때 그대로 쓰게 하기 위해서다(`test_v14_compat.py` 가 확인).
- 시각 지정 방식은 v1.4 와 같은 결과를 낸다. 같은 입력이면 블록 A, B, C, D 가 바이트 단위로 같다. `tcgen_core.py` 의 v1.4 부분(`build_entries`, `vm_block`, `esx_block`, `wipe_block`, `setup_block`)을 고치면 이 규칙이 깨진다.

### 3.3 순서 실행 (사용자 2026-11-15, 2026-11-16 지시)

- 케이스는 ESX 호스트별로 표의 순서대로 진행한다. 호스트끼리는 서로 기다리지 않는다.
- VM 전원(사용자 요구 2026-11-16 "VM 이 다 꺼져있으면 VM 둘다 완전히 킨다음에 잡 수행해야되는데 하나만 키고 수행함 VM off 설정없을때는 둘다 완전히 순차적으로 (lpage backing 완료되어야해서 다 올라온거 확인한다음) 킨다음 수행", "VM off 해놓고 테스트할때도있어서 테스트 케이스 등록할 때 off 설정도 필요함"): VM 행마다 `power`(`on` 기본, `off`)를 둔다. ESX 호스트가 있는 케이스는 이름이 있는 VM 행을 모두 그 케이스의 VM 으로 본다(v2.5 까지는 잡, 모니터링, 설정이 없는 VM 을 케이스에서 뺐다. 그런 VM 은 꺼져 있어도 켜지 않았다). `off` 인 VM 은 켜져 있으면 끈다. `on` 인 VM 은 표의 순서대로 하나씩 확인해 꺼져 있으면 켜고, 켜기 작업 완료, 1GB page backing 완료, ssh 로그인을 확인한 뒤 다음 VM 으로 넘어간다. 1GB page backing 규칙은 앞선 시험에서 VM 을 켤 때 쓰던 확인 스크립트와 같다: 목표 = `memSize` MB / 1024, 15초마다 읽고 목표에 닿으면 바로 완료, 6번 연속 늘지 않으면 멈춤(실패 수 > 0 이면 failed, 0 이면 stalled). backing 실패로 멈출 때는 설정을 되돌리지 않는다. vsish 노드를 읽지 못하면 WARN 을 남기고 넘어간다. ESX 호스트가 없는 케이스는 전원을 다루지 않는다. `off` 인 VM 에 잡이나 모니터링이 있으면 오류다.
- 한 케이스에서 잡이 있는 모든 VM 은 같은 분에 잡을 시작한다.
- 모니터링이 있으면 잡은 모니터링 시작 5분 뒤에 시작한다(설정값 `mon_lead_min`).
- 기본 프로파일은 `tcgen_core.py` 의 `DEFAULT_PROFILES` 에 있다. 데이터 폴더에 `profiles.json` 이 없을 때만 자동으로 넣고(`load_profiles(base, seed=True)`), [기본 프로파일 추가] 는 표에 없는 이름만 추가한다. 사용자가 고친 행을 덮어쓰지 않는다. 이름이나 내용을 바꾸면 `README.md` 7.4절의 표와 `tests/test_seq.py` 를 같이 고친다.
- 그 케이스에서 VM 을 켰으면 최소 N분(설정값 `seq_settle_min`, 기본 10)이 지난 뒤에 잡을 시작한다. 기준 시각은 마지막으로 켠 VM 의 준비(1GB page backing 확인, ssh 로그인)가 끝난 시각이다(`on.<VM>` 파일). 켜져 있던 VM 만 쓰면 이 대기를 넣지 않는다. 실행 계획과 도움말에 이 대기를 분 단위로 적는다(사용자 요청 2026-11-16 "VM 킨 다음 몇분후에 잡실행하는지 설명도 넣어줘").
- 시작 시각 준비(사용자 요청 2026-11-16 "만약 시작 시간 지정해두면 VM 설정 변경은 몇분 전에 하는 지 ..설명 써줘"): 시작 시각을 적은 케이스는 그 시각 N분 전(설정값 `seq_prep_lead_min`, 기본 60, plan 의 `PREP_LEAD_MIN`)까지 기다린 뒤 설정 적용과 VM 전원 맞추기를 한다. 기본값 60 은 이 판을 만들 때 정했다(메모리가 큰 VM 의 켜기 작업과 1GB page backing, 부팅, 켠 뒤 대기 10분, 모니터링 5분이 들어가도록). 0 이면 차례가 오는 대로 한다.
- 시작 시각과 케이스 사이 간격(사용자 결정 2026-11-16): 케이스의 `seq_start` 를 비우면 자동이고, 자동인 케이스의 잡은 앞 케이스의 잡이 끝난 시각에서 N분(설정값 `seq_gap_min`, 기본 30) 이상 지난 뒤에 시작한다. `seq_start` 에 시각을 적으면 그 시각에 잡을 시작하고 간격은 적용하지 않는다. 지킬 수 없으면 가능한 가장 이른 시각에 시작하고 WARN 을 남긴다. 앞 케이스가 끝나기를 기다리는 것, VM 을 켠 뒤의 대기, 잡 시작 최소 간격은 시각을 적은 케이스에도 적용한다. 시각 계산은 모두 `tcrun` 의 `register` 에 있다. 시각 지정 방식의 `start`, `interval` 과는 다른 칸이다(두 방식의 값이 섞이지 않게 따로 둔다).
- 잡 시작 최소 간격(사용자 요구 2026-11-16 "모든 잡들은 분단위로 다른시각에 시작되어야하거든? 겹치면 안됨", "호스트1과 호스트2의 첫번째케이스는 5분 차이 두고 실행되도록하고싶어"): 모든 잡 시작은 서로 N분(설정값 `seq_start_spacing_min`, 기본 5, plan 의 `SPACING_MIN`) 이상 떨어진다. ESX 호스트가 달라도, 같은 점프 VM 의 다른 실행과도 같다. `tcrun` 의 `register` 가 `claim_start` 로 잡 시작 시각을 `$MD`(= `~/.tcgen/minutes`)에 기록한다. 기록은 `$MD/.lock`(mkdir 잠금, pid 를 적고 그 프로세스가 없으면 지움)을 잡은 진행 하나만 한다. N분 안에 다른 기록이 있으면 그 가운데 가장 늦은 시각 + N분으로 옮기고 다시 확인한다. 기록 폴더의 `who` 는 '실행, ESX 호스트, 케이스', 줄 등록을 마치면 `reg` 를 만든다. 등록 실패, 너무 늦은 등록, 잡 시작 전 stop 에서는 `release_start` 로 지운다. 실행이 끝나면 `release_mine` 이 `reg` 없는 자기 기록(시작하지 않은 케이스의 시각)을 지운다. 진행이 비정상 종료되어 남은 `reg` 없는 미래 기록은 `claim_dead` 로 알아보고 무시한다. `start` 와 `run` 은 plan 의 `START` 줄(적은 시작 시각)을 먼저 기록한다(`claim_plan_starts`). 하루가 지난 기록은 `old_claims` 가 지운다. 기록은 파일을 하나씩 지운다(`rm_claim`, `unlock_md`). 폴더를 통째로 지우는 명령을 쓰지 않는다. PC 쪽 `build_seq` 는 N분보다 가까운 두 시작 시각을 오류로 한다(ESX 호스트가 달라도). 한 케이스 안의 VM 은 같은 분이다.
- 잡 종료는 프로세스 이름으로 판정한다: 잡이 있는 모든 VM 에서 한 번 이상 보인 뒤 연속 N회 없음. 확인하지 못한 것(ssh 실패, pgrep 없음)을 없음으로 세지 않는다. 판정할 수 없으면 다음 케이스로 넘어가지 않고 멈춘다.
- 잡이 실행되는 동안 시험 대상 VM 에 되도록 접속하지 않는다(사용자 결정 2026-11-16: 60초 간격은 부하가 되므로 30분에서 1시간 간격). 확인은 잡 시작 `FIRST_CHECK_SEC`(기본 60초) 뒤 한 번, 그 뒤 `POLL_SEC`(기본 1800초)마다 한다. 첫 확인에서 보이지 않은 VM 이 있으면 시작 대기 끝에 한 번 더 확인한다. 모든 VM 에서 프로세스가 없어진 뒤에만 1분 간격으로 다시 확인한다. 짧은 간격의 확인을 새로 넣지 않는다. 확인할 때마다 VM 마다 로그 한 줄(`check N (case <이름>) vm <이름>: <결과>`, 줄 앞 시각이 그 VM 을 확인한 때)과 `check N (case <이름>) done. next check <시각>` 한 줄을 남긴다(사용자 요청 2026-11-16: 확인 기록에 VM 이름과 시각이 보여야 함). `POLL_SEC` 이 120 을 넘으면 리포트용 CSV 의 잡 종료 시각을 비운다(실제 종료 시각을 그 간격 안에서 알 수 없기 때문).
- 설정은 값이 이미 다른 값으로 들어 있어도 오류 없이 적용한다: vmx 에서 같은 키(대소문자 무시)의 줄을 모두 지우고 한 줄을 추가한다. 값이 모두 같으면 VM 을 끄지 않는다.
- CPU affinity 같은 값을 계산하지 않는다. 사용자가 키와 값을 직접 넣는다.
- 재부팅해야 적용되는 호스트 설정은 다루지 않는다.
- 점프 VM 에서 ESX 로는 ssh 키로 접속한다. 로그는 사용자가 화면에 적은 점프 VM 폴더에 남긴다.
- 멈추거나 stop, cancel 을 받았을 때 실행 중인 잡을 건드리지 않는다.
- 잡을 확인하지 않는 케이스(사용자 결정 2026-11-17 "시작 시간 내가 지정하는거면 실행 확인 작업을 안하면 좋겠어", "+8.0 처럼 시간 간격 입력해도 정해진 시각에 동작하는 거니까 체크작업 없도록 해줘 체크할 때 부하가 꽤 되는거같음"): 시작 시각을 적은 케이스(시각 또는 `+간격`)는 잡 프로세스를 확인하지 않는다. 잡이 실행되는 동안 VM 에 접속하지 않는다. 예외는 하나다. 같은 ESX 호스트의 바로 다음 케이스가 자동이면 그 케이스가 이 케이스의 잡 종료를 기다리므로 확인한다(`build_seq` 가 경고로 알린다). 판정은 PC 의 `build_seq` 끝부분에서 하고 plan 의 `NOCHK` 줄로 넘긴다. 확인하지 않는 케이스가 끝나는 시각 = min(다음 케이스 준비 시작 − 2분, 잡 시작 + 최대 대기). 다음 케이스 준비 시작(handover) = 다음 케이스 잡 시작 − max(`seq_prep_lead_min`, 다음 케이스의 모니터링 간격 + 5)분. 모니터링 중지 줄(MX, EMX)은 시작 줄과 함께 그 시각으로 등록한다(`register` 의 `TSTOPN`). `wait_nocheck` 가 그 시각 20초 뒤에 줄을 지운다. 둘 다 없으면(마지막 케이스, 최대 대기 없음) 케이스를 열린 채로 두고 실행을 `done` 으로 끝낸다. 짧은 간격의 확인이나 '한 번만 확인' 을 이 케이스에 다시 넣지 않는다.
- `+간격` 시작 시각(사용자 요청 2026-11-16 "다음 케이스는 위케이스의 시작시간+ 8 로 하려면", 2026-11-17 "+8.0 처럼 시간 간격 입력"): `seq_start` 에 `+8:00`, `+8`, `+8.5`(소수 시간)를 적는다. `parse_seq_offset`, `fmt_seq_offset`. 기준은 표의 윗줄이 아니라 이번 생성에 넣는 케이스 가운데 같은 ESX 호스트의 바로 앞 케이스 시작 시각이다. 적용 체크한 케이스는 기준이 되지 않는다(시:분만 적은 시각은 생성할 때마다 날짜가 달라지므로). 앞 케이스가 없거나 자동이면 오류다.
- 프로세스 이름은 잡을 확인하는 케이스에만 필요하다. 확인하지 않는 케이스의 잡은 비워도 되고 그때는 plan 에 `PROC` 줄이 없다. `tcrun` 은 잡이 있는 VM 을 `JOB` 줄로 찾는다.
- 같은 ESX 호스트의 실행 대기(사용자 보고 2026-11-17 "처음 tcrun 으로 테스트 수행했다가 추가로 실험 계획 추가하거나 할때 잘안되는거같아"): ESX 호스트 하나에는 한 번에 한 진행만 일한다. 진행 중에 붙여넣은 실행은 대기(`queued`)했다가 앞 진행이 `done` 으로 끝나면 시작한다. 다른 상태로 끝나면 대기하던 실행은 `paused` 로 끝난다(멈춘 실행 뒤의 케이스를 스스로 이어 가지 않는 규칙과 같다). 순서는 `cmd_run` 이 잠금(`lock_md`) 안에서 그때 프로세스가 남아 있는 같은 호스트의 진행을 적어 두고(`QWAIT`) 자기 pid 파일을 쓰는 것으로 정한다.
- 줄이 남은 케이스(tcrun 출력의 `open case`): 진행이 끝난 뒤에도 crontab 줄이 호스트에 남아 있는 케이스다(`<호스트>.work/times` 가 비어 있지 않음). 멈춘 실행(paused, stopped, died)이 이런 케이스를 남겼으면 그 ESX 호스트의 새 실행을 시작하지 않는다(`host_block`: `cmd_start` 는 시작하지 않고 이유를 출력, P 블록은 `[PROBLEM]`, `cmd_run` 은 `paused`). 앞 잡이 실행 중일 수 있기 때문이다(2026-11-17 재현: stop 뒤 새 실행이 실행 중인 잡 옆에 새 잡을 등록함). `tcrun cancel` 이 그 줄을 지우고 모니터링을 중지한다. `done` 으로 끝난 실행이 남긴 케이스(확인하지 않고 끝나는 시각이 없는 마지막 케이스)는 다음 실행이 첫 케이스 준비 직전에 같은 처리를 한다(`take_over`, `close_open`). 다음 실행의 첫 케이스가 자동이면 앞 잡이 언제 끝나는지 알 수 없으므로 시작하지 않는다.
- 앞 실행이 진행 중이거나 줄이 남은 케이스가 있을 때 P 블록은 그 ESX 호스트의 VM 에 접속하지 않는다(실행 중인 잡에 부하를 주지 않음).
- stop 은 VM 을 켜고 기다리는 동안에도 바로 적용한다(사용자 보고 2026-11-17 "tcrun stop 으로 stop 도 안되는거같고"): `guard` 가 `G_STOP=1` 일 때 stop 요청 파일(`<호스트>.stop`)이 있는지 확인해 ssh 를 끝낸다(반환 125, `$W/stopwait`). `power_vms` 가 `PV_STOPPABLE=1` 로 `power_on` 을 부를 때만 그렇게 한다. 되돌리기(`apply_undo`) 중에는 끊지 않는다. stop 으로 끝낼 때는 설정을 되돌리지 않는다(되돌리면 VM 을 다시 끄게 됨). 설정 적용(`prepare`)은 끊지 않고 마친 뒤에 끝낸다.
- 설정 값이 하나라도 다르면 케이스의 VM 을 모두 끄고 바꾼 뒤 표의 순서대로 하나씩 켠다(사용자 2026-11-16 "설정변경 한다고 VM 을 끄면 VM1만 끄는게 아니라 전부끄고 설정 적용 한다음 순차적으로 켜야돼"). `prepare` 가 spec 의 모든 VM 을 끄고, `power_vms` 가 켠다.
- 실행 계획(`plan_view`)은 공통 규칙을 맨 위에 한 번 적고, 케이스마다 그 케이스의 값(시작, VM 전원, 설정, 모니터링, 잡, 모니터링 중지, 최대 대기)을 항목별 짧은 줄로 적는다(사용자 2026-11-16 "실행계획 너무 읽기어려워 가독성떨어짐"). 같은 설명을 케이스마다 되풀이하지 않는다. 화면은 제목 줄을 굵게 하고 [크게 보기] 로 줄을 접어 보인다.

### 3.4 순서 실행의 구현 규칙 (이 판을 만들 때 정한 것. 고치려면 시험을 함께 고친다)

- `tcrun` 은 plan 의 글을 `eval` 하지 않고 이 장비의 셸에 넘기지 않는다. `grep`, `sed`, `cut` 으로 꺼내 파일에 쓰고, 원격에서는 따옴표로 감싼 here-document 로 넘긴다(`test_tcrun_does_not_eval_the_plan`).
- `tcrun` 과 `tcgen_apply.py` 에 시험용 코드를 넣지 않는다. 시험은 가짜 `date`, `sleep` 과 경로 환경 변수(`TCGEN_TMP`, `TCGEN_CRON_DIR`, `TCGEN_VMFS_ROOT`, `TCGEN_POLL_SEC`)만 쓴다. 이 변수들은 실제 장비에서는 설정되지 않는다.
- `tcrun` 은 POSIX sh 로 쓴다. `local`, 배열, `[[ ]]` 를 쓰지 않는다. dash 에서도 실행한다.
- `tcgen_apply.py` 는 Python 3.5 문법으로 쓴다. f-string, 변수 주석, `subprocess.run` 을 쓰지 않는다.
- `tcgen_apply.py` 는 무엇이든 바꾸기 전에 대상을 모두 확인한다(VM 을 찾고, vmx 를 읽고, 호스트 옵션을 읽는다). 하나라도 안 되면 아무것도 바꾸지 않는다.
- crontab 등록은 v1.4 의 B 블록, C 블록과 같은 방법이다: 그 케이스의 표식 줄을 지우고 새 줄을 넣는다.
- 등록 시각은 등록을 마친 시점에 15초 이상 남아 있어야 한다. 모자라면 그 케이스의 줄을 모두 지우고, 여유를 두 배로 늘려 다시 등록한다(세 번까지). 지우는 동안 시작 시각이 지났으면 일부 호스트에서 시작됐을 수 있으므로 다시 등록하지 않고 멈춘다.
- 일부 VM 에만 줄이 들어간 채로 멈추지 않는다. 등록 중에 실패하면 그 케이스의 줄을 모두 지운다.
- 모니터링 중지 줄도 같은 여유를 확인한다. 모자라면 더 뒤 시각으로 다시 등록한다(세 번까지).
- `tcrun` 은 plan 의 이름(케이스, VM, ssh 대상, ESX 주소)에 명령줄에서 뜻이 달라지는 글자가 없는지 다시 확인한다(`names_ok`, `addr_ok`). 생성기의 검증과 같은 규칙이다.

### 3.5 테스트 케이스 표

- 케이스 행 아래 VM 행. VM 마다 잡, 모니터링, 설정 프로파일을 지정한다. VM 역할 구분(이름)은 두지 않는다.
- VM 이름 자동 입력 = ESX 호스트 + `vm_prefix` + 두 자리 번호.
- 시각 지정: 모니터링 시작 = 잡 시작 전 설정 분, 중지 = 자동, 직접 입력, 중지 없음 가운데 하나. 새 행은 윗줄 값을 복사하고 시작 시각은 윗줄 + 간격.
- '적용' 을 체크한 케이스는 생성에서 빠진다. 시각 지정에서는 시각 계산에 남는다.
- [명령어 생성] 은 넣을 케이스를 고르는 창을 거친다(사용자 요청 2026-11-16 "명령어 생성 하면 넣을 테스트케이스 선택하는 화면이 안나옴"). 처음 상태는 적용 체크하지 않은 케이스. 화면의 `generate_picked` 가 케이스 표의 사본에서 고르지 않은 케이스를 `applied=True` 로 바꿔 core 에 넘긴다(core 의 생성 함수는 바꾸지 않는다). 시각 지정의 D 블록 주의(`wipe_conflicts`)는 실제 적용 체크로 다시 계산한다. 탭 4 의 적용 체크는 바꾸지 않는다.
- [+ 케이스 추가] 는 새 케이스의 이름 칸을 바로 연다(복사한 케이스는 자동 이름이 골라진 채로). 이름 규칙은 `NAME_RE` 이고, 어기면 이유(crontab 줄과 진행 파일에 들어감)와 설명 칸을 알린다.
- 리포트용 CSV 에서 비교 기준 케이스를 정하지 않는다. [리포트용 CSV 저장] 은 고른 케이스를 탭 4 의 표 순서대로 저장한다(사용자 결정 2026-11-16. v1.4 의 `비교 기준 (첫 줄)` 칸은 v2.2 에서 뺐다). 비교에 쓰는 기준은 성능 리포트 생성기에서 정한다.
- 테스트 케이스 파일(사용자 결정 2026-11-16): 탭 4 의 표는 [불러오기], [다른 이름으로 저장] 으로 사용자가 정한 파일에 저장하고 불러온다. 정한 파일이 있으면 자동 저장도 그 파일에 한다. 정하지 않으면 데이터 폴더의 `test_cases.json` 을 쓴다. 실행 명령, 모니터링 명령, 설정 프로파일과 그 밖의 설정은 어느 파일을 쓰든 같이 쓴다. '테스트 종류' 를 만들어 고르는 방식은 쓰지 않는다(사용자가 불편하다고 뺀 방식). 설정의 `case_file` 이 정한 파일의 경로이고, `case_file_paths` 가 파일별로 기억하는 기록 CSV 와 로그 폴더다. `settings.json` 의 맨 위 `record_csv`, `log_dir` 는 기본 파일을 쓸 때의 값이다. 메모리의 설정에서 `record_csv`, `log_dir` 는 항상 지금 쓰는 파일의 값이다(`load_settings` 가 넣고 `save_settings` 가 나눠 적는다). 파일을 바꾸는 순서는 화면의 `use_case_file` 에 있다: 지금 표 저장(실패하면 바꾸지 않음), 새 파일 쓰기 또는 읽기, 설정 저장, 표 바꾸기, 탭 5 결과 지우기. 사용자가 정한 파일을 읽지 못해도 그 파일의 이름을 바꾸거나 지우지 않는다.
- 테스트 케이스 CSV 의 형식은 `CASE_CSV_HEADER` 와 `cases_to_csv`, `cases_from_csv` 에 있다. 열을 더하면 README 4.1절의 표와 `tests/test_seq.py` 의 `CaseFileTests` 를 같이 고친다. 읽을 때는 머리글 이름으로 열을 찾으므로 열이 없는 예전 파일도 읽힌다.
- 자동 백업(사용자 결정 2026-11-16, 하루 두 번): `auto_backup` 이 오전과 오후에 한 번씩 `backup/auto/<년월일>_<AM|PM>/` 을 만든다. 화면은 켤 때와 30분마다 `auto_backup_tick` 으로 확인한다. 최근 60개만 남긴다.
- 리포트용 CSV 의 머리글(`REPORT_HEADER`)은 성능 리포트 생성기의 케이스 정보 파일 형식과 같아야 한다. 한쪽을 고치면 다른 쪽도 같이 고친다. 순서 실행의 리포트용 CSV 는 `tcrun` 이 plan 의 `RPTH`, `RPTA`, `RPTB` 줄로 만든다.
- 적용 체크한 케이스는 고정된 기록이다(사용자 요청 2026-11-17 "테스트 명령 실행기에서 적용완료된거 순서를 바꾸거나 하면 잡 시작 시간 다 꼬이면서 기록이 엉키는거같아 이미 적용한 테스트 기록은 시작 시간 안바뀌게할수있어?"). 시각 지정에서 그 케이스의 간격, 잡 시작, 모니터링 중지, 잡 종료 (리포트) 는 그 케이스의 칸을 직접 고칠 때만 바뀌어야 한다. 2026-11-17 재현(v2.7): [위로], [아래로] 가 이 값들을 자리에 남겨 적용 체크한 케이스끼리 값이 서로 바뀌었고, 중간에 케이스를 추가해 잡 시작을 적으면 `recalc_starts` 가 아래의 적용 체크한 케이스를 다시 계산했다. 지키는 곳: `recalc_starts` 와 `interval_from_starts` 는 적용 체크한 행을 바꾸지 않는다. `swap_cases` 는 둘 중 하나라도 적용 체크한 케이스이면 값을 케이스와 함께 옮기고 적용 체크하지 않은 행의 잡 시작도 그대로 둔다(둘 다 적용 체크하지 않은 케이스이면 v1.4 와 같이 시각이 자리에 남는다). 윗줄이 적용 체크한 케이스인 행은 윗줄과 이어지지 않는 행으로 다룬다: `recalc_starts` 는 그 행을 다시 계산하지 않고(방금 추가하거나 간격을 고친 `from_index` 행만 예외), 윗줄이 달라졌을 때의 간격 맞추기(`fit_interval`: 순서 바꾸기, 삭제, 잡 시작 직접 입력)는 그 행과 윗줄이 모두 적용 체크하지 않은 케이스일 때만 한다. 지난 케이스와의 차이(며칠)를 간격에 넣으면 마지막 케이스의 자동 중지 시각(잡 시작 + 간격)이 오류 없이 며칠 뒤가 되기 때문이다(2026-11-17 화면 재현: 새 케이스를 적용 체크한 케이스 위로 옮기자 맨 아래 케이스의 간격이 8:00 에서 184:00 으로 바뀌고 자동 중지가 11-19 01:50 에서 11-26 09:50 이 됨. 이 규칙을 넣기 전 구현에서 확인). 자동 모니터링 중지 시각은 다음 행의 잡 시작으로 계산하므로 `freeze_applied` 가 적용 체크한 케이스의 계산값을 `applied_stop` 에 적어 두고 `case_schedule` 이 그 값을 쓴다(화면의 `calc_schedule` 이 시각 지정에서 표를 그리기 전에 부른다. 적용 체크를 끄면 지운다. 직접 입력 시각 칸 `stop_time` 은 자동으로 바꿔도 예전 값이 남으므로 이 용도로 쓰지 않는다). 화면은 적용 체크한 케이스의 간격, 잡 시작, 모니터링 중지 칸을 고치지 못하게 하고 안내를 보인다(`is_locked`, `locked_notice`). 순서 실행의 칸(시작 시각, 최대 대기)은 다른 행에 영향을 주지 않으므로 고정하지 않는다. 자동 중지의 '다음 케이스' 규칙(바로 아랫줄)은 바꾸지 않았다: 지난 적용 체크한 케이스를 건너뛰게 하면 새 케이스가 마지막 케이스 규칙(잡 시작 + 간격)으로 계산되는데, 잡 시작을 직접 적은 케이스의 간격은 윗줄과의 차이라서 며칠 뒤의 중지 시각이 오류 없이 만들어진다.

### 3.6 저장

- 설정, 명령 목록, 설정 프로파일, 케이스 표는 값이 달라질 때마다 자동 저장한다. 저장 버튼을 두지 않는다.
- 데이터는 생성기 폴더가 아니라 데이터 폴더에 둔다. 다시 빌드해도 데이터가 지워지지 않아야 한다.
- 백업에는 탭 4 의 표가 들어 있어야 한다. 사용자가 정한 테스트 케이스 파일은 데이터 폴더 밖에 있으므로 [설정 백업](`backup_to`)과 자동 백업(`auto_backup`)이 `case_file_<파일 이름>` 으로 함께 복사한다(`copy_case_file`). [백업 불러오기](`restore_from`)는 백업의 설정이 가리키는 파일을 그 사본으로 바꾸고, 바꾸기 전 내용을 `before_restore` 폴더에 남긴다(2026-11-17 확인: v2.6 까지는 [설정 백업] 에 사본이 없어 백업을 불러와도 표가 돌아오지 않았음).
- 읽지 못한 데이터 파일은 지우지 않고 이름을 바꿔 보관한다. 형식을 고치면 이전 형식을 읽어 변환하고 원본을 `backup` 에 남긴다.
- 새 값은 선택 항목으로 더한다. v1.4 가 만든 `settings.json`, `run_commands.csv`, `test_cases.json` 을 그대로 읽을 수 있어야 한다.

### 3.7 화면

- 테마는 clam, 색은 `COLORS` 사전 한 곳에서 정한다. 선택한 탭은 파란 바탕 흰 굵은 글씨.
- 쓸 수 없는 글자(`!`, 탭, 한글 등)는 생성 전에 오류로 알린다.
- 표에서 숨긴 열이 있을 때는 `EditableTable.set_visible` 을 쓴다. 누른 좌표의 열 순번은 화면의 순번이므로 `_double` 이 `columns` 의 순번으로 바꾼다.

## 4. 점프 VM 의 파일과 tcrun

| 파일 | 만드는 곳 | 비고 |
| :-- | :-- | :-- |
| `askpass`, `vmssh`, `setpw` | `vmssh_lines`, `setpw_lines`(v1.4 의 `VMSSH_LINES`, `SETPW_LINES` 에서 폴더 경로만 바꾼 것) | 기본 작업 폴더이면 v1.4 와 글자까지 같다. 시각 지정의 A 블록은 v1.4 의 것을 그대로 쓴다 |
| `esxssh`, `postsetup` | `esxssh_lines`, `postsetup_lines` | 짧은 파일. 블록에 `printf` 줄로 넣는다. `esxssh` 는 `-o LogLevel=ERROR` 와 작업 폴더의 `known_hosts` 를 쓴다 |
| `tcrun`, `tcgen_apply.py` | `tcgen_payload.py` | 긴 파일. gzip 뒤 base64 로 넣고 설치 뒤 sha256 을 확인한다 |

`tcrun` 의 하위 명령은 `check <plan>`, `start <plan>`, `run <plan> <esx>`, `status [-a]`, `stop [esx]`, `cancel [esx]`, `key`, `version` 이다. `start` 는 S 블록이 쓴다.

`run` 의 순서: 대기(`queue_wait`), 시작 조건 확인(`host_block`), 앞 실행이 줄을 남긴 케이스 목록(`open_runs done` → `TAKE`), 케이스마다 `run_case`. `run_case` 의 순서: 준비 시각 대기, 앞 실행이 남긴 줄 삭제와 모니터링 중지(첫 케이스만, `take_over`), `apply_settings`, `power_vms`, `register`, 그리고 확인하는 케이스는 `wait_job` 과 `stop_mon`, 확인하지 않는 케이스는 `wait_nocheck`.

작업 폴더(사용자 요청 2026-11-16 "tcgen 실행 위치 바꿔야되겠어.. 계정홈폴더로하니까 홈폴더 용량제한있음"): 설정 `jump_dir`(비우면 `~/.tcgen`). `jump_dir`, `sh_path` 가 화면의 글과 셸 글(`~/` → `$HOME/`)을 만든다. A 블록은 그 폴더에 설치하고, 폴더가 `~/.tcgen` 이 아니면 `~/.tcgen` 의 `id_esx`, `id_esx.pub`, `vmpw` 를 복사한다(ESX 키 재등록과 비밀번호 재입력을 피함). P, S 블록과 순서 실행의 D 블록도 그 폴더를 쓴다. `tcrun` 은 `$0` 의 폴더를 작업 폴더로 쓰므로 plan 에 폴더를 적지 않는다. 시각 지정(v1.4 방식)은 `~/.tcgen` 그대로다.

쓰기 확인: `tcrun start`, `run`, `check` 는 작업 폴더(실행 폴더)와 로그 폴더에 1 MB 를 `dd` 로 써 보고(`can_write`), 쓸 수 없으면 시작하지 않거나 `[PROBLEM]` 으로 알린다. 홈 폴더 quota 가 차면 접속 스크립트와 상태 파일이 비어 ssh 출력에 배너만 남는 일이 있었다(사용자 보고 2026-11-16, 원인은 정황).

ssh: `tcrun` 의 VM 접속과 `esxssh` 는 `-o LogLevel=ERROR`(로그인 배너와 `Permanently added` 안내를 출력하지 않음)와 `-o UserKnownHostsFile=<작업 폴더>/known_hosts` 를 쓴다. 실패 이유는 `first` 가 출력에서 ssh 의 오류 줄(denied, refused, timed out 등)을 먼저 고른다. VM 을 켠 뒤 ssh 로그인을 기다리는 동안 `Permission denied` 가 나오면 다시 시도하지 않는다(10초마다 30분 동안 다시 시도하면 계정 잠금 정책에 걸릴 수 있음).

`status`: 마지막 실행(상태 파일이 있는 가장 늦은 실행 ID)의 plan 에 있는 ESX 호스트를 모두 보인다. 상태 파일이 없는 호스트는 `not started` 와 `<호스트>.out` 의 끝 다섯 줄을 보인다. `stop`: 실행 중인 진행에만 stop 요청 파일을 만들고, 실행 중이 아닌 호스트는 상태와 `cancel` 안내를 출력한다(사용자 보고 2026-11-16 "tcrun status tcrun stop 이 호스트 1에만 적용되는거같아").

`status` 는 대기 중인 진행(`queued`)과 줄이 남은 케이스가 있는 진행도 보인다(`open case:` 줄). `stop` 은 대기 중인 진행에도 stop 요청 파일을 만든다.

`cancel`(사용자 요청 2026-11-16 "잘못수행했을때 취소도 용이하지않은거같아 pause 상태로 멈춰있음", 2026-11-17 재현으로 범위를 넓힘): 프로세스가 남아 있는 진행(진행 중, 대기 중)이나 줄이 남은 케이스가 있는 모든 실행의 호스트마다 `cancel_chain` 이 한다. 실행 ID 가 늦은 것부터 한다(대기 중인 진행을 먼저 끝내야, 앞 진행이 끝난 직후에 그 진행이 시작하지 않는다). 남은 줄을 지우고 모니터링을 중지하는 부분은 `close_case` 이고 `take_over` 도 같은 함수를 쓴다(`close_open` 은 앞 실행의 plan 을 읽어야 하므로 subshell 에서 실행한다). `done` 으로 끝난 실행이 남긴 케이스를 이렇게 처리하면 상태는 `done` 그대로다. 진행의 프로세스가 남아 있으면 프로세스 그룹에 TERM(10초 뒤 KILL). `<호스트>.work/times`(줄 등록을 마치면 `register` 가 '번호 모니터링시작 잡시작' 을 쓰고, 줄을 지우면 비움)에 적힌 케이스의 줄을 `unregister` 로 지운다. 모니터링 시작 시각이 지났으면 MX 줄(`\%` → `%`)과 EMX 줄을 ssh 로 바로 실행한다. 잡 프로세스는 끝내지 않고 `pgrep` 결과만 보인다(3.3절 '실행 중인 잡을 건드리지 않는다'). 이 실행과 호스트의 앞으로의 잡 시작 기록을 지우고, 결과 CSV 에 `cancelled` 행, 상태 `cancelled`. 설정은 되돌리지 않는다.

실행 자료는 `~/.tcgen/runs/<실행 ID>/` 에 둔다.

| 파일 | 내용 |
| :-- | :-- |
| `plan` | 블록이 푼 plan |
| `<호스트>.pid` | 진행 프로세스의 pid. 끝나면 지운다 |
| `<호스트>.state` | `state=`, `time=`, `case=`, `pos=`, `step=`, `text=` 줄. `tcrun status` 가 읽는다 |
| `<호스트>.stop` | `tcrun stop` 이 만드는 stop 요청 파일. 진행이 이 파일이 있는지 확인하고 멈춘다 |
| `<호스트>.out` | 진행 프로세스의 표준 출력(정상일 때는 비어 있다) |
| `<호스트>.work/` | 원격에 보낸 셸 글과 받은 출력, VM 별 확인 상태(`seen.<VM>`, `zero.<VM>`, `gone.<VM>`), 이 진행이 켠 VM 의 준비 완료 시각(`on.<VM>`) |

잡 시작 시각의 기록은 `~/.tcgen/minutes/<분의 epoch>/` 폴더이고 `who`(실행, ESX 호스트, 케이스)와 `reg`(줄 등록을 마침) 파일이 들어간다. `~/.tcgen/minutes/.lock/pid` 는 기록하는 동안의 잠금이다(3.3절).

호스트 자리의 이름은 ESX 호스트 이름이고, ESX 호스트를 적지 않은 케이스는 `noesx` 다.

시각 계산은 `register` 에 있다. 가장 늦은 시계 = 점프 VM 시계 + `OFF`(VM 과 ESX 시계가 점프 VM 보다 앞선 초의 최댓값). 첫 시작 시각 = (가장 늦은 시계 + 여유)를 분으로 올림. 여유는 75초이고, 줄을 등록할 호스트가 넷을 넘으면 한 대마다 4초를 더한다(`ahead`). VM 을 켠 경우 = max(그 값, (VM 준비 완료 시각 + `OFF` + N분 - 모니터링 간격)을 분으로 올림). 그 뒤 케이스 사이 간격, 시작 시각, 잡 시작 최소 간격(`claim_start`)을 차례로 적용한다.

ESX 호스트의 `tcgen_apply.py` 명령은 `check`, `prepare <tag>`, `poweron <vm> [초]`, `poweroff <vm> [초]`, `lpage <vm>`, `lpagewait <vm> [초]`, `rollback <tag>` 이다. `prepare` 는 값이 다를 때 VM 을 끄고 값을 바꾸기만 한다(켜지 않는다). 켜기는 `tcrun` 의 `power_vms` 가 `poweron`, `lpagewait`, ssh 로그인 확인 순서로 VM 마다 한다. spec 의 `off <vm>` 줄은 `check` 가 전원 비교(`TCGEN-POWER`)에 쓴다. VM 의 crontab 시각 칸은 VM 에서 `date -d @<초>` 로, ESX 의 시각 칸은 점프 VM 에서 UTC 로 만든다.

## 5. plan 형식

plan 은 UTF-8 글 파일이고 줄 단위다. 첫 낱말이 종류, 둘째 낱말이 케이스 번호(세 자리)다. 낱말 사이는 빈칸 하나다. `tcrun` 은 `grep "^<종류> <번호> "` 와 `cut -d' ' -f<N>-` 로 읽는다. 줄의 나머지는 글자 그대로 쓴다.

머리 부분은 다음과 같다.

| 줄 | 내용 |
| :-- | :-- |
| `TCGEN-PLAN 2` | 형식 번호. 첫 줄 |
| `VER <판>` | plan 을 만든 생성기의 판. `tcrun` 의 판과 다르면 시작하지 않는다 |
| `RUNID <실행 ID>` | `년월일-시분초`. 로그 파일 이름과 실행 폴더 이름에 쓴다 |
| `LOGDIR <경로>` | 점프 VM 로그 폴더. `~/` 로 시작하면 홈 폴더 |
| `GEN <시각>` | 생성 시각(참고용) |
| `SET <이름> <정수>` | `MON_LEAD_MIN`, `SETTLE_MIN`, `GAP_MIN`, `SPACING_MIN`, `PREP_LEAD_MIN`, `POLL_SEC`, `FIRST_CHECK_SEC`, `GONE_COUNT`, `START_WAIT_MIN`, `POWERON_WAIT_MIN`, `BOOT_WAIT_MIN`, `SHUTDOWN_WAIT_MIN`. plan 에 없는 이름은 `tcrun` 의 기본값을 쓴다 |
| `ADDR <ESX 호스트> <주소>` | ESX 접속 주소. 없으면 호스트 이름으로 접속 |
| `CHAIN <ESX 호스트>` | 진행 하나. ESX 호스트를 적지 않은 케이스는 `-` |
| `RPTH <CSV 한 줄>` | 리포트용 CSV 의 머리글 |

케이스 부분은 `CASE` 줄로 시작하고 `END` 줄로 끝난다.

| 줄 | 내용 |
| :-- | :-- |
| `CASE <번호> <ESX 호스트 또는 -> <케이스 이름>` | 케이스 시작. plan 의 순서가 실행 순서 |
| `MAXWAIT <번호> <분>` | 최대 대기. 0 이면 제한 없음 |
| `NOCHK <번호> <초> <년-월-일 시:분 또는 ->` | 잡을 확인하지 않는 케이스에만 있다. `<초>` 는 다음 케이스 준비를 시작하는 시각(epoch), 다음 케이스가 없으면 `0` 과 `-`. `START` 줄이 있는 케이스에만 쓴다 |
| `START <번호> <초> <년-월-일 시:분>` | 잡을 시작할 시각. 시각을 적은 케이스에만 있다. `<초>` 는 생성한 PC 의 시간대로 바꾼 epoch 이고 뒤의 글은 로그에 적는 용도다 |
| `RPTA <번호> <CSV 조각>` | 리포트용 CSV 한 행의 앞부분: 테스트 그룹, 케이스명, 설명, 호스트 이름 |
| `RPTB <번호> <CSV 조각>` | 뒷부분: VM, 종료 기준 VM. `tcrun` 은 `RPTA,잡 시작,잡 종료,RPTB` 로 한 행을 쓴다 |
| `VM <번호> <VM 이름> <ssh 대상>` | 그 케이스의 VM. 순서가 켜는 순서. ssh 대상은 `계정@VM` 또는 `VM` |
| `OFF <번호> <VM 이름>` | 그 케이스 동안 끌 VM. 같은 이름의 `VM` 줄이 있어야 한다. 없는 VM 은 켠다 |
| `AH <번호> </구역/옵션>=<값>` | ESX 호스트 옵션 |
| `AV <번호> <VM 이름> <키>=<값>` | vmx 키. 값이 비면 삭제 |
| `PAT <번호> <VM 이름> <정규식>` | 그 VM 에서 이 케이스의 줄을 찾는 `grep` 패턴(표식 + `$`) |
| `MS <번호> <VM 이름> <명령 글>` | 모니터링 시작. 명령 글 = `render_command` 결과 + 표식. 시각 칸은 `tcrun` 이 추가 |
| `JOB <번호> <VM 이름> <명령 글>` | 잡 |
| `PROC <번호> <VM 이름> <정규식>` | `pgrep -f` 에 넘길 패턴. 프로세스 이름의 정규식 특수 문자를 PC 에서 역슬래시 처리한 것(`proc_pattern`) |
| `MX <번호> <VM 이름> <명령 글>` | 모니터링 중지 |
| `EPAT <번호> <정규식>`, `EMS <번호> <명령 글>`, `EMX <번호> <명령 글>` | ESX 호스트의 패턴, 모니터링 시작, 모니터링 중지 |
| `END <번호>` | 케이스 끝 |

- 케이스에 `JOB` 줄이 없으면 잡이 없는 케이스다(설정과 VM 전원만 맞춤). `PROC` 줄은 프로세스 이름을 적은 잡에만 있다. 잡을 확인하는 케이스(`NOCHK` 줄 없음)의 잡에는 `PROC` 줄이 있어야 한다(없으면 `tcrun` 이 멈춘다).
- `MS` 나 `EMS` 줄이 있으면 모니터링이 있는 케이스다.
- 형식을 고치면 `PLAN_FORMAT`, `tcrun` 의 첫 줄 확인, 이 절, `test_plan_text` 를 함께 고친다. `tcrun` 과 생성기는 `VER` 이 같을 때만 함께 동작하므로 이전 형식을 읽을 필요는 없다.

## 6. 시험

```
python -m unittest discover -s tests -v
```

| 파일 | 내용 |
| :-- | :-- |
| `test_core.py`, `test_blocks_shell.py` | v1.4 에서 옮겨 온 시험. 진행 방식을 시각 지정으로 두고 실행한다 |
| `test_v14_compat.py` | 시각 지정의 블록을 v1.4 의 결과와 바이트 단위로 비교한다. 기준 자료는 `fixtures/v14_blocks.json` 이고 `make_v14_fixture.py` 가 v1.4 소스로 만든다. 옆 폴더(`../tcgen`)에 v1.4 소스가 있으면 그 코드도 직접 실행해 비교한다 |
| `test_seq.py` | 순서 실행의 단위 시험 |
| `test_apply.py` | `tcgen_apply.py` 시험 |
| `test_tcrun.py` | `tcrun` 통합 시험 |
| `test_seq_blocks_shell.py` | 대화형 tcsh, bash 에 블록 A, P, S 를 붙여넣는 시험 |
| `fakeenv.py` | 위 세 시험이 쓰는 가짜 환경 |
| `gui_smoke.py` | 화면 점검(수동 실행). Tk 8.6 이상의 Python 으로 실행한다 |
| `gui_fuzz_applied.py` | 탭 4 의 조작을 무작위 순서로 하면서 적용 체크한 케이스의 값이 그대로인지 보는 점검(수동 실행). 탭 4 의 시각 계산이나 순서 바꾸기를 고치면 시드를 바꿔 가며 실행한다 |

가짜 환경(`fakeenv.py`)은 시험 폴더 하나에 점프 VM, VM, ESX 호스트를 폴더로 만들고 가짜 명령을 `PATH` 앞에 둔다.

- 가짜 `ssh`: VM 대상은 제어 터미널이 없는지와 askpass 비밀번호를 확인한다. ESX 대상(`-i`, `-l root`)은 키 파일과 `authorized` 파일이 있을 때만 접속한다. VM 이 꺼져 있으면 접속을 거절한다.
- 가짜 `date`, `sleep`: 가상 시계. 시험에서는 시간이 30배 빨리 간다(`TCGEN_TEST_SPEED`). `tcrun` 은 시간을 `date` 와 `sleep` 으로만 다루므로 시험용 코드가 필요 없다.
- `CronSim`: 등록된 crontab 줄을 가상 시계의 그 분에 실행한다. VM 은 cronie 의 `%` 처리를, ESX 는 `cron.update` 가 있을 때만 다시 읽는 동작을 흉내 낸다.
- 가짜 `vim-cmd`, `esxcli`: Broadcom KB 343248, 320877, 310338 의 출력 형식을 따른다. 실제 ESX 의 출력이 이 가짜와 다르면 시험으로는 찾지 못한다. `README.md` 12절의 '실제 장비에서 확인할 것' 을 참조한다.
- dash 시험(`DashTests`): `PATH` 앞에 `sh` 를 dash 로 두어 `tcrun`, VM 과 ESX 에 보내는 글, cron 이 실행하는 줄을 모두 dash 로 실행한다.

화면 글자가 잘리는지는 `gui_smoke.py <그림 폴더>` 로 창을 PNG 로 저장해 확인한다(macOS). 창 크기는 환경 변수 `TCGEN_W`, `TCGEN_H` 로 정한다.

## 7. 고치는 절차

1. 고치기 전에 고칠 파일을 복사해 둔다.
2. 고친다. 동작이 달라지면 `tcgen_core.py` 의 `VERSION`, `jump/tcrun.sh` 의 `TCRUN_VERSION`, `jump/tcgen_apply.py` 의 `VERSION` 을 같은 새 값으로 고치고 `README.md` 를 같이 고친다. 세 값이 다르면 `test_versions_match` 가 실패한다.
3. `jump/` 의 파일을 고쳤으면 `python tools/make_payload.py` 를 실행한다. 실행하지 않으면 `test_payload_is_in_sync_with_sources` 가 실패한다.
4. `python -m unittest discover -s tests -v` 가 전부 통과하는지 본다. 블록이나 `jump/` 를 고쳤으면 tcsh, dash, perl 이 있는 Linux 나 macOS 에서 실행한다.
5. 화면을 고쳤으면 `python tests/gui_smoke.py` 를 실행한다.
6. Windows 실행 파일은 `build_windows.bat` 으로 만든다.
