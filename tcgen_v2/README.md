# 테스트 실행 명령 생성기 (tcgen) v2.2

> 이 생성기를 고치거나 AI 로 다시 만들 때는 `DEVELOPER.md`(구조, 설계 규칙, plan 형식, 시험)를 먼저 읽는다.

테스트 케이스 표를 입력하면 점프 VM 터미널에 붙여넣을 블록을 만든다.
사용자는 명령과 케이스를 화면에 입력하고 [명령어 생성] 을 누른 뒤, 만들어진 블록을 복사해 붙여넣는다.

v2 는 v1.4 와 따로 설치하고 따로 실행한다. 프로그램 이름, 데이터 폴더, 설정 폴더가 모두 다르다. v1.4 는 지우지 않고 그대로 둔다(13절).

| 판 | 달라진 것 |
| :-- | :-- |
| v2.0 | 순서 실행, 설정 프로파일 적용, 점프 VM 로그 |
| v2.1 | 탭 3 에 기본 프로파일 12개와 [기본 프로파일 추가] 버튼 추가(7.4절). 진행 방식과 블록의 동작은 v2.0 과 같다. 판 번호가 바뀌었으므로 점프 VM 에 A 블록을 한 번 다시 붙여넣는다 |
| v2.2 | [리포트용 CSV 저장] 창에서 `비교 기준 (첫 줄)` 칸을 뺐다. 고른 케이스를 탭 4 의 표 순서대로 저장한다. 비교 기준 케이스는 성능 리포트 생성기의 `기준 케이스` 칸에서 정한다(9.2절). 판 번호가 바뀌었으므로 점프 VM 에 A 블록을 한 번 다시 붙여넣는다 |

## 1. v1.4 와 달라진 것

| 항목 | v1.4 | v2 |
| :-- | :-- | :-- |
| 진행 방식 | 시각 지정 한 가지 | 순서 실행(기본값)과 시각 지정 중에서 고른다 |
| 다음 케이스로 넘어가는 시점 | 사용자가 케이스마다 잡 시작 시각과 간격을 입력한다 | 순서 실행: 점프 VM 이 잡의 프로세스가 끝난 것을 확인한 뒤 다음 케이스를 시작한다. 시각을 입력하지 않는다 |
| ESX 호스트와 VM 의 설정 | 다루지 않는다 | 순서 실행: 탭 3 의 설정 프로파일을 케이스 시작 전에 적용한다. 값이 다를 때만 VM 을 종료하고 다시 켠다 |
| ESX 호스트 작업 | 사용자가 ESX root SSH 창에 C 블록을 붙여넣는다 | 순서 실행: 점프 VM 이 ssh 키로 ESX 호스트에 접속한다. 키는 처음 한 번 등록한다 |
| 블록 | A, B, C, D | 순서 실행: A, P(점검), S(실행), D. 시각 지정: A, B, C, D |
| 실행 기록 | PC 의 테스트 기록 CSV 와 로그 CSV | 순서 실행: PC 의 기록에 더해 점프 VM 로그 폴더에 진행 로그, 결과 CSV, 리포트용 CSV 가 남는다 |
| 탭 | 4개 | 5개 (탭 3 설정 프로파일 추가) |
| 프로그램과 폴더 | `tcgen.exe`, `tcgen_data`, `%APPDATA%\tcgen` | `tcgen2.exe`, `tcgen2_data`, `%APPDATA%\tcgen2` |

시각 지정 방식은 v1.4 와 같은 동작이다. 같은 입력이면 B, C, D 블록이 v1.4 와 글자 하나까지 같다(시험 `test_v14_compat.py` 로 확인). 다른 점은 하나다. [리포트용 CSV 저장] 창에 `비교 기준 (첫 줄)` 칸이 없고 고른 케이스를 표 순서대로 저장한다(9.2절).

## 2. 구성

| 파일 | 내용 |
| :-- | :-- |
| `tcgen_app.py` | 화면 |
| `tcgen_core.py` | 시각 계산, crontab 줄, 붙여넣기 블록, 순서 실행의 검증과 plan, 기록 파일 저장 |
| `tcgen_payload.py` | 점프 VM 에 설치할 두 파일의 내용(자동 생성. 직접 고치지 않는다) |
| `jump\tcrun.sh` | 점프 VM 의 진행 스크립트 원본. 설치되면 `~/.tcgen/tcrun` 이 된다 |
| `jump\tcgen_apply.py` | ESX 호스트에서 실행하는 설정 적용 스크립트 원본 |
| `tools\make_payload.py` | `jump\` 의 두 파일을 `tcgen_payload.py` 로 옮긴다 |
| `run_gui.bat` | 실행. `tcgen2.exe` 가 있으면 그것을, 없으면 설치된 Python 으로 실행한다 |
| `build_windows.bat` | Windows 실행 파일(`dist\tcgen2\tcgen2.exe`) 빌드 |
| `tests\` | 자동 시험과 화면 점검(`gui_smoke.py`) |

Python 표준 라이브러리만 쓴다. 추가 패키지는 필요 없다.

## 3. 설치와 실행

- Python 3.8 이상이 있는 PC: `run_gui.bat` 을 실행한다. `python tcgen_app.py` 와 같다.
- Python 이 없는 PC: Python 과 인터넷이 있는 PC 에서 `build_windows.bat` 을 실행한다. 만들어진 `dist\tcgen2` 폴더를 통째로 복사해 `tcgen2.exe` 를 실행한다.

PyInstaller 설치 단계에서 내려받기가 실패하면, 빌드 스크립트가 pypi.org 와 files.pythonhosted.org 의 인증서 확인을 생략하는 옵션(`--trusted-host`)으로 한 번 더 시도한다.
회사망 보안 장비가 HTTPS 를 검사하면 pip 가 인증서를 확인하지 못해 이렇게 실패한다. 이 옵션은 그 실행에만 적용되고 PC 설정에 남지 않는다.
그래도 `FAILED while installing PyInstaller` 가 나오면 인터넷 연결이나 회사망 프록시를 확인한다.
회사에 Python 패키지 저장소가 있으면 `py -3 -m pip config --user set global.index-url https://<저장소 주소>/simple` 로 한 번 지정한 뒤 빌드한다.

### 3.1 데이터 폴더

설정, 명령 목록, 설정 프로파일, 테스트 케이스 표는 생성기 폴더가 아니라 데이터 폴더에 저장한다. 데이터 폴더 기본 위치는 `C:\Users\<계정>\tcgen2_data` 이다. 생성기를 다시 빌드하거나 다른 폴더로 옮겨도 데이터 폴더는 그대로 남는다. 다섯 파일 모두 값이 달라질 때마다 자동 저장되고, 생성기를 다시 열면 불러온다. 저장 버튼은 없다.

| 파일 (데이터 폴더 기준) | 내용 |
| :-- | :-- |
| `settings.json` | 설정 영역의 값(5.1절, 7.1절)과 화면에 없는 값(7.1절의 두 번째 표) |
| `run_commands.csv` | 탭 1 실행 명령 목록 |
| `monitor_commands.csv` | 탭 2 모니터링 명령 목록 |
| `profiles.json` | 탭 3 설정 프로파일. 파일이 없으면 처음 실행 때 기본 프로파일 12개로 만든다(7.4절) |
| `test_cases.json` | 탭 4 테스트 케이스 표와 적용 체크 상태 |
| `testcases\test_record.csv` | 테스트 기록 CSV 기본 위치 |
| `testcases\testcaselogging-년월일시분초.csv` | 생성할 때마다 만드는 로그 (기본 위치) |
| `backup\년월일시분초_before_restore\` | [백업 불러오기] 직전의 데이터 파일 |

| 설정 파일 | 내용 |
| :-- | :-- |
| `C:\Users\<계정>\AppData\Roaming\tcgen2\config.json` | [데이터 폴더 변경] 으로 정한 데이터 폴더 위치, 마지막으로 고른 백업 위치. 이 파일이 없으면 기본 위치를 쓴다 |

- 명령 목록은 화면에서만 고친다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다.
- 테스트 기록 CSV 나 로그 폴더를 데이터 폴더 밖으로 지정했다면 그 파일은 [설정 백업] 에 들어가지 않는다.
- `build_windows.bat` 을 다시 실행하면 PyInstaller 가 `dist\tcgen2` 폴더를 통째로 지우고 새로 만든다. 데이터는 데이터 폴더에 있어 지워지지 않는다.

### 3.2 v1 의 데이터 가져오기

v2 를 처음 실행할 때 `tcgen2_data` 에 데이터가 없고 v1 의 데이터 폴더에 데이터가 있으면, 아래 네 파일을 `tcgen2_data` 로 복사하고 안내 창을 한 번 보인다.

- 복사하는 파일: `settings.json`, `run_commands.csv`, `monitor_commands.csv`, `test_cases.json`
- v1 의 데이터 폴더: `%APPDATA%\tcgen\config.json` 에 적힌 폴더. 그 파일이 없으면 `C:\Users\<계정>\tcgen_data`
- v1 의 폴더와 파일은 읽기만 한다. 내용도 수정 시각도 그대로 둔다.
- 테스트 기록과 로그(`testcases\`), 백업(`backup\`)은 복사하지 않는다.
- v1 설정의 테스트 기록 CSV 나 로그 폴더가 v1 데이터 폴더 안을 가리키면 `tcgen2_data` 의 같은 위치로 고쳐 저장한다. v2 가 v1 폴더에 기록하지 않게 하기 위해서다. v1 데이터 폴더 밖의 경로는 그대로 두므로, 그 경우 v1.4 와 v2 가 같은 기록 파일에 이어 쓴다.
- v1 데이터에는 진행 방식과 프로세스 이름이 없다. 진행 방식은 순서 실행이 되고, 프로세스 이름은 탭 1 에서 입력한다.

## 4. 진행 방식

설정 영역의 `진행 방식` 에서 고른다. 고르면 바로 저장되고 화면이 그 방식에 맞게 달라진다.

| 진행 방식 | 동작 | 화면 |
| :-- | :-- | :-- |
| 순서 실행 (기본값) | 시각을 입력하지 않는다. 점프 VM 의 진행 스크립트(`tcrun`)가 케이스를 표의 순서대로 진행한다. 설정 적용, 모니터링 시작, 잡 시작, 잡 종료 확인, 모니터링 중지를 차례로 한다 | 탭 4 에 설정, 최대 대기 열이 보이고 시각 열은 숨긴다. 탭 5 에 블록 A, P, S, D 와 실행 계획이 나온다 |
| 시각 지정 | v1.4 와 같다. 케이스마다 잡 시작 시각을 정해 crontab 에 등록한다. 설정 프로파일은 쓰지 않는다. 케이스에 프로파일이 선택돼 있으면 경고만 한다 | 탭 4 에 간격, 잡 시작, 모니터링 시작, 모니터링 중지, 잡 종료 (리포트) 열이 보인다. 탭 5 에 블록 A, B, C, D 가 나온다 |

순서 실행의 사용 순서는 5절, 시각 지정의 사용 순서는 8절에 있다.

## 5. 순서 실행: 사용 순서

### 5.1 처음 한 번: A 블록과 ESX 키 등록

1. 설정 영역에서 진행 방식을 `순서 실행` 으로 둔다. `점프 VM 로그 폴더` 에 점프 VM 의 폴더를 적는다. 비우면 `~/tcgen_log` 를 쓴다.
2. 탭 4 에 케이스를 하나 이상 입력하고 [명령어 생성] 을 누른다(5.2절). A 블록은 생성 결과에 함께 나온다.
3. 탭 5 의 A 블록 [복사] 를 누르고 점프 VM 터미널에 붙여넣는다. A 블록은 다른 블록과 함께 붙여넣지 않는다. 붙여넣은 뒤 아무 출력이 없으면 Enter 를 한 번 누른다(bash 5.1 이상은 붙여넣은 글을 Enter 를 누를 때 실행한다).
4. 출력에서 아래 두 줄이 `OK` 인지 확인한다. `FAILED` 가 나오면 A 블록을 다시 붙여넣는다(붙여넣는 중에 글자가 빠진 경우다).

```
OK      /home/<계정>/.tcgen/tcrun
OK      /home/<계정>/.tcgen/tcgen_apply.py
```

5. 이어서 나오는 아래 형태의 한 줄을 복사해, 설정을 적용하거나 ESX 모니터링을 실행할 각 ESX 호스트의 root SSH 창에 한 번 붙여넣는다(6절).

```
echo 'ssh-rsa AAAA... <계정>@<점프 VM>' >> /etc/ssh/keys-root/authorized_keys
```

6. `VM password:` 가 나오면 VM 비밀번호를 입력한다(화면에 보이지 않는다). 비밀번호가 이미 저장돼 있으면 묻지 않고 `already saved` 를 출력한다.
7. 점프 VM 에서 `sh ~/.tcgen/esxssh <ESX 호스트> hostname` 을 실행한다. 비밀번호를 묻지 않고 ESX 호스트 이름이 나오면 키 등록이 끝난 것이다.

A 블록이 점프 VM 의 `~/.tcgen/` 에 설치하는 파일은 다음과 같다.

| 파일 | 내용 |
| :-- | :-- |
| `askpass`, `vmssh`, `setpw` | VM 자동 로그인과 비밀번호 입력. v1.4 와 내용이 같다 |
| `vmpw` | VM 비밀번호(권한 600). `setpw` 가 만든다 |
| `esxssh` | ESX 호스트에 키로 접속한다. `sh ~/.tcgen/esxssh <ESX 호스트> [명령]` |
| `postsetup` | A 블록의 마지막 단계. ESX 에 넣을 한 줄을 출력하고, 비밀번호가 없을 때만 `setpw` 를 실행한다 |
| `tcrun` | 진행 스크립트. 하위 명령은 5.5절 |
| `tcgen_apply.py` | 설정 적용 스크립트. `tcrun` 이 ESX 호스트의 `/tmp/tcgen/` 에 전송해 실행한다 |
| `id_esx`, `id_esx.pub` | ESX 접속용 ssh 키. 없을 때만 만든다 |
| `runs/<실행 ID>/` | 실행마다 plan, 상태, 임시 파일을 둔다 |

생성기를 새 판으로 바꾼 뒤에는 A 블록을 한 번 다시 붙여넣는다. 점프 VM 의 `tcrun` 판이 생성기의 판과 다르면 P 블록과 S 블록은 아무것도 시작하지 않고 `Paste block A again` 을 출력한다.

### 5.2 명령, 설정 프로파일, 케이스 입력

1. 탭 1 에 실행 명령을 등록하고 `프로세스 이름` 을 적는다. 프로세스 이름은 잡이 실행되는 동안 VM 에 떠 있는 프로세스의 명령줄에 들어 있는 글자다(7.2절).
2. 탭 2 에 모니터링 명령을 등록한다.
3. 설정을 적용하려면 탭 3 의 설정 프로파일을 쓴다. 기본 프로파일 12개가 들어 있고, 직접 추가할 수도 있다(7.4절).
4. 탭 4 에 케이스를 실행할 순서대로 입력한다. VM 행마다 잡과 모니터링을 고른다. 설정을 적용할 케이스는 케이스 행의 설정 칸에서 ESX 호스트 프로파일을, VM 행의 설정 칸에서 VM 프로파일을 고른다.
5. [명령어 생성] 을 누른다. 오류가 있으면 블록을 만들지 않고 오류 목록을 보인다.

케이스의 순서가 실행 순서다. 한 케이스 안에서 VM 행의 순서가 VM 을 켜는 순서다. ESX 호스트가 다른 케이스는 호스트별로 따로 진행하고 서로 기다리지 않는다.

### 5.3 점검 블록 (P)

실행 전에 탭 5 의 P 블록을 점프 VM 터미널에 붙여넣는다. 아무것도 바꾸지 않고 아래 항목을 확인해 출력한다. 같은 내용이 로그 폴더의 `tcrun-<실행 ID>-check.log` 에 저장된다.

| 확인 항목 | 문제일 때 출력 |
| :-- | :-- |
| 점프 VM 의 파일, VM 비밀번호, `ssh` 와 `setsid` 명령, 로그 폴더에 쓸 수 있는지 | `missing ...: paste block A again` 등 |
| ESX 호스트 키 접속, `python3` 와 `vim-cmd` 와 `esxcli`, root crontab 파일 | `ssh key login failed ... Register the key: sh ~/.tcgen/tcrun key` |
| 설정이 있는 케이스: VM 을 찾았는지(vmid, vmx 경로, 전원 상태), 설정마다 현재 값과 목표 값 | `settings: VM '...' is not registered on this host` 등 |
| VM 접속, `pgrep` 과 `crontab` 명령, 시계가 점프 VM 과 몇 초 다른지 | `ssh login failed`, `pgrep not found` |
| VM 시계끼리의 차이 | 30초를 넘으면 `the clocks of the VMs differ by N s` |

설정 비교 줄은 아래처럼 나온다. `[change]` 는 값이 달라 적용할 항목, `[same]` 은 이미 같은 항목이다.

```
TCGEN-VM esx01ev01 vmid=10 power=on vmx=/vmfs/volumes/datastore1/esx01ev01/esx01ev01.vmx
TCGEN-SET esx01ev01 sched.mem.pin: (none) -> "TRUE"  [change]
TCGEN-HOST /Numa/LocalityWeightActionAffinity (integer): 130 -> 0  [change]
  [ok] settings: 2 value(s) differ. The VMs of this case will be shut down and powered on.
```

마지막 줄이 `CHECK RESULT: OK` 이면 실행 블록을 붙여넣는다. `CHECK RESULT: N problem(s)` 이면 `[PROBLEM]` 줄을 고친 뒤 P 블록을 다시 붙여넣는다.

### 5.4 실행 블록 (S)

탭 5 의 S 블록 [복사] 를 누르면 확인 창이 나온다. 점프 VM 터미널에 붙여넣으면 ESX 호스트별 진행이 백그라운드로 시작되고 아래처럼 출력된다. 터미널을 닫아도 진행은 계속된다.

```
started: run 20261116-143000 esx esx01   log: /home/<계정>/tcgen_log/tcrun-20261116-143000-esx01.log
status: sh ~/.tcgen/tcrun status       stop: sh ~/.tcgen/tcrun stop
```

- 같은 S 블록을 다시 붙여넣어도 다시 시작하지 않는다. 다시 실행하려면 생성기에서 다시 생성한다(실행 ID 가 새로 정해진다).
- 같은 ESX 호스트의 진행이 이미 실행 중이면 그 호스트는 시작하지 않는다.
- 설정을 적용하는 케이스에서 값이 현재 값과 다르면 그 케이스의 VM 이 자동으로 종료되고 다시 켜진다.

### 5.5 진행 확인과 멈추기

| 명령 (점프 VM) | 하는 일 |
| :-- | :-- |
| `sh ~/.tcgen/tcrun status` | 마지막 실행과 실행 중인 실행의 상태, 지금 케이스와 단계, 로그의 마지막 세 줄을 보인다. `-a` 를 주면 모든 실행을 보인다 |
| `sh ~/.tcgen/tcrun stop` | 실행 중인 진행에 멈추라고 알린다. `stop <ESX 호스트>` 는 그 호스트의 진행만 멈춘다 |
| `sh ~/.tcgen/tcrun key` | ESX 호스트에 넣을 키 줄을 다시 출력한다 |
| `sh ~/.tcgen/tcrun check <plan>` | 점검. P 블록이 실행한다 |
| `sh ~/.tcgen/tcrun start <plan>` | plan 의 ESX 호스트마다 진행을 백그라운드로 시작한다. S 블록이 실행한다 |
| `sh ~/.tcgen/tcrun run <plan> <ESX 호스트>` | 한 ESX 호스트의 케이스를 차례로 진행한다. `start` 가 호스트마다 실행한다 |
| `sh ~/.tcgen/tcrun version` | 설치된 판 |

상태는 다음 다섯 가지다.

| 상태 | 뜻 |
| :-- | :-- |
| `running` | 진행 중. `step` 에 지금 단계가 나온다 |
| `done` | 모든 케이스가 끝났다 |
| `paused` | 문제가 있어 스스로 멈췄다. `text` 에 이유가 있다(5.8절) |
| `stopped` | `tcrun stop` 으로 멈췄다 |
| `died` | 진행 프로세스가 없다(점프 VM 재부팅 등). `~/.tcgen/runs/<실행 ID>/<ESX 호스트>.out` 을 본다 |

`tcrun stop` 은 실행 중인 잡을 건드리지 않는다. 멈추는 시점에 따라 하는 일이 다르다.

| stop 을 받은 시점 | 진행 스크립트가 하는 일 |
| :-- | :-- |
| 케이스를 시작하기 전, 설정 적용 직후 | 그대로 끝낸다. 설정 적용과 VM 켜기는 중간에 끊지 않고 마친 뒤에 끝낸다 |
| crontab 줄을 등록한 뒤, 잡 시작 전 | 그 케이스의 등록 줄을 지워 잡이 시작되지 않게 한다. 모니터링이 이미 시작됐으면 중지 명령을 등록해 실행한 뒤 끝낸다 |
| 잡이 실행 중 | 그대로 끝낸다. 잡과 모니터링은 계속 실행된다. 모니터링 중지 명령은 로그에 적어 둔다 |
| 모니터링 중지 단계 | 중지와 줄 삭제를 마친 뒤 끝낸다 |

### 5.6 케이스 한 개의 진행 순서

| 단계 | 하는 일 |
| :-- | :-- |
| 1. 설정 적용 | 설정이 있는 케이스만 한다. ESX 호스트에서 현재 값과 목표 값을 비교한다. 모두 같으면 VM 을 건드리지 않는다. 하나라도 다르면 그 케이스의 VM 을 모두 종료하고(게스트 종료 요청, 10분 안에 꺼지지 않으면 전원 끄기), 호스트 옵션을 변경하고, vmx 의 키를 교체한 뒤, VM 을 표의 순서대로 하나씩 켠다. 앞 VM 에 점프 VM 에서 ssh 로그인이 되는 것을 확인한 뒤 다음 VM 을 켠다 |
| 2. 시각 계산 | 그 케이스의 VM 과 점프 VM 의 시계 중 가장 늦은 값에 75초를 더해 분 단위로 올린 시각이 모니터링 시작이다(줄을 등록할 VM 과 ESX 가 합쳐 다섯 대 이상이면 넷을 넘는 한 대마다 4초를 더한다). 잡 시작은 모니터링 시작 5분 뒤다(설정 영역의 `모니터링 시작 N분 뒤 잡 시작`). 모니터링이 없으면 올린 시각이 잡 시작이다. VM 을 다시 켠 경우는 아래 규칙을 더 적용한다 |
| 3. 등록 | 각 VM 의 crontab 에 모니터링 시작 줄과 잡 줄을 넣는다. 한 케이스의 모든 VM 잡은 같은 분에 시작한다. ESX 모니터링은 ESX root crontab 에 넣는다(UTC) |
| 4. 잡 종료 확인 | 잡 시작 20초 뒤부터 15초 간격으로 3분, 그 뒤 60초 간격으로 각 VM 에서 `pgrep -f` 로 프로세스 이름을 찾는다. 잡이 있는 모든 VM 에서 한 번 이상 보인 뒤 3회 연속으로 없으면 종료로 판정한다 |
| 5. 모니터링 중지 | 중지 명령을 1~2분 뒤의 분에 등록하고, 그 시각 20초 뒤에 그 케이스의 줄을 VM 과 ESX 의 crontab 에서 지운다 |
| 6. 기록 | 로그 폴더의 세 파일에 기록하고 다음 케이스로 넘어간다 |

VM 을 다시 켠 뒤의 대기: 설정 적용에서 VM 을 다시 켰으면, 마지막 VM 의 ssh 로그인을 확인한 시각(R)에서 N분 이상 지난 뒤에 잡을 시작한다. N 은 설정 영역의 `VM 다시 켠 뒤 잡 시작까지 최소 N분` 이고 기본값은 10 이다.

- 모니터링이 있는 케이스: 모니터링 시작은 2단계의 시각과 `R + N분 - 5분` 을 분 단위로 올린 시각 중 늦은 쪽이다. 잡 시작은 모니터링 시작 5분 뒤 그대로다.
- 모니터링이 없는 케이스: 잡 시작은 2단계의 시각과 `R + N분` 을 분 단위로 올린 시각 중 늦은 쪽이다.
- VM 을 다시 켜지 않은 케이스(설정 없음, 값이 이미 같음)에는 이 대기가 없다.
- 설정만 있는 케이스에서 VM 을 다시 켜고 그다음 케이스가 같은 VM 에서 잡을 실행하면, 그다음 케이스에도 `R + N분` 을 적용한다.
- N 을 0 으로 두면 2단계의 시각을 그대로 쓴다.

판정을 못 하는 경우에는 넘어가지 않고 멈춘다.

- `pgrep` 이 없거나 ssh 가 실패한 확인은 '알 수 없음'이다. 없음으로 세지 않고 연속 횟수를 0 으로 다시 설정한다.
- 잡 시작 뒤 10분 안에 프로세스가 한 번도 보이지 않는 VM 이 있으면 멈춘다.
- 탭 4 의 최대 대기를 넘으면 멈춘다.

### 5.7 점프 VM 로그 폴더의 파일

실행마다 ESX 호스트별로 세 파일이 생긴다. ESX 호스트를 적지 않은 케이스는 파일 이름의 호스트 자리에 `noesx` 가 들어간다. 글은 ASCII 영어다. 시각은 점프 VM 의 현지 시각이다.

| 파일 | 내용 |
| :-- | :-- |
| `tcrun-<실행 ID>-<ESX 호스트>.log` | 진행 로그. 시간순 한 줄씩 |
| `tcrun-<실행 ID>-<ESX 호스트>-result.csv` | 케이스별 결과 한 행 |
| `tcrun-<실행 ID>-<ESX 호스트>-perfreport_cases.csv` | 성능 리포트 생성기의 케이스 정보 파일. 끝난 케이스만 들어간다 |
| `tcrun-<실행 ID>-check.log` | 점검 블록의 출력 |

진행 로그에서 찾을 줄은 다음과 같다.

| 줄에 들어 있는 글 | 뜻 |
| :-- | :-- |
| `==== case <이름> (N of M) begin` | 케이스 시작 |
| `TCGEN-SET`, `TCGEN-HOST` | 설정 한 항목의 변경 전 값과 목표 값. `[change]` 또는 `[same]` |
| `TCGEN-DONE` | 적용한 호스트 옵션(전 값과 후 값), 수정한 vmx 와 백업 파일 경로 |
| `settings: every value is already as wanted` | 값이 모두 같아 VM 을 건드리지 않았다 |
| `vm <이름>: ssh login works N s after power on` | VM 을 켠 뒤 로그인이 된 시점 |
| `settle:` | VM 을 다시 켠 뒤의 대기를 적용했는지, 시작 시각을 얼마나 미뤘는지 |
| `registered on vm <이름>:` 과 그 아래 줄 | crontab 에 등록한 줄 그대로 |
| `times: monitoring start ..., job start ...` | 정한 시각 |
| `poll: vm <이름> process seen for the first time` | 프로세스를 처음 본 시점 |
| `poll: vm <이름> no process (N of 3 in a row)` | 연속 없음 횟수 |
| `job ended:` | 종료로 판정한 시각 |
| `removed the lines of this case` | crontab 줄 삭제 |
| `==== case <이름> done` | 케이스 끝 |
| `WARN` | 진행은 계속하지만 확인할 일 |
| `PAUSED:` 또는 `STOPPED on request:` | 멈춘 이유. 그 아래 `Not finished:` 줄에 끝나지 않은 케이스 이름이 나온다 |

결과 CSV 의 열은 다음과 같다.

| 열 | 내용 |
| :-- | :-- |
| `case`, `esx` | 케이스 이름, ESX 호스트 |
| `apply` | 설정 적용 결과. `none`(설정 없음), `nochange`(값이 같음), `changed`(적용함), `rolledback`(이전 값으로 복원함) |
| `begin`, `end` | 케이스를 시작한 시각, 끝낸 시각 |
| `vms_on` | VM 켜기 완료 시각(마지막 VM 의 ssh 로그인 확인 시각). VM 을 다시 켜지 않았으면 빈칸 |
| `monitor_start`, `job_start` | crontab 에 등록한 모니터링 시작 시각, 잡 시작 시각 |
| `first_seen` | 잡이 있는 모든 VM 에서 프로세스가 보인 시각 |
| `job_end` | 잡 종료 시각. 마지막 VM 에서 프로세스가 처음으로 보이지 않은 확인 시각 |
| `monitor_stop` | 모니터링 중지 명령을 등록한 시각 |
| `status` | `done`, `done (settings only)`, `paused: <이유>`, `stopped: <이유>` |

리포트용 CSV 는 PC 로 가져와 성능 리포트 생성기의 `케이스 정보 파일` 에서 고른다. UTF-8(BOM) 이고 열은 시각 지정의 리포트용 CSV 와 같다(9.2절). `잡 시작 시각` 과 `잡 종료 시각` 은 위 결과 CSV 의 `job_start`, `job_end` 다. 테스트 그룹, 설명, 종료 기준 VM 은 탭 4 에 적은 값이다. 순서 실행에서 탭 4 의 [리포트용 CSV 저장] 은 이 파일의 위치만 안내한다.

### 5.8 멈췄을 때 이어서 하는 방법

1. `sh ~/.tcgen/tcrun status` 와 진행 로그의 `PAUSED:` 줄에서 이유를 확인한다.
2. 아래 표에 따라 원인을 고친다.
3. 생성기의 탭 4 에서 끝난 케이스(결과 CSV 의 `status` 가 `done` 인 케이스)를 적용 체크한다.
4. [명령어 생성] 을 다시 누르고 P 블록, S 블록을 붙여넣는다. 남은 케이스가 처음부터 진행된다.

| 멈춘 이유 (로그의 글) | 멈춘 뒤의 상태 | 할 일 |
| :-- | :-- | :-- |
| `settings ... were not applied` (없는 VM, 없는 호스트 옵션, 일시 중지된 VM 등) | 아무것도 바꾸지 않았다 | 프로파일이나 VM 이름을 고친다 |
| `power on of vm ... failed`, `did not accept ssh login` | 설정을 이전 값으로 복원했다(vmx 는 백업 파일로, 호스트 옵션은 이전 값으로). 켜져 있던 VM 을 순서대로 다시 켜 보았다 | ESX 에서 VM 상태를 확인한다. 켜지지 않은 VM 은 직접 켠다 |
| `crontab lines were not registered` | 그 케이스의 줄을 모두 지웠다. 아무것도 시작하지 않았다 | 그 VM 의 접속과 crontab 을 확인한다 |
| `was too slow 3 times` | 등록이 시작 시각 15초 전까지 끝나지 않아 줄을 모두 지웠다. 아무것도 시작하지 않았다 | VM 접속이 느린 원인을 확인한다 |
| `took too long: the first start time ... passed` | 등록이 늦어 줄을 지웠지만, 지우는 동안 시작 시각이 지났다. 일부 VM 에서 모니터링이나 잡이 시작됐을 수 있다 | 각 VM 에서 프로세스를 확인하고 필요하면 직접 중지한다 |
| `the process was never seen` | 잡 줄과 모니터링 줄은 실행된 상태다. 모니터링은 계속 실행 중이다 | 프로세스 이름과 잡 명령을 확인한다. 모니터링은 로그에 적힌 중지 명령으로 직접 중지한다 |
| `did not end within the maximum wait` | 잡과 모니터링이 계속 실행 중이다 | 잡을 확인한다. 끝난 뒤 모니터링을 직접 중지한다 |
| `monitoring stop ... could not be registered` | 잡은 끝났다. 그 호스트의 모니터링이 계속 실행 중일 수 있다 | 로그에 적힌 중지 명령을 그 호스트에서 실행한다 |

멈춘 케이스의 crontab 줄이 VM 에 남아 있어도 된다. 같은 이름의 케이스를 다시 실행하면 그 줄을 지우고 새로 등록한다. 모두 지우려면 D 블록을 쓴다.

## 6. ssh 키 접속 (점프 VM 에서 ESX 호스트로)

순서 실행에서 점프 VM 은 ESX 호스트에 root 계정으로, 비밀번호 없이 ssh 키로 접속한다. ESX 비밀번호는 어디에도 저장하지 않는다. 방법은 Broadcom KB 313767 (ESXi 7.0, 8.0) 의 공개 키 인증이다.

A 블록이 키를 만들고 ESX 에 넣을 한 줄을 출력한다(5.1절). 같은 일을 직접 하려면 아래 명령을 쓴다.

```
# 1) 점프 VM: 키 만들기 (이미 있으면 생략)
ssh-keygen -t rsa -b 4096 -N "" -f ~/.tcgen/id_esx
cat ~/.tcgen/id_esx.pub

# 2) 각 ESX 호스트의 root SSH 창: 위에서 출력된 공개 키 한 줄을 넣는다
echo '<공개 키 한 줄>' >> /etc/ssh/keys-root/authorized_keys

# 3) 점프 VM: 확인. 비밀번호를 묻지 않고 ESX 호스트 이름이 나와야 한다
sh ~/.tcgen/esxssh esx01 hostname
ssh -i ~/.tcgen/id_esx -o BatchMode=yes root@esx01 hostname
```

- ESX 호스트의 SSH 서비스가 켜져 있어야 한다. 잠금 모드(Lockdown Mode)에서는 접속되지 않는다.
- ESX 호스트 이름으로 접속되지 않으면 설정 영역의 `ESX 접속 주소` 에 `esx01=10.0.0.11;esx02=10.0.0.12` 처럼 적는다. 탭 4 의 ESX 호스트 이름은 그대로 두고 접속만 그 주소로 한다.
- 키를 빼려면 ESX 호스트의 `/etc/ssh/keys-root/authorized_keys` 에서 그 줄을 지운다.
- 키 파일 `~/.tcgen/id_esx` 는 본인만 읽을 수 있게 저장된다(권한 600). 이 파일이 있으면 등록한 ESX 호스트에 root 로 접속할 수 있으므로 다른 곳에 복사하지 않는다.

## 7. 화면

화면은 위에서부터 설정 영역, 탭 5개, 상태 줄로 이루어진다.

- 지금 보고 있는 탭은 파란 바탕에 흰 굵은 글씨로 표시된다.
- 탭마다 표 위에 버튼이 있다. 오른쪽 [도움말] 을 누르면 그 탭의 자세한 설명 창이 열린다. 탭 4 와 탭 5 의 도움말은 진행 방식에 따라 내용이 다르다.
- 맨 아래 상태 줄에는 데이터 폴더 경로와 마지막 자동 저장 시각이 나온다. 블록을 복사하면 복사한 블록 이름과 줄 수가 나온다.

### 7.2 탭 1. 실행 명령

| 열 | 내용 |
| :-- | :-- |
| App명 | 응용 이름 |
| 명령어 명 | 탭 4 에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 잡 조건 설명 | 예: 1 job, 4 jobs 동시. 로그 CSV 의 '설명' 열에 함께 기록한다 |
| 프로세스 이름 | 순서 실행에서 잡 종료를 확인하는 데 쓴다. 시각 지정에서는 쓰지 않는다 |
| 경로/실행 명령 | 절대 경로로 입력한다. 이 명령이 crontab 에 한 줄로 그대로 들어간다 |

프로세스 이름은 다음 규칙으로 적는다.

- 잡이 실행되는 동안 VM 에 떠 있는 프로세스의 명령줄에 들어 있는 글자를 적는다. 점프 VM 이 VM 에서 `pgrep -f` 로 이 글자를 찾는다. 적은 글자를 그대로 찾는다(정규식으로 해석하지 않는다).
- 잡의 처음부터 끝까지 떠 있는 프로세스를 고른다. 예: 실행 스크립트 이름 `run_a.sh`. 중간에 30초 넘게 그 이름의 프로세스가 없는 구간이 있으면 그 시점에 종료로 판정될 수 있다.
- 다른 프로세스의 명령줄에 같은 글자가 들어 있으면 잡이 끝나지 않은 것으로 판정된다. 모니터링 명령, 로그 파일을 연 편집기나 `tail` 이 그런 예다. 그 잡에서만 쓰는 글자를 적는다.
- ASCII 문자만 쓴다. 작은따옴표, `!`, 역슬래시는 쓸 수 없다. 80자 이하.

명령 안에 쓸 수 있는 변수는 두 가지다.

| 변수 | 값 |
| :-- | :-- |
| `<vm이름>` | 명령이 실행되는 VM 의 hostname (`hostname -s`). ESX 명령에서는 ESX 호스트 이름 |
| `<실행시각>` | 명령이 실행된 시각 14자리, KST. 예: `20261109000000` |

예: `/home/tester/bench/run_a.sh >> /home/tester/log/run_a-<vm이름>-<실행시각>.log 2>&1`

### 7.3 탭 2. 모니터링 명령

탭 1 의 열에서 프로세스 이름이 빠지고 실행 위치(VM 또는 ESX), 시작 명령, 중지 명령이 더해진다. 어떤 모니터링 명령이든 직접 등록한다.

- 실행 위치가 VM 인 명령은 탭 4 의 VM 행에서, ESX 인 명령은 케이스 행에서 고른다.
- 중지 명령을 비우면 중지 줄을 만들지 않는다.

### 7.4 탭 3. 설정 프로파일

순서 실행에서 케이스를 시작하기 전에 적용할 설정 묶음이다. 시각 지정에서는 쓰지 않는다.

| 열 | 내용 |
| :-- | :-- |
| 프로파일 이름 | 탭 4 에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 대상 | `ESX 호스트` 또는 `VM`. 케이스 행의 설정 칸에는 대상이 ESX 호스트인 프로파일이, VM 행의 설정 칸에는 대상이 VM 인 프로파일이 나온다 |
| 설정 내용 | 칸을 두 번 누르면 여러 줄 입력 창이 열린다. 한 줄에 `키 = 값` 하나를 적는다. `#` 으로 시작하는 줄은 설명이다 |
| 설명 | 한글을 쓸 수 있다 |

대상이 VM 인 프로파일은 vmx 파일의 키를 적는다.

```
sched.mem.pin = "TRUE"
sched.cpu.affinity = 0,1,2,3
numa.nodeAffinity =
```

- vmx 파일의 줄(`키 = "값"`)을 그대로 붙여넣어도 된다. 따옴표는 벗겨서 받는다.
- 값을 비우면 그 키의 줄을 vmx 에서 지운다.
- 키는 대소문자를 구분하지 않는다. 값은 글자 그대로 비교한다(`TRUE` 와 `true` 는 다른 값으로 본다).
- CPU affinity 같은 값을 계산하는 기능은 없다. 키와 값을 직접 적는다.
- VM 을 구별하는 값이나 파일 위치를 적는 키는 넣을 수 없다: `displayName`, `uuid.bios`, `uuid.location`, `vc.uuid`, `nvram`, `config.version`, `virtualHW.version`, `.encoding`, `extendedConfigFile`, `vmxstats.filename`, `sched.swap.derivedName`, `checkpoint.vmState`, 이름이 `.fileName` 으로 끝나는 키.

대상이 ESX 호스트인 프로파일은 호스트 고급 설정을 적는다.

```
Numa.LocalityWeightActionAffinity = 0
/Cpu/HTWholeCoreThreshold = 0
```

- 이름은 `/구역/옵션` 또는 `구역.옵션` 으로 적는다. `구역.옵션` 은 점을 `/` 로 바꾸고 앞에 `/` 를 추가해 `esxcli system settings advanced` 의 이름으로 쓴다.
- 값을 비울 수 없다(호스트 옵션은 지울 수 없다).
- 재부팅해야 적용되는 호스트 설정은 넣지 않는다. 그런 설정은 수동으로 적용한다.

프로파일을 여러 개 고르면 탭 3 의 표 순서대로 합친다. 같은 키가 겹치면 아래쪽 프로파일의 값을 쓴다.

#### 기본 프로파일

생성기를 처음 실행하면(데이터 폴더에 `profiles.json` 이 없으면) 탭 3 에 아래 12개가 들어 있다. 고치거나 삭제해도 된다.

| 프로파일 이름 | 대상 | 설정 내용 | 뜻 |
| :-- | :-- | :-- | :-- |
| `lpage_1g_on` | VM | `sched.mem.lpage.enable1GPage = TRUE`, `sched.mem.pin = TRUE`, `sched.mem.prealloc = TRUE`, `sched.mem.prealloc.pinnedMainMem = TRUE`, `sched.swap.vmxSwapEnabled = FALSE` | 1GB page 키 5개 적용 |
| `lpage_1g_off` | VM | 위 다섯 키의 값을 비움 | 1GB page 키 5개 삭제 |
| `halt_in_monitor_on` | VM | `monitor_control.halt_in_monitor = TRUE`, `monitor.idleLoopSpinBeforeHalt = TRUE`, `monitor.idleLoopMinSpinUS = 50`, `monitor_control.disable_pause_loop_exiting = TRUE` | 유휴 vCPU 처리 키 4개 적용 |
| `halt_in_monitor_off` | VM | 위 네 키의 값을 비움 | 유휴 vCPU 처리 키 4개 삭제 |
| `latency_high` | VM | `sched.cpu.latencySensitivity = high` | Latency Sensitivity high |
| `latency_normal` | VM | `sched.cpu.latencySensitivity = normal` | Latency Sensitivity normal (기본값) |
| `vpmc_on` | VM | `vpmc.enable = TRUE` | vPMC 사용. 게스트 perf 의 하드웨어 이벤트 수집에 쓴다 |
| `vpmc_off` | VM | `vpmc.enable` 의 값을 비움 | vPMC 키 삭제 |
| `kstats_on` | VM | `vmx.buildType = stats`, `vmx.log.keepOld = 20` | vmx stats 빌드, vmware.log 보존 수 20 |
| `kstats_off` | VM | 위 두 키의 값을 비움 | vmx stats 빌드 키와 로그 보존 수 키 삭제 |
| `ht_wholecore_1` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 1` | 호스트 옵션 Cpu.HTWholeCoreThreshold 를 1 로 변경 |
| `ht_wholecore_800` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 800` | 같은 옵션을 기본값 800 으로 변경 |

- 이름이 `_off` 로 끝나는 프로파일은 값을 비워 둔 것이라 그 키의 줄을 vmx 에서 지운다. 키가 없는 VM 에서는 바꿀 것이 없어 VM 을 끄지 않는다.
- `lpage_1g_on` 은 VM 의 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Backing Guest vRAM with 1 GB Pages).
- `latency_high` 는 CPU 와 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Adjust Latency Sensitivity).
- 두 경우 모두 진행 스크립트가 설정을 이전 값으로 복원한 뒤 멈춘다(5.8절). 예약 값은 이 생성기가 바꾸지 않는다.
- [기본 프로파일 추가] 는 표에 없는 이름의 기본 프로파일만 표 끝에 추가한다. 이름이 같은 행은 고친 내용 그대로 둔다. 처음 값으로 복원하려면 그 행을 삭제한 뒤 버튼을 누른다.
- 이미 쓰던 데이터 폴더(`profiles.json` 이 있는 폴더)에는 자동으로 넣지 않는다. [기본 프로파일 추가] 를 한 번 누른다.
- CPU affinity, 예약, shares 는 기본 프로파일에 없다. VM 마다 값이 다르므로 직접 프로파일을 만들어 적는다.

적용 방법은 다음과 같다(ESX 호스트에서 `tcgen_apply.py` 가 한다).

1. 케이스의 VM 을 `vim-cmd vmsvc/getallvms` 에서 이름이 정확히 같은 줄로 찾는다. 찾지 못하거나 같은 이름이 둘 이상이면 아무것도 바꾸지 않고 멈춘다.
2. 목표 값을 현재 값(vmx 파일, `esxcli system settings advanced list -o`)과 비교한다. 모두 같으면 끝낸다.
3. 그 케이스의 VM 을 모두 종료한다. `power.shutdown` 으로 요청하고, 10분 안에 꺼지지 않거나 게스트 종료를 할 수 없으면 `power.off` 로 끈다.
4. 호스트 옵션을 `esxcli system settings advanced set` 으로 변경하고 다시 읽어 확인한다(Broadcom KB 310338).
5. vmx 를 같은 폴더에 `<이름>.vmx.tcgen-<시각>` 으로 복사해 둔다(최근 5개만 남긴다). 목표 키와 이름이 같은 줄을 모두 지우고 `키 = "값"` 한 줄을 추가한다. 같은 키가 다른 값으로 여러 줄 있어도 한 줄만 남는다. 다른 줄은 그대로 둔다. `vim-cmd vmsvc/reload` 를 실행한다(Broadcom KB 343248).
6. 진행 스크립트가 VM 을 표의 순서대로 하나씩 켠다.

중간에 실패하면 vmx 를 복사해 둔 파일로 복원하고 호스트 옵션을 이전 값으로 복원한 뒤 멈춘다. 일시 중지(Suspended) 상태의 VM 이 있으면 아무것도 바꾸지 않고 멈춘다.

### 7.5 탭 4. 테스트 케이스

케이스 행(옅은 파란 바탕, 굵은 글씨) 아래에 그 케이스의 VM 행(`└`, 흰 바탕)이 달린다. VM 은 몇 대든 둘 수 있다.

두 진행 방식에 공통인 열은 다음과 같다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 적용 | 체크하면 [명령어 생성] 에서 빠진다. 이미 실행하거나 등록한 케이스에 체크한다. 칸을 누르거나 행을 고르고 Space 를 누른다 | 없음 |
| 케이스 / VM | 케이스 이름. 영문, 숫자, `.` `_` `-` 만 사용. 적용 체크한 행을 포함해 중복 불가 | VM 이름. 같은 케이스 안에서 중복 불가 |
| 설명 | 시험 조건 설명. 한글을 쓸 수 있다. 기록 CSV 와 리포트용 CSV 에 들어간다 | 없음 |
| ESX 호스트 | 입력하면 VM 이름이 ESX 호스트+`ev01`, `ev02` … 로 자동 입력된다 | 없음 |
| 잡 | 없음 | 탭 1 의 명령어 명 중에서 고른다. `(없음)` 이면 그 VM 에는 잡이 없다 |
| 모니터링 | ESX 모니터링. 칸을 두 번 누르면 실행 위치가 ESX 인 명령만 나오는 선택 창이 열린다 | 그 VM 의 모니터링. 실행 위치가 VM 인 명령만 나온다 |
| 테스트 그룹 | 리포트용 CSV 의 `테스트 그룹`. 비워도 된다 | 없음 |
| 종료 기준 VM | 없음 | 칸을 두 번 누르면 `기준` 이 되고 다시 누르면 해제된다. 리포트용 CSV 에 들어간다 |

순서 실행에서만 보이는 열은 다음과 같다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 설정 | ESX 호스트에 적용할 프로파일. 칸을 두 번 누르면 대상이 ESX 호스트인 프로파일만 나오는 선택 창이 열린다 | 그 VM 에 적용할 프로파일. 대상이 VM 인 프로파일만 나온다 |
| 최대 대기 | 잡 시작부터 이 시간이 지나도 잡이 끝나지 않으면 진행을 멈춘다. `12:00` 형식(시간:분). 비우면 제한 없음 | 없음 |

순서 실행에서 케이스를 구성하는 규칙은 다음과 같다.

- 잡, 모니터링, 설정 가운데 하나라도 지정한 VM 행이 그 케이스의 VM 이다. 아무것도 지정하지 않은 VM 행은 쓰지 않는다. 끄지도 켜지도 않는다.
- 잡이 있는 VM 의 명령에는 탭 1 의 프로세스 이름이 있어야 한다.
- 모니터링만 있고 잡이 없는 케이스는 오류다. 잡의 프로세스가 끝난 것을 보고 모니터링을 중지하기 때문이다.
- 잡도 모니터링도 없고 설정만 있는 케이스는 허용한다. 설정만 적용하고 다음 케이스로 넘어간다.
- 설정이나 ESX 모니터링이 있는 케이스는 ESX 호스트가 있어야 한다.
- 같은 VM 을 ESX 호스트가 다른 두 케이스에 넣으면 오류다. 호스트별 진행이 서로 기다리지 않아 같은 VM 을 동시에 쓰게 되기 때문이다.
- [위로], [아래로] 로 케이스를 옮기면 케이스의 값이 모두 함께 옮겨진다.

시각 지정에서만 보이는 열(간격, 잡 시작, 모니터링 시작, 모니터링 중지, 잡 종료 (리포트))과 그 규칙은 8절에 있다.

### 7.6 탭 5. 생성 결과

[명령어 생성] 을 누르면 입력을 검사하고, 오류가 없으면 기록 파일을 저장한 뒤 블록을 보여 준다. 오류가 있으면 블록과 기록을 만들지 않는다.

순서 실행의 블록은 다음과 같다. 모두 점프 VM 터미널에 붙여넣는다.

| 블록 | 붙여넣는 때 | 하는 일 |
| :-- | :-- | :-- |
| A. 점프 VM 최초 1회 설정 | 처음 한 번, 생성기를 새 판으로 교체한 뒤 한 번 | 5.1절 |
| P. 점검 블록 | 실행 전 | plan 을 점프 VM 에 저장하고 `tcrun check` 를 실행한다. 아무것도 변경하지 않는다(5.3절) |
| S. 실행 블록 | 점검이 OK 인 뒤 | plan 을 점프 VM 에 저장하고 ESX 호스트별 진행을 시작한다(5.4절) |
| D. VM crontab 전체 삭제 | 필요할 때만 | 케이스의 VM 에 접속해 crontab 을 모두 지운다(`crontab -r`). 지우기 전 내용은 그 VM 홈 폴더의 `tcgen_crontab_backup-년월일시분초.txt` 에 저장한다. 진행 중에 붙여넣으면 등록된 줄이 지워져 잡이 시작되지 않는다 |

블록 아래의 `실행 계획` 칸에는 케이스마다 점프 VM 이 하는 일과 등록할 명령이 글로 나온다. 붙여넣기 전에 이 글로 순서와 설정 값을 확인한다.

plan 은 케이스의 내용을 담은 파일이다. P 블록과 S 블록 안에 압축해(gzip, base64) 들어 있고, 붙여넣으면 `~/.tcgen/runs/<실행 ID>/plan` 에 저장된다. 저장한 뒤 sha256 을 확인하고, 다르면 아무것도 시작하지 않는다.

시각 지정의 블록(A, B, C, D)은 8.2절에 있다.

## 8. 시각 지정: 사용 순서와 화면

진행 방식을 `시각 지정` 으로 두면 v1.4 와 같은 동작이다.

### 8.1 탭 4 의 열 (시각 지정)

| 열 | 케이스 행 |
| :-- | :-- |
| 간격 | 윗줄 잡 시작부터 이 케이스 잡 시작까지의 시간. `12:00` 형식 |
| 잡 시작 (KST) | `2026-11-09 10:00:00` 형식. 분 단위. 그 케이스의 모든 VM 잡이 이 시각에 시작한다 |
| 모니터링 시작 | 잡 시작 5분 전 (자동 계산) |
| 모니터링 중지 | 칸을 두 번 누르면 자동, 직접 입력, 중지 없음 중에서 고른다. 자동은 다음 케이스 잡 시작 10분 전이고, 마지막 케이스는 잡 시작 + 간격 - 10분 |
| 잡 종료 (리포트) | 리포트용 CSV 의 `잡 종료 시각`. 비우면 `자동` 으로 보이고 성능 리포트 생성기가 종료 시각을 정한다 |

- 잡과 모니터링이 모두 없는 VM 은 등록하지 않는다. 잡이 `(없음)` 이고 모니터링이 있으면 모니터링만 등록한다.
- [+ 케이스 추가]: 선택한 케이스를 VM 구성까지 복사해 아래에 넣는다. 잡 시작 = 윗줄 잡 시작 + 간격.
- 케이스를 옮길 때는 순서만 달라지고 잡 시작, 간격, 모니터링 중지 설정은 그 행에 남는다.
- 잡 시작이나 간격을 고치면 아래 케이스의 잡 시작이 다시 계산된다.
- 적용 체크한 케이스도 표에 남아 시각 계산에 쓰인다.

### 8.2 블록 (시각 지정)

| 블록 | 붙여넣는 곳 | 하는 일 |
| :-- | :-- | :-- |
| A. 점프 VM 최초 1회 설정 | 점프 VM 터미널 (처음 한 번) | `~/.tcgen/vmssh`, `askpass`, `setpw` 를 만들고 VM 비밀번호를 입력받아 `~/.tcgen/vmpw` 에 저장한다. v1.4 의 A 블록과 같다. 순서 실행의 A 블록을 이미 붙여넣었으면 생략한다 |
| B. VM 등록 블록 | 점프 VM 터미널 (생성할 때마다) | 잡이나 모니터링이 있는 VM 마다 ssh 로 접속해 crontab 에 줄을 등록하고 등록된 줄을 출력한다 |
| C. ESX 블록 | 그 ESX 의 root SSH 창 | `/var/spool/cron/crontabs/root` 에 줄을 추가하고 `cron.update` 로 crond 에 알린다 (Broadcom KB 323138 절차) |
| D. VM crontab 전체 삭제 | 점프 VM 터미널 (필요할 때만, B 보다 먼저) | B 블록과 같은 VM 의 crontab 을 모두 지운다 |

### 8.3 사용 순서 (시각 지정)

1. 탭 1, 탭 2 에 명령을 등록한다.
2. 탭 4 에 케이스를 입력한다. 케이스 행에 이름, ESX 호스트, 간격, 잡 시작을 넣고, VM 행마다 잡과 모니터링을 고른다. [명령어 생성] 을 누른다.
3. 점프 VM 에서 처음 한 번만 A 블록을 붙여넣는다. `VM password:` 가 나오면 VM 비밀번호를 입력한다.
4. 점프 VM 에 B 블록을 붙여넣는다. VM 마다 `---- VM이름`, `== hostname 시각`, 등록된 `# tcgen` 줄이 출력된다.
5. ESX 의 root SSH 창에 C 블록을 붙여넣는다. ESX 가 여러 대이면 C 블록의 호스트 목록에서 하나씩 골라 복사한다.
6. 시험이 끝나면 탭 4 에서 [리포트용 CSV 저장] 으로 리포트할 케이스를 저장한다(9.2절).

같은 블록을 다시 붙여넣어도 줄이 늘지 않는다. 케이스를 고쳐 다시 생성하면, 블록에 들어 있는 케이스의 기존 줄을 지우고 새 줄을 넣는다.

### 8.4 crontab 에 들어가는 줄

명령 하나가 crontab 한 줄이 된다. 줄 끝의 `# tcgen 케이스이름 호스트` 는 기존 줄을 찾는 표식이다. 순서 실행도 같은 형태의 줄을 등록하고, 시각 칸만 점프 VM 이 실행할 때 정한다.

```
55 23 19 11 * TC_HOST=`hostname -s`; TC_START=`date +\%Y\%m\%d\%H\%M\%S`; /home/tester/mon/start_mon.sh >> /home/tester/log/mon-${TC_HOST}-${TC_START}.log # tcgen TC-base-a esx01ev01
00 00 20 11 * TC_HOST=`hostname -s`; TC_START=`date +\%Y\%m\%d\%H\%M\%S`; /home/tester/bench/run_a.sh >> /home/tester/log/run_a-${TC_HOST}-${TC_START}.log 2>&1 # tcgen TC-base-a esx01ev01
50 11 20 11 * /home/tester/mon/stop_mon.sh # tcgen TC-base-a esx01ev01
```

- 변수를 쓴 명령만 앞에 `TC_HOST=...;`, `TC_START=...;` 가 추가된다. 등록한 명령은 고치지 않는다.
- cron 은 홈 폴더에서 명령을 실행한다.
- VM 의 cron(cronie)은 명령 안의 `%` 를 줄바꿈으로 처리하므로 VM 줄은 `%` 를 `\%` 로 넣는다.
- ESX 의 crond(busybox)는 명령을 고치지 않고 실행하므로 ESX 줄은 입력한 그대로 넣는다.
- ESX 시계는 UTC 다. ESX 줄의 시각은 UTC 로 넣는다.
- cron 줄에는 연도가 없다. 시각 지정에서 지난 시각을 넣으면 내년 같은 날짜에 실행되므로 생성할 때 경고한다.

### 8.5 확인과 삭제

```
crontab -l | grep ' # tcgen '                                   # VM: 등록된 줄 확인
crontab -l | grep -v ' # tcgen TC-base-a ' | crontab -          # VM: 케이스 TC-base-a 줄 삭제
grep ' # tcgen ' /var/spool/cron/crontabs/root                  # ESX: 등록된 줄 확인
```

ESX 에서 줄을 지운 뒤에는 `/bin/echo root >> /var/spool/cron/crontabs/cron.update` 를 실행한다.

## 9. PC 의 기록 파일

### 9.1 테스트 기록 CSV 와 로그 CSV

| 파일 | 행 | 열 |
| :-- | :-- | :-- |
| 테스트 기록 CSV | 케이스 하나에 한 행 | 테스트 케이스 이름, 생성 시각, ESX 호스트, VM 구성, 잡 시작(KST), 간격, 모니터링, 모니터링 시작(KST), 모니터링 중지(KST), 설명, 테스트 그룹, 잡 종료(리포트), 종료 기준 VM. 순서 실행은 여기에 진행 방식, 설정, 실행 ID 열을 더한다 |
| 로그 CSV (`testcaselogging-년월일시분초.csv`) | 등록할 명령 하나에 한 행. 순서 실행은 설정 한 항목에도 한 행 | 테스트 케이스 이름, 생성 시각, 구분, 대상, 실행 위치, 명령어 명, App명, 설명, 실행 시각(KST), crontab 시각 기준, 명령, crontab 줄, 케이스 정보. 순서 실행은 프로세스 이름, 설정, 실행 ID 열을 더한다 |

- 순서 실행에서는 생성할 때 시각을 알 수 없으므로 시각 칸을 비운다. 실제 시각은 점프 VM 로그 폴더의 결과 CSV 에 있다. 실행 ID 로 두 기록을 맞춘다.
- 기존 테스트 기록 CSV 의 머리글에 없는 열은 머리글 끝에 덧붙이고 이어서 기록한다. 덧붙이기 전 원본은 데이터 폴더 `backup` 에 `<시각>_before_header_change_<파일 이름>` 으로 복사한다.

### 9.2 리포트용 CSV (성능 리포트 생성기 연동)

시각 지정에서는 탭 4 의 [리포트용 CSV 저장] 으로 만든다. 저장할 케이스를 고르고 저장 위치를 정한다. 고른 케이스는 탭 4 의 표 순서대로 들어간다. 순서 실행에서는 점프 VM 이 만든다(5.7절).

| 열 | 넣는 값 |
| :-- | :-- |
| 테스트 그룹 | 탭 4 테스트 그룹 |
| 케이스명 | 케이스 이름 |
| 설명 | 탭 4 설명 |
| 호스트 이름 | ESX 호스트 |
| 잡 시작 시각 | 시각 지정: 잡 시작 (KST). 순서 실행: 점프 VM 이 등록한 잡 시작 시각 |
| 잡 종료 시각 | 시각 지정: 잡 종료 (리포트). `자동` 이면 빈칸. 순서 실행: 종료로 판정한 시각 |
| VM | 잡이나 모니터링을 지정한 VM 이름을 `;` 로 연결한다 |
| 종료 기준 VM | 종료 기준으로 지정한 VM 이름을 `;` 로 연결한다 |

- 파일은 UTF-8(BOM) CSV 다.
- 순서 실행의 시각은 점프 VM 의 현지 시각이다. 점프 VM 과 성능 데이터의 시간대가 같아야 한다.
- 순서 실행의 파일은 실행한 순서대로 행이 들어간다.
- 비교 기준 케이스는 이 생성기에서 정하지 않는다. 성능 리포트 생성기의 `기준 케이스` 칸에 케이스 이름을 적는다. 그 칸을 비우면 리포트 생성기는 CSV 의 첫 줄 케이스를 기준 케이스로 쓴다. v1.4 의 저장 창에 있던 `비교 기준 (첫 줄)` 칸은 v2.2 에 없다.

## 10. 제한과 주의

순서 실행에 해당하는 것은 다음과 같다.

- 실제 ESX 호스트, VM, 점프 VM 에서 아직 실행하지 않았다. 12절의 '실제 장비에서 확인할 것' 을 먼저 본다. 처음에는 중요하지 않은 VM 한 대로 P 블록과 S 블록을 실행해 본다.
- 설정 값이 현재 값과 다른 케이스에서는 그 케이스의 VM 이 자동으로 종료되고 다시 켜진다. 그 VM 에서 실행 중인 다른 작업이 있으면 끊긴다.
- 재부팅해야 적용되는 ESX 호스트 설정은 다루지 않는다. 수동으로 적용하고 재부팅한 뒤에 실행한다.
- 설정을 적용하는 케이스의 VM 은 탭 4 에 적은 ESX 호스트에 등록돼 있어야 한다. DRS 가 VM 을 다른 호스트로 옮겼으면 VM 을 찾지 못해 아무것도 바꾸지 않고 멈춘다.
- 잡, 모니터링, 설정을 지정하지 않은 VM 은 건드리지 않는다. 같은 ESX 호스트에서 켜져 있는 다른 VM 은 그대로 켜져 있다.
- 잡의 프로세스는 잡 시작 20초 뒤에 처음 확인하고 그 뒤 15초 간격으로 확인한다. 프로세스가 30초 이상 떠 있지 않으면 한 번도 보지 못해 10분 뒤에 멈춘다.
- 종료 판정은 프로세스가 끝난 뒤 30초에서 3분 뒤에 난다(확인 간격과 연속 3회). 결과 CSV 의 `job_end` 는 프로세스가 처음으로 보이지 않은 확인 시각이다.
- 같은 케이스의 VM 시계가 서로 다르면 잡이 그만큼 어긋나 시작한다. 30초를 넘으면 로그에 `WARN` 이 남는다.
- VM 켜기 작업은 최대 90분을 기다린다(`settings.json` 의 `seq_poweron_wait_min`). 90분 안에 끝나지 않으면 실패로 처리하고 설정을 이전 값으로 복원한다. 로그의 `powered on (vim-cmd vmsvc/power.on took N s)` 줄에 실제로 걸린 초가 남는다.
- VM 에 전원 켜기 질문(복사했는지 이동했는지 등)이 대기 중이면 `power.on` 이 끝나지 않아 위 한도까지 기다린다. 진행이 `power on <VM>` 단계에서 오래 머물면 ESX 에서 그 VM 의 질문을 확인한다.
- ESX 를 재부팅하면 root crontab 의 줄이 지워진다(Broadcom KB 323138). 진행 중에 ESX 를 재부팅하지 않는다.
- 점프 VM 을 재부팅하면 진행이 끝난다. 상태가 `died` 로 보인다. 5.8절의 방법으로 이어서 실행한다.
- 점프 VM 과 VM 과 ESX 의 시계가 크게 다르지 않아야 한다. 시각은 가장 늦은 시계를 기준으로 정한다.
- ESX 호스트의 `/tmp/tcgen/` 에 적용 스크립트와 실행 기록(`apply.log`, `state-<실행 ID>-<번호>.json`)이 남는다. ESX 를 재부팅하면 지워진다.

두 진행 방식에 공통인 것은 다음과 같다.

- 블록은 점프 VM 의 셸이 csh, tcsh, bash 중 무엇이든 같은 블록을 쓴다. 터미널이 줄바꿈을 CR+LF 로 보내도 된다.
- 명령에 `!`, 탭, 한글을 쓸 수 없다(한글은 변수 이름에만). csh 가 붙여넣는 글의 `!` 를 이전 명령 불러오기로, 탭을 자동 완성으로 처리하기 때문이다.
- 이름(케이스, 호스트, 명령어 명, 프로파일 이름)은 영문, 숫자, `.` `_` `-` 만 쓴다. 순서 실행에서 호스트와 VM 이름은 영문이나 숫자로 시작해야 한다.
- VM 비밀번호는 점프 VM 의 `~/.tcgen/vmpw` 에만 저장한다(본인만 읽기). 생성기 파일, CSV, 블록에는 비밀번호가 들어가지 않는다. ESX 비밀번호는 저장하지 않는다.
- 비밀번호를 고칠 때는 점프 VM 에서 `sh ~/.tcgen/setpw` 를 실행한다.

## 11. 자주 나오는 출력

| 출력 | 뜻과 할 일 |
| :-- | :-- |
| `FAILED  .../tcrun (sha256 differs. Paste block A again)` | A 블록을 붙여넣는 중에 글자가 빠졌다. A 블록을 다시 붙여넣는다 |
| `==== tcrun on this jump VM is not installed, tcgen is 2.2` | A 블록을 붙여넣지 않았다 |
| `==== plan FAILED (sha256 differs)` | P 블록이나 S 블록을 붙여넣는 중에 글자가 빠졌다. 그 블록을 다시 붙여넣는다 |
| `==== esx01: run ... was already started on this jump VM` | 같은 S 블록을 두 번 붙여넣었다. 다시 실행하려면 다시 생성한다 |
| `==== esx01: run ... is still running for this ESX host` | 앞의 실행이 끝나지 않았다. `tcrun status` 로 확인한다 |
| `ssh key login failed ... Permission denied` | ESX 호스트에 키가 없다. 6절 |
| `==== <VM> FAILED (ssh exit 255)` (B, D 블록) | VM 접속이 안 된다. 계정과 비밀번호(`sh ~/.tcgen/setpw`)를 확인한다 |

### 실제 장비에서 확인할 것

자동 시험은 가짜 명령으로 실행한다. 아래 항목은 실제 장비에서만 확인된다. 처음 쓸 때 P 블록의 출력과 진행 로그로 하나씩 확인한다.

| 항목 | 가짜 환경에서 가정한 것 | 확인 방법 |
| :-- | :-- | :-- |
| `vim-cmd vmsvc/getallvms` 의 출력 | 줄이 `vmid 이름 [데이터스토어] 경로.vmx ...` 형태 | P 블록의 `TCGEN-VM` 줄에 vmid 와 vmx 경로가 맞게 나오는지 |
| `vim-cmd vmsvc/get.summary` 의 `vmPathName` | `vmPathName = "[데이터스토어] 경로.vmx"` 형태. 없으면 getallvms 의 값을 쓴다 | 위와 같음 |
| `vim-cmd vmsvc/power.getstate` 의 출력 | `Powered on`, `Powered off`, `Suspended` 가운데 하나가 들어 있다 | P 블록의 `power=on` |
| `power.shutdown` 이 안 될 때(VMware Tools 없음) | 종료 코드가 0 이 아니거나 출력에 `fault` 가 들어 있다 | 진행 로그의 `guest shutdown is not possible` |
| `esxcli system settings advanced list -o` 의 출력 | `Type: integer` 또는 `string`, `Int Value:`, `String Value:` 줄 | P 블록의 `TCGEN-HOST` 줄의 현재 값 |
| ESX 의 `python3` | 3.5 이상. `/tmp/tcgen/` 의 스크립트를 `python3 <파일>` 로 실행할 수 있다 | P 블록의 `python3 found` 와 설정 비교 줄 |
| ESX 의 `/etc/ssh/keys-root/authorized_keys` | 줄을 추가하면 root 키 접속이 된다. 재부팅 뒤에도 남는지는 확인하지 않았다 | `sh ~/.tcgen/esxssh <ESX> hostname` |
| ESX 의 `sh`(busybox), `sha256sum`, `/bin/echo` | here-document, `read -r`, `printf` 가 dash 와 같게 동작 | 진행 로그의 `registered on esx` |
| ESX crond | `cron.update` 에 root 를 쓰면 1분 안에 crontab 을 다시 읽는다 | ESX 모니터링이 등록한 분에 시작하는지 |
| VM 의 cron | 등록 75초 뒤의 분에 새 줄을 실행한다 | 모니터링과 잡이 등록한 분에 시작하는지 |
| VM 의 `pgrep -f`, `date -d @<초>` | procps 의 pgrep, GNU date | P 블록의 VM 줄, 진행 로그의 `poll:` 줄 |
| 점프 VM 의 `setsid`, `base64 --decode`, `gzip`, `sha256sum` | util-linux, coreutils | A 블록의 `OK` 두 줄, S 블록의 `started:` |
| 터미널을 닫은 뒤의 진행 | `setsid` 로 시작한 진행은 터미널을 닫아도 계속된다. 점프 VM 이 로그아웃할 때 사용자 프로세스를 모두 끝내게 설정돼 있으면(systemd-logind 의 `KillUserProcesses=yes`) 끝난다 | S 블록을 붙여넣고 터미널을 닫은 뒤 다시 접속해 `sh ~/.tcgen/tcrun status` |
| 300줄쯤 되는 A 블록 붙여넣기 | 터미널이 글자를 빠뜨리지 않는다. 빠뜨리면 `FAILED` 가 나온다 | A 블록의 `OK` 두 줄 |

## 13. v1.4 로 돌아가는 방법

v2 는 v1.4 의 프로그램, 데이터 폴더(`tcgen_data`), 설정 폴더(`%APPDATA%\tcgen`)를 고치지 않는다. v1.4 를 그대로 다시 실행하면 된다.

1. 점프 VM 에서 순서 실행이 진행 중이면 `sh ~/.tcgen/tcrun stop` 으로 멈춘다. `sh ~/.tcgen/tcrun status` 로 `running` 이 없는지 확인한다.
2. PC 에서 v1.4 를 실행한다(`dist\tcgen\tcgen.exe` 또는 v1.4 소스 폴더의 `run_gui.bat`). v1.4 의 데이터가 v2 를 쓰기 전 상태 그대로 보인다. v2 에서 입력한 내용은 `tcgen2_data` 에만 있다.
3. 점프 VM 의 `~/.tcgen/vmssh`, `askpass`, `setpw`, `vmpw` 는 v1.4 와 같은 파일이다. v1.4 의 B 블록과 D 블록을 그대로 붙여넣을 수 있다. A 블록을 다시 붙여넣을 필요가 없다.
4. v2 가 VM crontab 에 남긴 줄이 있으면 지운다. 표식이 v1.4 와 같은 `# tcgen 케이스이름 호스트` 이므로 8.5절의 명령이나 v1.4 의 D 블록으로 지운다.

v2 가 추가한 것을 지우려면 다음과 같이 한다. 지우지 않아도 v1.4 의 동작에는 영향이 없다.

| 위치 | 지울 것 |
| :-- | :-- |
| 점프 VM | `~/.tcgen/tcrun`, `tcgen_apply.py`, `esxssh`, `postsetup`, `id_esx`, `id_esx.pub`, `runs/` 와 점프 VM 로그 폴더 |
| ESX 호스트 | `/etc/ssh/keys-root/authorized_keys` 에서 점프 VM 의 키 줄, `/tmp/tcgen/` |
| 데이터스토어 | VM 폴더의 `<이름>.vmx.tcgen-<시각>` (설정을 적용하기 전의 vmx 복사본) |
| PC | `tcgen2_data`, `%APPDATA%\tcgen2`, `dist\tcgen2` |

v2 가 적용한 ESX 호스트 옵션과 vmx 의 키는 v1.4 로 돌아가도 그대로 남는다. 이전 값은 진행 로그의 `TCGEN-SET`, `TCGEN-HOST` 줄과 vmx 복사본에서 확인한다.

테스트 기록 CSV 를 v1.4 와 v2 가 같은 파일로 쓰는 경우(3.2절), v2 가 머리글 끝에 추가한 열(진행 방식, 설정, 실행 ID)은 v1.4 가 이어 쓸 때 빈칸으로 남는다.

## 14. 개발 자료

구조, 설계 규칙, 고치는 절차는 `DEVELOPER.md` 에 있다. 순서 실행에서 PC 가 점프 VM 에 넘기는 plan 의 형식은 `DEVELOPER.md` 5절에 있다.

- plan 은 줄 단위 글 파일이다. 첫 낱말이 종류(`CASE`, `VM`, `AH`, `AV`, `MS`, `JOB`, `PROC`, `MX`, `EMS`, `EMX`, `END` 등), 둘째 낱말이 케이스 번호다.
- 점프 VM 의 진행 스크립트는 plan 을 `grep`, `sed`, `cut` 으로만 읽는다. plan 의 글을 셸 명령으로 실행하지 않는다.
- `jump\tcrun.sh` 나 `jump\tcgen_apply.py` 를 고친 뒤에는 `python tools\make_payload.py` 를 실행하고, 점프 VM 에 A 블록을 다시 붙여넣는다.
