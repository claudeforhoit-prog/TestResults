# 테스트 실행 명령 생성기 (tcgen) v2.7

> 이 생성기를 고치거나 AI 로 다시 만들 때는 `DEVELOPER.md`(구조, 설계 규칙, plan 형식, 시험)를 먼저 읽는다.

테스트 케이스 표를 입력하면 점프 VM 터미널에 붙여넣을 블록을 만든다.
사용자는 명령과 케이스를 화면에 입력하고 [명령어 생성] 을 누른 뒤, 만들어진 블록을 복사해 붙여넣는다.

v2 는 v1.4 와 따로 설치하고 따로 실행한다. 프로그램 이름, 데이터 폴더, 설정 폴더가 모두 다르다. v1.4 는 지우지 않고 그대로 둔다(13절).

VM 을 켠 뒤 ssh 로그인이 거부되면 다시 시도하지 않는다(계정 잠금 방지). 실행 계획을 공통 규칙과 케이스별 항목으로 다시 썼다(탭 5 의 [크게 보기]). 점프 VM 의 진행 스크립트가 바뀌었으므로 A 블록을 한 번 다시 붙여넣는다 |
| v2.7 | 잡 확인: 시작 시각을 적은 케이스는 잡 프로세스를 확인하지 않는다(5.6절). 잡이 실행되는 동안 VM 에 접속하지 않고, 다음 케이스 준비 2분 전에 모니터링을 중지하고 넘어간다. 시작 시각 칸에 `+8:00` 처럼 앞 케이스 시작 시각 기준의 간격을 적을 수 있다. 실행 대기: 앞 실행이 진행 중인 ESX 호스트에 새 S 블록을 붙여넣으면 대기했다가 앞 실행이 끝나면 스스로 시작한다(5.4절). `tcrun cancel` 은 진행 중이거나 대기 중인 실행을 모두 끝내고, 끝난 실행이 남긴 줄과 모니터링도 정리한다. 줄을 남긴 채 멈춘 실행이 있으면 그 ESX 호스트의 새 실행은 `cancel` 뒤에 시작한다. `tcrun stop` 은 VM 을 켜고 기다리는 동안에도 바로 적용된다. [설정 백업] 이 따로 지정한 테스트 케이스 파일도 복사하고 [백업 불러오기] 가 그 파일을 되돌린다(7.1절). 점프 VM 의 진행 스크립트가 바뀌었으므로 A 블록을 한 번 다시 붙여넣는다 |

## 1. v1.4 와 달라진 것

| 항목 | v1.4 | v2 |
| :-- | :-- | :-- |
| 진행 방식 | 시각 지정 한 가지 | 순서 실행(기본값)과 시각 지정 중에서 고른다 |
| 다음 케이스로 넘어가는 시점 | 사용자가 케이스마다 잡 시작 시각과 간격을 입력한다 | 순서 실행: 점프 VM 이 잡의 프로세스가 끝난 것을 확인한 뒤 다음 케이스를 시작한다. 시각은 적지 않아도 되고, 필요한 케이스에만 시작 시각을 적는다. 케이스 사이 간격을 둘 수 있다 |
| ESX 호스트와 VM 의 설정 | 다루지 않는다 | 순서 실행: 탭 3 의 설정 프로파일을 케이스 시작 전에 적용한다. 값이 다를 때만 VM 을 종료하고 다시 켠다 |
| VM 전원 | 다루지 않는다 | 순서 실행: VM 행의 `전원` 칸대로 맞춘다. 끔인 VM 은 끄고, 켬인 VM 은 꺼져 있으면 하나씩 켠다(1GB page backing 과 ssh 로그인 확인) |
| ESX 호스트 작업 | 사용자가 ESX root SSH 창에 C 블록을 붙여넣는다 | 순서 실행: 점프 VM 이 ssh 키로 ESX 호스트에 접속한다. 키는 처음 한 번 등록한다 |
| 블록 | A, B, C, D | 순서 실행: A, P(점검), S(실행), D. 시각 지정: A, B, C, D |
| 실행 기록 | PC 의 테스트 기록 CSV 와 로그 CSV | 순서 실행: PC 의 기록에 더해 점프 VM 로그 폴더에 진행 로그, 결과 CSV, 리포트용 CSV 가 남는다 |
| 탭 | 4개 | 5개 (탭 3 설정 프로파일 추가) |
| 프로그램과 폴더 | `tcgen.exe`, `tcgen_data`, `%APPDATA%\tcgen` | `tcgen2.exe`, `tcgen2_data`, `%APPDATA%\tcgen2` |

시각 지정 방식은 v1.4 와 같은 동작이다. 같은 입력이면 B, C, D 블록이 v1.4 와 글자 하나까지 같다(시험 `test_v14_compat.py` 로 확인). 다른 점은 하나다. [리포트용 CSV 저장] 창에 `비교 기준 (첫 줄)` 칸이 없고 고른 케이스를 표 순서대로 저장한다(9.2절).

## 2. 구성

| 파일 | 내용 |
| :-- | :-- |
| `tcgen_app.py` | 화면 |
| `tcgen_core.py` | 시각 계산, crontab 줄, 붙여넣기 블록, 순서 실행의 검증과 plan, 기록 파일 저장 |
| `tcgen_payload.py` | 점프 VM 에 설치할 두 파일의 내용(자동 생성. 직접 고치지 않는다) |
| `jump\tcrun.sh` | 점프 VM 의 진행 스크립트 원본. 설치되면 `~/.tcgen/tcrun` 이 된다 |
| `jump\tcgen_apply.py` | ESX 호스트에서 실행하는 설정 적용 스크립트 원본 |
| `tools\make_payload.py` | `jump\` 의 두 파일을 `tcgen_payload.py` 로 옮긴다 |
| `run_gui.bat` | 실행. `tcgen2.exe` 가 있으면 그것을, 없으면 설치된 Python 으로 실행한다 |
| `build_windows.bat` | Windows 실행 파일(`dist\tcgen2\tcgen2.exe`) 빌드 |
| `tests\` | 자동 시험과 화면 점검(`gui_smoke.py`) |

Python 표준 라이브러리만 쓴다. 추가 패키지는 필요 없다.

## 3. 설치와 실행

- Python 3.8 이상이 있는 PC: `run_gui.bat` 을 실행한다. `python tcgen_app.py` 와 같다.
- Python 이 없는 PC: Python 과 인터넷이 있는 PC 에서 `build_windows.bat` 을 실행한다. 만들어진 `dist\tcgen2` 폴더를 통째로 복사해 `tcgen2.exe` 를 실행한다.

PyInstaller 설치 단계에서 내려받기가 실패하면, 빌드 스크립트가 pypi.org 와 files.pythonhosted.org 의 인증서 확인을 생략하는 옵션(`--trusted-host`)으로 한 번 더 시도한다.
회사망 보안 장비가 HTTPS 를 검사하면 pip 가 인증서를 확인하지 못해 이렇게 실패한다. 이 옵션은 그 실행에만 적용되고 PC 설정에 남지 않는다.
그래도 `FAILED while installing PyInstaller` 가 나오면 인터넷 연결이나 회사망 프록시를 확인한다.
회사에 Python 패키지 저장소가 있으면 `py -3 -m pip config --user set global.index-url https://<저장소 주소>/simple` 로 한 번 지정한 뒤 빌드한다.

### 3.1 데이터 폴더

설정, 명령 목록, 설정 프로파일, 테스트 케이스 표는 생성기 폴더가 아니라 데이터 폴더에 저장한다. 데이터 폴더 기본 위치는 `C:\Users\<계정>\tcgen2_data` 이다. 생성기를 다시 빌드하거나 다른 폴더로 옮겨도 데이터 폴더는 그대로 남는다. 다섯 파일 모두 값이 달라질 때마다 자동 저장되고, 생성기를 다시 열면 불러온다. 저장 버튼은 없다.

| 파일 (데이터 폴더 기준) | 내용 |
| :-- | :-- |
| `settings.json` | 설정 영역의 값(5.1절, 7.1절)과 화면에 없는 값(7.1절의 두 번째 표) |
| `run_commands.csv` | 탭 1 실행 명령 목록 |
| `monitor_commands.csv` | 탭 2 모니터링 명령 목록 |
| `profiles.json` | 탭 3 설정 프로파일. 파일이 없으면 처음 실행 때 기본 프로파일 12개로 만든다(7.4절) |
| `test_cases.json` | 탭 4 테스트 케이스 표와 적용 체크 상태. 테스트 케이스 파일을 따로 지정하지 않았을 때 쓴다(4.1절) |
| `testcases\test_record.csv` | 테스트 기록 CSV 기본 위치 |
| `testcases\testcaselogging-년월일시분초.csv` | 생성할 때마다 만드는 로그 (기본 위치) |
| `backup\년월일시분초_before_restore\` | [백업 불러오기] 직전의 데이터 파일 |
| `backup\auto\년월일_AM\`, `backup\auto\년월일_PM\` | 하루 두 번 자동 백업(4.2절) |

| 설정 파일 | 내용 |
| :-- | :-- |
| `C:\Users\<계정>\AppData\Roaming\tcgen2\config.json` | [데이터 폴더 변경] 으로 정한 데이터 폴더 위치, 마지막으로 고른 백업 위치. 이 파일이 없으면 기본 위치를 쓴다 |

- 명령 목록은 화면에서만 고친다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다.
- 테스트 기록 CSV 나 로그 폴더를 데이터 폴더 밖으로 지정했다면 그 파일은 [설정 백업] 에 들어가지 않는다.
- `build_windows.bat` 을 다시 실행하면 PyInstaller 가 `dist\tcgen2` 폴더를 통째로 지우고 새로 만든다. 데이터는 데이터 폴더에 있어 지워지지 않는다.

### 3.2 v1 의 데이터 가져오기

v2 를 처음 실행할 때 `tcgen2_data` 에 데이터가 없고 v1 의 데이터 폴더에 데이터가 있으면, 아래 네 파일을 `tcgen2_data` 로 복사하고 안내 창을 한 번 보인다.

- 복사하는 파일: `settings.json`, `run_commands.csv`, `monitor_commands.csv`, `test_cases.json`
- v1 의 데이터 폴더: `%APPDATA%\tcgen\config.json` 에 적힌 폴더. 그 파일이 없으면 `C:\Users\<계정>\tcgen_data`
- v1 의 폴더와 파일은 읽기만 한다. 내용도 수정 시각도 그대로 둔다.
- 테스트 기록과 로그(`testcases\`), 백업(`backup\`)은 복사하지 않는다.
- v1 설정의 테스트 기록 CSV 나 로그 폴더가 v1 데이터 폴더 안을 가리키면 `tcgen2_data` 의 같은 위치로 고쳐 저장한다. v2 가 v1 폴더에 기록하지 않게 하기 위해서다. v1 데이터 폴더 밖의 경로는 그대로 두므로, 그 경우 v1.4 와 v2 가 같은 기록 파일에 이어 쓴다.
- v1 데이터에는 진행 방식과 프로세스 이름이 없다. 진행 방식은 순서 실행이 되고, 프로세스 이름은 탭 1 에서 입력한다.

## 4. 진행 방식

설정 영역의 `진행 방식` 에서 고른다. 고르면 바로 저장되고 화면이 그 방식에 맞게 달라진다.

| 진행 방식 | 동작 | 화면 |
| :-- | :-- | :-- |
| 순서 실행 (기본값) | 점프 VM 의 진행 스크립트(`tcrun`)가 케이스를 표의 순서대로 진행한다. 설정 적용, 모니터링 시작, 잡 시작, 잡 종료 확인, 모니터링 중지를 차례로 한다. 케이스의 시작 시각을 비우면 앞 케이스가 끝난 뒤 자동으로 시작하고, 적으면 그 시각에 시작한다(5.6절) | 탭 4 에 설정, 최대 대기, 시작 시각 열이 보이고 시각 지정의 시각 열은 숨긴다. 탭 5 에 블록 A, P, S, D 와 실행 계획이 나온다 |
| 시각 지정 | v1.4 와 같다. 케이스마다 잡 시작 시각을 정해 crontab 에 등록한다. 설정 프로파일은 쓰지 않는다. 케이스에 프로파일이 선택돼 있으면 경고만 한다 | 탭 4 에 간격, 잡 시작, 모니터링 시작, 모니터링 중지, 잡 종료 (리포트) 열이 보인다. 탭 5 에 블록 A, B, C, D 가 나온다 |

순서 실행의 사용 순서는 5절, 시각 지정의 사용 순서는 8절에 있다.

### 4.1 테스트 케이스 파일 (불러오기, 다른 이름으로 저장)

탭 4 의 테스트 케이스 표를 파일로 저장해 두고 필요할 때 불러온다. 시험하는 서버나 시험 종류마다 파일을 따로 두는 데 쓴다.
설정 영역 맨 위의 `테스트 케이스 파일` 칸에 지금 쓰는 파일이 보인다.

| 상태 | 동작 |
| :-- | :-- |
| 파일을 지정하지 않음 (처음 상태) | 데이터 폴더의 `test_cases.json` 을 자동으로 만들고, 표를 고칠 때마다 거기에 자동 저장한다 |
| [다른 이름으로 저장] 으로 파일을 지정 | 지금 표를 그 파일에 저장한다. 그 뒤로는 표를 고칠 때마다 그 파일에 자동 저장한다. 이전 파일은 마지막 상태로 남는다 |
| [불러오기] 로 파일을 지정 | 그 파일의 표를 탭 4 에 불러온다. 그 뒤로는 표를 고칠 때마다 그 파일에 자동 저장한다 |

- 파일에는 케이스 행과 VM 행의 모든 칸이 들어간다: 적용 체크, 케이스 이름, 설명, ESX 호스트, VM 이름, VM 전원, 잡, 모니터링, 설정 프로파일 선택, 최대 대기, 테스트 그룹, 종료 기준 VM, 시각 지정의 간격과 시각 값. 불러오면 저장한 상태 그대로 보인다.
- 실행 명령(탭 1), 모니터링 명령(탭 2), 설정 프로파일(탭 3), 설정 영역의 나머지 값은 어느 파일을 쓰든 같이 쓴다. 고치면 모든 파일에 적용된다.
- `테스트 기록 CSV` 와 `로그 폴더` 는 테스트 케이스 파일마다 마지막에 쓰던 값을 기억한다. 파일을 불러오면 그 값으로 함께 바뀐다. 처음 쓰는 파일은 지금 값을 그대로 쓴다.
- 파일 형식은 CSV(UTF-8, BOM)다. 파일 이름을 `.json` 으로 끝내면 `test_cases.json` 과 같은 JSON 으로 저장한다. [불러오기] 는 두 형식을 모두 읽는다.
- 파일을 바꾸면 탭 5 의 이전 생성 결과를 지운다. 다른 케이스의 블록을 붙여넣는 실수를 막기 위해서다. 점프 VM 에서 진행 중인 실행에는 영향이 없다.
- 생성기를 다시 열면 마지막에 쓰던 파일을 불러온다. 그 파일을 찾지 못하거나 읽지 못하면 그 파일은 그대로 두고 데이터 폴더의 `test_cases.json` 으로 바꾼 뒤 알린다.
- 지정하지 않은 상태로 돌아가려면 [불러오기] 에서 데이터 폴더의 `test_cases.json` 을 고른다.
- `테스트 기록 CSV`(생성 내용을 적어 두는 파일)는 테스트 케이스 파일이 아니다. [불러오기] 에서 고르면 불러오지 않고 알린다.
- 순서 실행의 `시작 시각` 칸은 적은 그대로 저장된다(`10:00`, `+8:00`, 날짜가 있는 시각). 비워 둔(`자동`) 케이스는 파일에도 비어 있다. 자동으로 실행한 케이스의 실제 시작 시각은 점프 VM 이 실행할 때 정하므로 이 파일에는 들어가지 않고, 점프 VM 로그 폴더의 결과 CSV 와 리포트용 CSV 에 남는다(5.7절). v2.4 전에 저장한 파일과 시각 지정으로 쓰던 파일에는 이 칸이 없어 불러오면 `자동` 으로 보인다. 그 파일의 `잡 시작` 값(시각 지정용)은 그대로 남아 있다.

테스트 케이스 CSV 의 열은 다음과 같다. 케이스마다 `케이스` 행 하나가 있고 그 아래에 그 케이스의 `VM` 행이 온다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 구분 | `케이스` | `VM` |
| 적용 | 적용 체크했으면 `예` | 빈칸 |
| 케이스 이름, 설명, ESX 호스트 | 값 | 빈칸 |
| VM 이름, 잡 | 빈칸 | 값. 잡이 없으면 `(없음)` |
| 모니터링 | ESX 모니터링 명령어 명 | 그 VM 의 모니터링 명령어 명 |
| 설정 | ESX 호스트 설정 프로파일 이름 | 그 VM 의 설정 프로파일 이름 |
| 최대 대기, 테스트 그룹 | 값 | 빈칸 |
| 종료 기준 VM | 빈칸 | 기준이면 `기준` |
| 간격, 잡 시작, 모니터링 중지, 모니터링 중지 시각, 잡 종료 (리포트) | 시각 지정에서 쓰는 값. 모니터링 중지는 `자동`, `직접 입력`, `중지 없음` | 빈칸 |
| 시작 시각 (순서 실행) | 순서 실행에서 잡을 시작할 시각. 비어 있으면 자동 | 빈칸 |
| 전원 | 빈칸 | 순서 실행에서 그 VM 의 전원. `켬` 또는 `끔`. 이 열이 없는 예전 파일은 모두 켬으로 읽는다 |

- 한 칸에 이름이 여러 개면 `; ` 로 구분한다.
- 이 파일은 화면에서 고치는 것을 권한다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다. 읽지 못하게 된 경우에는 자동 백업(4.2절)의 `case_file_<파일 이름>` 을 다른 폴더에 복사한 뒤 [불러오기] 로 고른다(백업 폴더 안의 파일을 바로 고르면 그 뒤로 고친 내용이 그 백업 폴더 안에 저장되고, 그 폴더는 보관 수인 최근 60개를 넘으면 지워진다).

### 4.2 자동 백업 (하루 두 번)

생성기가 켜져 있는 동안 오전에 한 번, 오후에 한 번 데이터 파일을 데이터 폴더의 `backup\auto\` 에 복사한다. 따로 할 일은 없다.

| 항목 | 내용 |
| :-- | :-- |
| 시점 | 생성기를 켤 때와 그 뒤 30분마다 확인한다. 그 시간대(0시~12시 전은 `AM`, 12시부터는 `PM`)의 백업이 아직 없으면 만든다 |
| 위치 | `<데이터 폴더>\backup\auto\<년월일>_AM\`, `<년월일>_PM\` |
| 들어가는 파일 | `settings.json`, `run_commands.csv`, `monitor_commands.csv`, `profiles.json`, `test_cases.json`, 그리고 지정한 테스트 케이스 파일의 사본 `case_file_<파일 이름>` |
| 보관 | 최근 60개(30일치). 그보다 오래된 것은 지운다 |
| 되돌리기 | [백업 불러오기] 에서 그 폴더를 고른다. 지정한 테스트 케이스 파일도 그 폴더의 사본 `case_file_<파일 이름>` 의 내용으로 바뀐다(바꾸기 전 내용은 데이터 폴더의 `backup` 아래에 복사해 둔다). 테스트 케이스 파일만 되돌리려면 그 사본을 다른 폴더에 복사한 뒤 [불러오기] 로 고른다 |

- 생성기를 켜지 않은 날에는 백업을 만들지 않는다. 그날은 데이터가 바뀌지 않기 때문이다.
- 테스트 기록 CSV 와 로그 파일은 자동 백업에 넣지 않는다. 이 파일까지 복사하려면 [설정 백업] 을 쓴다.

## 5. 순서 실행: 사용 순서

### 5.1 처음 한 번: A 블록과 ESX 키 등록

1. 설정 영역에서 진행 방식을 `순서 실행` 으로 둔다. `점프 VM 로그 폴더` 에 점프 VM 의 폴더를 적는다. 비우면 `~/tcgen_log` 를 쓴다. `점프 VM 작업 폴더` 는 비우면 `~/.tcgen` 이다. 점프 VM 계정의 홈 폴더 용량이 작으면 작업 폴더에 큰 디스크의 폴더(예: `/data/<계정>/tcgen`)를 적는다. 로그 폴더를 비워 두면 `<작업 폴더>/log` 에 로그가 남는다.
2. 탭 4 에 케이스를 하나 이상 입력하고 [명령어 생성] 을 누른 뒤, 열리는 선택 창에서 [생성] 을 누른다(5.2절). A 블록은 생성 결과에 함께 나온다.
3. 탭 5 의 A 블록 [복사] 를 누르고 점프 VM 터미널에 붙여넣는다. A 블록은 다른 블록과 함께 붙여넣지 않는다. 붙여넣은 뒤 아무 출력이 없으면 Enter 를 한 번 누른다(bash 5.1 이상은 붙여넣은 글을 Enter 를 누를 때 실행한다).
4. 출력에서 아래 두 줄이 `OK` 인지 확인한다. `FAILED` 가 나오면 A 블록을 다시 붙여넣는다(붙여넣는 중에 글자가 빠진 경우다).

```
OK      /home/<계정>/.tcgen/tcrun
OK      /home/<계정>/.tcgen/tcgen_apply.py
```

작업 폴더를 `~/.tcgen` 이 아닌 폴더로 정했으면 경로가 그 폴더로 나온다. 이때 `~/.tcgen` 에 ESX 키(`id_esx`, `id_esx.pub`)와 VM 비밀번호(`vmpw`)가 있으면 새 폴더로 복사하고 `copied:` 줄을 출력한다. 그래서 ESX 호스트에 키를 다시 등록하지 않아도 되고 비밀번호도 다시 묻지 않는다.

5. 이어서 나오는 아래 형태의 한 줄을 복사해, 설정을 적용하거나 ESX 모니터링을 실행할 각 ESX 호스트의 root SSH 창에 한 번 붙여넣는다(6절).

```
echo 'ssh-rsa AAAA... <계정>@<점프 VM>' >> /etc/ssh/keys-root/authorized_keys
```

6. `VM password:` 가 나오면 VM 비밀번호를 입력한다(화면에 보이지 않는다). 비밀번호가 이미 저장돼 있으면 묻지 않고 `already saved` 를 출력한다.
7. 점프 VM 에서 `sh ~/.tcgen/esxssh <ESX 호스트> hostname` 을 실행한다(작업 폴더를 바꿨으면 `~/.tcgen` 대신 그 폴더). 비밀번호를 묻지 않고 ESX 호스트 이름이 나오면 키 등록이 끝난 것이다.

A 블록이 점프 VM 작업 폴더(기본 `~/.tcgen/`)에 설치하는 파일은 다음과 같다. 이 절과 아래 절의 `~/.tcgen` 은 작업 폴더를 바꿨으면 그 폴더로 읽는다.

| 파일 | 내용 |
| :-- | :-- |
| `askpass`, `vmssh`, `setpw` | VM 자동 로그인과 비밀번호 입력. v1.4 와 내용이 같다 |
| `vmpw` | VM 비밀번호(권한 600). `setpw` 가 만든다 |
| `esxssh` | ESX 호스트에 키로 접속한다. `sh ~/.tcgen/esxssh <ESX 호스트> [명령]` |
| `postsetup` | A 블록의 마지막 단계. ESX 에 넣을 한 줄을 출력하고, 비밀번호가 없을 때만 `setpw` 를 실행한다 |
| `tcrun` | 진행 스크립트. 하위 명령은 5.5절 |
| `tcgen_apply.py` | 설정 적용 스크립트. `tcrun` 이 ESX 호스트의 `/tmp/tcgen/` 에 전송해 실행한다 |
| `id_esx`, `id_esx.pub` | ESX 접속용 ssh 키. 없을 때만 만든다 |
| `runs/<실행 ID>/` | 실행마다 plan, 상태, 임시 파일을 둔다 |
| `minutes/<초>/` | 잡 시작 시각의 기록. 진행 스크립트가 잡 시작 시각을 정할 때 만들고, 하루가 지나면 지운다(5.6절) |
| `known_hosts` | 진행 스크립트와 `esxssh` 가 접속한 VM, ESX 호스트의 ssh 호스트 키. 홈 폴더의 `~/.ssh/known_hosts` 에는 쓰지 않는다 |

생성기를 새 판으로 바꾼 뒤에는 A 블록을 한 번 다시 붙여넣는다. 점프 VM 의 `tcrun` 판이 생성기의 판과 다르면 P 블록과 S 블록은 아무것도 시작하지 않고 `Paste block A again` 을 출력한다.

### 5.2 명령, 설정 프로파일, 케이스 입력

1. 탭 1 에 실행 명령을 등록하고 `프로세스 이름` 을 적는다. 프로세스 이름은 잡이 실행되는 동안 VM 에 떠 있는 프로세스의 명령줄에 들어 있는 글자다(7.2절).
2. 탭 2 에 모니터링 명령을 등록한다.
3. 설정을 적용하려면 탭 3 의 설정 프로파일을 쓴다. 기본 프로파일 12개가 들어 있고, 직접 추가할 수도 있다(7.4절).
4. 탭 4 에 케이스를 실행할 순서대로 입력한다. VM 행마다 전원(켬, 끔), 잡, 모니터링을 고른다. 설정을 적용할 케이스는 케이스 행의 설정 칸에서 ESX 호스트 프로파일을, VM 행의 설정 칸에서 VM 프로파일을 고른다.
5. [명령어 생성] 을 누른다. 넣을 케이스를 고르는 창이 열린다. 처음에는 적용 체크하지 않은 케이스가 골라져 있다. 고른 뒤 [생성] 을 누른다(7.5절). 오류가 있으면 블록을 만들지 않고 오류 목록을 보인다.

케이스의 순서가 실행 순서다. 한 케이스 안에서 VM 행의 순서가 VM 을 켜는 순서다. ESX 호스트가 다른 케이스는 호스트별로 따로 진행하고 서로 기다리지 않는다.

### 5.3 점검 블록 (P)

실행 전에 탭 5 의 P 블록을 점프 VM 터미널에 붙여넣는다. 아무것도 바꾸지 않고 아래 항목을 확인해 출력한다. 같은 내용이 로그 폴더의 `tcrun-<실행 ID>-check.log` 에 저장된다.

| 확인 항목 | 문제일 때 출력 |
| :-- | :-- |
| 점프 VM 의 파일, VM 비밀번호, `ssh` 와 `setsid` 명령, 로그 폴더에 쓸 수 있는지 | `missing ...: paste block A again` 등 |
| ESX 호스트 키 접속, `python3` 와 `vim-cmd` 와 `esxcli`, root crontab 파일. ESX 호스트가 있고 VM 이 있는 케이스는 모두 확인한다(VM 전원을 맞추기 때문) | `ssh key login failed ... Register the key: sh ~/.tcgen/tcrun key` |
| 시작 시각을 적은 케이스: 이미 지난 시각인지, 이 점프 VM 의 다른 실행의 잡 시작과 `잡 시작 최소 간격` 보다 가까운지 | `the start time ... has already passed`, `is less than 5 min from the job start ...` |
| ESX 호스트가 있는 케이스: VM 을 찾았는지(vmid, vmx 경로, 전원 상태), 설정마다 현재 값과 목표 값, VM 마다 지금 전원과 케이스가 원하는 전원 | `settings and VM power: VM '...' is not registered on this host` 등 |
| 같은 ESX 호스트의 다른 실행: 진행 중인 실행이 있으면 이 실행이 대기하게 된다고 알리고, 그 실행의 지금 케이스와 단계를 보인다. 줄을 남긴 채 멈춘 실행이 있으면 문제로 알린다 | `block S would not start this run. run ... ended as paused and left case ... open ... Close it first: sh ~/.tcgen/tcrun cancel esx01` |
| 시작 시각을 적은 케이스: 잡을 확인하지 않는다는 것과 케이스가 끝나는 때 | (문제 아님) `not checked: ... End of the case: ...` |
| VM 접속, `crontab` 명령, 시계가 점프 VM 과 몇 초 다른지, 잡을 확인하는 케이스의 `pgrep`. 지금 꺼져 있어 실행이 켤 VM 과 전원 끔인 VM 은 접속하지 않는다. 같은 ESX 호스트에 진행 중인 실행이나 crontab 줄이 남은 케이스가 있으면 그 호스트의 VM 에는 접속하지 않는다(실행 중인 잡에 부하를 주지 않음) | `ssh login failed`, `pgrep not found` |
| VM 시계끼리의 차이 | 30초를 넘으면 `the clocks of the VMs differ by N s` |

설정과 전원 비교 줄은 아래처럼 나온다. `[change]` 는 실행이 바꿀 항목, `[same]` 은 이미 같은 항목이다.

```
TCGEN-VM esx01ev01 vmid=10 power=on vmx=/vmfs/volumes/datastore1/esx01ev01/esx01ev01.vmx
TCGEN-SET esx01ev01 sched.mem.pin: (none) -> "TRUE"  [change]
TCGEN-HOST /Numa/LocalityWeightActionAffinity (integer): 130 -> 0  [change]
TCGEN-POWER esx01ev01 now=on want=on  [same]
TCGEN-POWER esx01ev02 now=off want=on  [change]
  [ok] settings and VM power: 2 value(s) differ, 1 VM(s) to power on. The run changes them before the job (when a value differs, the VMs of the case are shut down first).
  [ok] vm esx01ev02: powered off now. The run powers it on and then waits for its ssh login.
```

마지막 줄이 `CHECK RESULT: OK` 이면 실행 블록을 붙여넣는다. `CHECK RESULT: N problem(s)` 이면 `[PROBLEM]` 줄을 고친 뒤 P 블록을 다시 붙여넣는다.

### 5.4 실행 블록 (S)

탭 5 의 S 블록 [복사] 를 누르면 확인 창이 나온다. 점프 VM 터미널에 붙여넣으면 ESX 호스트별 진행이 백그라운드로 시작되고 아래처럼 출력된다. 터미널을 닫아도 진행은 계속된다.

```
started: run 20261116-143000 esx esx01   log: /home/<계정>/tcgen_log/tcrun-20261116-143000-esx01.log
status: sh ~/.tcgen/tcrun status       stop: sh ~/.tcgen/tcrun stop
```

- 같은 S 블록을 다시 붙여넣어도 다시 시작하지 않는다. 다시 실행하려면 생성기에서 다시 생성한다(실행 ID 가 새로 정해진다).
- 실행을 더할 때: 앞 실행이 진행 중인 ESX 호스트에 새 실행의 S 블록을 붙여넣으면 그 호스트의 진행은 대기한다. 출력은 `queued:` 로 시작한다. 앞 실행이 `done` 으로 끝나면 스스로 시작한다. ESX 호스트 하나에는 한 번에 한 실행만 진행한다.

```
queued:  run 20261117-101500 esx esx01   waiting for run 20261116-143000 of this ESX host to end. It starts when that has ended as done   log: ...
```

- 앞 실행이 `done` 이 아닌 상태(paused, stopped, cancelled, died)로 끝나면 대기하던 실행은 시작하지 않고 `paused` 로 끝난다. 앞 실행을 확인한 뒤 다시 생성한다.
- 앞 실행이 crontab 줄을 남긴 채 끝났으면(멈춘 케이스의 줄, 모니터링) 새 실행은 시작하지 않고 `==== esx01: not started. ...` 로 이유를 알린다. `sh ~/.tcgen/tcrun cancel esx01` 로 정리한 뒤 같은 S 블록을 다시 붙여넣는다. P 블록도 같은 내용을 `[PROBLEM]` 으로 알린다.
- 앞 실행이 진행 중이거나 앞 케이스의 잡이 끝났는지 알 수 없을 때 P 블록은 그 ESX 호스트의 VM 에 접속하지 않는다. 실행 중인 잡에 부하를 주지 않기 위해서다.
- 설정을 적용하는 케이스에서 값이 현재 값과 다르면 그 케이스의 VM 이 자동으로 종료되고 다시 켜진다.
- 전원 끔인 VM 이 켜져 있으면 자동으로 꺼진다. 켬인 VM 이 꺼져 있으면 자동으로 켜진다(5.6절).

### 5.5 진행 확인과 멈추기

| 명령 (점프 VM) | 하는 일 |
| :-- | :-- |
| `sh ~/.tcgen/tcrun status` | 마지막 실행의 모든 ESX 호스트, 진행 중이거나 대기 중인 실행, 줄을 남긴 실행의 상태를 보인다. 지금 케이스와 단계, 로그의 마지막 세 줄이 함께 나온다. 멈춘 호스트는 이유를, 진행이 시작하지 못한 호스트는 `not started` 와 그 출력을, 줄이 남은 케이스는 `open case:` 줄을 보인다. `-a` 를 주면 모든 실행을 보인다 |
| `sh ~/.tcgen/tcrun stop` | 진행 중이거나 대기 중인 진행에 멈추라고 알린다. `stop <ESX 호스트>` 는 그 호스트의 진행만 멈춘다. 진행만 멈춘다. 시작된 잡, 모니터링, crontab 줄은 그대로 둔다 |
| `sh ~/.tcgen/tcrun cancel` | 진행 중이거나 대기 중인 실행을 모두 바로 끝내고, 줄과 모니터링을 정리한다. `cancel <ESX 호스트>` 는 그 호스트만. 아래 '취소' 참조 |
| `sh ~/.tcgen/tcrun key` | ESX 호스트에 넣을 키 줄을 다시 출력한다 |
| `sh ~/.tcgen/tcrun check <plan>` | 점검. P 블록이 실행한다 |
| `sh ~/.tcgen/tcrun start <plan>` | plan 의 ESX 호스트마다 진행을 백그라운드로 시작한다. S 블록이 실행한다 |
| `sh ~/.tcgen/tcrun run <plan> <ESX 호스트>` | 한 ESX 호스트의 케이스를 차례로 진행한다. `start` 가 호스트마다 실행한다 |
| `sh ~/.tcgen/tcrun version` | 설치된 판 |

상태는 다음과 같다.

| 상태 | 뜻 |
| :-- | :-- |
| `running` | 진행 중. `step` 에 지금 단계가 나온다 |
| `queued` | 같은 ESX 호스트의 앞 실행이 끝나기를 기다리는 중 |
| `done` | 모든 케이스가 끝났다. 끝나는 시각이 없는 마지막 케이스가 있으면 그 케이스는 열린 채로 남는다(`open case:` 줄, 5.6절) |
| `cancelled` | `tcrun cancel` 로 끝냈다 |
| `paused` | 문제가 있어 스스로 멈췄다. `text` 에 이유가 있다(5.8절) |
| `stopped` | `tcrun stop` 으로 멈췄다 |
| `died` | 진행 프로세스가 없다(점프 VM 재부팅 등). `~/.tcgen/runs/<실행 ID>/<ESX 호스트>.out` 을 본다 |

`tcrun stop` 은 진행만 멈춘다. 실행 중인 잡과 모니터링, 등록된 crontab 줄은 그대로 둔다. 줄을 지우고 모니터링을 중지하려면 `tcrun cancel` 을 쓴다. 멈추는 시점에 따라 하는 일이 다르다.

| stop 을 받은 시점 | 진행 스크립트가 하는 일 |
| :-- | :-- |
| 대기(queued) 중, 케이스를 시작하기 전, 시작 시각 준비를 기다리는 동안 | 그대로 끝낸다 |
| 설정 적용 중 | 설정 적용(VM 종료, 값 변경)을 마친 뒤 끝낸다. 값을 바꿨으면 그 케이스의 VM 은 꺼진 채로 남는다 |
| VM 을 켜는 중(켜기 작업, 1GB page backing 확인, ssh 로그인 대기) | 기다리지 않고 바로 끝낸다. ESX 호스트에서 시작된 켜기 작업은 끝까지 진행된다. 설정은 되돌리지 않고, 아직 켜지 않은 VM 은 꺼진 채로 남는다 |
| crontab 줄을 등록한 뒤, 잡 시작 전 | 그 케이스의 등록 줄을 지워 잡이 시작되지 않게 한다. 모니터링이 이미 시작됐으면 중지 명령을 등록해 실행한 뒤 끝낸다 |
| 잡이 실행 중 | 그대로 끝낸다. 잡과 모니터링은 계속 실행된다. 모니터링 중지 명령은 로그에 적어 둔다. 그 케이스의 줄이 남아 있으므로 `status` 에 `open case:` 로 보인다 |
| 모니터링 중지 단계 | 중지와 줄 삭제를 마친 뒤 끝낸다 |

취소(`tcrun cancel`)는 잘못 시작한 실행이나 멈춘(paused, stopped) 실행을 정리할 때 쓴다. `stop` 과 달리 기다리지 않는다. 대상은 진행 중이거나 대기 중인 실행 전부와, 끝난 실행의 케이스 가운데 crontab 줄이 남아 있는 것(`status` 의 `open case`) 전부다. `cancel <ESX 호스트>` 는 그 호스트의 것만 한다. 대기 중인 실행을 먼저 끝낸다.

1. 진행이 실행 중이거나 대기 중이면 바로 끝낸다. ESX 호스트에서 설정 적용이나 VM 켜기를 하던 중이었으면 ESX 의 그 작업은 끝까지 진행된다(출력에 `WARN` 이 나온다).
2. 진행하던 케이스(또는 끝난 실행이 남긴 케이스)의 crontab 줄을 VM 과 ESX 에서 지운다. 아직 시작하지 않은 모니터링과 잡은 시작되지 않는다.
3. 그 케이스의 모니터링이 이미 시작됐으면 모니터링 중지 명령을 바로 한 번 실행한다.
4. 실행 중인 잡은 끝내지 않는다. 잡이 있는 VM 마다 프로세스 이름에 맞는 프로세스 수를 보인다. 끝내야 하면 그 VM 에서 직접 끝낸다.
5. 이 실행이 기록한 앞으로의 잡 시작 시각을 지운다(5.6절의 잡 시작 최소 간격).
6. 상태가 `cancelled` 가 된다. 적용한 설정은 되돌리지 않는다. 결과 CSV 에 `cancelled` 행이 남는다. `done` 으로 끝난 실행이 남긴 케이스의 줄을 지운 경우에는 상태가 `done` 그대로이고 결과 CSV 에 `closed by sh tcrun cancel` 행이 남는다.
7. 끝낼 실행도 남은 줄도 없으면 `nothing to cancel` 을 출력한다.

### 5.6 케이스 한 개의 진행 순서

| 단계 | 하는 일 |
| :-- | :-- |
| 0. 준비 시각 | 시작 시각을 적은 케이스만 한다. 그 시각 60분 전(설정 영역의 `시작 시각 준비`)까지 기다린다. 이미 지났으면 바로 다음 단계로 간다 |
| 1. 설정 적용 | 설정이 있는 케이스만 한다. ESX 호스트에서 현재 값과 목표 값을 비교한다. 모두 같으면 VM 을 끄지 않는다. 하나라도 다르면 그 케이스의 VM 을 모두 종료하고(게스트 종료 요청, 10분 안에 꺼지지 않으면 전원 끄기), 호스트 옵션을 변경하고, vmx 의 키를 교체한다 |
| 2. VM 전원 | ESX 호스트가 있는 케이스만 한다. 전원 칸이 끔인 VM 이 켜져 있으면 끈다. 켬인 VM 은 표의 순서대로 하나씩 확인해 꺼져 있으면 켠다. VM 하나마다 켜기 작업 완료, 1GB page backing 완료(1GB page 를 쓰는 VM 만), 점프 VM 에서 ssh 로그인을 확인한 뒤 다음 VM 으로 넘어간다. 아래 'VM 전원' 참조 |
| 3. 시각 계산 | 그 케이스의 VM 과 점프 VM 의 시계 중 가장 늦은 값에 75초를 더해 분 단위로 올린 시각이 모니터링 시작이다(줄을 등록할 VM 과 ESX 가 합쳐 다섯 대 이상이면 넷을 넘는 한 대마다 4초를 더한다). 잡 시작은 모니터링 시작 5분 뒤다(설정 영역의 `모니터링 시작 N분 뒤 잡 시작`). 모니터링이 없으면 올린 시각이 잡 시작이다. VM 을 켠 뒤의 대기, 케이스 사이 간격, 시작 시각, 잡 시작 최소 간격을 이어서 적용한다(아래) |
| 4. 등록 | 각 VM 의 crontab 에 모니터링 시작 줄과 잡 줄을 넣는다. 한 케이스의 모든 VM 잡은 같은 분에 시작한다. ESX 모니터링은 ESX root crontab 에 넣는다(UTC). 잡을 확인하지 않는 케이스는 모니터링 중지 줄도 이때 함께 넣는다 |
| 5. 잡 종료 확인 | 잡을 확인하는 케이스만 한다(아래 '잡을 확인하는 케이스와 확인하지 않는 케이스'). 각 VM 에 ssh 로 접속해 `pgrep -f` 로 프로세스 이름을 찾는다. 잡 시작 1분 뒤에 한 번 확인하고, 그 뒤로는 `잡 종료 확인 간격`(설정 영역, 기본 30분)마다 확인한다. 잡이 있는 모든 VM 에서 한 번 이상 보인 뒤 3회 연속으로 없으면 종료로 판정한다. 잡을 확인하지 않는 케이스는 이 단계 대신 정해진 시각까지 기다린다 |
| 6. 모니터링 중지 | 잡을 확인하는 케이스: 중지 명령을 1~2분 뒤의 분에 등록하고, 그 시각 20초 뒤에 그 케이스의 줄을 VM 과 ESX 의 crontab 에서 지운다. 잡을 확인하지 않는 케이스: 4단계에서 등록한 중지 줄이 정해진 시각에 실행되고, 그 20초 뒤에 줄을 지운다 |
| 7. 기록 | 로그 폴더의 세 파일에 기록하고 다음 케이스로 넘어간다 |

VM 전원: 2단계에서 VM 전원을 케이스가 원하는 대로 맞춘다.

- ESX 호스트가 있는 케이스는 이름이 있는 VM 행이 모두 그 케이스의 VM 이다. 잡, 모니터링, 설정이 없는 VM 도 전원이 켬이면 켠다. v2.5 까지는 이런 VM 을 쓰지 않았다(끄지도 켜지도 않음).
- ESX 호스트가 없는 케이스는 VM 전원을 다루지 않는다. 잡, 모니터링, 설정이 있는 VM 행만 쓰고, 그 VM 은 켜져 있어야 한다. 전원 끔을 고르면 [명령어 생성] 에서 오류가 난다.
- 전원 끔인 VM 에는 잡과 모니터링을 지정할 수 없다(오류). 끔인 VM 만 있는 케이스는 허용한다. 그 VM 을 끄고 다음 케이스로 넘어간다.
- 1GB page backing 확인: vmx 에 `sched.mem.lpage.enable1GPage = "TRUE"` 가 있는 VM 만 확인한다. ESX 호스트에서 `esxcli vm process list` 로 VM 의 world ID 를 찾고, `vsish -e get /memory/lpage/vmLpage/<world ID>` 의 `Current number of 1GB page backings` 를 15초마다 읽는다. 이 값이 vmx 의 `memSize`(MB) / 1024 와 같아지면 완료다. 앞선 시험에서 VM 을 켤 때 쓰던 확인 규칙과 같다.
- backing 수가 6번 연속(90초) 늘지 않으면 멈춘다. `1GB page backing attempts failed` 가 0 보다 크면 ESX 호스트에 연속된 1GB 빈 메모리가 없다는 뜻이다. 그 VM 을 끄고, 다른 VM 을 끄거나 호스트를 재부팅해 메모리를 비운 뒤 다시 실행한다. 이때 그 케이스가 적용한 설정은 되돌리지 않는다.
- vsish 노드를 2분 동안 읽지 못하면 로그에 `WARN` 을 남기고 기다리지 않고 넘어간다.
- 이미 켜져 있던 VM 도 backing 과 ssh 로그인을 한 번 확인한다. 켜져 있던 VM 은 아래 대기를 만들지 않는다.
- VM 을 켜거나 끄지 못하면(켜기 작업 오류, 부팅 대기 30분 안에 ssh 로그인 안 됨) 멈춘다. 그 케이스가 설정을 바꿨으면 설정을 되돌리고 켜져 있던 VM 을 다시 켜 본 뒤 멈춘다.

VM 을 켠 뒤의 대기: 그 케이스에서 VM 을 켰으면, 마지막으로 켠 VM 의 준비(1GB page backing 확인, ssh 로그인)가 끝난 시각(R)에서 N분 이상 지난 뒤에 잡을 시작한다. N 은 설정 영역의 `VM 켠 뒤 잡 시작까지 최소 N분` 이고 기본값은 10 이다.

- 모니터링이 있는 케이스: 모니터링 시작은 3단계의 시각과 `R + N분 - 5분` 을 분 단위로 올린 시각 중 늦은 쪽이다. 잡 시작은 모니터링 시작 5분 뒤 그대로다.
- 모니터링이 없는 케이스: 잡 시작은 3단계의 시각과 `R + N분` 을 분 단위로 올린 시각 중 늦은 쪽이다.
- 예: VM 2대가 모두 꺼져 있고 모니터링이 있는 케이스. ev01 을 켜고 backing 과 ssh 로그인을 확인한 뒤 ev02 를 켜고 같은 확인을 마친 시각이 10:20 이면, 모니터링은 10:25 이후에, 잡은 10:30 이후에 시작한다.
- 그 케이스에서 켠 VM 이 없으면(모두 켜져 있었음) 이 대기가 없다.
- 설정만 있는 케이스에서 VM 을 켜고 그다음 케이스가 같은 VM 에서 잡을 실행하면, 그다음 케이스에도 `R + N분` 을 적용한다.
- N 을 0 으로 두면 3단계의 시각을 그대로 쓴다.

잡을 확인하는 케이스와 확인하지 않는 케이스: 시작 시각을 적은 케이스(시각 또는 `+간격`)는 정해진 시각에 진행하므로 잡 프로세스를 확인하지 않는다. 접속과 `pgrep` 실행이 측정 중인 VM 에 부하가 되기 때문이다.

| 케이스 | 잡 확인 | 케이스가 끝나는 때 |
| :-- | :-- | :-- |
| 시작 시각을 적었고, 같은 ESX 호스트의 다음 케이스도 시작 시각을 적음 | 안 함 | 다음 케이스 준비 시작(다음 케이스 잡 시작 − `시작 시각 준비`) 2분 전에 모니터링을 중지하고 줄을 지운다. `최대 대기` 를 적었으면 잡 시작 + 최대 대기가 더 이를 때 그 시각에 끝낸다 |
| 시작 시각을 적었고, 그 ESX 호스트의 마지막 케이스 | 안 함 | `최대 대기` 를 적었으면 잡 시작 + 최대 대기. 비웠으면 끝나는 시각이 없다(아래) |
| 시작 시각을 적었지만 다음 케이스가 자동 | 함 | 잡 종료를 확인한 뒤(다음 케이스가 이 케이스의 잡 종료를 기다리기 때문). [명령어 생성] 이 경고로 알린다 |
| 시작 시각이 자동 | 함 | 잡 종료를 확인한 뒤 |

- 확인하지 않는 케이스에서 점프 VM 이 VM 에 접속하는 때: 준비 때 VM 마다 2~3번(ssh 로그인 확인, 시계 확인, crontab 등록), 케이스가 끝난 뒤 1번(crontab 줄 삭제). 잡이 실행되는 동안에는 접속하지 않는다.
- 확인하지 않으므로 잡이 예정보다 길어져도 알지 못한다. 다음 케이스 준비 시각이 되면 모니터링을 중지하고 다음 케이스의 설정 적용과 VM 전원 맞추기를 시작한다. 설정 값이 다르면 VM 을 끄므로, 그때까지 끝나지 않은 잡은 중단된다. 케이스 사이의 시간을 잡 실행 시간과 `시작 시각 준비`(기본 60분)를 더한 것보다 길게 잡는다.
- 예: 케이스 1 을 10:00, 케이스 2 를 `+8:00`(18:00)으로 적으면 케이스 1 의 모니터링은 16:58 에 중지되고 17:00 부터 케이스 2 를 준비한다. 케이스 1 의 잡은 16:58 전에 끝나야 한다.
- 끝나는 시각이 없는 마지막 케이스(최대 대기 비움): 잡 시작 뒤 실행은 `done` 으로 끝난다. 그 케이스의 모니터링은 계속 실행되고 crontab 줄도 남는다(`status` 에 `open case` 로 나온다). 같은 ESX 호스트의 다음 실행이 첫 케이스(시작 시각을 적은 케이스) 준비를 시작할 때 모니터링 중지 명령을 실행하고 줄을 지운다. 다음 실행이 없으면 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 가 같은 일을 한다. [명령어 생성] 이 이 경우를 경고로 알린다.
- 리포트용 CSV 의 `잡 종료 시각` 은 비워 둔다(성능 리포트 생성기가 정한다). 결과 CSV 의 `first_seen`, `job_end` 도 빈칸이고 `status` 는 `done (not checked)` 다.
- 확인하지 않는 케이스에만 쓰는 잡은 탭 1 의 `프로세스 이름` 을 비워도 된다.

잡 종료를 확인하는 때(확인하는 케이스): 잡이 실행되는 동안에는 VM 에 되도록 접속하지 않는다.

| 때 | 확인 |
| :-- | :-- |
| 잡 시작 1분 뒤 | 한 번. 프로세스가 떴는지 본다. 이 확인이 없으면 잡이 시작되지 않은 경우와 끝난 경우를 구분하지 못한다 |
| 첫 확인에서 프로세스가 보이지 않은 VM 이 있을 때 | 잡 시작 10분 뒤에 한 번 더. 그때도 보이지 않으면 멈춘다 |
| 그 뒤 | `잡 종료 확인 간격`(기본 30분)마다 한 번 |
| 모든 VM 에서 프로세스가 없어진 뒤 | 1분 간격으로 두 번 더 확인해 종료를 확정한다. 잡이 끝난 뒤라 측정에 영향이 없다 |

- 종료를 아는 시점은 실제 종료보다 최대 확인 간격만큼 늦다. 모니터링 중지와 다음 케이스 시작도 그만큼 늦어진다.
- 확인 간격이 2분을 넘으면 리포트용 CSV 의 `잡 종료 시각` 을 비워 둔다. 비우면 성능 리포트 생성기가 종료 시각을 정한다. 결과 CSV 의 `job_end` 에는 프로세스가 없는 것을 처음 확인한 시각을 적는다.
- 확인할 때마다 진행 로그에 VM 마다 한 줄이 남는다. 줄 앞의 시각이 그 VM 을 확인한 시각이다. 예와 보는 방법은 5.7절에 있다.
- 확인 간격은 설정 영역에서 분 단위로 고친다(예: 60). 1분 안에 끝나는 잡은 첫 확인에서 보이지 않아 멈춘다.

시작 시각과 케이스 사이 간격: 케이스마다 탭 4 의 `시작 시각` 칸으로 잡을 시작할 때를 정한다.

| 시작 시각 칸 | 잡을 시작하는 때 |
| :-- | :-- |
| 비움 (`자동`) | 앞 케이스의 잡이 끝난 시각(종료로 판정한 시각)에서 `케이스 사이 간격`(설정 영역, 기본 30분) 이상 지난 뒤. 그 ESX 호스트에서 잡이 있는 첫 케이스는 준비가 끝나는 대로 시작한다 |
| 시각을 적음 | 그 시각. 모니터링이 있으면 모니터링은 그 5분 전에 시작한다. 케이스 사이 간격은 적용하지 않는다 |
| `+간격` 을 적음 | 같은 ESX 호스트의 바로 앞 케이스 시작 시각에서 그 간격 뒤. `+8:00`(8시간), `+8`(8시간), `+8.5`(8시간 30분)처럼 적는다. 저장할 때 `+8:00` 형태로 고친다 |

- 시각은 `10:00` 처럼 시:분만 적거나 `2026-11-20 10:00:00` 처럼 날짜까지 적는다. 시:분만 적으면 [명령어 생성] 을 누른 뒤 처음 오는 그 시각이다. 분 단위다.
- 예: 케이스 1 에 `10:00` 을 적고 케이스 2~5 를 비우면, 케이스 1 은 10시에 시작하고 2~5 는 앞 케이스의 잡이 끝나고 30분 뒤에 차례로 시작한다.
- 예: 케이스 1 에 `10:00`, 케이스 2~3 에 `+8:00` 을 적으면 10:00, 18:00, 다음 날 02:00 에 시작한다. 세 케이스 모두 잡을 확인하지 않는다.
- `+간격` 의 기준은 표의 바로 윗줄이 아니라 같은 ESX 호스트의 바로 앞 케이스다. 이번 생성에 넣는 케이스만 본다(적용 체크한 케이스와 선택 창에서 뺀 케이스는 기준이 되지 않는다). 그래서 ESX 호스트마다 이번 생성의 첫 케이스에는 시각을 직접 적는다. 앞 케이스가 자동이면 [명령어 생성] 에서 오류가 난다.
- 시작 시각을 적은 케이스가 이어질 때 뒤 케이스의 준비 시작이 앞 케이스의 잡 시작보다 빠르거나 3분 안이면 [명령어 생성] 에서 오류가 난다.
- 시작 시각을 적은 케이스는 그 시각 60분 전(설정 영역의 `시작 시각 준비`)에 설정 적용과 VM 전원 맞추기를 시작한다. 앞 케이스가 잡을 확인하는 케이스이고 그때까지 끝나지 않으면 끝난 뒤 바로 시작한다. 0 으로 두면 차례가 오는 대로 한다(앞 케이스가 잡을 확인하지 않는 케이스이면 잡 시작 5분 전, 모니터링이 있으면 10분 전).
- 시작 시각을 비운 케이스는 앞 케이스가 끝나면 바로 설정 적용과 VM 전원 맞추기를 한다. 케이스 사이 간격은 잡을 시작하는 시각에만 적용한다.
- 적은 시각을 지킬 수 없으면(앞 케이스가 그때까지 끝나지 않음, VM 을 켠 뒤의 대기가 남음, 다른 잡 시작과 가까움) 가능한 가장 이른 시각에 시작하고 로그에 `WARN the start time ... cannot be met` 을 남긴다. 메모리가 큰 VM 을 여러 대 켜는 케이스는 `시작 시각 준비` 를 늘린다.
- 이미 지난 시각을 적으면 [명령어 생성] 에서 오류가 난다. P 블록도 지난 시각을 `[PROBLEM]` 으로 알린다.
- 시각은 이 PC 의 시계와 시간대를 기준으로 초 단위 값으로 바꿔 plan 에 넣는다. PC, 점프 VM, VM 의 시계가 맞아 있어야 그 시각에 시작한다.
- 케이스 사이 간격을 0 으로 두면 앞 케이스가 끝나는 대로 다음 케이스를 시작한다.

잡 시작 최소 간격: ESX 호스트가 여러 대이면 호스트마다 진행이 따로 돌지만, 모든 잡 시작은 서로 N분 이상 떨어진다. N 은 설정 영역의 `잡 시작 최소 간격`(기본 5분)이다. 같은 점프 VM 에서 돌리는 다른 실행의 잡과도 같다.

- 예: ESX 호스트 2대에 케이스를 2개씩 두고 함께 시작하면, 호스트 1 의 첫 잡이 10:12 에 시작할 때 호스트 2 의 첫 잡은 10:17 이후에 시작한다.
- 진행 스크립트는 잡 시작 시각을 정할 때 그 시각을 점프 VM 의 `~/.tcgen/minutes/` 에 먼저 기록한다. N분 안에 다른 잡의 시작이 기록돼 있으면 그 잡 시작 N분 뒤로 옮기고 로그에 `spacing: the job of ... starts ..., less than N min from ...` 을 남긴다. 기록은 잠금(`~/.tcgen/minutes/.lock`)을 잡은 진행 하나만 하므로 두 진행이 동시에 가까운 시각을 고르지 못한다.
- 시작 시각을 적은 케이스는 실행을 시작할 때 그 시각을 먼저 기록한다. 그래서 자동으로 시각을 정하는 다른 호스트의 케이스가 그 시각을 피한다.
- 시작 시각을 적은 두 케이스가 N분보다 가까우면 ESX 호스트가 달라도 [명령어 생성] 에서 오류가 난다. 적은 시각이 이 점프 VM 의 다른 실행의 잡 시작과 N분보다 가까우면 P 블록이 `[PROBLEM]` 으로 알린다. 그대로 실행하면 그 잡은 N분 뒤로 옮겨 시작한다.
- 실행이 끝나거나 멈추면 그 실행이 기록해 두고 시작하지 않은 잡의 시각을 지운다. 하루가 지난 기록도 지운다.
- 한 케이스 안의 VM 들은 지금처럼 같은 분에 잡을 시작한다.
- 점프 VM 이 둘 이상이면 서로의 기록을 보지 못한다. 한 시험에는 점프 VM 하나를 쓴다.

판정을 못 하는 경우에는 넘어가지 않고 멈춘다.

- `pgrep` 이 없거나 ssh 가 실패한 확인은 '알 수 없음'이다. 없음으로 세지 않고 연속 횟수를 0 으로 다시 설정한다.
- 잡 시작 뒤 10분 안에 프로세스가 한 번도 보이지 않는 VM 이 있으면 멈춘다.
- 탭 4 의 최대 대기를 넘으면 멈춘다.

### 5.7 점프 VM 로그 폴더의 파일

실행마다 ESX 호스트별로 세 파일이 생긴다. ESX 호스트를 적지 않은 케이스는 파일 이름의 호스트 자리에 `noesx` 가 들어간다. 글은 ASCII 영어다. 시각은 점프 VM 의 현지 시각이다.

| 파일 | 내용 |
| :-- | :-- |
| `tcrun-<실행 ID>-<ESX 호스트>.log` | 진행 로그. 시간순 한 줄씩 |
| `tcrun-<실행 ID>-<ESX 호스트>-result.csv` | 케이스별 결과 한 행 |
| `tcrun-<실행 ID>-<ESX 호스트>-perfreport_cases.csv` | 성능 리포트 생성기의 케이스 정보 파일. 끝난 케이스만 들어간다 |
| `tcrun-<실행 ID>-check.log` | 점검 블록의 출력 |

진행 로그는 점프 VM 에만 있다. PC 로는 오지 않는다. 점프 VM 에서 아래 명령으로 본다.

```
sh ~/.tcgen/tcrun status                                   # 지금 단계, 다음 확인 시각, 로그의 마지막 세 줄
tail -f ~/tcgen_log/tcrun-<실행 ID>-<ESX 호스트>.log        # 로그를 계속 보기 (Ctrl+C 로 끝냄)
grep ' check ' ~/tcgen_log/tcrun-<실행 ID>-<ESX 호스트>.log  # 잡 확인 줄만 보기
```

`~/tcgen_log` 는 설정 영역의 `점프 VM 로그 폴더` 를 비웠을 때의 위치다. 폴더를 적었으면 그 폴더다. S 블록을 붙여넣으면 `started:` 줄에 로그 파일의 전체 경로가 나온다.

잡 확인 줄은 아래처럼 남는다. 확인할 때마다 잡이 있는 VM 마다 한 줄이고, 줄 앞의 시각이 그 VM 을 확인한 시각(점프 VM 의 시계)이다. VM 들을 차례로 확인한 뒤 `done` 줄에 다음 확인 시각이 나온다.

```
2026-11-20 10:09:10 check 1 (case caseA) vm esx01ev01: 1 process(es) running (seen for the first time)
2026-11-20 10:09:18 check 1 (case caseA) vm esx01ev02: 1 process(es) running (seen for the first time)
2026-11-20 10:09:24 check 1 (case caseA) done. next check 2026-11-20 10:39:24
2026-11-20 10:39:32 check 2 (case caseA) vm esx01ev01: 1 process(es) running
2026-11-20 10:39:38 check 2 (case caseA) vm esx01ev02: no process (1 of 3 in a row)
2026-11-20 10:39:42 check 2 (case caseA) done. next check 2026-11-20 11:09:42
```

| 결과 | 뜻 |
| :-- | :-- |
| `N process(es) running` | 프로세스 이름이 들어 있는 프로세스가 N 개 있다. 처음 찾았으면 `(seen for the first time)` 이 붙는다 |
| `no process (N of 3 in a row)` | 한 번 이상 보였던 프로세스가 없다. 3회 연속이면 그 VM 의 잡이 끝난 것이다 |
| `no process yet (not seen since the job start)` | 잡 시작 뒤 아직 한 번도 보지 못했다. 시작 대기(10분)가 지나도 그대로면 멈춘다 |
| `unknown (ssh exit N: ...)` | 그 VM 에 접속하지 못했다. 끝난 것으로 세지 않는다 |

- 줄 앞의 시각은 점프 VM 의 시계다. VM 의 시계와 몇 초 다른지는 같은 케이스의 `clock: vm <이름> is N s ahead of the jump VM` 줄에 있다.

진행 로그에서 찾을 줄은 다음과 같다.

| 줄에 들어 있는 글 | 뜻 |
| :-- | :-- |
| `==== case <이름> (N of M) begin` | 케이스 시작 |
| `TCGEN-SET`, `TCGEN-HOST` | 설정 한 항목의 변경 전 값과 목표 값. `[change]` 또는 `[same]` |
| `TCGEN-DONE` | 적용한 호스트 옵션(전 값과 후 값), 수정한 vmx 와 백업 파일 경로 |
| `start time ...: the preparation (settings, VM power) starts N min before it` | 시작 시각을 적은 케이스에서 준비를 시작할 시각까지 기다린다 |
| `settings: every value is already as wanted` | 값이 모두 같아 설정 때문에 VM 을 끄지 않았다 |
| `VM power: ...` | VM 전원 맞추기의 시작과 끝. 끝 줄에 그 케이스가 켠 VM 과 마지막 VM 의 준비가 끝난 시각이 나온다 |
| `vm <이름>: shut down (the case wants it off)` | 전원 끔인 VM 을 껐다 |
| `vm <이름>: 1GB page backing complete (N of M 1GB pages, ...)` | 1GB page backing 이 끝났다. 바로 위의 `1GB page backings, target, failed attempts:` 줄이 읽은 값의 변화다 |
| `vm <이름>: ssh login works, ready N s after the power on started` | 그 VM 의 준비가 끝났다. 켜기 시작한 때부터 backing 확인과 ssh 로그인까지 걸린 시간 |
| `settle:` | VM 을 켠 뒤의 대기를 적용했는지, 시작 시각을 얼마나 미뤘는지 |
| `gap:` | 케이스 사이 간격을 적용했는지, 시작 시각을 얼마나 미뤘는지 |
| `start time: the plan sets the job start ...` | 탭 4 에 적은 시작 시각에 잡을 시작하도록 정했다 |
| `spacing: the job of ... starts ..., less than N min from ...` | 다른 잡의 시작과 N분보다 가까워 이 잡을 옮겼다 |
| `registered on vm <이름>:` 과 그 아래 줄 | crontab 에 등록한 줄 그대로 |
| `times: monitoring start ..., job start ...` | 정한 시각 |
| `check N (case <이름>) vm <이름>: ...` | 잡 확인 한 번에 VM 마다 한 줄. 시각, 케이스, VM 이름, 결과(위 표) |
| `check N (case <이름>) done. next check <시각>` | 그 확인을 마친 때와 다음 확인 시각 |
| `job ended:` | 종료로 판정한 시각 |
| `removed the lines of this case` | crontab 줄 삭제 |
| `==== case <이름> done` | 케이스 끝 |
| `not checked: the plan sets the start time of this case. End of the case: <시각>` | 잡을 확인하지 않는 케이스. 그 시각에 모니터링을 중지하고 줄을 지운다 |
| `the job start time ... has passed. The job of case <이름> is not checked` | 잡 시작 시각이 지났다. 이 줄 뒤로 케이스가 끝날 때까지 VM 에 접속하지 않는다 |
| `end of case <이름>: <시각> (time of the plan, the job was not checked)` | 정해진 시각에 케이스를 끝냈다 |
| `case <이름> stays open` | 끝나는 시각이 없는 마지막 케이스. 모니터링과 줄을 남기고 실행을 끝냈다 |
| `queued: ...` | 같은 ESX 호스트의 앞 실행이 끝나기를 기다린다 |
| `run <실행 ID> left its last case open ... Closing it now` | 앞 실행이 줄을 남긴 마지막 케이스를 이 실행이 첫 케이스 준비 직전에 처리했다(모니터링 중지, 줄 삭제) |
| `CANCEL requested`, `CANCELLED`, `case <이름> is closed` | `tcrun cancel` 이 한 일 |
| `WARN` | 진행은 계속하지만 확인할 일 |
| `PAUSED:` 또는 `STOPPED on request:` | 멈춘 이유. 그 아래 `Not finished:` 줄에 끝나지 않은 케이스 이름이 나온다 |

결과 CSV 의 열은 다음과 같다.

| 열 | 내용 |
| :-- | :-- |
| `case`, `esx` | 케이스 이름, ESX 호스트 |
| `apply` | 설정 적용 결과. `none`(설정 없음), `nochange`(값이 같음), `changed`(적용함), `rolledback`(이전 값으로 복원함) |
| `begin`, `end` | 케이스를 시작한 시각, 끝낸 시각 |
| `vms_on` | 그 케이스가 켠 VM 가운데 마지막 VM 의 준비(1GB page backing 확인, ssh 로그인)가 끝난 시각. 켠 VM 이 없으면 빈칸 |
| `monitor_start`, `job_start` | crontab 에 등록한 모니터링 시작 시각, 잡 시작 시각 |
| `first_seen` | 잡이 있는 모든 VM 에서 프로세스가 보인 시각 |
| `job_end` | 잡 종료 시각. 마지막 VM 에서 프로세스가 처음으로 보이지 않은 확인 시각. 실제 종료는 그보다 최대 확인 간격만큼 앞이다 |
| `monitor_stop` | 모니터링 중지 명령을 등록한 시각 |
| `status` | `done`, `done (settings only)`, `done (not checked)`(잡을 확인하지 않은 케이스), `done (not checked, open)`(끝나는 시각이 없어 모니터링과 crontab 줄이 남음), `paused: <이유>`, `stopped: <이유>`, `cancelled`, `closed by ...`(남은 줄을 지우고 모니터링을 중지함) |

리포트용 CSV 는 PC 로 가져와 성능 리포트 생성기의 `케이스 정보 파일` 에서 고른다. UTF-8(BOM) 이고 열은 시각 지정의 리포트용 CSV 와 같다(9.2절). `잡 시작 시각` 은 위 결과 CSV 의 `job_start` 다. `잡 종료 시각` 은 잡 종료 확인 간격이 2분 이하일 때만 `job_end` 를 적고, 그보다 길면 비워 둔다(성능 리포트 생성기가 정한다). 테스트 그룹, 설명, 종료 기준 VM 은 탭 4 에 적은 값이다. 순서 실행에서 탭 4 의 [리포트용 CSV 저장] 은 이 파일의 위치만 안내한다.

### 5.8 멈췄을 때 이어서 하는 방법

1. `sh ~/.tcgen/tcrun status` 와 진행 로그의 `PAUSED:` 줄에서 이유를 확인한다.
2. 아래 표에 따라 원인을 고친다.
3. `status` 에 `open case:` 줄이 있으면 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 를 실행한다. 멈춘 케이스의 crontab 줄을 지우고 시작된 모니터링을 중지한다. 이것을 하기 전에는 그 ESX 호스트의 새 실행이 시작되지 않는다(P 블록이 `[PROBLEM]` 으로 알린다).
4. 생성기의 탭 4 에서 끝난 케이스(결과 CSV 의 `status` 가 `done` 으로 시작하는 케이스)를 적용 체크한다.
5. [명령어 생성] 을 다시 누르고 P 블록, S 블록을 붙여넣는다. 남은 케이스가 처음부터 진행된다.

| 멈춘 이유 (로그의 글) | 멈춘 뒤의 상태 | 할 일 |
| :-- | :-- | :-- |
| `settings ... were not applied` (없는 VM, 없는 호스트 옵션, 일시 중지된 VM 등) | 아무것도 바꾸지 않았다 | 프로파일이나 VM 이름을 고친다 |
| `power on of vm ... failed`, `did not accept ssh login`, `power off of vm ... failed` | 그 케이스가 설정을 바꿨으면 이전 값으로 복원했다(vmx 는 백업 파일로, 호스트 옵션은 이전 값으로). 켜져 있던 VM 을 순서대로 다시 켜 보았다 | ESX 에서 VM 상태를 확인한다. 켜지지 않은 VM 은 직접 켠다 |
| `the 1GB page backing stopped at ...`, `does not increase at ...`, `was not complete within ...` | 설정은 적용한 그대로 두었다. 그 VM 은 켜진 채로 있다 | 그 VM 을 끄고, 다른 VM 을 끄거나 ESX 호스트를 재부팅해 메모리를 비운 뒤 다시 실행한다(`failed attempts` 가 0 이면 VM 의 메모리 예약 설정을 확인한다) |
| `ssh login was refused (... Permission denied ...). Not tried again` | VM 을 켰지만 그 VM 이 ssh 로그인을 거부했다. 계정이 잠기지 않도록 다시 시도하지 않는다 | VM 의 계정과 비밀번호(`sh ~/.tcgen/setpw`)를 확인한다. 같은 비밀번호로 직접 ssh 로그인이 되는지 본다 |
| `crontab lines were not registered` | 그 케이스의 줄을 모두 지웠다. 아무것도 시작하지 않았다 | 그 VM 의 접속과 crontab 을 확인한다 |
| `was too slow 3 times` | 등록이 시작 시각 15초 전까지 끝나지 않아 줄을 모두 지웠다. 아무것도 시작하지 않았다 | VM 접속이 느린 원인을 확인한다 |
| `took too long: the first start time ... passed` | 등록이 늦어 줄을 지웠지만, 지우는 동안 시작 시각이 지났다. 일부 VM 에서 모니터링이나 잡이 시작됐을 수 있다 | 각 VM 에서 프로세스를 확인하고 필요하면 직접 중지한다 |
| `the process was never seen` | 잡 줄과 모니터링 줄은 실행된 상태다. 모니터링은 계속 실행 중이다 | 프로세스 이름과 잡 명령을 확인한다. `tcrun cancel` 로 줄을 지우고 모니터링을 중지한다 |
| `did not end within the maximum wait` | 잡과 모니터링이 계속 실행 중이다 | 잡을 확인한다. 끝난 뒤 `tcrun cancel` 로 줄을 지우고 모니터링을 중지한다 |
| `run ... of this ESX host ended as <상태>, not as done` | 대기하던 실행이다. 앞 실행이 `done` 으로 끝나지 않아 시작하지 않았다 | 앞 실행을 위 방법으로 정리한 뒤 다시 생성한다 |
| `the job of case ... would start ..., but the case must end ...` | 잡을 확인하지 않는 케이스의 잡 시작이 밀려 끝나는 시각을 넘었다. 아무것도 시작하지 않았다 | 시작 시각을 다시 정해 생성한다 |
| `monitoring stop ... could not be registered` | 잡은 끝났다. 그 호스트의 모니터링이 계속 실행 중일 수 있다 | 로그에 적힌 중지 명령을 그 호스트에서 실행한다 |

멈춘 케이스의 crontab 줄과 모니터링은 `sh ~/.tcgen/tcrun cancel` 로 정리한다(5.5절). VM 의 crontab 을 모두 지우려면 D 블록을 쓴다. D 블록은 모니터링을 중지하지 않는다.

### 5.9 BM 서버에서 실행

VM 행은 점프 VM 이 ssh 로 접속하는 대상이다. BM 서버를 VM 행에 적으면 VM 과 같은 방식으로 잡과 모니터링을 실행한다.

1. 탭 4 의 케이스에서 `ESX 호스트` 칸을 비운다.
2. VM 행의 이름에 BM 서버의 호스트 이름(또는 IP 주소)을 적고, 잡과 모니터링(실행 위치가 VM 인 명령)을 고른다.
3. 나머지는 VM 과 같다. 잡과 모니터링은 BM 서버의 crontab 에 등록하고, 잡 종료도 같은 방식으로 확인한다.

- 설정 프로파일, ESX 모니터링, 전원 끔은 쓸 수 없다. ESX 호스트가 없기 때문이다. 케이스에 지정하면 [명령어 생성] 에서 오류가 난다. BM 서버는 켜져 있어야 한다.
- BM 서버의 계정과 비밀번호가 VM 과 같아야 자동 로그인이 된다(`VM 접속 계정` 과 `sh ~/.tcgen/setpw` 로 저장한 비밀번호를 쓴다). 다르면 점프 VM 의 ssh 공개 키를 BM 서버의 `~/.ssh/authorized_keys` 에 넣는다.
- ESX 호스트를 비운 케이스는 한 줄로 차례대로 진행한다. 로그 파일 이름의 호스트 자리에는 `noesx` 가 들어간다.
- BM 서버에 `crontab` 과 `pgrep` 명령이 있어야 한다. P 블록이 확인한다.

## 6. ssh 키 접속 (점프 VM 에서 ESX 호스트로)

순서 실행에서 점프 VM 은 ESX 호스트에 root 계정으로, 비밀번호 없이 ssh 키로 접속한다. ESX 비밀번호는 어디에도 저장하지 않는다. 방법은 Broadcom KB 313767 (ESXi 7.0, 8.0) 의 공개 키 인증이다.

A 블록이 키를 만들고 ESX 에 넣을 한 줄을 출력한다(5.1절). 같은 일을 직접 하려면 아래 명령을 쓴다.

```
# 1) 점프 VM: 키 만들기 (이미 있으면 생략)
ssh-keygen -t rsa -b 4096 -N "" -f ~/.tcgen/id_esx
cat ~/.tcgen/id_esx.pub

# 2) 각 ESX 호스트의 root SSH 창: 위에서 출력된 공개 키 한 줄을 넣는다
echo '<공개 키 한 줄>' >> /etc/ssh/keys-root/authorized_keys

# 3) 점프 VM: 확인. 비밀번호를 묻지 않고 ESX 호스트 이름이 나와야 한다
sh ~/.tcgen/esxssh esx01 hostname
ssh -i ~/.tcgen/id_esx -o BatchMode=yes root@esx01 hostname
```

- ESX 호스트의 SSH 서비스가 켜져 있어야 한다. 잠금 모드(Lockdown Mode)에서는 접속되지 않는다.
- ESX 호스트 이름으로 접속되지 않으면 설정 영역의 `ESX 접속 주소` 에 `esx01=10.0.0.11;esx02=10.0.0.12` 처럼 적는다. 탭 4 의 ESX 호스트 이름은 그대로 두고 접속만 그 주소로 한다.
- 키를 빼려면 ESX 호스트의 `/etc/ssh/keys-root/authorized_keys` 에서 그 줄을 지운다.
- 키 파일 `~/.tcgen/id_esx` 는 본인만 읽을 수 있게 저장된다(권한 600). 이 파일이 있으면 등록한 ESX 호스트에 root 로 접속할 수 있으므로 다른 곳에 복사하지 않는다.

## 7. 화면

화면은 위에서부터 설정 영역, 탭 5개, 상태 줄로 이루어진다.

- 지금 보고 있는 탭은 파란 바탕에 흰 굵은 글씨로 표시된다.
- 탭마다 표 위에 버튼이 있다. 오른쪽 [도움말] 을 누르면 그 탭의 자세한 설명 창이 열린다. 탭 4 와 탭 5 의 도움말은 진행 방식에 따라 내용이 다르다.
- 맨 아래 상태 줄에는 데이터 폴더 경로, 지금 쓰는 테스트 케이스 파일의 이름, 마지막 자동 저장 시각이 나온다. 블록을 복사하면 복사한 블록 이름과 줄 수가 나온다.

### 7.1 설정 영역

값을 고치면 바로 데이터 폴더의 `settings.json` 에 저장된다.

| 항목 | 진행 방식 | 내용 |
| :-- | :-- | :-- |
| 테스트 케이스 파일, [불러오기], [다른 이름으로 저장] | 공통 | 탭 4 의 표를 저장하는 파일(4.1절). 지정하지 않으면 데이터 폴더에 자동 저장한다 |
| 테스트 기록 CSV [찾기] | 공통 | 기존 파일을 고르거나 새 파일 이름을 적는다. 생성할 때마다 케이스 하나에 한 행을 추가한다. 테스트 케이스 파일마다 마지막 값을 기억한다 |
| 로그 폴더 [찾기] | 공통 | PC 의 폴더. 생성할 때마다 `testcaselogging-년월일시분초.csv` 를 만든다. 테스트 케이스 파일마다 마지막 값을 기억한다 |
| 진행 방식 | 공통 | 순서 실행 또는 시각 지정(4절) |
| VM 접속 계정 | 공통 | 점프 VM 에서 ssh 로 접속할 계정. 비우면 점프 VM 의 현재 계정으로 접속한다 |
| 모니터링 시작 N분 뒤 잡 시작 | 순서 실행 | 기본 5. 잡 시작 = 모니터링 시작 N분 뒤 |
| VM 켠 뒤 잡 시작까지 최소 N분 | 순서 실행 | 기본 10. 0 이상의 정수. VM 을 켠 케이스의 잡은 마지막으로 켠 VM 의 준비가 끝난 뒤 N분이 지나야 시작한다(5.6절). 0 이면 기다리지 않는다 |
| 케이스 사이 간격 N분 | 순서 실행 | 기본 30. 0 이상의 정수. 시작 시각을 비운 케이스의 잡은 앞 케이스의 잡이 끝난 시각에서 N분 이상 지난 뒤에 시작한다(5.6절). 0 이면 기다리지 않는다 |
| 잡 시작 최소 간격 N분 | 순서 실행 | 기본 5. 1 이상의 정수. 모든 잡 시작은 서로 N분 이상 떨어진다(ESX 호스트가 달라도, 이 점프 VM 의 다른 실행과도. 5.6절) |
| 시작 시각 준비 N분 전 | 순서 실행 | 기본 60. 0 이상의 정수. 시작 시각을 적은 케이스는 그 시각 N분 전에 설정 적용과 VM 전원 맞추기를 시작한다(5.6절). 0 이면 차례가 오는 대로 한다 |
| 잡 종료 확인 간격 N분 | 순서 실행 | 기본 30. 1 이상의 정수. 잡이 실행되는 동안 VM 에 접속해 프로세스를 찾는 주기다(5.6절). `settings.json` 에는 초(`seq_poll_sec`)로 저장한다 |
| 점프 VM 로그 폴더 | 순서 실행 | 점프 VM 의 폴더. `/` 또는 `~/` 로 시작하고 영문, 숫자, `.` `_` `-` `/` `+` `@` `,` `:` 만 쓴다. 공백과 한글은 쓸 수 없다. 비우면 `~/tcgen_log`, 점프 VM 작업 폴더를 적었으면 `<작업 폴더>/log` |
| 점프 VM 작업 폴더 | 순서 실행 | 진행 스크립트, ESX 키, VM 비밀번호, 실행 기록을 두는 점프 VM 의 폴더. 글자 규칙은 로그 폴더와 같다. 비우면 `~/.tcgen`. 바꾸면 A 블록을 다시 붙여넣는다(5.1절). P, S, D 블록과 화면의 안내가 이 폴더를 쓴다 |
| ESX 접속 주소 | 순서 실행 | 선택. `호스트이름=주소` 를 `;` 로 구분한다. 비우면 ESX 호스트 이름으로 접속한다 |
| 모니터링 시작 N분 전 | 시각 지정 | 기본 5. 모니터링 시작 = 잡 시작 N분 전. 위의 '모니터링 시작 N분 뒤 잡 시작' 과 같은 값을 쓴다 |
| 모니터링 중지 N분 전 | 시각 지정 | 기본 10. 자동 중지 = 다음 케이스 잡 시작 N분 전 |
| [설정 백업] | 공통 | 백업을 저장할 폴더를 고르면 그 안에 `tcgen2_backup_년월일시분초` 폴더를 만들고 데이터 파일과 `testcases` 폴더를 복사한다. 테스트 케이스 파일을 따로 지정해 쓰고 있으면 그 파일도 `case_file_<파일 이름>` 으로 함께 복사한다(탭 4 의 표가 그 파일에 있다) |
| [백업 불러오기] | 공통 | 백업 폴더를 고르면 그 데이터 파일로 현재 데이터를 교체하고 화면을 다시 채운다. 교체 전 현재 파일은 데이터 폴더 `backup` 아래에 복사해 둔다. 백업에 테스트 케이스 파일의 사본(`case_file_<파일 이름>`)이 있으면 그 파일도 백업한 때의 내용으로 바꾼다. 바꾸기 전 내용은 같은 `backup` 폴더에 복사해 둔다. 사본이 없는 백업(v2.6 까지의 [설정 백업])은 그 파일을 바꾸지 않으므로 탭 4 의 표는 그 파일의 지금 내용 그대로다 |
| [데이터 폴더 열기] | 공통 | 데이터 폴더를 연다 |
| [데이터 폴더 변경] | 공통 | 새 폴더를 고르면 지금 데이터를 복사하고 그 폴더를 데이터 폴더로 쓴다. 고른 폴더에 이미 데이터가 있으면 그 데이터를 불러온다. 위치는 `config.json` 에 저장되어 다음 실행에도 쓴다. 생성기 폴더 안은 고를 수 없다 |
| [테스트 케이스 폴더 열기] | 공통 | PC 의 로그 폴더(`testcaselogging-*.csv`)를 연다 |

화면에 없고 `settings.json` 에서만 고치는 값은 다음과 같다. 생성기를 끈 상태에서 고친다.

| 키 | 기본값 | 내용 |
| :-- | :-- | :-- |
| `seq_poll_sec` | 1800 | 순서 실행: 잡 종료 확인 간격(초). 화면의 `잡 종료 확인 간격` 칸(분)과 같은 값이다. 1분보다 짧게 하려면 이 값을 고친다 |
| `seq_first_check_sec` | 60 | 순서 실행: 잡 시작 뒤 프로세스가 떴는지 처음 확인하는 때(초) |
| `seq_gone_count` | 3 | 순서 실행: 프로세스가 이 횟수만큼 연속으로 없으면 종료로 판정 |
| `seq_start_wait_min` | 10 | 순서 실행: 잡 시작 뒤 이 시간 안에 프로세스가 한 번도 보이지 않으면 멈춤 |
| `seq_poweron_wait_min` | 90 | 순서 실행: ESX 의 VM 켜기 작업(`vim-cmd vmsvc/power.on`)이 끝나기를 기다리는 최대 시간. 메모리가 큰 VM 은 켜기 작업이 수 분 이상 걸린다 |
| `seq_boot_wait_min` | 30 | 순서 실행: VM 켜기 작업이 끝난 뒤 ssh 로그인을 기다리는 최대 시간 |
| `seq_shutdown_wait_min` | 10 | 순서 실행: 게스트 종료를 기다리는 최대 시간. 넘으면 전원 끄기 |
| `vm_prefix`, `default_vms` | `ev`, 2 | VM 이름 자동 입력. VM 이름 = ESX 호스트 + `vm_prefix` + 두 자리 번호, 새 케이스의 VM 수 = `default_vms` |

### 7.2 탭 1. 실행 명령

| 열 | 내용 |
| :-- | :-- |
| App명 | 응용 이름 |
| 명령어 명 | 탭 4 에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 잡 조건 설명 | 예: 1 job, 4 jobs 동시. 로그 CSV 의 '설명' 열에 함께 기록한다 |
| 프로세스 이름 | 순서 실행에서 잡 종료를 확인하는 데 쓴다(잡을 확인하는 케이스, 5.6절). `tcrun cancel` 이 남은 잡 프로세스를 보일 때도 쓴다. 시각 지정에서는 쓰지 않는다 |
| 경로/실행 명령 | 절대 경로로 입력한다. 이 명령이 crontab 에 한 줄로 그대로 들어간다 |

프로세스 이름은 다음 규칙으로 적는다.

- 잡이 실행되는 동안 VM 에 떠 있는 프로세스의 명령줄에 들어 있는 글자를 적는다. 점프 VM 이 VM 에서 `pgrep -f` 로 이 글자를 찾는다. 적은 글자를 그대로 찾는다(정규식으로 해석하지 않는다).
- 잡의 처음부터 끝까지 떠 있는 프로세스를 고른다. 예: 실행 스크립트 이름 `run_a.sh`. 중간에 30초 넘게 그 이름의 프로세스가 없는 구간이 있으면 그 시점에 종료로 판정될 수 있다.
- 다른 프로세스의 명령줄에 같은 글자가 들어 있으면 잡이 끝나지 않은 것으로 판정된다. 모니터링 명령, 로그 파일을 연 편집기나 `tail` 이 그런 예다. 그 잡에서만 쓰는 글자를 적는다.
- ASCII 문자만 쓴다. 작은따옴표, `!`, 역슬래시는 쓸 수 없다. 80자 이하.

명령 안에 쓸 수 있는 변수는 두 가지다.

| 변수 | 값 |
| :-- | :-- |
| `<vm이름>` | 명령이 실행되는 VM 의 hostname (`hostname -s`). ESX 명령에서는 ESX 호스트 이름 |
| `<실행시각>` | 명령이 실행된 시각 14자리, KST. 예: `20261109000000` |

예: `/home/tester/bench/run_a.sh >> /home/tester/log/run_a-<vm이름>-<실행시각>.log 2>&1`

### 7.3 탭 2. 모니터링 명령

탭 1 의 열에서 프로세스 이름이 빠지고 실행 위치(VM 또는 ESX), 시작 명령, 중지 명령이 더해진다. 어떤 모니터링 명령이든 직접 등록한다.

- 실행 위치가 VM 인 명령은 탭 4 의 VM 행에서, ESX 인 명령은 케이스 행에서 고른다.
- 중지 명령을 비우면 중지 줄을 만들지 않는다.

### 7.4 탭 3. 설정 프로파일

순서 실행에서 케이스를 시작하기 전에 적용할 설정 묶음이다. 시각 지정에서는 쓰지 않는다.

| 열 | 내용 |
| :-- | :-- |
| 프로파일 이름 | 탭 4 에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 대상 | `ESX 호스트` 또는 `VM`. 케이스 행의 설정 칸에는 대상이 ESX 호스트인 프로파일이, VM 행의 설정 칸에는 대상이 VM 인 프로파일이 나온다 |
| 설정 내용 | 칸을 두 번 누르면 여러 줄 입력 창이 열린다. 한 줄에 `키 = 값` 하나를 적는다. `#` 으로 시작하는 줄은 설명이다 |
| 설명 | 한글을 쓸 수 있다 |

대상이 VM 인 프로파일은 vmx 파일의 키를 적는다.

```
sched.mem.pin = "TRUE"
sched.cpu.affinity = 0,1,2,3
numa.nodeAffinity =
```

- vmx 파일의 줄(`키 = "값"`)을 그대로 붙여넣어도 된다. 따옴표는 벗겨서 받는다.
- 값을 비우면 그 키의 줄을 vmx 에서 지운다.
- 키는 대소문자를 구분하지 않는다. 값은 글자 그대로 비교한다(`TRUE` 와 `true` 는 다른 값으로 본다).
- CPU affinity 같은 값을 계산하는 기능은 없다. 키와 값을 직접 적는다.
- VM 을 구별하는 값이나 파일 위치를 적는 키는 넣을 수 없다: `displayName`, `uuid.bios`, `uuid.location`, `vc.uuid`, `nvram`, `config.version`, `virtualHW.version`, `.encoding`, `extendedConfigFile`, `vmxstats.filename`, `sched.swap.derivedName`, `checkpoint.vmState`, 이름이 `.fileName` 으로 끝나는 키.

대상이 ESX 호스트인 프로파일은 호스트 고급 설정을 적는다.

```
Numa.LocalityWeightActionAffinity = 0
/Cpu/HTWholeCoreThreshold = 0
```

- 이름은 `/구역/옵션` 또는 `구역.옵션` 으로 적는다. `구역.옵션` 은 점을 `/` 로 바꾸고 앞에 `/` 를 추가해 `esxcli system settings advanced` 의 이름으로 쓴다.
- 값을 비울 수 없다(호스트 옵션은 지울 수 없다).
- 재부팅해야 적용되는 호스트 설정은 넣지 않는다. 그런 설정은 수동으로 적용한다.

프로파일을 여러 개 고르면 탭 3 의 표 순서대로 합친다. 같은 키가 겹치면 아래쪽 프로파일의 값을 쓴다.

#### 기본 프로파일

생성기를 처음 실행하면(데이터 폴더에 `profiles.json` 이 없으면) 탭 3 에 아래 12개가 들어 있다. 고치거나 삭제해도 된다.

| 프로파일 이름 | 대상 | 설정 내용 | 뜻 |
| :-- | :-- | :-- | :-- |
| `lpage_1g_on` | VM | `sched.mem.lpage.enable1GPage = TRUE`, `sched.mem.pin = TRUE`, `sched.mem.prealloc = TRUE`, `sched.mem.prealloc.pinnedMainMem = TRUE`, `sched.swap.vmxSwapEnabled = FALSE` | 1GB page 키 5개 적용 |
| `lpage_1g_off` | VM | 위 다섯 키의 값을 비움 | 1GB page 키 5개 삭제 |
| `halt_in_monitor_on` | VM | `monitor_control.halt_in_monitor = TRUE`, `monitor.idleLoopSpinBeforeHalt = TRUE`, `monitor.idleLoopMinSpinUS = 50`, `monitor_control.disable_pause_loop_exiting = TRUE` | 유휴 vCPU 처리 키 4개 적용 |
| `halt_in_monitor_off` | VM | 위 네 키의 값을 비움 | 유휴 vCPU 처리 키 4개 삭제 |
| `latency_high` | VM | `sched.cpu.latencySensitivity = high` | Latency Sensitivity high |
| `latency_normal` | VM | `sched.cpu.latencySensitivity = normal` | Latency Sensitivity normal (기본값) |
| `vpmc_on` | VM | `vpmc.enable = TRUE` | vPMC 사용. 게스트 perf 의 하드웨어 이벤트 수집에 쓴다 |
| `vpmc_off` | VM | `vpmc.enable` 의 값을 비움 | vPMC 키 삭제 |
| `kstats_on` | VM | `vmx.buildType = stats`, `vmx.log.keepOld = 20` | vmx stats 빌드, vmware.log 보존 수 20 |
| `kstats_off` | VM | 위 두 키의 값을 비움 | vmx stats 빌드 키와 로그 보존 수 키 삭제 |
| `ht_wholecore_1` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 1` | 호스트 옵션 Cpu.HTWholeCoreThreshold 를 1 로 변경 |
| `ht_wholecore_800` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 800` | 같은 옵션을 기본값 800 으로 변경 |

- 이름이 `_off` 로 끝나는 프로파일은 값을 비워 둔 것이라 그 키의 줄을 vmx 에서 지운다. 키가 없는 VM 에서는 바꿀 것이 없어 VM 을 끄지 않는다.
- `lpage_1g_on` 은 VM 의 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Backing Guest vRAM with 1 GB Pages).
- `latency_high` 는 CPU 와 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Adjust Latency Sensitivity).
- 두 경우 모두 진행 스크립트가 설정을 이전 값으로 복원한 뒤 멈춘다(5.8절). 예약 값은 이 생성기가 바꾸지 않는다.
- [기본 프로파일 추가] 는 표에 없는 이름의 기본 프로파일만 표 끝에 추가한다. 이름이 같은 행은 고친 내용 그대로 둔다. 처음 값으로 복원하려면 그 행을 삭제한 뒤 버튼을 누른다.
- 이미 쓰던 데이터 폴더(`profiles.json` 이 있는 폴더)에는 자동으로 넣지 않는다. [기본 프로파일 추가] 를 한 번 누른다.
- CPU affinity, 예약, shares 는 기본 프로파일에 없다. VM 마다 값이 다르므로 직접 프로파일을 만들어 적는다.

적용 방법은 다음과 같다(ESX 호스트에서 `tcgen_apply.py` 가 한다).

1. 케이스의 VM 을 `vim-cmd vmsvc/getallvms` 에서 이름이 정확히 같은 줄로 찾는다. 찾지 못하거나 같은 이름이 둘 이상이면 아무것도 바꾸지 않고 멈춘다.
2. 목표 값을 현재 값(vmx 파일, `esxcli system settings advanced list -o`)과 비교한다. 모두 같으면 끝낸다.
3. 그 케이스의 VM 을 모두 종료한다. `power.shutdown` 으로 요청하고, 10분 안에 꺼지지 않거나 게스트 종료를 할 수 없으면 `power.off` 로 끈다.
4. 호스트 옵션을 `esxcli system settings advanced set` 으로 변경하고 다시 읽어 확인한다(Broadcom KB 310338).
5. vmx 를 같은 폴더에 `<이름>.vmx.tcgen-<시각>` 으로 복사해 둔다(최근 5개만 남긴다). 목표 키와 이름이 같은 줄을 모두 지우고 `키 = "값"` 한 줄을 추가한다. 같은 키가 다른 값으로 여러 줄 있어도 한 줄만 남는다. 다른 줄은 그대로 둔다. `vim-cmd vmsvc/reload` 를 실행한다(Broadcom KB 343248).
6. 진행 스크립트가 VM 을 표의 순서대로 하나씩 켠다.

중간에 실패하면 vmx 를 복사해 둔 파일로 복원하고 호스트 옵션을 이전 값으로 복원한 뒤 멈춘다. 일시 중지(Suspended) 상태의 VM 이 있으면 아무것도 바꾸지 않고 멈춘다.

### 7.5 탭 4. 테스트 케이스

케이스 행(옅은 파란 바탕, 굵은 글씨) 아래에 그 케이스의 VM 행(`└`, 흰 바탕)이 달린다. VM 은 몇 대든 둘 수 있다.

칸을 고치려면 그 칸을 두 번 누르거나, 행을 고르고 Enter 또는 F2 를 누른다. 고친 뒤 Enter 를 누르면 저장되고 Esc 를 누르면 취소된다. [+ 케이스 추가] 를 누르면 새 케이스의 이름 칸이 바로 열린다. 복사한 케이스는 자동 이름(`<원래 이름>-r2`)이 골라진 채로 열리므로 바로 치면 새 이름으로 바뀐다. 쓸 수 없는 글자가 든 이름은 저장하지 않고 이유를 알린다.

두 진행 방식에 공통인 열은 다음과 같다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 적용 | 이미 실행하거나 등록한 케이스에 체크한다. 체크한 케이스는 [명령어 생성] 의 선택 창에서 처음에 빠진 채로 나온다. 칸을 누르거나 행을 고르고 Space 를 누른다 | 없음 |
| 케이스 / VM | 케이스 이름. 영문, 숫자, `.` `_` `-` 만 사용(공백, 한글, 괄호 불가. 한글은 설명 칸에 적는다). 적용 체크한 행을 포함해 중복 불가 | VM 이름. 같은 케이스 안에서 중복 불가 |
| 설명 | 시험 조건 설명. 한글을 쓸 수 있다. 기록 CSV 와 리포트용 CSV 에 들어간다 | 없음 |
| ESX 호스트 | 입력하면 VM 이름이 ESX 호스트+`ev01`, `ev02` … 로 자동 입력된다 | 없음 |
| 전원 (순서 실행) | 없음 | `켬` 또는 `끔`. 새 VM 은 켬이다. 순서 실행이 케이스 전에 이 값대로 VM 을 끄거나 켠다(5.6절). 시각 지정에서는 보이지 않는다 |
| 잡 | 없음 | 탭 1 의 명령어 명 중에서 고른다. `(없음)` 이면 그 VM 에는 잡이 없다 |
| 모니터링 | ESX 모니터링. 칸을 두 번 누르면 실행 위치가 ESX 인 명령만 나오는 선택 창이 열린다 | 그 VM 의 모니터링. 실행 위치가 VM 인 명령만 나온다 |
| 테스트 그룹 | 리포트용 CSV 의 `테스트 그룹`. 비워도 된다 | 없음 |
| 종료 기준 VM | 없음 | 칸을 두 번 누르면 `기준` 이 되고 다시 누르면 해제된다. 리포트용 CSV 에 들어간다 |

순서 실행에서만 보이는 열은 다음과 같다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 설정 | ESX 호스트에 적용할 프로파일. 칸을 두 번 누르면 대상이 ESX 호스트인 프로파일만 나오는 선택 창이 열린다 | 그 VM 에 적용할 프로파일. 대상이 VM 인 프로파일만 나온다 |
| 최대 대기 | 잡을 확인하는 케이스: 잡 시작부터 이 시간이 지나도 잡이 끝나지 않으면 진행을 멈춘다. 잡을 확인하지 않는 케이스: 이 시간이 지나면 모니터링을 중지하고 케이스를 끝낸다(5.6절). `12:00` 형식(시간:분). 비우면 제한 없음 | 없음 |
| 시작 시각 | 잡을 시작할 시각. 비우면 `자동`(앞 케이스의 잡이 끝나고 케이스 사이 간격 뒤). `10:00` 또는 `2026-11-20 10:00:00` 형식, 또는 `+8:00` 처럼 같은 ESX 호스트의 앞 케이스 시작 시각 기준의 간격(5.6절). 시각이나 간격을 적은 케이스는 잡을 확인하지 않는다. [+ 케이스 추가] 로 복사하면 시각은 `자동` 이 되고 `+간격` 은 그대로 복사된다 | 없음 |

순서 실행에서 케이스를 구성하는 규칙은 다음과 같다.

- ESX 호스트가 있는 케이스: 이름이 있는 VM 행이 모두 그 케이스의 VM 이다. 전원 칸이 켬이면 켜고(꺼져 있으면), 끔이면 끈다.
- ESX 호스트가 없는 케이스: 잡, 모니터링, 설정 가운데 하나라도 지정한 VM 행이 그 케이스의 VM 이다. 전원은 다루지 않는다.
- 전원 끔인 VM 에는 잡과 모니터링을 지정할 수 없다.
- 잡을 확인하는 케이스(5.6절)에서 잡이 있는 VM 의 명령에는 탭 1 의 프로세스 이름이 있어야 한다. 확인하지 않는 케이스에만 쓰는 잡은 비워도 된다.
- 모니터링만 있고 잡이 없는 케이스는 오류다. 잡의 프로세스가 끝난 것을 보고 모니터링을 중지하기 때문이다.
- 잡도 모니터링도 없고 설정만 있는 케이스는 허용한다. 설정만 적용하고 다음 케이스로 넘어간다.
- 설정, ESX 모니터링, 전원 끔인 VM 이 있는 케이스는 ESX 호스트가 있어야 한다.
- 같은 VM 을 ESX 호스트가 다른 두 케이스에 넣으면 오류다. 호스트별 진행이 서로 기다리지 않아 같은 VM 을 동시에 쓰게 되기 때문이다.
- [위로], [아래로] 로 케이스를 옮기면 케이스의 값이 모두 함께 옮겨진다.

시각 지정에서만 보이는 열(간격, 잡 시작, 모니터링 시작, 모니터링 중지, 잡 종료 (리포트))과 그 규칙은 8절에 있다.

#### [명령어 생성] 의 선택 창

[명령어 생성] 을 누르면 블록에 넣을 케이스를 고르는 창이 열린다. 두 진행 방식에서 같다.

| 항목 | 내용 |
| :-- | :-- |
| 넣기 칸 | 체크한 케이스만 블록과 기록에 넣는다. 칸을 누르거나 행을 고르고 Space 를 누르면 바뀐다 |
| 처음 상태 | 탭 4 에서 적용 체크하지 않은 케이스가 체크되어 있다. 적용 체크한 케이스도 체크하면 넣는다(다시 실행할 때) |
| 보이는 칸 | 케이스, 설명, ESX 호스트, 잡이나 모니터링이 있는 VM, 시작 시각(순서 실행) 또는 잡 시작(시각 지정), 적용 체크 여부 |
| [모두 선택], [모두 해제], [적용 체크하지 않은 케이스만] | 체크를 한 번에 바꾼다 |
| [생성] | 고른 케이스로 블록과 기록을 만든다. 하나도 고르지 않으면 안내만 하고 창은 남는다 |
| [취소] | 아무것도 만들지 않는다 |

- 순서 실행은 고른 케이스를 탭 4 의 표 순서대로 진행한다. 순서는 탭 4 의 [위로], [아래로] 로 바꾼다.
- 시각 지정에서 고르지 않은 케이스는 블록과 기록에서 빠지지만, 다른 케이스의 시각 계산(자동 모니터링 중지 등)에는 그대로 쓴다. 적용 체크한 케이스와 같은 방식이다.
- 이 창은 탭 4 의 적용 체크를 바꾸지 않는다. 실행이 끝난 케이스는 탭 4 에서 직접 적용 체크한다.

### 7.6 탭 5. 생성 결과

[명령어 생성] 을 누르고 선택 창에서 [생성] 을 누르면 고른 케이스의 입력을 검사하고, 오류가 없으면 기록 파일을 저장한 뒤 블록을 보여 준다. 오류가 있으면 블록과 기록을 만들지 않는다.

순서 실행의 블록은 다음과 같다. 모두 점프 VM 터미널에 붙여넣는다.

| 블록 | 붙여넣는 때 | 하는 일 |
| :-- | :-- | :-- |
| A. 점프 VM 최초 1회 설정 | 처음 한 번, 생성기를 새 판으로 교체한 뒤 한 번 | 5.1절 |
| P. 점검 블록 | 실행 전 | plan 을 점프 VM 에 저장하고 `tcrun check` 를 실행한다. 아무것도 변경하지 않는다(5.3절) |
| S. 실행 블록 | 점검이 OK 인 뒤 | plan 을 점프 VM 에 저장하고 ESX 호스트별 진행을 시작한다(5.4절) |
| D. VM crontab 전체 삭제 | 필요할 때만 | 케이스의 VM 에 접속해 crontab 을 모두 지운다(`crontab -r`). 지우기 전 내용은 그 VM 홈 폴더의 `tcgen_crontab_backup-년월일시분초.txt` 에 저장한다. 진행 중에 붙여넣으면 등록된 줄이 지워져 잡이 시작되지 않는다 |

블록 아래의 `실행 계획` 칸에는 케이스마다 점프 VM 이 하는 일과 등록할 명령이 글로 나온다. 붙여넣기 전에 이 글로 순서와 설정 값을 확인한다.

plan 은 케이스의 내용을 담은 파일이다. P 블록과 S 블록 안에 압축해(gzip, base64) 들어 있고, 붙여넣으면 `~/.tcgen/runs/<실행 ID>/plan` 에 저장된다. 저장한 뒤 sha256 을 확인하고, 다르면 아무것도 시작하지 않는다.

시각 지정의 블록(A, B, C, D)은 8.2절에 있다.

## 8. 시각 지정: 사용 순서와 화면

진행 방식을 `시각 지정` 으로 두면 v1.4 와 같은 동작이다.

### 8.1 탭 4 의 열 (시각 지정)

| 열 | 케이스 행 |
| :-- | :-- |
| 간격 | 윗줄 잡 시작부터 이 케이스 잡 시작까지의 시간. `12:00` 형식 |
| 잡 시작 (KST) | `2026-11-09 10:00:00` 형식. 분 단위. 그 케이스의 모든 VM 잡이 이 시각에 시작한다 |
| 모니터링 시작 | 잡 시작 5분 전 (자동 계산) |
| 모니터링 중지 | 칸을 두 번 누르면 자동, 직접 입력, 중지 없음 중에서 고른다. 자동은 다음 케이스 잡 시작 10분 전이고, 마지막 케이스는 잡 시작 + 간격 - 10분 |
| 잡 종료 (리포트) | 리포트용 CSV 의 `잡 종료 시각`. 비우면 `자동` 으로 보이고 성능 리포트 생성기가 종료 시각을 정한다 |

- 잡과 모니터링이 모두 없는 VM 은 등록하지 않는다. 잡이 `(없음)` 이고 모니터링이 있으면 모니터링만 등록한다.
- [+ 케이스 추가]: 선택한 케이스를 VM 구성까지 복사해 아래에 넣는다. 잡 시작 = 윗줄 잡 시작 + 간격.
- 케이스를 옮길 때는 순서만 달라지고 잡 시작, 간격, 모니터링 중지 설정은 그 행에 남는다.
- 잡 시작이나 간격을 고치면 아래 케이스의 잡 시작이 다시 계산된다.
- 적용 체크한 케이스도 표에 남아 시각 계산에 쓰인다.

### 8.2 블록 (시각 지정)

| 블록 | 붙여넣는 곳 | 하는 일 |
| :-- | :-- | :-- |
| A. 점프 VM 최초 1회 설정 | 점프 VM 터미널 (처음 한 번) | `~/.tcgen/vmssh`, `askpass`, `setpw` 를 만들고 VM 비밀번호를 입력받아 `~/.tcgen/vmpw` 에 저장한다. v1.4 의 A 블록과 같다. 순서 실행의 A 블록을 이미 붙여넣었으면 생략한다 |
| B. VM 등록 블록 | 점프 VM 터미널 (생성할 때마다) | 잡이나 모니터링이 있는 VM 마다 ssh 로 접속해 crontab 에 줄을 등록하고 등록된 줄을 출력한다 |
| C. ESX 블록 | 그 ESX 의 root SSH 창 | `/var/spool/cron/crontabs/root` 에 줄을 추가하고 `cron.update` 로 crond 에 알린다 (Broadcom KB 323138 절차) |
| D. VM crontab 전체 삭제 | 점프 VM 터미널 (필요할 때만, B 보다 먼저) | B 블록과 같은 VM 의 crontab 을 모두 지운다 |

### 8.3 사용 순서 (시각 지정)

1. 탭 1, 탭 2 에 명령을 등록한다.
2. 탭 4 에 케이스를 입력한다. 케이스 행에 이름, ESX 호스트, 간격, 잡 시작을 넣고, VM 행마다 잡과 모니터링을 고른다. [명령어 생성] 을 누르고 선택 창에서 [생성] 을 누른다.
3. 점프 VM 에서 처음 한 번만 A 블록을 붙여넣는다. `VM password:` 가 나오면 VM 비밀번호를 입력한다.
4. 점프 VM 에 B 블록을 붙여넣는다. VM 마다 `---- VM이름`, `== hostname 시각`, 등록된 `# tcgen` 줄이 출력된다.
5. ESX 의 root SSH 창에 C 블록을 붙여넣는다. ESX 가 여러 대이면 C 블록의 호스트 목록에서 하나씩 골라 복사한다.
6. 시험이 끝나면 탭 4 에서 [리포트용 CSV 저장] 으로 리포트할 케이스를 저장한다(9.2절).

같은 블록을 다시 붙여넣어도 줄이 늘지 않는다. 케이스를 고쳐 다시 생성하면, 블록에 들어 있는 케이스의 기존 줄을 지우고 새 줄을 넣는다.

### 8.4 crontab 에 들어가는 줄

명령 하나가 crontab 한 줄이 된다. 줄 끝의 `# tcgen 케이스이름 호스트` 는 기존 줄을 찾는 표식이다. 순서 실행도 같은 형태의 줄을 등록하고, 시각 칸만 점프 VM 이 실행할 때 정한다.

```
55 23 19 11 * TC_HOST=`hostname -s`; TC_START=`date +\%Y\%m\%d\%H\%M\%S`; /home/tester/mon/start_mon.sh >> /home/tester/log/mon-${TC_HOST}-${TC_START}.log # tcgen TC-base-a esx01ev01
00 00 20 11 * TC_HOST=`hostname -s`; TC_START=`date +\%Y\%m\%d\%H\%M\%S`; /home/tester/bench/run_a.sh >> /home/tester/log/run_a-${TC_HOST}-${TC_START}.log 2>&1 # tcgen TC-base-a esx01ev01
50 11 20 11 * /home/tester/mon/stop_mon.sh # tcgen TC-base-a esx01ev01
```

- 변수를 쓴 명령만 앞에 `TC_HOST=...;`, `TC_START=...;` 가 추가된다. 등록한 명령은 고치지 않는다.
- cron 은 홈 폴더에서 명령을 실행한다.
- VM 의 cron(cronie)은 명령 안의 `%` 를 줄바꿈으로 처리하므로 VM 줄은 `%` 를 `\%` 로 넣는다.
- ESX 의 crond(busybox)는 명령을 고치지 않고 실행하므로 ESX 줄은 입력한 그대로 넣는다.
- ESX 시계는 UTC 다. ESX 줄의 시각은 UTC 로 넣는다.
- cron 줄에는 연도가 없다. 시각 지정에서 지난 시각을 넣으면 내년 같은 날짜에 실행되므로 생성할 때 경고한다.

### 8.5 확인과 삭제

```
crontab -l | grep ' # tcgen '                                   # VM: 등록된 줄 확인
crontab -l | grep -v ' # tcgen TC-base-a ' | crontab -          # VM: 케이스 TC-base-a 줄 삭제
grep ' # tcgen ' /var/spool/cron/crontabs/root                  # ESX: 등록된 줄 확인
```

ESX 에서 줄을 지운 뒤에는 `/bin/echo root >> /var/spool/cron/crontabs/cron.update` 를 실행한다.

### 9.2 리포트용 CSV (성능 리포트 생성기 연동)

시각 지정에서는 탭 4 의 [리포트용 CSV 저장] 으로 만든다. 저장할 케이스를 고르고 저장 위치를 정한다. 고른 케이스는 탭 4 의 표 순서대로 들어간다. 순서 실행에서는 점프 VM 이 만든다(5.7절).

| 열 | 넣는 값 |
| :-- | :-- |
| 테스트 그룹 | 탭 4 테스트 그룹 |
| 케이스명 | 케이스 이름 |
| 설명 | 탭 4 설명 |
| 호스트 이름 | ESX 호스트 |
| 잡 시작 시각 | 시각 지정: 잡 시작 (KST). 순서 실행: 점프 VM 이 등록한 잡 시작 시각 |
| 잡 종료 시각 | 시각 지정: 잡 종료 (리포트). `자동` 이면 빈칸. 순서 실행: 잡 종료 확인 간격이 2분 이하이면 종료로 판정한 시각, 그보다 길면 빈칸 |
| VM | 잡이나 모니터링을 지정한 VM 이름을 `;` 로 연결한다 |
| 종료 기준 VM | 종료 기준으로 지정한 VM 이름을 `;` 로 연결한다 |

- 파일은 UTF-8(BOM) CSV 다.
- 순서 실행의 시각은 점프 VM 의 현지 시각이다. 점프 VM 과 성능 데이터의 시간대가 같아야 한다.
- 순서 실행의 파일은 실행한 순서대로 행이 들어간다.
- 비교에 쓰는 기준은 이 생성기에서 정하지 않는다. 성능 리포트 생성기에서 정한다. v1.4 의 저장 창에 있던 `비교 기준 (첫 줄)` 칸은 v2.2 부터 없다.

## 10. 제한과 주의

순서 실행에 해당하는 것은 다음과 같다.

- 실제 ESX 호스트, VM, 점프 VM 에서 아직 실행하지 않았다. 12절의 '실제 장비에서 확인할 것' 을 먼저 본다. 처음에는 중요하지 않은 VM 한 대로 P 블록과 S 블록을 실행해 본다.
- 설정 값이 현재 값과 다른 케이스에서는 그 케이스의 VM 이 자동으로 종료되고 다시 켜진다. 그 VM 에서 실행 중인 다른 작업이 있으면 끊긴다.
- 재부팅해야 적용되는 ESX 호스트 설정은 다루지 않는다. 수동으로 적용하고 재부팅한 뒤에 실행한다.
- 설정을 적용하는 케이스의 VM 은 탭 4 에 적은 ESX 호스트에 등록돼 있어야 한다. DRS 가 VM 을 다른 호스트로 옮겼으면 VM 을 찾지 못해 아무것도 바꾸지 않고 멈춘다.
- 탭 4 에 적지 않은 VM 은 건드리지 않는다. 같은 ESX 호스트에서 켜져 있는 다른 VM 은 그대로 켜져 있다. ESX 호스트가 있는 케이스에서 이름이 있는 VM 행은 잡이 없어도 그 케이스의 VM 이다(전원 칸대로 켜거나 끈다).
- 점프 VM 작업 폴더와 로그 폴더에 쓸 수 없으면(디스크 가득, 계정의 디스크 quota) 진행이 접속 스크립트와 상태 파일을 쓰지 못한다. 실행(S)과 점검(P)은 시작 전에 두 폴더에 1 MB 를 써 보고, 쓸 수 없으면 시작하지 않는다. 홈 폴더 용량이 작으면 두 폴더를 큰 디스크로 옮긴다(7.1절).
- 잡의 프로세스는 잡 시작 1분 뒤에 처음 확인한다. 1분 안에 끝나는 잡은 보지 못해 10분 뒤에 멈춘다.
- 종료 판정은 프로세스가 끝난 뒤 다음 확인 때 난다. 확인 간격이 30분이면 최대 30분 늦다. 결과 CSV 의 `job_end` 는 프로세스가 처음으로 보이지 않은 확인 시각이다.
- 같은 케이스의 VM 시계가 서로 다르면 잡이 그만큼 어긋나 시작한다. 30초를 넘으면 로그에 `WARN` 이 남는다.
- VM 켜기 작업은 최대 90분을 기다린다(`settings.json` 의 `seq_poweron_wait_min`). 90분 안에 끝나지 않으면 실패로 처리하고 설정을 이전 값으로 복원한다. 로그의 `powered on (vim-cmd vmsvc/power.on took N s)` 줄에 실제로 걸린 초가 남는다.
- VM 에 전원 켜기 질문(복사했는지 이동했는지 등)이 대기 중이면 `power.on` 이 끝나지 않아 위 한도까지 기다린다. 진행이 `power on <VM>` 단계에서 오래 머물면 ESX 에서 그 VM 의 질문을 확인한다.
- ESX 를 재부팅하면 root crontab 의 줄이 지워진다(Broadcom KB 323138). 진행 중에 ESX 를 재부팅하지 않는다.
- 점프 VM 을 재부팅하면 진행이 끝난다. 상태가 `died` 로 보인다. 5.8절의 방법으로 이어서 실행한다. 대기(queued) 중이던 실행도 끝나므로 다시 생성해 붙여넣는다.
- 잡을 확인하지 않는 케이스는 잡이 실제로 시작됐는지, 끝났는지 보지 않는다. 잡 명령이 틀려 시작되지 않아도 진행은 정해진 시각대로 계속된다. 처음 쓰는 명령은 잡을 확인하는 케이스(시작 시각 자동)로 한 번 실행해 보거나 VM 에서 직접 확인한다.
- 점프 VM 과 VM 과 ESX 의 시계가 크게 다르지 않아야 한다. 시각은 가장 늦은 시계를 기준으로 정한다.
- ESX 호스트의 `/tmp/tcgen/` 에 적용 스크립트와 실행 기록(`apply.log`, `state-<실행 ID>-<번호>.json`)이 남는다. ESX 를 재부팅하면 지워진다.

두 진행 방식에 공통인 것은 다음과 같다.

- 블록은 점프 VM 의 셸이 csh, tcsh, bash 중 무엇이든 같은 블록을 쓴다. 터미널이 줄바꿈을 CR+LF 로 보내도 된다.
- 명령에 `!`, 탭, 한글을 쓸 수 없다(한글은 변수 이름에만). csh 가 붙여넣는 글의 `!` 를 이전 명령 불러오기로, 탭을 자동 완성으로 처리하기 때문이다.
- 이름(케이스, 호스트, 명령어 명, 프로파일 이름)은 영문, 숫자, `.` `_` `-` 만 쓴다. 순서 실행에서 호스트와 VM 이름은 영문이나 숫자로 시작해야 한다.
- VM 비밀번호는 점프 VM 의 `~/.tcgen/vmpw`(순서 실행은 작업 폴더의 `vmpw`)에만 저장한다(본인만 읽기). 생성기 파일, CSV, 블록에는 비밀번호가 들어가지 않는다. ESX 비밀번호는 저장하지 않는다.
- 비밀번호를 고칠 때는 점프 VM 에서 `sh ~/.tcgen/setpw` 를 실행한다.

## 11. 자주 나오는 출력

| 출력 | 뜻과 할 일 |
| :-- | :-- |
| `FAILED  .../tcrun (sha256 differs. Paste block A again. Check the free space and quota of ...)` | A 블록을 붙여넣는 중에 글자가 빠졌거나 작업 폴더에 쓸 수 없다. 작업 폴더의 여유 공간을 확인하고 A 블록을 다시 붙여넣는다 |
| `1 MB cannot be written in ... (disk full or disk quota ...)` | 작업 폴더나 로그 폴더에 쓸 수 없다. 설정 영역에서 두 폴더를 여유 공간이 있는 폴더로 바꾸고 A 블록을 다시 붙여넣은 뒤 다시 생성한다 |
| `==== tcrun on this jump VM is not installed, tcgen is 2.6` | A 블록을 붙여넣지 않았다 |
| `==== plan FAILED (sha256 differs)` | P 블록이나 S 블록을 붙여넣는 중에 글자가 빠졌거나 작업 폴더에 쓸 수 없다. 여유 공간을 확인하고 그 블록을 다시 붙여넣는다 |
| `==== esx01: run ... was already started on this jump VM` | 같은 S 블록을 두 번 붙여넣었다. 다시 실행하려면 다시 생성한다 |
| `queued:  run ... esx esx01   waiting for run ...` | 같은 ESX 호스트의 앞 실행이 진행 중이라 대기한다. 앞 실행이 `done` 으로 끝나면 스스로 시작한다 |
| `==== esx01: not started. run ... ended as paused and left case ... open` | 앞 실행이 줄을 남긴 채 멈췄다. `sh ~/.tcgen/tcrun cancel esx01` 로 정리한 뒤 같은 S 블록을 다시 붙여넣는다 |
| `==== esx01: not started. case ... is still open ... the first case of this run has no start time` | 앞 실행의 마지막 케이스(잡 확인 안 함, 끝나는 시각 없음)의 모니터링과 crontab 줄이 남아 있고 이 실행의 첫 케이스가 자동이다. 첫 케이스에 시작 시각을 적어 다시 생성하거나 `tcrun cancel esx01` 로 남은 줄을 먼저 지운다 |
| `ssh key login failed ... Permission denied` | ESX 호스트에 키가 없다. 6절 |
| `==== <VM> FAILED (ssh exit 255)` (B, D 블록) | VM 접속이 안 된다. 계정과 비밀번호(`sh ~/.tcgen/setpw`)를 확인한다 |

자동 시험은 가짜 명령으로 실행한다. 아래 항목은 실제 장비에서만 확인된다. 처음 쓸 때 P 블록의 출력과 진행 로그로 하나씩 확인한다.

| 항목 | 가짜 환경에서 가정한 것 | 확인 방법 |
| :-- | :-- | :-- |
| `vim-cmd vmsvc/getallvms` 의 출력 | 줄이 `vmid 이름 [데이터스토어] 경로.vmx ...` 형태 | P 블록의 `TCGEN-VM` 줄에 vmid 와 vmx 경로가 맞게 나오는지 |
| `vim-cmd vmsvc/get.summary` 의 `vmPathName` | `vmPathName = "[데이터스토어] 경로.vmx"` 형태. 없으면 getallvms 의 값을 쓴다 | 위와 같음 |
| `vim-cmd vmsvc/power.getstate` 의 출력 | `Powered on`, `Powered off`, `Suspended` 가운데 하나가 들어 있다 | P 블록의 `power=on` |
| `power.shutdown` 이 안 될 때(VMware Tools 없음) | 종료 코드가 0 이 아니거나 출력에 `fault` 가 들어 있다 | 진행 로그의 `guest shutdown is not possible` |
| `esxcli system settings advanced list -o` 의 출력 | `Type: integer` 또는 `string`, `Int Value:`, `String Value:` 줄 | P 블록의 `TCGEN-HOST` 줄의 현재 값 |
| ESX 의 `python3` | 3.5 이상. `/tmp/tcgen/` 의 스크립트를 `python3 <파일>` 로 실행할 수 있다 | P 블록의 `python3 found` 와 설정 비교 줄 |
| `esxcli vm process list` 의 출력 | VM 마다 `Display Name:`, `World ID:`, `VMX Cartel ID:` 줄이 있다(KB 1014165 의 형식) | 1GB page 를 쓰는 VM 을 켠 뒤 진행 로그의 `1GB page backing complete` |
| ssh 의 `-o LogLevel=ERROR` | 로그인 배너와 `Permanently added` 안내를 출력하지 않고, 접속 실패와 로그인 거부 같은 오류는 출력한다(OpenSSH 는 배너를 INFO 단계에서만 출력) | P 블록과 진행 로그에 배너 글이 섞이지 않는지 |
| `vsish -e get /memory/lpage/vmLpage/<world ID>` | `Current number of 1GB page backings:`, `1GB page backing attempts failed:` 줄이 있다. 앞선 시험에서 VM 을 켤 때 읽던 노드와 형식(사용자 확인 2026-09-23) | 위와 같음. 읽지 못하면 진행 로그에 `WARN ... could not be read` 가 남는다 |
| ESX 의 `/etc/ssh/keys-root/authorized_keys` | 줄을 추가하면 root 키 접속이 된다. 재부팅 뒤에도 남는지는 확인하지 않았다 | `sh ~/.tcgen/esxssh <ESX> hostname` |
| ESX 의 `sh`(busybox), `sha256sum`, `/bin/echo` | here-document, `read -r`, `printf` 가 dash 와 같게 동작 | 진행 로그의 `registered on esx` |
| ESX crond | `cron.update` 에 root 를 쓰면 1분 안에 crontab 을 다시 읽는다 | ESX 모니터링이 등록한 분에 시작하는지 |
| VM 의 cron | 등록 75초 뒤의 분에 새 줄을 실행한다 | 모니터링과 잡이 등록한 분에 시작하는지 |
| VM 의 `pgrep -f`, `date -d @<초>` | procps 의 pgrep, GNU date | P 블록의 VM 줄, 진행 로그의 `check` 줄 |
| 점프 VM 의 `setsid`, `base64 --decode`, `gzip`, `sha256sum` | util-linux, coreutils | A 블록의 `OK` 두 줄, S 블록의 `started:` |
| 터미널을 닫은 뒤의 진행 | `setsid` 로 시작한 진행은 터미널을 닫아도 계속된다. 점프 VM 이 로그아웃할 때 사용자 프로세스를 모두 끝내게 설정돼 있으면(systemd-logind 의 `KillUserProcesses=yes`) 끝난다 | S 블록을 붙여넣고 터미널을 닫은 뒤 다시 접속해 `sh ~/.tcgen/tcrun status` |
| 300줄쯤 되는 A 블록 붙여넣기 | 터미널이 글자를 빠뜨리지 않는다. 빠뜨리면 `FAILED` 가 나온다 | A 블록의 `OK` 두 줄 |

## 13. v1.4 로 돌아가는 방법

v2 는 v1.4 의 프로그램, 데이터 폴더(`tcgen_data`), 설정 폴더(`%APPDATA%\tcgen`)를 고치지 않는다. v1.4 를 그대로 다시 실행하면 된다.

1. 점프 VM 에서 순서 실행이 진행 중이면 `sh ~/.tcgen/tcrun stop` 으로 멈춘다. `sh ~/.tcgen/tcrun status` 로 `running` 이 없는지 확인한다.
2. PC 에서 v1.4 를 실행한다(`dist\tcgen\tcgen.exe` 또는 v1.4 소스 폴더의 `run_gui.bat`). v1.4 의 데이터가 v2 를 쓰기 전 상태 그대로 보인다. v2 에서 입력한 내용은 `tcgen2_data` 에만 있다.
3. 점프 VM 의 `~/.tcgen/vmssh`, `askpass`, `setpw`, `vmpw` 는 v1.4 와 같은 파일이다. v1.4 의 B 블록과 D 블록을 그대로 붙여넣을 수 있다. A 블록을 다시 붙여넣을 필요가 없다.
4. v2 가 VM crontab 에 남긴 줄이 있으면 지운다. 표식이 v1.4 와 같은 `# tcgen 케이스이름 호스트` 이므로 8.5절의 명령이나 v1.4 의 D 블록으로 지운다.

v2 가 추가한 것을 지우려면 다음과 같이 한다. 지우지 않아도 v1.4 의 동작에는 영향이 없다.

| 위치 | 지울 것 |
| :-- | :-- |
| 점프 VM | `~/.tcgen/tcrun`, `tcgen_apply.py`, `esxssh`, `postsetup`, `id_esx`, `id_esx.pub`, `runs/` 와 점프 VM 로그 폴더 |
| ESX 호스트 | `/etc/ssh/keys-root/authorized_keys` 에서 점프 VM 의 키 줄, `/tmp/tcgen/` |
| 데이터스토어 | VM 폴더의 `<이름>.vmx.tcgen-<시각>` (설정을 적용하기 전의 vmx 복사본) |
| PC | `tcgen2_data`, `%APPDATA%\tcgen2`, `dist\tcgen2` |

v2 가 적용한 ESX 호스트 옵션과 vmx 의 키는 v1.4 로 돌아가도 그대로 남는다. 이전 값은 진행 로그의 `TCGEN-SET`, `TCGEN-HOST` 줄과 vmx 복사본에서 확인한다.

테스트 기록 CSV 를 v1.4 와 v2 가 같은 파일로 쓰는 경우(3.2절), v2 가 머리글 끝에 추가한 열(진행 방식, 설정, 실행 ID)은 v1.4 가 이어 쓸 때 빈칸으로 남는다.

## 14. 개발 자료

구조, 설계 규칙, 고치는 절차는 `DEVELOPER.md` 에 있다. 순서 실행에서 PC 가 점프 VM 에 넘기는 plan 의 형식은 `DEVELOPER.md` 5절에 있다.

- plan 은 줄 단위 글 파일이다. 첫 낱말이 종류(`CASE`, `VM`, `AH`, `AV`, `MS`, `JOB`, `PROC`, `MX`, `EMS`, `EMX`, `END` 등), 둘째 낱말이 케이스 번호다.
- 점프 VM 의 진행 스크립트는 plan 을 `grep`, `sed`, `cut` 으로만 읽는다. plan 의 글을 셸 명령으로 실행하지 않는다.
- `jump\tcrun.sh` 나 `jump\tcgen_apply.py` 를 고친 뒤에는 `python tools\make_payload.py` 를 실행하고, 점프 VM 에 A 블록을 다시 붙여넣는다.
