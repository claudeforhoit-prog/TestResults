# 테스트 실행 명령 생성기 (tcgen) v2.13

> 이 생성기를 고치거나 AI 로 다시 만들 때는 `DEVELOPER.md`(구조, 설계 규칙, plan 형식, 시험)를 먼저 읽는다.

테스트 케이스 표에 케이스마다 잡을 시작할 시각을 적으면, 점프 VM 터미널에 붙여넣을 블록을 만든다.
점프 VM 의 진행 스크립트(tcrun)가 그 시각에 잡이 시작되도록 VM 의 crontab 에 등록하고, 잡 시작 전에 설정 적용, 구성 스냅샷, 모니터링 시작을 한다.

v2 는 v1.4 와 따로 설치하고 따로 실행한다. 프로그램 이름, 데이터 폴더, 설정 폴더가 모두 다르다. v1.4 는 지우지 않고 그대로 둔다(13절).

## 1. 사용 순서

| 순서 | 할 일 | 절 |
| :-- | :-- | :-- |
| 1 | 탭 1 에 잡 명령, 탭 2 에 모니터링 명령, 탭 3 에 설정 프로파일을 입력한다 | 5절 |
| 2 | 탭 4 에 케이스를 입력하고 `시작 시각` 칸에 잡을 시작할 시각을 적는다. `잡 시작 (환산)` 칸에서 계산된 시각을 확인한다 | 5.5절 |
| 3 | [명령어 생성] 을 누른다. 탭 5 에 타임라인과 블록 A, P, S, D 가 나온다 | 6.1절 |
| 4 | 처음 한 번(그리고 생성기의 판이 달라졌을 때) A 블록을 점프 VM 터미널에 붙여넣고 ESX 호스트에 키를 등록한다 | 6.2절 |
| 5 | P 블록을 붙여넣어 점검한다. 마지막 줄이 `CHECK RESULT: OK` 인지 확인한다 | 6.3절 |
| 6 | S 블록을 붙여넣는다. 점프 VM 로그 폴더의 `tcrun-<실행 ID>-jobs.csv` 에서 crontab 등록 결과를 확인한다 | 6.4절, 8절 |
| 7 | 실행한 케이스를 탭 4 에서 적용 체크한다. 필요하면 [리포트용 CSV 저장] 으로 성능 리포트 생성기의 케이스 정보 파일을 만든다 | 5.5절, 9.2절 |

잡 시작 전에 점프 VM 이 하는 일은 다음과 같다. T 는 케이스의 잡 시작 시각이고, 분 값은 설정 영역의 기본값이다.

| 케이스 | S 블록 실행 직후 | T-30분 | T-10분 | T-5분 | T | 잡 실행 중 |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 설정 변경이 없는 케이스 | crontab 에 잡 등록 | (없음) | 구성 스냅샷 | 모니터링 시작 | 잡 시작 | VM 접속 없음 |
| 설정 변경이 있는 케이스 | (없음) | VM 종료 -> 설정 적용 -> VM 전원 ON -> crontab 에 잡 등록 | 구성 스냅샷 | 모니터링 시작 | 잡 시작 | VM 접속 없음 |

- 잡은 탭 4 에 적은 시작 시각에 시작한다. 진행 스크립트는 시작 시각을 변경하지 않는다.
- 진행 스크립트는 잡이 끝났는지 확인하지 않는다. 다음 케이스의 시작 시각은 앞 케이스의 잡이 끝나는 때를 보고 사용자가 정한다.

## 2. v2.12, v2.13 에서 달라진 것

v2.13 은 v2.12 에 VCF Operations 기록을 더했다. 설정 영역에 `Operations 주소`, `Operations 계정`, `Operations 암호` 칸이 생겼다. 주소를 적으면 구성 스냅샷 때 점프 VM 이 VM 설정과 케이스의 호스트 옵션을 Operations 에 기록한다(7.4절). 주소를 비우면 v2.12 와 같게 동작한다. v2.12 에서 올릴 때도 A 블록을 다시 붙여넣는다.

v2.11 을 쓰던 경우에 확인할 것은 다음과 같다.

| 항목 | v2.11 | v2.12 |
| :-- | :-- | :-- |
| 진행 방식 | 설정 영역에서 `순서 실행`, `시각 지정` 을 고름 | 칸이 없다. 방식은 하나다(시작 시각에 잡 시작). `시각 지정` 방식은 화면에서 고를 수 없다 |
| 시작 시각의 `자동` | 앞 케이스의 잡 프로세스가 끝난 것을 확인한 뒤 시작 | 없다. 잡이 있는 케이스는 시작 시각을 적어야 한다. `자동` 이라고 적혀 있던 칸은 `입력 필요` 로 보인다 |
| `+간격` 의 기준 | 같은 ESX 호스트의 바로 앞 케이스 | 표의 바로 윗줄 케이스. ESX 호스트가 달라도 윗줄이 기준이다 |
| 계산된 잡 시작 | 화면에 없음 | `잡 시작 (환산)` 칸에 보인다 |
| crontab 등록 시점 | 케이스마다 잡 시작 60분 전부터 준비한 뒤 등록 | 설정 변경이 없는 케이스는 S 블록 직후에 한꺼번에 등록. 설정 변경이 있는 케이스는 잡 시작 30분 전에 변경하고 등록 |
| 잡 시작 시각 | 변경 작업 뒤 대기, 스냅샷 뒤 대기 때문에 늦어질 수 있음 | 변경하지 않는다. 등록할 수 없으면 등록하지 않고 기록에 이유를 남긴다 |
| 구성 스냅샷 | 줄을 등록하기 전에 읽음 | 모든 케이스에서 잡 시작 10분 전에 읽음. 줄은 그 전에 등록돼 있다 |
| 설정 영역 | 변경 작업 뒤, 스냅샷 뒤, 케이스 사이 간격, 잡 종료 확인 간격, 시작 시각 준비(60분) | `잡 시작 기준:` 설정 적용 30분 전, 구성 스냅샷 10분 전, 모니터링 시작 5분 전. 그리고 잡 시작 최소 간격 |
| 탭 1 의 프로세스 이름 | 잡 종료 확인에 사용 | 열이 없다 |
| 등록 결과 | 진행 로그에서 찾음 | `tcrun-<실행 ID>-jobs.csv` 에 케이스, ESX 호스트, VM, 잡 시작, 등록 여부가 남는다 |
| 한 VM 에서 등록이 안 될 때 | 다른 VM 의 줄을 지움. VM 의 응답이 늦으면 다른 VM 의 잡이 먼저 시작될 수 있었음 | VM 접속마다 첫 실행 시각 15초 전까지 남은 시간만 주고, VM 도 자기 시계가 그 시각을 지났으면 줄을 받지 않는다. 확인할 VM 은 `jobs.csv` 의 그 VM 행에 적는다(7.3절) |
| `tcrun cancel` 이 접속하지 못한 VM | 지운 것으로 출력하고 그 줄은 남음 | 그 VM 이름을 출력한다. 다시 실행하면 남은 줄만 지운다(6.5절) |
| 탭 5 | 결과 글, 블록, 실행 계획 | 타임라인 표 추가. 오류와 알림은 한 줄 |
| [리포트용 CSV 저장] | 시각 지정에서만 | 쓴다. 잡 시작은 `잡 시작 (환산)` 칸의 시각 |

판을 올릴 때 할 일은 다음과 같다.

1. 점프 VM 에서 진행 중인 실행이 없는지 확인한다(`sh ~/.tcgen/tcrun status`). v2.11 의 실행이 남긴 crontab 줄이 있으면 `sh ~/.tcgen/tcrun cancel` 로 지운 뒤에 판을 올린다.
2. 새 판의 A 블록을 점프 VM 에 다시 붙여넣는다. 생성기와 진행 스크립트의 판 번호가 같아야 한다(v2.12 에서 v2.13 으로 올릴 때도 같다).
3. 탭 4 에서 `잡 시작 (환산)` 칸을 확인한다. `+간격` 의 기준이 바로 윗줄로 변경됐으므로, ESX 호스트가 섞여 있는 표는 시각이 v2.11 과 다르게 계산된다.
4. v2.11 에서 생성하고 아직 적용 체크하지 않은 케이스는 적용 체크를 먼저 한다. 적용 체크한 케이스의 시작 시각은 생성한 때의 날짜 시각으로 고정된다.
5. 설정 파일의 `시작 시각 준비` 가 예전 기본값 60분이면 `설정 적용` 30분 전으로 한 번 변경된다. 직접 고친 값은 그대로 둔다.

이전 판을 받는 방법은 14절, 판별 변경 내역은 15절에 있다.

## 3. 구성

| 파일 | 내용 |
| :-- | :-- |
| `tcgen_app.py` | 화면 |
| `tcgen_core.py` | 시작 시각 계산, 검증, plan 과 붙여넣기 블록, 타임라인, 기록 파일 저장 |
| `tcgen_payload.py` | 점프 VM 에 설치할 두 파일의 내용(자동 생성. 직접 고치지 않는다) |
| `jump\tcrun.sh` | 점프 VM 의 진행 스크립트 원본. 설치되면 `~/.tcgen/tcrun` 이 된다 |
| `jump\tcgen_apply.py` | ESX 호스트에서 실행하는 설정 적용 스크립트 원본 |
| `tools\make_payload.py` | `jump\` 의 두 파일을 `tcgen_payload.py` 로 옮긴다 |
| `run_gui.bat` | 실행. `tcgen2.exe` 가 있으면 그것을, 없으면 설치된 Python 으로 실행한다 |
| `build_windows.bat` | Windows 실행 파일(`dist\tcgen2\tcgen2.exe`) 빌드 |
| `tests\` | 자동 시험과 화면 점검(`gui_smoke.py`) |

Python 표준 라이브러리만 쓴다. 추가 패키지는 필요 없다.

## 4. 설치와 실행

- Python 3.8 이상이 있는 PC: `run_gui.bat` 을 실행한다. `python tcgen_app.py` 와 같다.
- Python 이 없는 PC: Python 과 인터넷이 있는 PC 에서 `build_windows.bat` 을 실행한다. 만들어진 `dist\tcgen2` 폴더를 통째로 복사해 `tcgen2.exe` 를 실행한다.

PyInstaller 설치 단계에서 내려받기가 실패하면, 빌드 스크립트가 pypi.org 와 files.pythonhosted.org 의 인증서 확인을 생략하는 옵션(`--trusted-host`)으로 한 번 더 시도한다.
회사망 보안 장비가 HTTPS 를 검사하면 pip 가 인증서를 확인하지 못해 이렇게 실패한다. 이 옵션은 그 실행에만 적용되고 PC 설정에 남지 않는다.
그래도 `FAILED while installing PyInstaller` 가 나오면 인터넷 연결이나 회사망 프록시를 확인한다.
회사에 Python 패키지 저장소가 있으면 `py -3 -m pip config --user set global.index-url https://<저장소 주소>/simple` 로 한 번 지정한 뒤 빌드한다.

### 4.1 데이터 폴더

설정, 명령 목록, 설정 프로파일, 테스트 케이스 표는 생성기 폴더가 아니라 데이터 폴더에 저장한다. 데이터 폴더 기본 위치는 `C:\Users\<계정>\tcgen2_data` 이다. 생성기를 다시 빌드하거나 다른 폴더로 옮겨도 데이터 폴더는 그대로 남는다. 다섯 파일 모두 값이 달라질 때마다 자동 저장되고, 생성기를 다시 열면 불러온다. 저장 버튼은 없다.

| 파일 (데이터 폴더 기준) | 내용 |
| :-- | :-- |
| `settings.json` | 설정 영역의 값과 화면에 없는 값(5.1절) |
| `run_commands.csv` | 탭 1 실행 명령 목록 |
| `monitor_commands.csv` | 탭 2 모니터링 명령 목록 |
| `profiles.json` | 탭 3 설정 프로파일. 파일이 없으면 처음 실행 때 기본 프로파일 12개로 만든다(5.4절) |
| `test_cases.json` | 탭 4 테스트 케이스 표와 적용 체크 상태. 테스트 케이스 파일을 따로 지정하지 않았을 때 쓴다(4.3절) |
| `testcases\test_record.csv` | 테스트 기록 CSV 기본 위치 |
| `testcases\testcaselogging-년월일시분초.csv` | 생성할 때마다 만드는 로그 (기본 위치) |
| `backup\년월일시분초_before_restore\` | [백업 불러오기] 직전의 데이터 파일 |
| `backup\auto\년월일_AM\`, `backup\auto\년월일_PM\` | 하루 두 번 자동 백업(4.4절) |

| 설정 파일 | 내용 |
| :-- | :-- |
| `C:\Users\<계정>\AppData\Roaming\tcgen2\config.json` | [데이터 폴더 변경] 으로 정한 데이터 폴더 위치, 마지막으로 고른 백업 위치. 이 파일이 없으면 기본 위치를 쓴다 |

- 명령 목록은 화면에서만 고친다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다.
- 테스트 기록 CSV 나 로그 폴더를 데이터 폴더 밖으로 지정했다면 그 파일은 [설정 백업] 에 들어가지 않는다.
- `build_windows.bat` 을 다시 실행하면 PyInstaller 가 `dist\tcgen2` 폴더를 통째로 지우고 새로 만든다. 데이터는 데이터 폴더에 있어 지워지지 않는다.

### 4.2 v1 의 데이터 가져오기

v2 를 처음 실행할 때 `tcgen2_data` 에 데이터가 없고 v1 의 데이터 폴더에 데이터가 있으면, 아래 네 파일을 `tcgen2_data` 로 복사하고 안내 창을 한 번 보인다.

- 복사하는 파일: `settings.json`, `run_commands.csv`, `monitor_commands.csv`, `test_cases.json`
- v1 의 데이터 폴더: `%APPDATA%\tcgen\config.json` 에 적힌 폴더. 그 파일이 없으면 `C:\Users\<계정>\tcgen_data`
- v1 의 폴더와 파일은 읽기만 한다. 내용도 수정 시각도 그대로 둔다.
- 테스트 기록과 로그(`testcases\`), 백업(`backup\`)은 복사하지 않는다.
- v1 설정의 테스트 기록 CSV 나 로그 폴더가 v1 데이터 폴더 안을 가리키면 `tcgen2_data` 의 같은 위치로 고쳐 저장한다. v2 가 v1 폴더에 기록하지 않게 하기 위해서다. v1 데이터 폴더 밖의 경로는 그대로 두므로, 그 경우 v1.4 와 v2 가 같은 기록 파일에 이어 쓴다.
- v1 데이터의 케이스에는 `시작 시각` 칸이 없다. 가져온 뒤 탭 4 에서 시작 시각을 적는다.

### 4.3 테스트 케이스 파일 (불러오기, 다른 이름으로 저장)

탭 4 의 테스트 케이스 표를 파일로 저장해 두고 필요할 때 불러온다. 시험하는 서버나 시험 종류마다 파일을 따로 두는 데 쓴다.
설정 영역 맨 위의 `테스트 케이스 파일` 칸에 지금 쓰는 파일이 보인다.

| 상태 | 동작 |
| :-- | :-- |
| 파일을 지정하지 않음 (처음 상태) | 데이터 폴더의 `test_cases.json` 을 자동으로 만들고, 표를 고칠 때마다 거기에 자동 저장한다 |
| [다른 이름으로 저장] 으로 파일을 지정 | 지금 표를 그 파일에 저장한다. 그 뒤로는 표를 고칠 때마다 그 파일에 자동 저장한다. 이전 파일은 마지막 상태로 남는다 |
| [불러오기] 로 파일을 지정 | 그 파일의 표를 탭 4 에 불러온다. 그 뒤로는 표를 고칠 때마다 그 파일에 자동 저장한다 |

- 파일에는 케이스 행과 VM 행의 모든 칸이 들어간다: 적용 체크, 케이스 이름, 설명, ESX 호스트, VM 이름, VM 전원, 잡, 모니터링, 설정 프로파일 선택, 최대 대기, 테스트 그룹, 종료 기준 VM, 시작 시각. 불러오면 저장한 상태 그대로 보인다.
- 실행 명령(탭 1), 모니터링 명령(탭 2), 설정 프로파일(탭 3), 설정 영역의 나머지 값은 어느 파일을 쓰든 같이 쓴다. 고치면 모든 파일에 적용된다.
- `테스트 기록 CSV` 와 `로그 폴더` 는 테스트 케이스 파일마다 마지막에 쓰던 값을 기억한다. 파일을 불러오면 그 값으로 함께 변경된다. 처음 쓰는 파일은 지금 값을 그대로 쓴다.
- 파일 형식은 CSV(UTF-8, BOM)다. 파일 이름을 `.json` 으로 끝내면 `test_cases.json` 과 같은 JSON 으로 저장한다. [불러오기] 는 두 형식을 모두 읽는다.
- 파일을 바꾸면 탭 5 의 이전 생성 결과를 지운다. 다른 케이스의 블록을 붙여넣는 실수를 막기 위해서다. 점프 VM 에서 진행 중인 실행에는 영향이 없다.
- 생성기를 다시 열면 마지막에 쓰던 파일을 불러온다. 그 파일을 찾지 못하거나 읽지 못하면 그 파일은 그대로 두고 데이터 폴더의 `test_cases.json` 으로 바꾼 뒤 알린다.
- 지정하지 않은 상태로 돌아가려면 [불러오기] 에서 데이터 폴더의 `test_cases.json` 을 고른다.
- `테스트 기록 CSV`(생성 내용을 적어 두는 파일)는 테스트 케이스 파일이 아니다. [불러오기] 에서 고르면 불러오지 않고 알린다.
- `시작 시각` 칸은 적은 그대로 저장된다(날짜 시각, `+8:00`). 적용 체크한 케이스는 날짜 시각으로 고정된 값이 저장된다(5.5절). v2.11 까지의 파일에 `자동` 이라고 적혀 있던 칸은 `입력 필요` 로 보이므로 시각을 적는다.

테스트 케이스 CSV 의 열은 다음과 같다. 케이스마다 `케이스` 행 하나가 있고 그 아래에 그 케이스의 `VM` 행이 온다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 구분 | `케이스` | `VM` |
| 적용 | 적용 체크했으면 `예` | 빈칸 |
| 케이스 이름, 설명, ESX 호스트 | 값 | 빈칸 |
| VM 이름, 잡 | 빈칸 | 값. 잡이 없으면 `(없음)` |
| 모니터링 | ESX 모니터링 명령어 명 | 그 VM 의 모니터링 명령어 명 |
| 설정 | ESX 호스트 설정 프로파일 이름 | 그 VM 의 설정 프로파일 이름 |
| 최대 대기, 테스트 그룹 | 값 | 빈칸 |
| 종료 기준 VM | 빈칸 | 기준이면 `기준` |
| 간격, 잡 시작, 모니터링 중지, 모니터링 중지 시각 | 화면에서 고를 수 없는 시각 지정 방식의 값(파일 형식을 유지한다) | 빈칸 |
| 잡 종료 (리포트) | 리포트용 CSV 의 잡 종료 시각. 비우면 성능 리포트 생성기가 정한다 | 빈칸 |
| 시작 시각 (순서 실행) | 잡을 시작할 시각(날짜 시각, `+간격`). 열 이름은 예전 판과 같다 | 빈칸 |
| 전원 | 빈칸 | 그 VM 의 전원. `켬` 또는 `끔`. 이 열이 없는 예전 파일은 모두 켬으로 읽는다 |
| 모니터링 중지 (적용 때 고정) | 시각 지정 방식의 값(파일 형식을 유지한다) | 빈칸 |

- 한 칸에 이름이 여러 개면 `; ` 로 구분한다.
- 이 파일은 화면에서 고치는 것을 권한다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다. 읽지 못하게 된 경우에는 자동 백업(4.4절)의 `case_file_<파일 이름>` 을 다른 폴더에 복사한 뒤 [불러오기] 로 고른다(백업 폴더 안의 파일을 바로 고르면 그 뒤로 고친 내용이 그 백업 폴더 안에 저장되고, 그 폴더는 보관 수인 최근 60개를 넘으면 지워진다).

### 4.4 자동 백업 (하루 두 번)

생성기가 켜져 있는 동안 오전에 한 번, 오후에 한 번 데이터 파일을 데이터 폴더의 `backup\auto\` 에 복사한다. 따로 할 일은 없다.

| 항목 | 내용 |
| :-- | :-- |
| 시점 | 생성기를 켤 때와 그 뒤 30분마다 확인한다. 그 시간대(0시~12시 전은 `AM`, 12시부터는 `PM`)의 백업이 아직 없으면 만든다 |
| 위치 | `<데이터 폴더>\backup\auto\<년월일>_AM\`, `<년월일>_PM\` |
| 들어가는 파일 | `settings.json`, `run_commands.csv`, `monitor_commands.csv`, `profiles.json`, `test_cases.json`, 그리고 지정한 테스트 케이스 파일의 사본 `case_file_<파일 이름>` |
| 보관 | 최근 60개(30일치). 그보다 오래된 것은 지운다 |
| 되돌리기 | [백업 불러오기] 에서 그 폴더를 고른다. 지정한 테스트 케이스 파일도 그 폴더의 사본 `case_file_<파일 이름>` 의 내용으로 변경된다(변경하기 전 내용은 데이터 폴더의 `backup` 아래에 복사해 둔다). 테스트 케이스 파일만 되돌리려면 그 사본을 다른 폴더에 복사한 뒤 [불러오기] 로 고른다 |

- 생성기를 켜지 않은 날에는 백업을 만들지 않는다. 그날은 데이터가 바뀌지 않기 때문이다.
- 테스트 기록 CSV 와 로그 파일은 자동 백업에 넣지 않는다. 이 파일까지 복사하려면 [설정 백업] 을 쓴다.

## 5. 입력: 설정, 명령, 설정 프로파일, 테스트 케이스

칸을 두 번 누르거나 행을 고르고 Enter(또는 F2)를 누르면 고친다. 값은 달라질 때마다 데이터 폴더에 자동 저장된다. 저장 버튼은 없다.

### 5.1 설정 영역

| 항목 | 내용 |
| :-- | :-- |
| 테스트 케이스 파일, [불러오기], [다른 이름으로 저장] | 탭 4 의 표를 저장하는 파일(4.3절). 지정하지 않으면 데이터 폴더에 자동 저장한다 |
| 테스트 기록 CSV [찾기] | 기존 파일을 고르거나 새 파일 이름을 적는다. 생성할 때마다 케이스 하나에 한 행을 추가한다(9.1절) |
| 로그 폴더 [찾기] | PC 의 폴더. 생성할 때마다 `testcaselogging-년월일시분초.csv` 를 만든다 |
| VM 접속 계정 | 점프 VM 에서 ssh 로 접속할 계정. 비우면 점프 VM 의 현재 계정으로 접속한다 |
| 잡 시작 기준: 설정 적용 N분 전 | 기본 30. 설정이나 VM 전원이 호스트와 다른 케이스는 잡 시작 N분 전에 VM 종료, 설정 적용, VM 전원 ON 을 한다(7.2절) |
| 잡 시작 기준: 구성 스냅샷 N분 전 | 기본 10. 모든 케이스에서 잡 시작 N분 전에 구성 스냅샷을 읽는다(7.4절). `설정 적용 N분 전` 보다 작아야 한다 |
| 잡 시작 기준: 모니터링 시작 N분 전 | 기본 5. 모니터링이 있는 케이스는 잡 시작 N분 전에 모니터링을 시작한다. `설정 적용 N분 전` 보다 작아야 한다 |
| 잡 시작 최소 간격 N분 | 기본 5. 모든 잡 시작은 서로 N분 이상 떨어져야 한다(ESX 호스트가 달라도). 더 가까우면 [명령어 생성] 이 오류로 알린다 |
| 점프 VM 로그 폴더 | 점프 VM 의 폴더. `/` 또는 `~/` 로 시작하고 영문, 숫자, `.` `_` `-` `/` `+` `@` `,` `:` 만 쓴다. 비우면 `~/tcgen_log`, 점프 VM 작업 폴더를 적었으면 `<작업 폴더>/log` |
| ESX 접속 주소 | 선택. `호스트이름=주소` 를 `;` 로 구분한다. 비우면 ESX 호스트 이름으로 접속한다 |
| 점프 VM 작업 폴더 | 진행 스크립트, ESX 키, VM 비밀번호, 실행 기록을 두는 점프 VM 의 폴더. 비우면 `~/.tcgen`. 변경하면 A 블록을 다시 붙여넣는다(6.2절) |
| 스냅샷 때 VM 에서 실행할 명령 | 선택. 구성 스냅샷 때 케이스의 켜져 있는 VM 마다 실행할 명령 한 줄(7.4절). 게스트 구성을 VCF Operations 에 기록하는 guest_config_push 를 VM 안의 경로로 적는다. 500자 이하이고 한글, `!`, 탭, 변수는 쓸 수 없다 |
| Operations 주소 | 선택. VCF Operations 의 이름이나 IP. 비우면 Operations 에 기록하지 않는다. 적으면 구성 스냅샷 때 점프 VM 이 VM 설정과 케이스의 호스트 옵션을 기록한다(7.4절) |
| Operations 계정 | Operations 의 로컬 계정(인증 소스 LOCAL) |
| Operations 암호 | 적고 Enter 를 누르거나 다른 칸으로 가면 암호화해 저장하고 칸을 비운다. 옆에 `저장됨` 또는 `없음` 이 보인다. 암호 자체는 저장하지 않는다. guest_config_push 의 `OPS_PASS_ENC`, `OPS_ENC_KEY` 와 같은 방식이다. 주소와 계정을 모두 지우면 저장해 둔 암호도 지운다 |
| [설정 백업] | 고른 폴더에 `tcgen2_backup_년월일시분초` 폴더를 만들고 데이터 파일과 `testcases` 폴더를 복사한다. 따로 지정한 테스트 케이스 파일도 `case_file_<파일 이름>` 으로 함께 복사한다 |
| [백업 불러오기] | 고른 백업 폴더의 데이터 파일로 현재 데이터를 교체한다. 교체 전 파일은 데이터 폴더 `backup` 아래에 복사해 둔다 |

| 키 | 기본값 | 내용 |
| :-- | :-- | :-- |
| `seq_poweron_wait_min` | 90 | ESX 의 VM 켜기 작업(`vim-cmd vmsvc/power.on`)이 끝나기를 기다리는 최대 시간(분) |

### 5.2 탭 1. 실행 명령

| 열 | 내용 |
| :-- | :-- |
| App명 | 분류용 이름 |
| 명령어 명 | 탭 4 의 잡 칸에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 잡 조건 설명 | 한글을 쓸 수 있다 |
| 경로/실행 명령 | crontab 에 한 줄로 그대로 들어간다. 절대 경로로 적는다(cron 은 홈 폴더에서 실행한다) |

- 변수: `<vm이름>` = VM 게스트 hostname, `<실행시각>` = 실행 시각 14자리(예: 20261109000000).
- 예: `/home/tester/bench/run_a.sh >> /home/tester/log/run_a-<vm이름>-<실행시각>.log 2>&1`
- 명령에 `!`, 탭, 한글은 쓸 수 없다(10절).

| 열 | 내용 |
| :-- | :-- |
| App명, 명령어 명, 설명 | 탭 1 과 같다 |
| 실행 위치 | `VM` 이면 그 VM 의 crontab 에, `ESX` 이면 ESX 호스트의 root crontab 에 등록한다 |
| 시작 명령 | 잡 시작 N분 전(설정 영역의 `모니터링 시작 N분 전`)에 실행한다 |

### 5.4 탭 3. 설정 프로파일

케이스의 잡 시작 전에 적용할 설정 묶음이다. 적용하는 때는 잡 시작 30분 전이다(설정 영역의 `설정 적용 N분 전`. 7.2절).

| 열 | 내용 |
| :-- | :-- |
| 프로파일 이름 | 탭 4 에서 고르는 이름. 영문, 숫자, `.` `_` `-` 만 사용, 중복 불가 |
| 대상 | `ESX 호스트` 또는 `VM`. 케이스 행의 설정 칸에는 대상이 ESX 호스트인 프로파일이, VM 행의 설정 칸에는 대상이 VM 인 프로파일이 나온다 |
| 설정 내용 | 칸을 두 번 누르면 여러 줄 입력 창이 열린다. 한 줄에 `키 = 값` 하나를 적는다. `#` 으로 시작하는 줄은 설명이다 |
| 설명 | 한글을 쓸 수 있다 |

대상이 VM 인 프로파일은 vmx 파일의 키를 적는다.

```
sched.mem.pin = "TRUE"
sched.cpu.affinity = 0,1,2,3
numa.nodeAffinity =
```

- vmx 파일의 줄(`키 = "값"`)을 그대로 붙여넣어도 된다. 따옴표는 벗겨서 받는다.
- 값을 비우면 그 키의 줄을 vmx 에서 지운다.
- 키는 대소문자를 구분하지 않는다. 값은 글자 그대로 비교한다(`TRUE` 와 `true` 는 다른 값으로 본다).
- CPU affinity 같은 값을 계산하는 기능은 없다. 키와 값을 직접 적는다.
- VM 을 구별하는 값이나 파일 위치를 적는 키는 넣을 수 없다: `displayName`, `uuid.bios`, `uuid.location`, `vc.uuid`, `nvram`, `config.version`, `virtualHW.version`, `.encoding`, `extendedConfigFile`, `vmxstats.filename`, `sched.swap.derivedName`, `checkpoint.vmState`, 이름이 `.fileName` 으로 끝나는 키.

대상이 ESX 호스트인 프로파일은 호스트 고급 설정을 적는다.

```
Numa.LocalityWeightActionAffinity = 0
/Cpu/HTWholeCoreThreshold = 0
```

- 이름은 `/구역/옵션` 또는 `구역.옵션` 으로 적는다. `구역.옵션` 은 점을 `/` 로 바꾸고 앞에 `/` 를 추가해 `esxcli system settings advanced` 의 이름으로 쓴다.
- 값을 비울 수 없다(호스트 옵션은 지울 수 없다).
- 재부팅해야 적용되는 호스트 설정은 넣지 않는다. 그런 설정은 수동으로 적용한다.

프로파일을 여러 개 고르면 탭 3 의 표 순서대로 합친다. 같은 키가 겹치면 아래쪽 프로파일의 값을 쓴다.

#### 기본 프로파일

생성기를 처음 실행하면(데이터 폴더에 `profiles.json` 이 없으면) 탭 3 에 아래 12개가 들어 있다. 고치거나 삭제해도 된다.

| 프로파일 이름 | 대상 | 설정 내용 | 뜻 |
| :-- | :-- | :-- | :-- |
| `lpage_1g_on` | VM | `sched.mem.lpage.enable1GPage = TRUE`, `sched.mem.pin = TRUE`, `sched.mem.prealloc = TRUE`, `sched.mem.prealloc.pinnedMainMem = TRUE`, `sched.swap.vmxSwapEnabled = FALSE` | 1GB page 키 5개 적용 |
| `lpage_1g_off` | VM | 위 다섯 키의 값을 비움 | 1GB page 키 5개 삭제 |
| `halt_in_monitor_on` | VM | `monitor_control.halt_in_monitor = TRUE`, `monitor.idleLoopSpinBeforeHalt = TRUE`, `monitor.idleLoopMinSpinUS = 50`, `monitor_control.disable_pause_loop_exiting = TRUE` | 유휴 vCPU 처리 키 4개 적용 |
| `halt_in_monitor_off` | VM | 위 네 키의 값을 비움 | 유휴 vCPU 처리 키 4개 삭제 |
| `latency_high` | VM | `sched.cpu.latencySensitivity = high` | Latency Sensitivity high |
| `latency_normal` | VM | `sched.cpu.latencySensitivity = normal` | Latency Sensitivity normal (기본값) |
| `vpmc_on` | VM | `vpmc.enable = TRUE` | vPMC 사용. 게스트 perf 의 하드웨어 이벤트 수집에 쓴다 |
| `vpmc_off` | VM | `vpmc.enable` 의 값을 비움 | vPMC 키 삭제 |
| `kstats_on` | VM | `vmx.buildType = stats`, `vmx.log.keepOld = 20` | vmx stats 빌드, vmware.log 보존 수 20 |
| `kstats_off` | VM | 위 두 키의 값을 비움 | vmx stats 빌드 키와 로그 보존 수 키 삭제 |
| `ht_wholecore_1` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 1` | 호스트 옵션 Cpu.HTWholeCoreThreshold 를 1 로 변경 |
| `ht_wholecore_800` | ESX 호스트 | `/Cpu/HTWholeCoreThreshold = 800` | 같은 옵션을 기본값 800 으로 변경 |

- 이름이 `_off` 로 끝나는 프로파일은 값을 비워 둔 것이라 그 키의 줄을 vmx 에서 지운다. 키가 없는 VM 에서는 바꿀 것이 없어 VM 을 끄지 않는다.
- `lpage_1g_on` 은 VM 의 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Backing Guest vRAM with 1 GB Pages).
- `latency_high` 는 CPU 와 메모리 전체 예약이 있어야 한다. 없으면 VM 이 켜지지 않는다(Broadcom 문서 Adjust Latency Sensitivity).
- 두 경우 모두 진행 스크립트가 설정을 이전 값으로 복원한 뒤 멈춘다(6.5절). 예약 값은 이 생성기가 바꾸지 않는다.
- [기본 프로파일 추가] 는 표에 없는 이름의 기본 프로파일만 표 끝에 추가한다. 이름이 같은 행은 고친 내용 그대로 둔다. 처음 값으로 복원하려면 그 행을 삭제한 뒤 버튼을 누른다.
- 이미 쓰던 데이터 폴더(`profiles.json` 이 있는 폴더)에는 자동으로 넣지 않는다. [기본 프로파일 추가] 를 한 번 누른다.
- CPU affinity, 예약, shares 는 기본 프로파일에 없다. VM 마다 값이 다르므로 직접 프로파일을 만들어 적는다.

적용 방법은 다음과 같다(ESX 호스트에서 `tcgen_apply.py` 가 한다).

1. 케이스의 VM 을 `vim-cmd vmsvc/getallvms` 에서 이름이 정확히 같은 줄로 찾는다. 찾지 못하거나 같은 이름이 둘 이상이면 아무것도 바꾸지 않고 멈춘다.
2. 목표 값을 현재 값(vmx 파일, `esxcli system settings advanced list -o`)과 비교한다. 모두 같으면 끝낸다.
3. 그 케이스의 VM 을 모두 종료한다. `power.shutdown` 으로 요청하고, 10분 안에 꺼지지 않거나 게스트 종료를 할 수 없으면 `power.off` 로 끈다.
4. 호스트 옵션을 `esxcli system settings advanced set` 으로 변경하고 다시 읽어 확인한다(Broadcom KB 310338).
5. vmx 를 같은 폴더에 `<이름>.vmx.tcgen-<시각>` 으로 복사해 둔다(최근 5개만 남긴다). 목표 키와 이름이 같은 줄을 모두 지우고 `키 = "값"` 한 줄을 추가한다. 같은 키가 다른 값으로 여러 줄 있어도 한 줄만 남는다. 다른 줄은 그대로 둔다. `vim-cmd vmsvc/reload` 를 실행한다(Broadcom KB 343248).
6. 진행 스크립트가 VM 을 표의 순서대로 하나씩 켠다.

중간에 실패하면 vmx 를 복사해 둔 파일로 복원하고 호스트 옵션을 이전 값으로 복원한 뒤 멈춘다. 일시 중지(Suspended) 상태의 VM 이 있으면 아무것도 바꾸지 않고 멈춘다.

### 5.5 탭 4. 테스트 케이스

케이스 행(옅은 파란 바탕, 굵은 글씨) 아래에 그 케이스의 VM 행(└)이 온다.

| 열 | 케이스 행 | VM 행 |
| :-- | :-- | :-- |
| 적용 | 실행한 케이스에 체크한다 | |
| 케이스 / VM | 케이스 이름. 영문, 숫자, `.` `_` `-` 만 사용 | VM 이름 |
| 설명 | 시험 조건. 한글을 쓸 수 있다 | |
| ESX 호스트 | 그 케이스의 VM 이 있는 ESX 호스트. BM 서버는 비운다(7.8절) | |
| 전원 | | `켬` 또는 `끔`. 끔인 VM 은 켜져 있으면 끄고, 켬인 VM 은 꺼져 있으면 켠다 |
| 잡 | | 탭 1 의 명령어 명 또는 `(없음)` |
| 모니터링 | 실행 위치가 ESX 인 모니터링 | 그 VM 의 모니터링 |
| 설정 | 대상이 ESX 호스트인 프로파일 | 대상이 VM 인 프로파일 |
| 최대 대기 | 시간:분(예: `12:00`). 모니터링을 중지할 때를 정하는 데만 쓴다(7.5절) | |
| 시작 시각 | 잡을 시작할 시각 | |
| 잡 시작 (환산) | 시작 시각 칸의 값으로 계산한 잡 시작 시각. 고칠 수 없다 | |
| 테스트 그룹, 잡 종료 (리포트), 종료 기준 VM | 성능 리포트 생성기에 넘기는 값(9.2절) | 종료 기준 VM 은 VM 행에서 지정 |

시작 시각 칸에는 다음 가운데 하나를 적는다.

| 적는 값 | 뜻 | 잡 시작 (환산) 칸 |
| :-- | :-- | :-- |
| 날짜 시각 `2026-11-20 10:00:00` | 그 시각 | `2026-11-20 10:00` |
| `+간격` `+10:00`, `+10`, `+8:30`, `+8.5` | 표의 바로 윗줄 케이스의 시작 시각에서 그만큼 뒤. ESX 호스트가 달라도 바로 윗줄이 기준이다 | 윗줄이 `2026-11-20 10:00` 이고 `+10:00` 이면 `2026-11-20 20:00` |
| 시:분 `10:00` | 지금부터 처음 오는 그 시각. 날짜를 붙여 저장한다 | 그 날짜 시각 |
| 빈 칸 | 잡이 있는 케이스이면 `입력 필요` 로 보이고 [명령어 생성] 이 오류로 알린다 | 빈 칸 |

- `+간격` 을 계산할 수 없으면(윗줄에 시각이 없음, 표의 첫 줄) 환산 칸에 `계산 불가` 로 보인다.
- 윗줄의 시각을 고치거나 가운데에 케이스를 넣으면 아래 줄의 환산 시각이 그 윗줄 기준으로 다시 계산된다. 적용 체크한 케이스는 변경되지 않는다.
- 같은 ESX 호스트의 케이스는 표의 순서가 시작 시각 순서여야 한다.
- 설정이 앞 케이스와 다른 케이스의 시작 시각은 앞 케이스의 잡이 끝난 시각에서 30분 넘게 뒤로 정한다. 잡 시작 30분 전에 그 케이스의 VM 을 종료하므로, 앞 케이스의 잡이 그때 실행 중이면 잡이 중단된다.
- 잡이 없는 케이스(설정과 VM 전원만 맞춤): 시작 시각을 적으면 그 시각에 하고, 비우면 다음 잡 케이스의 잡 시작 30분 전에 한다.

버튼은 다음과 같다.

| 버튼 | 하는 일 |
| :-- | :-- |
| [+ 케이스 추가] | 선택한 케이스를 VM 구성과 설정까지 복사해 그 아래에 넣는다. 시작 시각은 `+간격` 이면 그대로 복사하고 시각이면 비운다. 표가 비어 있으면 새 케이스를 만들고 시작 시각에 다음 정시를 넣는다 |
| [+ VM 추가] | 선택한 케이스에 다음 번호 VM 을 추가한다 |
| [삭제], [위로], [아래로] | 케이스 행을 고르면 케이스를, VM 행을 고르면 그 VM 을 대상으로 한다. 케이스의 순서가 처리 순서이고 VM 의 순서가 VM 을 켜는 순서다 |
| [기록 대조] | 적용 체크한 케이스의 시작 시각을 테스트 기록 CSV 의 마지막 생성 기록이나 예전 표 파일(백업)과 대조한다. 값이 다른 케이스를 보이고, 고른 케이스의 값을 그 값으로 되돌린다. 되돌리기 전의 표는 데이터 폴더의 `backup` 아래에 저장한다 |
| [리포트용 CSV 저장] | 성능 리포트 생성기의 케이스 정보 파일을 저장한다(9.2절) |
| [명령어 생성] | 넣을 케이스를 고르는 창이 열린다. 처음에는 적용 체크하지 않은 케이스가 골라져 있다(6.1절) |

적용 체크한 케이스는 실행한 기록으로 고정한다.

- 적용 체크하면 그 케이스는 [명령어 생성] 의 선택 창에서 처음에 빠진 채로 나온다.
- 시작 시각에 `+간격` 을 적은 케이스를 적용 체크하면 칸의 값을 날짜 시각으로 변경해 고정한다. 값은 마지막 [명령어 생성] 때 계획한 시각이다(이 창에서 만든 결과, 없으면 테스트 기록 CSV 의 마지막 생성 기록, 그것도 없으면 지금 표로 계산한 값).
- 적용 체크한 케이스의 시작 시각은 고칠 수 없다. 고치려면 적용 체크를 끄고 고친 뒤 다시 체크한다.
- 다른 케이스를 추가, 삭제, 수정하거나 순서를 변경해도 적용 체크한 케이스의 시작 시각은 달라지지 않는다.
- 적용 체크한 케이스 아래에 `+간격` 케이스를 이어 적을 수 있다. 윗줄이 적용 체크한 케이스여도 그 시작 시각이 기준이다.

## 6. 생성과 실행

### 6.1 [명령어 생성] 과 탭 5

[명령어 생성] 을 누르면 넣을 케이스를 고르는 창이 열린다. [생성] 을 누르면 탭 5 에 결과가 나오고, 테스트 기록 CSV 에 케이스마다 한 행이 추가된다(9.1절).

| 탭 5 의 칸 | 내용 |
| :-- | :-- |
| 결과 글 | 생성 시각, 테스트 기록 CSV 와 로그 파일, 실행 ID, 등록 결과가 남을 파일(`tcrun-<실행 ID>-jobs.csv`). 오류와 알림은 한 줄씩 나온다 |
| 블록 A, P, S, D | [복사] 를 누르면 그 블록 전체가 클립보드에 들어간다. 점프 VM 터미널에서는 마우스 오른쪽 또는 Shift+Insert 로 붙여넣는다 |
| 타임라인 | 잡 시작 전에 하는 일을 설정 변경이 없는 케이스와 있는 케이스로 나눠 보인다(1절의 표). 그 아래에 이번 생성에서 호스트와 설정을 비교하는 케이스와 그 시각이 나온다 |
| 실행 계획 | 케이스마다 잡 시작, 설정을 변경하는 시각, 등록할 명령. 창이 낮으면 이 칸은 숨겨지고, 도구 줄의 [실행 계획 보기] 로 큰 창에서 본다 |

- 오류가 있으면 블록과 기록을 만들지 않는다. 오류 글의 칸 이름은 화면의 칸 이름과 같다(11절).
- `알림:` 은 생성을 막지 않는다. 예: 마지막 케이스의 모니터링 중지 시각이 없음(7.5절).
- 생성할 때마다 실행 ID(생성 시각)가 새로 정해진다. 같은 S 블록을 다시 붙여넣어도 다시 시작하지 않는다.

### 6.2 처음 한 번: A 블록과 ESX 키 등록

1. 설정 영역의 `점프 VM 로그 폴더` 에 점프 VM 의 폴더를 적는다. 비우면 `~/tcgen_log` 를 쓴다. `점프 VM 작업 폴더` 는 비우면 `~/.tcgen` 이다. 점프 VM 계정의 홈 폴더 용량이 작으면 작업 폴더에 큰 디스크의 폴더(예: `/data/<계정>/tcgen`)를 적는다. 로그 폴더를 비워 두면 `<작업 폴더>/log` 에 로그가 남는다.
2. 탭 4 에 케이스를 하나 이상 입력하고 [명령어 생성] 을 누른 뒤, 열리는 선택 창에서 [생성] 을 누른다(6.1절). A 블록은 생성 결과에 함께 나온다.
3. 탭 5 의 A 블록 [복사] 를 누르고 점프 VM 터미널에 붙여넣는다. A 블록은 다른 블록과 함께 붙여넣지 않는다. 붙여넣은 뒤 아무 출력이 없으면 Enter 를 한 번 누른다(bash 5.1 이상은 붙여넣은 글을 Enter 를 누를 때 실행한다).
4. 출력에서 아래 두 줄이 `OK` 인지 확인한다. `FAILED` 가 나오면 A 블록을 다시 붙여넣는다(붙여넣는 중에 글자가 빠진 경우다).

```
OK      /home/<계정>/.tcgen/tcrun
OK      /home/<계정>/.tcgen/tcgen_apply.py
```

작업 폴더를 `~/.tcgen` 이 아닌 폴더로 정했으면 경로가 그 폴더로 나온다. 이때 `~/.tcgen` 에 ESX 키(`id_esx`, `id_esx.pub`)와 VM 비밀번호(`vmpw`)가 있으면 새 폴더로 복사하고 `copied:` 줄을 출력한다. 그래서 ESX 호스트에 키를 다시 등록하지 않아도 되고 비밀번호도 다시 묻지 않는다.

5. 이어서 나오는 아래 형태의 한 줄을 복사해, 설정을 적용하거나 ESX 모니터링을 실행할 각 ESX 호스트의 root SSH 창에 한 번 붙여넣는다.

```
echo 'ssh-rsa AAAA... <계정>@<점프 VM>' >> /etc/ssh/keys-root/authorized_keys
```

6. `VM password:` 가 나오면 VM 비밀번호를 입력한다(화면에 보이지 않는다). 비밀번호가 이미 저장돼 있으면 묻지 않고 `already saved` 를 출력한다.
7. 점프 VM 에서 `sh ~/.tcgen/esxssh <ESX 호스트> hostname` 을 실행한다(작업 폴더를 바꿨으면 `~/.tcgen` 대신 그 폴더). 비밀번호를 묻지 않고 ESX 호스트 이름이 나오면 키 등록이 끝난 것이다.

A 블록이 점프 VM 작업 폴더(기본 `~/.tcgen/`)에 설치하는 파일은 다음과 같다. 이 절과 아래 절의 `~/.tcgen` 은 작업 폴더를 바꿨으면 그 폴더로 읽는다.

| 파일 | 내용 |
| :-- | :-- |
| `askpass`, `vmssh`, `setpw` | VM 자동 로그인과 비밀번호 입력. v1.4 와 내용이 같다 |
| `vmpw` | VM 비밀번호(권한 600). `setpw` 가 만든다 |
| `esxssh` | ESX 호스트에 키로 접속한다. `sh ~/.tcgen/esxssh <ESX 호스트> [명령]` |
| `postsetup` | A 블록의 마지막 단계. ESX 에 넣을 한 줄을 출력하고, 비밀번호가 없을 때만 `setpw` 를 실행한다 |
| `tcrun` | 진행 스크립트. 하위 명령은 6.5절 |
| `tcgen_apply.py` | 설정 적용 스크립트. `tcrun` 이 ESX 호스트의 `/tmp/tcgen/` 에 전송해 실행한다 |
| `id_esx`, `id_esx.pub` | ESX 접속용 ssh 키. 없을 때만 만든다 |
| `runs/<실행 ID>/` | 실행마다 plan, 상태, 임시 파일을 둔다 |
| `minutes/<초>/` | 이 점프 VM 의 실행들이 등록한 잡 시작 시각의 기록(잡 시작 최소 간격의 확인용). 하루가 지나면 지운다 |
| `known_hosts` | 진행 스크립트와 `esxssh` 가 접속한 VM, ESX 호스트의 ssh 호스트 키. 홈 폴더의 `~/.ssh/known_hosts` 에는 쓰지 않는다 |

생성기를 새 판으로 바꾼 뒤에는 A 블록을 한 번 다시 붙여넣는다. 점프 VM 의 `tcrun` 판이 생성기의 판과 다르면 P 블록과 S 블록은 아무것도 시작하지 않고 `Paste block A again` 을 출력한다.

#### ssh 키 접속 (점프 VM 에서 ESX 호스트로)

점프 VM 은 ESX 호스트에 root 계정으로, 비밀번호 없이 ssh 키로 접속한다. ESX 비밀번호는 어디에도 저장하지 않는다. 방법은 Broadcom KB 313767 (ESXi 7.0, 8.0) 의 공개 키 인증이다.

A 블록이 키를 만들고 ESX 에 넣을 한 줄을 출력한다. 같은 일을 직접 하려면 아래 명령을 쓴다.

```
# 1) 점프 VM: 키 만들기 (이미 있으면 생략)
ssh-keygen -t rsa -b 4096 -N "" -f ~/.tcgen/id_esx
cat ~/.tcgen/id_esx.pub

# 2) 각 ESX 호스트의 root SSH 창: 위에서 출력된 공개 키 한 줄을 넣는다
echo '<공개 키 한 줄>' >> /etc/ssh/keys-root/authorized_keys

# 3) 점프 VM: 확인. 비밀번호를 묻지 않고 ESX 호스트 이름이 나와야 한다
sh ~/.tcgen/esxssh esx01 hostname
ssh -i ~/.tcgen/id_esx -o BatchMode=yes root@esx01 hostname
```

- ESX 호스트의 SSH 서비스가 켜져 있어야 한다. 잠금 모드(Lockdown Mode)에서는 접속되지 않는다.
- ESX 호스트 이름으로 접속되지 않으면 설정 영역의 `ESX 접속 주소` 에 `esx01=10.0.0.11;esx02=10.0.0.12` 처럼 적는다. 탭 4 의 ESX 호스트 이름은 그대로 두고 접속만 그 주소로 한다.
- 키를 빼려면 ESX 호스트의 `/etc/ssh/keys-root/authorized_keys` 에서 그 줄을 지운다.
- 키 파일 `~/.tcgen/id_esx` 는 본인만 읽을 수 있게 저장된다(권한 600). 이 파일이 있으면 등록한 ESX 호스트에 root 로 접속할 수 있으므로 다른 곳에 복사하지 않는다.

### 6.3 점검 블록 (P)

실행 전에 탭 5 의 P 블록을 점프 VM 터미널에 붙여넣는다. 아무것도 변경하지 않고 아래 항목을 확인해 출력한다. 같은 내용이 로그 폴더의 `tcrun-<실행 ID>-check.log` 에 저장된다.

| 확인 항목 | 문제일 때 출력 |
| :-- | :-- |
| 점프 VM 의 파일, VM 비밀번호, `ssh` 와 `setsid` 명령, 작업 폴더와 로그 폴더에 쓸 수 있는지 | `missing ...: paste block A again` 등 |
| ESX 호스트 키 접속, `python3` 와 `vim-cmd` 와 `esxcli`, root crontab 파일 | `ssh key login failed ... Register the key: sh ~/.tcgen/tcrun key` |
| 케이스의 시작 시각: 이미 지났는지, 이 점프 VM 의 다른 실행의 잡 시작과 `잡 시작 최소 간격` 보다 가까운지 | `the start time ... has already passed`, `is less than 5 min from the job start ...` |
| ESX 호스트가 있는 케이스: VM 을 찾았는지, 설정마다 현재 값과 목표 값, VM 마다 지금 전원과 케이스가 원하는 전원 | `settings and VM power: VM '...' is not registered on this host` 등 |
| ESX 호스트의 첫 케이스: 설정이나 전원이 호스트와 다른데 설정을 변경할 시각(잡 시작 30분 전)이 이미 지났는지 | `its settings or VM power differ from the host, and the time to change them ... has passed` |
| 같은 ESX 호스트의 다른 실행: 진행 중이면 이 실행이 대기한다고 알리고 그 실행이 끝나는 시각을 보인다. 이 실행의 케이스 가운데 잡 시작이 그 시각의 2분 뒤보다 이른 것은 문제로 알린다(대기하는 동안 시작 시각이 지나 등록되지 않는다). 줄을 남긴 채 멈춘 실행이 있으면 문제로 알린다 | `its job start is less than 2 min after the end of run ...`, `block S would not start this run. ... Remove them first: sh ~/.tcgen/tcrun cancel esx01` |
| VM 접속, `crontab` 명령, 시계가 점프 VM 과 몇 초 다른지. 꺼져 있어 실행이 켤 VM 과 전원 끔인 VM 에는 접속하지 않는다. 같은 ESX 호스트에 진행 중인 실행이나 crontab 줄이 남은 실행이 있으면 그 호스트의 VM 에는 접속하지 않는다(실행 중인 잡에 부하를 주지 않음) | `ssh login failed` |
| VM 시계끼리의 차이 | 30초를 넘으면 `the clocks of the VMs differ by N s` |
| `Operations 주소` 를 적었으면 Operations 로그인과, 케이스의 VM 과 ESX 호스트의 객체가 Operations 에 있는지(기록하지 않는다) | `VCF Operations: login to VCF Operations ... failed`, `VCF Operations has no VirtualMachine object with this name` |
| `스냅샷 때 VM 에서 실행할 명령` 을 적었으면 켜져 있는 VM 마다 그 스크립트 파일을 읽을 수 있는지(명령은 실행하지 않는다) | `the file of the command at the config snapshot is not there or cannot be read: <경로>` |

설정과 전원 비교 줄은 아래처럼 나온다. `[change]` 는 실행이 변경할 항목, `[same]` 은 이미 같은 항목이다.

```
TCGEN-VM esx01ev01 vmid=10 power=on vmx=/vmfs/volumes/datastore1/esx01ev01/esx01ev01.vmx
TCGEN-SET esx01ev01 sched.mem.pin: (none) -> "TRUE"  [change]
TCGEN-HOST /Numa/LocalityWeightActionAffinity (integer): 130 -> 0  [change]
TCGEN-POWER esx01ev02 now=off want=on  [change]
  [ok] settings and VM power: 2 value(s) differ, 1 VM(s) to power on (compared with the hosts as they are now). The run changes them 30 min before the job start of the case (when a value differs, the VMs of the case are shut down first).
```

P 블록은 모든 케이스를 지금의 호스트와 비교한다. 뒤 케이스의 비교 결과는 앞 케이스가 설정을 변경하기 전의 값과 비교한 것이다.

마지막 줄이 `CHECK RESULT: OK` 이면 S 블록을 붙여넣는다. `CHECK RESULT: N problem(s)` 이면 `[PROBLEM]` 줄을 고친 뒤 P 블록을 다시 붙여넣는다.

### 6.4 실행 블록 (S)

탭 5 의 S 블록 [복사] 를 누르면 확인 창이 나온다. 점프 VM 터미널에 붙여넣으면 ESX 호스트별 진행이 백그라운드로 시작되고 아래처럼 출력된다. 터미널을 닫아도 진행은 계속된다.

```
started: run 20261120-100000 esx esx01   log: /home/<계정>/tcgen_log/tcrun-20261120-100000-esx01.log
status: sh ~/.tcgen/tcrun status       stop: sh ~/.tcgen/tcrun stop       cancel: sh ~/.tcgen/tcrun cancel
files in /home/<계정>/tcgen_log : tcrun-20261120-100000-jobs.csv (which jobs are registered in crontab), ...
```

- 설정 변경이 없는 케이스의 잡은 이때 바로 crontab 에 등록된다. 등록 결과는 `tcrun-<실행 ID>-jobs.csv` 에서 확인한다(8.1절).
- 실행을 더할 때: 앞 실행이 진행 중인 ESX 호스트에 새 실행의 S 블록을 붙여넣으면 그 호스트의 진행은 대기한다. 출력은 `queued:` 로 시작하고 앞 실행이 끝나는 시각이 함께 나온다(`waiting for run ... to end (about <시각>, 1 min after its last job start)`). 앞 실행이 `done` 으로 끝나면 스스로 시작한다. ESX 호스트 하나에는 한 번에 한 실행만 진행한다. 진행은 마지막 잡 시작 1분 뒤에 끝나므로, 대기하는 실행의 등록은 그 뒤에 한다.
- 앞 실행이 `done` 이 아닌 상태(paused, stopped, cancelled, died)로 끝나면 대기하던 실행은 시작하지 않고 `paused` 로 끝난다. 앞 실행을 확인한 뒤 다시 생성한다.
- 앞 실행이 paused 나 stopped 로 끝나 crontab 줄이 남아 있으면 새 실행은 시작하지 않고 `==== esx01: not started. ...` 로 이유를 알린다. `sh ~/.tcgen/tcrun cancel esx01` 을 실행한 뒤 같은 S 블록을 다시 붙여넣는다.
- 앞 실행이 `done` 으로 끝나 남긴 줄은 새 실행이 지운다(7.6절).

### 6.5 진행 확인, 중지, 취소

| 명령 (점프 VM) | 하는 일 |
| :-- | :-- |
| `sh ~/.tcgen/tcrun status` | 마지막 실행의 모든 ESX 호스트, 진행 중이거나 대기 중인 실행, crontab 줄이 남은 실행의 상태를 보인다. 지금 케이스와 단계, 로그의 마지막 세 줄이 함께 나온다. `-a` 를 주면 모든 실행을 보인다 |
| `sh ~/.tcgen/tcrun stop [ESX 호스트]` | 진행만 끝낸다. 이미 등록한 crontab 줄은 남으므로 그 잡은 시작 시각에 시작한다. 아직 등록하지 않은 케이스는 등록하지 않는다 |
| `sh ~/.tcgen/tcrun cancel [ESX 호스트]` | 진행 중이거나 대기 중인 실행을 바로 끝내고 등록한 crontab 줄을 지운다. 시작 전인 잡은 시작하지 않는다. 실행 중인 잡은 끝내지 않는다. 시작된 모니터링은 중지 명령을 실행한다. 적용한 설정은 그대로 둔다. 끝난 실행이 남긴 줄도 지운다. 접속하지 못한 VM 이 있으면 `crontab lines of case <이름> NOT removed on: <VM>` 을 출력하고 그 VM 의 줄은 남는다(그 잡은 아직 시작할 수 있다). 접속이 되는 때에 같은 명령을 다시 실행하면 남은 VM 의 줄만 지운다 |
| `sh ~/.tcgen/tcrun key` | ESX 호스트에 넣을 키 줄을 다시 출력한다 |
| `sh ~/.tcgen/tcrun version` | 설치된 판 |

작업 폴더를 `~/.tcgen` 이 아닌 폴더로 정했으면 명령의 `~/.tcgen` 대신 그 폴더를 적는다.

| 상태 | 뜻 |
| :-- | :-- |
| `running` | 진행 중. `step` 과 `text` 에 지금 단계가 나온다(예: `waiting until ... to take the config snapshot of case ...`) |
| `queued` | 같은 ESX 호스트의 앞 실행이 끝나기를 기다리는 중 |
| `done` | 모든 케이스를 처리했다. `text` 에 등록한 케이스 수와 등록하지 못한 케이스 수가 나온다. crontab 줄은 호스트에 남아 있다(7.6절) |
| `paused` | 문제가 있어 스스로 멈췄다. `text` 에 이유가 있다 |
| `stopped` | `tcrun stop` 으로 끝냈다 |
| `cancelled` | `tcrun cancel` 로 끝냈다 |
| `died` | 진행 프로세스가 없다(점프 VM 재부팅 등). `~/.tcgen/runs/<실행 ID>/<ESX 호스트>.out` 을 본다 |

`stop` 을 받은 시점에 따라 하는 일이 다르다.

| stop 을 받은 시점 | 진행 스크립트가 하는 일 |
| :-- | :-- |
| 대기(queued) 중, 설정을 변경할 시각을 기다리는 동안 | 그대로 끝낸다. 그 케이스와 뒤 케이스는 등록되지 않는다 |
| 설정 적용 중 | 설정 적용(VM 종료, 값 변경)을 마친 뒤 끝낸다. 값을 변경했으면 그 케이스의 VM 은 꺼진 채로 남는다 |
| VM 을 켜는 중 | 기다리지 않고 바로 끝낸다. ESX 호스트에서 시작된 켜기 작업은 끝까지 진행된다. 설정은 되돌리지 않는다 |
| 줄을 등록한 뒤(구성 스냅샷이나 마지막 잡 시작을 기다리는 동안) | 그대로 끝낸다. 등록된 줄은 남아 그 잡은 시작 시각에 시작한다. 그 뒤 케이스의 구성 스냅샷은 읽지 않는다 |

진행이 멈추면(paused) 로그의 `PAUSED:` 줄에서 이유를 확인하고 고친다. `tcrun-<실행 ID>-jobs.csv` 에서 등록된 케이스를 확인한다. 등록된 케이스의 잡은 시작 시각에 시작한다. 나머지를 실행하려면 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 로 남은 줄을 지우고(등록된 잡도 지워진다), 실행한 케이스를 탭 4 에서 적용 체크한 뒤 다시 생성해 S 블록을 붙여넣는다.

## 7. 점프 VM 이 하는 일

### 7.1 케이스의 처리 순서

진행 스크립트(tcrun)는 ESX 호스트마다 따로 실행되고, 그 호스트의 케이스를 표의 순서대로 처리한다. ESX 호스트가 여러 대이면 서로 기다리지 않는다.

1. 설정이나 VM 전원이 호스트와 다를 수 있는 케이스에서 호스트의 현재 값과 비교한다(7.2절).
2. 값이 같으면 그 케이스와, 뒤에 오는 같은 설정의 케이스들의 잡을 crontab 에 한꺼번에 등록한다. 첫 케이스가 여기에 해당하면 S 블록 직후에 등록된다.
3. 값이 다르면 그 케이스의 잡 시작 30분 전까지 기다린 뒤 VM 종료, 설정 적용, VM 전원 ON 을 하고, 그 케이스와 뒤에 오는 같은 설정의 케이스들을 등록한다.
4. 케이스마다 잡 시작 10분 전에 구성 스냅샷을 읽는다(7.4절).
5. 마지막 잡 시작 1분 뒤에 진행을 끝낸다(7.6절).

잡이 실행되는 동안에는 VM 에 접속하지 않는다. VM 에 접속하는 때는 crontab 등록, 구성 스냅샷, 설정 변경 뒤의 로그인 확인뿐이다.

### 7.2 설정 변경이 있는 케이스의 판정

| 케이스 | 판정 |
| :-- | :-- |
| ESX 호스트의 첫 케이스 | 실행을 시작할 때 호스트의 현재 값과 비교한다. 다르면 설정 변경이 있는 케이스다 |
| 설정 프로파일, VM 전원, VM 구성이 바로 앞 케이스와 다른 케이스 | 그 케이스의 잡 시작 30분 전에 호스트와 비교한다. 다르면 설정 변경이 있는 케이스다 |
| 바로 앞 케이스와 같은 케이스 | 비교하지 않는다. 설정 변경이 없는 케이스다 |
| ESX 호스트가 없는 케이스 | 설정과 전원을 다루지 않는다 |

탭 5 의 타임라인 아래와 실행 계획에 어느 케이스를 언제 비교하는지 나온다. 설정을 적용하는 방법은 5.4절에 있다.

- 목표 값이 현재 값과 모두 같으면 VM 을 끄지 않는다.
- 값이 하나라도 다르면 그 케이스의 VM 을 모두 종료하고 값을 변경한 뒤, VM 을 표의 순서대로 하나씩 켠다. VM 마다 켜기 작업이 끝나고, 1GB page 를 쓰는 VM 은 1GB page backing 수가 메모리 GB 수와 같아지고, ssh 로그인이 되면 다음 VM 으로 넘어간다.
- VM 을 켜지 못하면 설정을 이전 값으로 복원하고 멈춘다(paused).

### 7.3 crontab 등록

- 잡 줄은 plan 에 적힌 시작 시각 그대로 등록한다. 모니터링 시작 줄은 잡 시작 5분 전, 모니터링 중지 줄은 7.5절의 시각으로 함께 등록한다.
- 등록 결과는 `tcrun-<실행 ID>-jobs.csv` 에 VM 마다 한 행으로 남는다(8.1절).
- 등록하려는 때에 잡 시작 시각이 이미 지났거나 1분이 남지 않았으면 그 케이스는 등록하지 않는다. 기록에 `not registered` 와 이유가 남고, 진행은 다음 케이스로 계속된다.
- 한 케이스의 줄은 그 케이스의 모든 VM 과 ESX 호스트에 첫 실행 시각(모니터링 시작 시각, 모니터링이 없으면 잡 시작 시각) 15초 전까지 들어가야 한다. 한 곳이라도 그때까지 줄을 받지 못하면 그 케이스를 등록하지 않고, 이미 줄을 받은 VM 의 줄을 지운다(일부 VM 에서만 시작되는 것을 막는다). 시작 시각은 옮기지 않는다.
- VM 접속 하나에는 첫 실행 시각 15초 전까지 남은 시간만 준다(최대 60초). VM 도 줄을 받는 때에 자기 시계가 그 시각을 지났으면 줄을 받지 않는다.
- 등록하지 않은 케이스에서 확인할 VM 이 있으면 `jobs.csv` 의 그 VM 행에 적는다(8.1절): 줄을 지우지 못한 VM, 답이 없던 VM, 줄을 지운 때가 그 VM 의 시계로 첫 실행 시각 뒤인 VM(그 시각의 명령이 이미 실행됐을 수 있다. 시작된 모니터링에는 중지 명령을 실행한다).
- 줄이 남았거나 뒤늦게 들어올 수 있는 VM 이 있으면 그 케이스는 줄 목록에 남는다. 같은 ESX 호스트의 다음 실행이나 `tcrun cancel` 이 그 VM 의 줄을 다시 지운다.
- 다른 실행의 잡 시작과 `잡 시작 최소 간격` 보다 가까우면 로그에 WARN 을 남기고 적은 시각 그대로 등록한다.

### 7.4 구성 스냅샷과 VCF Operations 기록

모든 케이스에서 잡 시작 10분 전에 그 케이스 VM 의 구성을 점프 VM 로그 폴더의 csv 로 남긴다(8.3절). 읽기만 하고, 읽지 못해도 케이스는 진행한다.

- VM 설정: ESX 호스트에서 각 VM 의 vmx 파일을 읽는다.
- Guest OS 설정: 켜져 있는 VM 마다 한 번 접속해 THP, hugepages 등을 읽는다.
- 이 실행이 방금 켠 VM 은 마지막 VM 의 준비가 끝나고 60초 뒤에 읽는다(게스트가 부팅 때 적용하는 설정이 들어가게 한다).
- 잡 시작까지 1분이 남지 않았으면 읽지 않고 로그에 WARN 을 남긴다.

설정 영역의 `스냅샷 때 VM 에서 실행할 명령` 을 적었으면 구성 스냅샷 때 케이스의 켜져 있는 VM 마다 그 명령을 실행한다.

- 게스트 구성을 VCF Operations 에 기록하는 guest_config_push 를 적는다. 예: `bash <스크립트 폴더>/guest_config_push.sh --target auto`. VM 에서는 VM 객체에, BM 서버에서는 BM 호스트 객체에 기록한다(guest_config_push 1.1 이상).
- 명령은 모든 VM 에 같은 글로 실행한다. 스크립트가 모든 VM(과 BM 서버)의 같은 경로에 있어야 한다.
- 결과는 스냅샷 csv 의 `snapshot command` 행과 진행 로그의 `config snapshot: command on vm <VM>: ...` 줄에 남는다. 실패해도 케이스는 진행한다.
- 명령 하나에 최대 150초를 기다린다. 잡 시작 2분 전이 지나면 남은 VM 에서는 실행하지 않는다(`not run (no time left before the job start)`).

설정 영역의 `Operations 주소`, `Operations 계정`, `Operations 암호` 를 적었으면 구성 스냅샷 때 점프 VM 이 아래 값을 VCF Operations 에 기록한다(v2.13).

| 기록하는 값 | Operations 의 객체 | 속성 이름 |
| :-- | :-- | :-- |
| VM 설정: 구성 스냅샷 csv 의 `vm advanced config` 구간. config_snapshot 이 기록하던 11개 키와, 이번 실행의 설정 프로파일이 다루는 vmx 키 | 이름이 VM 이름과 같은 VirtualMachine 객체 | `Custom Configuration\|VM\|<키>` |
| 케이스의 호스트 옵션(케이스 행의 설정 프로파일에 적은 옵션). 값은 구성 스냅샷 때 ESX 호스트에서 읽은 값이다 | 이름이 ESX 호스트 이름과 같은 HostSystem 객체. 없으면 `<ESX 호스트>.<도메인>`, `ESX 접속 주소` 의 주소로 찾는다 | `Custom Configuration\|Host\|<구역.옵션>` |

- Guest OS 설정은 여기서 기록하지 않는다. `스냅샷 때 VM 에서 실행할 명령` 의 guest_config_push 가 게스트와 BM 서버 안에서 기록한다(`Custom Configuration|Guest|*`).
- `sched.mem.pin` 은 설정 프로파일이 그 키를 다룰 때만 기록한다. CPU affinity 키는 기록하지 않는다. vmx 에 없는 키의 값은 `(없음)` 이다.
- 호출은 guest_config_push 와 같다: 토큰 발급(`/suite-api/api/auth/token/acquire`), 객체 조회(`/api/resources`), 속성 기록(`/api/resources/<id>/properties`). 케이스마다 한 번 로그인한다.
- 점프 VM 에 `curl`, `openssl`(1.1.1 이상), 그리고 `python3` 나 `jq` 가 있어야 하고, 점프 VM 에서 Operations 로 HTTPS 접속이 돼야 한다. 인증서는 확인하지 않는다(guest_config_push 의 기본과 같다. `settings.json` 의 `ops_verify_tls` 를 `true` 로 하면 확인한다).
- 결과는 스냅샷 csv 의 `operations write` 행(VM 마다 `ok: N properties`, `not written (...)`, `failed (...)`)과 진행 로그의 `config snapshot: VCF Operations: ...` 줄에 남는다. 기록하지 못해도 케이스는 진행하고 로그에 WARN 이 남는다.
- ESX 호스트가 없는 케이스(BM 서버)는 VM 설정이 없으므로 여기서 기록하지 않는다.
- 호스트 옵션을 스냅샷 때 읽지 못하면 그 옵션은 기록하지 않고 로그에 WARN 을 남긴다(`N of M host option(s) of the case not read ...`).
- 암호: PC 의 `settings.json` 에는 암호화한 글과 키가 저장된다. P 블록과 S 블록에 든 plan, 점프 VM 의 `runs/<실행 ID>/plan`(본인만 읽기)에도 같은 두 값이 들어간다. 암호 자체와 토큰은 로그에 남지 않고, 점프 VM 에서 명령줄 인자로 넘기지 않는다(본인만 읽는 임시 파일로 넘기고 바로 지운다). 블록을 다른 사람에게 넘기지 않는다(10절).

### 7.5 모니터링

| 항목 | 때 |
| :-- | :-- |
| 시작 | 잡 시작 5분 전(설정 영역의 `모니터링 시작 N분 전`). crontab 줄로 등록한다 |
| 중지 (중지 명령이 있는 모니터링) | 같은 ESX 호스트의 다음 잡 케이스의 잡 시작 32분 전(`설정 적용 N분 전` + 2분). crontab 줄로 등록한다 |
| 중지: 최대 대기를 적은 케이스 | 잡 시작 + 최대 대기가 위 시각보다 이르면 그 시각 |
| 중지: 그 ESX 호스트의 마지막 케이스 | 최대 대기를 적었으면 잡 시작 + 최대 대기. 적지 않았으면 중지 줄을 등록하지 않는다. 같은 ESX 호스트의 다음 실행이 첫 잡 시작 30분 전에 중지 명령을 실행하고, `tcrun cancel` 도 중지 명령을 실행한다 |

- 등록하려는 때에 모니터링 시작 시각이 이미 지났으면(설정 변경이 늦게 끝난 경우) 1분 이상 남은 가장 이른 분에 모니터링을 시작하게 등록하고 로그에 WARN 을 남긴다. 잡 시작 시각은 그대로다.

### 7.6 실행의 끝과 다음 실행

- 진행은 그 ESX 호스트의 마지막 잡 시작 1분 뒤에 끝난다(`done`). 등록한 crontab 줄은 VM 과 ESX 호스트에 그대로 남는다. 잡이 실행되는 동안 VM 에 접속하지 않기 위해서다.
- 같은 ESX 호스트의 다음 실행을 시작하면, 설정 변경이 없는 케이스는 바로 등록한다. 앞 실행이 남긴 줄은 다음 실행의 첫 잡 시작 30분 전에 지운다. 이때 앞 실행의 마지막 케이스 모니터링이 중지되지 않았으면 중지 명령을 실행한다. 접속하지 못한 VM 의 줄은 남고 로그에 WARN 이 남는다. 그다음 실행이나 `tcrun cancel` 이 그 줄을 다시 지운다.
- 다음 실행에 앞 실행과 이름이 같은 케이스가 있으면 그 케이스의 앞 실행 줄은 다음 실행을 시작할 때 바로 지운다.
- 다음 실행 없이 줄을 지우려면 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 를 실행한다.

### 7.7 시각을 지킬 수 없을 때

잡 시작 시각은 변경하지 않는다. 지킬 수 없는 경우의 동작은 다음과 같다.

| 경우 | 동작 | 기록 |
| :-- | :-- | :-- |
| 설정이 호스트와 다른데 설정을 변경할 시각(잡 시작 30분 전)이 이미 지남(S 블록을 늦게 붙여넣은 경우) | 바로 변경하고, 잡은 적은 시각에 등록한다 | 로그에 WARN. jobs.csv 에 `registered (settings changed N min before the job start. The setting is 30 min)` |
| 설정 변경이 잡 시작 전에 끝나지 않음 | 그 케이스는 등록하지 않는다. 같은 설정의 뒤 케이스는 적은 시각에 등록한다 | jobs.csv 에 `not registered (its job start time ... has passed or is less than 1 min away)` |
| 그 설정을 쓰는 케이스의 잡 시작이 모두 지남 | 설정을 변경하지 않는다(VM 을 끄지 않는다) | 로그에 WARN, jobs.csv 에 `not registered` |
| 설정 변경이 모니터링 시작 시각 뒤에 끝남 | 모니터링을 가장 이른 분에 시작하게 등록한다. 잡은 적은 시각에 등록한다 | 로그에 WARN, jobs.csv 에 `registered (monitoring starts N min before the job start. ...)` |
| 한 VM 이 첫 실행 시각 15초 전까지 줄을 받지 못함(접속이 느림, 그 VM 의 시계가 빠름, 접속 안 됨) | 그 케이스는 등록하지 않는다. 줄을 받은 다른 VM 의 줄을 지운다 | 로그에 WARN, jobs.csv 에 `not registered (vm <VM>: ...)`. 확인할 VM 은 그 VM 행에 적는다(7.3절) |

P 블록은 첫 케이스의 설정이 호스트와 다르고 설정을 변경할 시각이 이미 지났으면 `[PROBLEM]` 으로 알린다. 그때는 시작 시각을 늦춰 다시 생성한다.

### 7.8 BM 서버에서 실행

ESX 호스트 칸을 비운 케이스는 설정과 전원을 다루지 않는다. 잡과 모니터링만 등록한다.

- VM 이름 칸에 BM 서버의 호스트 이름을 적는다. 서버는 켜져 있어야 하고, 점프 VM 에서 VM 접속 계정으로 ssh 로그인이 돼야 한다.
- ESX 호스트가 없는 케이스들은 한 진행(`noesx`)으로 묶여 표의 순서대로 처리된다. 설정 변경이 없으므로 S 블록 직후에 모두 등록된다.
- 구성 스냅샷은 Guest OS 구간만 남긴다. `스냅샷 때 VM 에서 실행할 명령` 은 BM 서버에서도 실행한다.

## 8. 점프 VM 로그 폴더의 파일

`~/tcgen_log` 는 설정 영역의 `점프 VM 로그 폴더` 를 비웠을 때의 위치다. ESX 호스트를 적지 않은 케이스는 파일 이름의 호스트 자리에 `noesx` 가 들어간다. 글은 ASCII 영어이고 시각은 점프 VM 의 현지 시각이다.

| 파일 | 내용 |
| :-- | :-- |
| `tcrun-<실행 ID>-jobs.csv` | crontab 등록 기록. 실행 하나에 한 파일이고, 잡이 있는 VM 마다 한 행(8.1절) |
| `tcrun-<실행 ID>-<ESX 호스트>.log` | 진행 로그. 시간순 한 줄씩(8.2절) |
| `tcrun-<실행 ID>-<ESX 호스트>-result.csv` | 케이스별 결과 한 행 |
| `tcrun-<실행 ID>-<ESX 호스트>-perfreport_cases.csv` | 성능 리포트 생성기의 케이스 정보 파일. 등록한 케이스만 들어간다. 잡 시작은 plan 의 시각, 잡 종료는 빈칸 |
| `tcrun-<실행 ID>-<ESX 호스트>-config-<케이스 번호>-<케이스>.csv` | 구성 스냅샷. 등록한 케이스마다 한 개(8.3절) |
| `tcrun-<실행 ID>-check.log` | 점검 블록의 출력 |

### 8.1 등록 기록 (jobs.csv)

```
case,esx,vm,job_start,crontab
TC-01,esx01,esx01ev01,2026-11-20 10:00,"registered"
TC-01,esx01,esx01ev02,2026-11-20 10:00,"registered"
TC-02,esx01,esx01ev01,2026-11-20 20:00,"registered"
TC-03,esx01,esx01ev01,2026-11-21 06:00,"not registered (the run ended as paused: vm esx01ev01 did not accept ssh login within 30 min after power on ...)"
```

| `crontab` 열의 값 | 뜻 |
| :-- | :-- |
| `registered` | 그 VM 의 crontab 에 잡 줄을 등록했다. 잡은 `job_start` 에 시작한다 |
| `registered (...)` | 등록했고 확인할 내용이 있다. 설정을 잡 시작 몇 분 전에 변경했는지, 모니터링이 몇 분 전에 시작하는지(7.7절) |
| `not registered (<이유>)` | 등록하지 않았다. 그 잡은 시작하지 않는다 |
| `not registered (<이유>). <그 VM 에서 확인할 것>` | 등록하지 않은 케이스인데 그 VM 에 확인할 것이 있다. `The lines could NOT be removed on this VM again`: 줄이 그 VM 에 남아 있다. `It is not known whether the lines are on this VM`: 답이 없어 알 수 없다. `This VM gave no answer while it was taking the lines ... they may still arrive`: 줄이 뒤늦게 들어올 수 있다. 이 셋은 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 로 줄을 지운다. `The lines were removed on this VM at <시각> ..., after the first start time`: 줄은 지웠지만 그 시각의 명령이 그 VM 에서 이미 실행됐을 수 있다 |
| `not registered (the run ended as paused: ...)` | 진행이 멈추거나(`paused`) 중지되거나(`stopped`) 취소돼(`cancelled`) 그 케이스까지 가지 못했다 |
| `removed before the job start (<누가>)` | 등록했던 줄을 잡 시작 전에 지웠다(`sh tcrun cancel`). 등록 행 아래에 한 행이 더 생긴다 |
| `NOT removed on this VM (...)` | `tcrun cancel` 이 그 VM 에 접속하지 못해 줄을 지우지 못했다. 그 잡은 `job_start` 에 시작한다. 접속이 되는 때에 cancel 을 다시 실행한다 |

설정 변경이 있는 케이스는 설정을 변경한 뒤(잡 시작 30분 전쯤)에 행이 생긴다. 그 전에는 파일에 없다. 진행 프로세스가 사라진 경우(`died`. 점프 VM 재부팅 등)에는 그때까지 등록하지 못한 케이스의 행이 생기지 않는다. 행이 없는 케이스는 등록되지 않은 것이다.

### 8.2 진행 로그

```
sh ~/.tcgen/tcrun status                                   # 지금 단계와 로그의 마지막 세 줄
tail -f ~/tcgen_log/tcrun-<실행 ID>-<ESX 호스트>.log        # 로그를 계속 보기 (Ctrl+C 로 끝냄)
```

| 줄에 들어 있는 글 | 뜻 |
| :-- | :-- |
| `==== case <이름> (N of M) begin. VMs: ... Job start <시각>` | 케이스 처리 시작 |
| `settings and VM power: already as wanted. Nothing is changed` | 값이 호스트와 같아 변경하지 않았다 |
| `settings and VM power: N value(s) differ. They are changed at <시각> (30 min before the job start ...)` | 값이 달라 그 시각에 변경한다 |
| `TCGEN-SET`, `TCGEN-HOST`, `TCGEN-DONE` | 설정 한 항목의 변경 전 값과 목표 값, 적용한 내용과 vmx 백업 파일 경로 |
| `vm <이름>: ssh login works, ready N s after the power on started` | 그 VM 의 준비가 끝났다 |
| `registered: case <이름>, job start <시각>[, monitoring start ...][, monitoring stop ...], VMs: ...` | 그 케이스의 줄을 crontab 에 등록했다 |
| `registration: N of M case(s) of this part are in crontab now. Record: <jobs.csv>` | 같은 설정의 케이스들을 한꺼번에 등록한 결과 |
| `WARN not registered: case <이름>, job start <시각>: <이유>` | 그 케이스를 등록하지 않았다 |
| `WARN case <이름> is not registered, but ...` | 등록하지 않은 케이스의 줄이 어떤 VM 에 남았거나, 첫 실행 시각에 남아 있었거나, 뒤늦게 들어올 수 있다. `jobs.csv` 의 그 VM 행을 본다(8.1절) |
| `config snapshot (before the job of this case ...): <파일>` | 구성 스냅샷을 남겼다 |
| `config snapshot: command on vm <이름>: ok (...)` | 스냅샷 때 VM 에서 실행할 명령이 성공했다 |
| `==== case <이름> done. job start <시각> (crontab)` | 그 케이스의 처리를 마쳤다(잡은 crontab 이 그 시각에 시작한다) |
| `run <실행 ID> left crontab lines ... Removing them now` | 앞 실행이 남긴 줄을 지웠다 |
| `run finished: N case(s), N job case(s) registered, N not registered` | 진행 끝 |
| `queued: ...` | 같은 ESX 호스트의 앞 실행이 끝나기를 기다린다 |
| `WARN` | 진행은 계속하지만 확인할 일 |
| `PAUSED:` 또는 `STOPPED on request:` | 멈춘 이유. 그 아래 `Not finished:` 줄에 처리하지 못한 케이스 이름이 나온다(모든 케이스를 처리한 뒤의 stop 에는 이 줄이 없다) |

결과 CSV(`-result.csv`)의 열은 `case, esx, apply, begin, vms_on, monitor_start, job_start, first_seen, job_end, monitor_stop, end, status` 다. `apply` 는 `none`, `changed`, `rolledback` 가운데 하나다. `status` 는 `registered`, `not registered`, `done (settings only)`, `paused: <이유>`, `stopped: <이유>` 가운데 하나다. `first_seen` 과 `job_end` 는 비어 있다(잡을 확인하지 않는다).

### 8.3 구성 스냅샷 파일

| 항목 | 내용 |
| :-- | :-- |
| 남기는 때 | 등록한 케이스마다 잡 시작 10분 전(설정 영역의 `구성 스냅샷 N분 전`) |
| 대상 | 그 케이스의 VM (이름이 있는 VM 행 전부) |
| VM 설정 | ESX 호스트에서 각 VM 의 vmx 파일을 읽는다. VM 기본 정보(power state, cpu, cores per socket / sockets, memory, memory reservation, cpu shares, mem shares, latency sensitivity), vm advanced config(config_snapshot 의 12개 키와 이번 실행의 설정 프로파일이 다루는 vmx 키), CPU affinity |
| Guest OS 설정 | 켜져 있는 VM 마다 한 번 접속해 읽는다: THP enabled, THP defrag, khugepaged scan_sleep_millisecs, khugepaged pages_to_scan, kernel.numa_balancing, hugepages 2MB nr_hugepages, hugepages 1GB nr_hugepages, default_hugepagesz (cmdline), kernel |
| 배치 | config_snapshot 의 VM 표와 같다. 열은 구분, 항목, VM 이름. 구간의 첫 행은 값을 읽은 시각이다. vmx 에 없는 키와 읽지 못한 값은 `(없음)` 으로 적는다 |
| 형식 | UTF-8(BOM), 줄 끝 CR+LF. 엑셀에서 열린다 |

- vCenter 가 아니라 ESX 호스트의 vmx 파일에서 읽는다. vmx 에 적히지 않은 기본값은 `(없음)` 으로 나온다.
- 전원 끔인 VM 은 VM 설정만 적고 Guest OS 값은 `(없음)` 이다. ESX 호스트를 적지 않은 케이스는 Guest OS 구간만 있다.
- Guest OS 설정은 스냅샷을 남긴 때의 값이다. 잡 명령이 시작하면서 게스트 설정을 변경하면 그 값은 들어가지 않는다.
- 읽지 못한 부분이 있으면 진행 로그에 `WARN config snapshot of case <케이스> is not complete: <이유>` 줄이 남고, 읽은 부분만 파일에 적는다.
- `Operations 주소` 를 적었으면 `vm advanced config` 구간의 마지막 행 `operations write` 에 VM 마다 Operations 기록 결과가 들어간다(7.4절).

### 9.1 테스트 기록 CSV 와 로그 CSV

| 파일 | 행 | 열 |

| 테스트 기록 CSV | 생성할 때마다 케이스 하나에 한 행 | 테스트 케이스 이름, 생성 시각, ESX 호스트, VM 구성, 잡 시작(KST), 간격, 모니터링, 모니터링 시작(KST), 모니터링 중지(KST), 설명, 테스트 그룹, 잡 종료(리포트), 종료 기준 VM, 진행 방식, 설정, 실행 ID |
| 로그 CSV (`testcaselogging-년월일시분초.csv`) | 등록할 명령 하나, 설정 한 항목에 한 행 | 테스트 케이스 이름, 생성 시각, 구분, 대상, 실행 위치, 명령어 명, App명, 설명, 실행 시각(KST), crontab 시각 기준, 명령, crontab 줄, 케이스 정보, 설정, 실행 ID |

- 실제로 등록됐는지는 점프 VM 의 `tcrun-<실행 ID>-jobs.csv` 에서 확인한다(8.1절). 실행 ID 열로 두 파일을 맞춘다.
- `진행 방식` 열의 값은 예전 판과 같은 `순서 실행` 이다(파일 형식을 유지한다).
- 기존 테스트 기록 CSV 의 머리글에 없는 열은 머리글 끝에 덧붙이고 이어서 기록한다. 덧붙이기 전 원본은 데이터 폴더 `backup` 에 복사한다.

## 10. 제한과 주의

- 실제 ESX 호스트, VM, 점프 VM, VCF Operations 에서 v2.12 와 v2.13 을 아직 실행하지 않았다. 12절의 '실제 장비에서 확인할 것' 을 먼저 본다. 처음에는 중요하지 않은 VM 한 대로 P 블록과 S 블록을 실행해 본다.
- 진행 스크립트는 잡이 시작됐는지, 끝났는지 확인하지 않는다. 잡 명령이 틀려 시작되지 않아도 진행은 계속된다. 처음 쓰는 명령은 VM 에서 직접 확인한다.
- 설정이 앞 케이스와 다른 케이스는 잡 시작 30분 전에 그 케이스의 VM 을 종료한다. 그때 앞 케이스의 잡이 실행 중이면 중단된다. 시작 시각은 앞 케이스의 잡이 끝나는 때를 보고 정한다.
- 설정 변경(VM 종료, 설정 적용, VM 전원 ON, 1GB page backing, ssh 로그인)이 30분 안에 끝나지 않으면 그 케이스는 등록되지 않는다. 메모리가 큰 VM 여러 대는 더 걸릴 수 있다. 그때는 설정 영역의 `설정 적용 N분 전` 을 늘린다.
- 한 ESX 호스트의 케이스는 차례로 실행하는 것을 전제로 한다. 모니터링 중지 시각과 앞 실행이 남긴 줄의 삭제는 같은 ESX 호스트의 다음 케이스(다음 실행의 첫 케이스)의 잡 시작을 기준으로 정한다. 같은 ESX 호스트에서 VM 을 나눠 잡을 겹쳐 실행하면 앞 케이스의 모니터링이 다음 케이스의 잡 시작 32분 전에 중지된다.
- 같은 ESX 호스트에 실행을 더하면 앞 실행의 마지막 잡이 시작된 뒤에 등록된다(6.4절). 그 전에 시작해야 하는 케이스를 더하려면 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 로 앞 실행을 끝내고, 남은 케이스와 함께 다시 생성한다.
- 재부팅해야 적용되는 ESX 호스트 설정은 다루지 않는다. 수동으로 적용하고 재부팅한 뒤에 실행한다.
- 설정을 적용하는 케이스의 VM 은 탭 4 에 적은 ESX 호스트에 등록돼 있어야 한다. DRS 가 VM 을 다른 호스트로 옮겼으면 VM 을 찾지 못해 아무것도 변경하지 않고 멈춘다.
- 탭 4 에 적지 않은 VM 은 다루지 않는다. ESX 호스트가 있는 케이스에서 이름이 있는 VM 행은 잡이 없어도 그 케이스의 VM 이다(전원 칸대로 켜거나 끈다).
- 등록한 crontab 줄은 다음 실행이나 `tcrun cancel` 이 지울 때까지 남는다. 줄에는 월과 일이 들어 있어, 지우지 않고 1년이 지나면 같은 날짜에 다시 실행된다.
- 같은 케이스의 VM 시계가 서로 다르면 잡이 그만큼 어긋나 시작한다. P 블록이 30초를 넘는 차이를 알린다.
- VM 의 `crontab` 명령이 멈춰 답이 없으면 진행 스크립트는 남은 시간이 지난 뒤 접속을 끊는다. 그 VM 에는 그 뒤에도 줄이 들어갈 수 있다. `jobs.csv` 의 그 VM 행에 `they may still arrive` 가 남으면 그 VM 의 crontab 을 확인하거나 `sh ~/.tcgen/tcrun cancel <ESX 호스트>` 를 실행한다.
- VM 켜기 작업은 최대 90분을 기다린다(`settings.json` 의 `seq_poweron_wait_min`). VM 에 전원 켜기 질문이 대기 중이면 `power.on` 이 끝나지 않는다.
- ESX 를 재부팅하면 root crontab 의 줄이 지워진다(Broadcom KB 323138). 진행 중에 ESX 를 재부팅하지 않는다.
- 점프 VM 을 재부팅하면 진행이 끝난다(`died`). 이미 등록한 줄은 VM 에 남아 그 잡은 시작한다. 등록하지 않은 케이스는 다시 생성해 실행한다.
- 점프 VM 작업 폴더와 로그 폴더에 쓸 수 없으면(디스크 가득, 계정의 디스크 quota) 실행(S)과 점검(P)이 시작하지 않는다. 설정 영역에서 두 폴더를 여유 공간이 있는 폴더로 정한다.
- 블록은 점프 VM 의 셸이 csh, tcsh, bash 중 무엇이든 같은 블록을 쓴다. 터미널이 줄바꿈을 CR+LF 로 보내도 된다.
- 명령에 `!`, 탭, 한글을 쓸 수 없다. csh 가 붙여넣는 글의 `!` 를 이전 명령 불러오기로, 탭을 자동 완성으로 처리하기 때문이다.
- 이름(케이스, 호스트, VM, 명령어 명, 프로파일 이름)은 영문, 숫자, `.` `_` `-` 만 쓴다. 호스트와 VM 이름은 영문이나 숫자로 시작해야 한다.
- VM 비밀번호는 점프 VM 작업 폴더의 `vmpw` 에만 저장한다(본인만 읽기). 생성기 파일, CSV, 블록에는 비밀번호가 들어가지 않는다. ESX 비밀번호는 저장하지 않는다. 비밀번호를 고칠 때는 점프 VM 에서 `sh ~/.tcgen/setpw` 를 실행한다.
- `Operations 주소` 를 적은 생성의 P 블록과 S 블록에는 Operations 계정, 암호화한 암호, 그 암호를 푸는 키가 들어 있다(붙여넣는 글에서는 보이지 않지만 풀 수 있다). 블록을 메일이나 메신저로 넘기지 않는다. 테스트 기록 CSV 와 로그 CSV 에는 이 값이 들어가지 않는다.
- 명령 목록과 테스트 케이스 파일은 화면에서만 고친다. 엑셀로 열어 저장하면 DRM 이 파일을 암호화해 생성기가 읽지 못할 수 있다.

## 11. 자주 나오는 출력

[명령어 생성] 이 내는 글은 한 줄이고, 고칠 칸과 값을 적는다.

| 글 | 할 일 |
| :-- | :-- |
| `오류: N번째 케이스 <이름>: 시작 시각 칸이 비어 있음. ...` | 그 케이스의 시작 시각 칸에 날짜 시각이나 `+간격` 을 적는다 |

| `오류: ... 시작 시각 <시각> 이(가) 이미 지났음 (지금 <시각>). 시각을 고칠 것` | 앞으로 올 시각으로 고친다. 실행한 케이스이면 적용 체크한다 |
| `오류: ... 시작 시각 <시각> 이(가) <케이스> 의 시작 시각 <시각> 과 5분 이상 떨어져 있지 않음. ...` | 두 시각 가운데 하나를 고친다(설정 영역의 `잡 시작 최소 간격`) |
| `오류: ... 시작 시각 <시각> 이(가) 같은 ESX 호스트의 앞 케이스(<시각>)보다 빠름. ...` | 표의 순서를 시작 시각 순서로 맞춘다 |
| `오류: ... 시작 시각을 <시각> 이후로 고칠 것. 설정이 앞 케이스와 달라 잡 시작 30분 전에 VM 을 종료하는데, ...` | 그 케이스의 시작 시각을 적힌 시각 이후로 늦춘다 |
| `오류: ... 모니터링을 중지할 시각 <시각> 이(가) 잡 시작 <시각> 보다 빠르거나 같음. ...` | 다음 케이스의 시작 시각을 늦추거나 최대 대기를 늘린다 |
| `오류: 설정: '설정 적용 N분 전'(10)은 '구성 스냅샷 N분 전'(10)보다 커야 함` | 설정 영역의 두 칸을 고친다 |
| `오류: 설정: 'Operations 암호' 를 입력할 것 ('Operations 주소' 를 비우면 Operations 에 기록하지 않음)` | 설정 영역의 `Operations 암호` 칸에 암호를 적고 Enter 를 누른다. 기록하지 않으려면 `Operations 주소` 를 비운다 |
| `알림: 마지막 케이스(<이름>)는 모니터링 중지 시각이 없음. ...` | 오류가 아니다. 정해진 때에 중지하려면 그 케이스의 `최대 대기` 칸에 시간을 적는다(7.5절) |
| `경고: N번째 케이스 <이름>: 잡, 모니터링, 설정이 하나도 없고 전원을 끌 VM 도 없어 건너뜀` | 그 케이스는 생성에서 빠진다. 잡을 지정했는지 확인한다 |

점프 VM 터미널의 출력은 다음과 같다.

| 출력 | 뜻과 할 일 |
| :-- | :-- |
| `FAILED  .../tcrun (sha256 differs. Paste block A again. ...)` | A 블록을 붙여넣는 중에 글자가 빠졌거나 작업 폴더에 쓸 수 없다. 작업 폴더의 여유 공간을 확인하고 A 블록을 다시 붙여넣는다 |
| `==== tcrun 2.12, plan made by tcgen 2.13: paste block A again. Nothing started.` | 점프 VM 의 진행 스크립트가 예전 판이다. A 블록을 다시 붙여넣는다 |
| `1 MB cannot be written in ... (disk full or disk quota ...)` | 작업 폴더나 로그 폴더에 쓸 수 없다. 설정 영역에서 두 폴더를 고치고 A 블록을 다시 붙여넣은 뒤 다시 생성한다 |
| `==== plan FAILED (sha256 differs)` | P 블록이나 S 블록을 붙여넣는 중에 글자가 빠졌다. 그 블록을 다시 붙여넣는다 |
| `==== esx01: run ... was already started on this jump VM` | 같은 S 블록을 두 번 붙여넣었다. 다시 실행하려면 다시 생성한다 |
| `queued:  run ... esx esx01   waiting for run ... to end (about <시각>, ...)` | 같은 ESX 호스트의 앞 실행이 진행 중이라 대기한다. 앞 실행이 그 시각쯤 `done` 으로 끝나면 스스로 시작한다 |
| `[PROBLEM] case <이름>: its job start is less than 2 min after the end of run ...` | 같은 ESX 호스트의 앞 실행이 끝나기 전에 시작해야 하는 케이스다. 대기하는 동안 시작 시각이 지나 등록되지 않는다. 시작 시각을 늦추거나, `sh ~/.tcgen/tcrun cancel esx01` 로 앞 실행을 끝내고 남은 케이스와 함께 다시 생성한다 |
| `crontab lines of case <이름> NOT removed on: <VM> ...` | `tcrun cancel` 이 그 VM 에 접속하지 못했다. 그 VM 의 잡은 아직 시작할 수 있다. 접속이 되는 때에 `sh ~/.tcgen/tcrun cancel esx01` 을 다시 실행한다 |
| `==== esx01: not started. run ... ended as paused and crontab lines of its case(s) are still on the hosts ...` | 앞 실행이 줄을 남긴 채 멈췄다. `sh ~/.tcgen/tcrun cancel esx01` 을 실행한 뒤 같은 S 블록을 다시 붙여넣는다 |
| `ssh key login failed ... Permission denied` | ESX 호스트에 키가 없다. 6.2절 |
| `[PROBLEM] VCF Operations: login to VCF Operations <주소> failed (account <계정>, curl exit N: ...)` | 주소, 계정, 암호를 확인한다. `curl exit 6` 이나 `7` 은 점프 VM 에서 그 주소로 접속하지 못한 것이다 |
| `[PROBLEM] vm <이름>: VCF Operations has no VirtualMachine object with this name. ...` | Operations 에 그 이름의 VM 객체가 없다. VM 이름이 vCenter 의 이름과 같은지 확인한다. 그대로 실행하면 그 VM 의 설정만 기록되지 않는다 |
| `[PROBLEM] case <이름>: its settings or VM power differ from the host, and the time to change them (...) has passed` | 첫 케이스의 잡 시작까지 30분이 남지 않았다. 시작 시각을 늦춰 다시 생성한다 |

| 항목 | 가짜 환경에서 가정한 것 | 확인 방법 |

| `esxcli system settings advanced list -o` 의 출력 | `Type: integer` 또는 `string`, `Int Value:`, `String Value:` 줄 | P 블록의 `TCGEN-HOST` 줄의 현재 값 |

| `esxcli vm process list` 의 출력 | VM 마다 `Display Name:`, `World ID:`, `VMX Cartel ID:` 줄이 있다(KB 1014165 의 형식) | 1GB page 를 쓰는 VM 을 켠 뒤 진행 로그의 `1GB page backing complete` |
| ssh 의 `-o LogLevel=ERROR` | 로그인 배너와 `Permanently added` 안내를 출력하지 않고, 접속 실패와 로그인 거부 같은 오류는 출력한다(OpenSSH 는 배너를 INFO 단계에서만 출력) | P 블록과 진행 로그에 배너 글이 섞이지 않는지 |
| `vsish -e get /memory/lpage/vmLpage/<world ID>` | `Current number of 1GB page backings:`, `1GB page backing attempts failed:` 줄이 있다. 앞선 시험에서 VM 을 켤 때 읽던 노드와 형식(사용자 확인 2026-09-23) | 위와 같음. 읽지 못하면 진행 로그에 `WARN ... could not be read` 가 남는다 |
| ESX 의 `/etc/ssh/keys-root/authorized_keys` | 줄을 추가하면 root 키 접속이 된다. 재부팅 뒤에도 남는지는 확인하지 않았다 | `sh ~/.tcgen/esxssh <ESX> hostname` |
| ESX 의 `sh`(busybox), `sha256sum`, `/bin/echo` | here-document, `read -r`, `printf` 가 dash 와 같게 동작 | 진행 로그의 `registered on esx` |
| ESX crond | `cron.update` 에 root 를 쓰면 1분 안에 crontab 을 다시 읽는다 | ESX 모니터링이 등록한 분에 시작하는지 |
| VM 의 cron | 등록 15초 뒤의 분에 새 줄을 실행한다 | 잡이 등록한 분에 시작하는지(잡 로그의 시각) |
| VM 의 `date -d @<초>` | GNU date | P 블록의 VM 줄 |
| 점프 VM 의 `setsid`, `base64 --decode`, `gzip`, `sha256sum` | util-linux, coreutils | A 블록의 `OK` 두 줄, S 블록의 `started:` |
| 구성 스냅샷의 VM 설정 | vmx 파일에 `numvcpus`, `memSize`, `sched.*`, `numa.*`, `monitor*` 키가 `키 = "값"` 줄로 적혀 있다(설정 적용이 고치는 파일과 같다). vSphere 가 기본값인 항목은 vmx 에 적지 않는다 | 첫 케이스의 구성 스냅샷 파일을 vCenter 의 VM 설정, config_snapshot 의 VM 표와 비교 |
| 구성 스냅샷의 Guest OS 설정 | 게스트의 일반 계정이 `/sys/kernel/mm/transparent_hugepage/*`, `/sys/kernel/mm/hugepages/*/nr_hugepages`, `/proc/sys/kernel/numa_balancing`, `/proc/cmdline` 을 읽을 수 있다. 점프 VM 에 `awk` 가 있다 | 구성 스냅샷 파일의 Guest OS 구간을 게스트에서 `guest_config_push.sh --dry-run` 으로 본 값과 비교. 진행 로그에 `WARN config snapshot` 이 없는지 |
| 스냅샷 때 VM 에서 실행할 명령 | 게스트(BM 서버 포함)의 그 경로에 guest_config_push 가 있고, BM 서버에는 1.1 이상의 판과 `--target auto` 또는 `--target bm` 이 필요하고, 접속 계정이 실행할 수 있고, 게스트에서 Operations 로 접속이 된다. 스크립트의 마지막 출력 줄이 결과를 알린다(`[OPS] ... recorded` 또는 `[ERROR] ...`) | P 블록의 `the file of the command at the config snapshot is there` 줄, 첫 케이스의 진행 로그 `config snapshot: command on vm ...: ok` 줄, Operations 의 VM 객체 속성 `Custom Configuration|Guest|Collected At` 의 시각 |
| 설정 변경에 걸리는 시간 | VM 종료, 설정 적용, VM 전원 ON(1GB page backing, ssh 로그인)이 30분(`설정 적용 N분 전`) 안에 끝난다. 메모리가 큰 VM 여러 대는 더 걸릴 수 있다 | 진행 로그의 `ssh login works, ready N s` 줄과 `registered:` 줄의 시각. 등록되지 않았으면 jobs.csv 의 `not registered` |
| 터미널을 닫은 뒤의 진행 | `setsid` 로 시작한 진행은 터미널을 닫아도 계속된다. 점프 VM 이 로그아웃할 때 사용자 프로세스를 모두 끝내게 설정돼 있으면(systemd-logind 의 `KillUserProcesses=yes`) 끝난다 | S 블록을 붙여넣고 터미널을 닫은 뒤 다시 접속해 `sh ~/.tcgen/tcrun status` |
| crontab 등록 뒤 잡의 시작 | 등록한 분에 cron 이 잡을 시작한다. 진행 스크립트는 잡이 시작됐는지 확인하지 않는다 | VM 의 잡 로그 |
| VCF Operations 기록 | suite-api 의 토큰 발급, 객체 조회(`adapterKindKey=VMWARE`, `resourceKind=VirtualMachine` 과 `HostSystem`, `name`, `regex`), 속성 기록이 guest_config_push 가 쓰는 것과 같게 동작한다. 계정은 인증 소스 LOCAL 이다. 점프 VM 에 curl, openssl 1.1.1 이상, python3 나 jq 가 있다 | P 블록의 `VCF Operations ...: login works` 와 객체 줄. 실행 뒤 Operations 의 VM 객체 속성 `Custom Configuration\|VM` |
| 300줄쯤 되는 A 블록 붙여넣기 | 터미널이 글자를 빠뜨리지 않는다. 빠뜨리면 `FAILED` 가 나온다 | A 블록의 `OK` 두 줄 |

## 13. v1.4 로 돌아가는 방법

v2 는 v1.4 의 프로그램, 데이터 폴더(`tcgen_data`), 설정 폴더(`%APPDATA%\tcgen`)를 고치지 않는다. v1.4 를 그대로 다시 실행하면 된다.

1. 점프 VM 에서 진행 중인 실행이 있거나 crontab 줄이 남아 있으면 `sh ~/.tcgen/tcrun cancel` 로 끝낸다. `sh ~/.tcgen/tcrun status` 로 확인한다.
2. PC 에서 v1.4 를 실행한다(`dist\tcgen\tcgen.exe` 또는 v1.4 소스 폴더의 `run_gui.bat`). v1.4 의 데이터가 v2 를 쓰기 전 상태 그대로 보인다. v2 에서 입력한 내용은 `tcgen2_data` 에만 있다.
3. 점프 VM 의 `~/.tcgen/vmssh`, `askpass`, `setpw`, `vmpw` 는 v1.4 와 같은 파일이다. v1.4 의 B 블록과 D 블록을 그대로 붙여넣을 수 있다. A 블록을 다시 붙여넣을 필요가 없다.
4. v2 가 VM crontab 에 남긴 줄이 있으면 지운다. 표식이 v1.4 와 같은 `# tcgen 케이스이름 호스트` 이므로 v1.4 의 D 블록으로 지운다.

v2 가 추가한 것을 지우려면 다음과 같이 한다. 지우지 않아도 v1.4 의 동작에는 영향이 없다.

| 위치 | 지울 것 |
| :-- | :-- |
| 점프 VM | `~/.tcgen/tcrun`, `tcgen_apply.py`, `esxssh`, `postsetup`, `id_esx`, `id_esx.pub`, `runs/` 와 점프 VM 로그 폴더 |
| ESX 호스트 | `/etc/ssh/keys-root/authorized_keys` 에서 점프 VM 의 키 줄, `/tmp/tcgen/` |
| 데이터스토어 | VM 폴더의 `<이름>.vmx.tcgen-<시각>` (설정을 적용하기 전의 vmx 복사본) |
| PC | `tcgen2_data`, `%APPDATA%\tcgen2`, `dist\tcgen2` |

v2 가 적용한 ESX 호스트 옵션과 vmx 의 키는 v1.4 로 돌아가도 그대로 남는다. 이전 값은 진행 로그의 `TCGEN-SET`, `TCGEN-HOST` 줄과 vmx 복사본에서 확인한다.

테스트 기록 CSV 를 v1.4 와 v2 가 같은 파일로 쓰는 경우(4.2절), v2 가 머리글 끝에 추가한 열(진행 방식, 설정, 실행 ID)은 v1.4 가 이어 쓸 때 빈칸으로 남는다.

## 14. 이전 판을 받는 방법

저장소에 올릴 때마다 판 번호를 올리고 그 커밋에 태그 `tcgen-v<판 번호>` 를 등록한다. 같은 판 번호로 다시 올리지 않는다(v2.12 부터). v1.0 부터 v2.11 까지의 태그는 2026-11-18 에 등록했다.

- 받기: GitHub 저장소 화면에서 `main` 버튼을 누르고 Tags 에서 판(예: `tcgen-v2.10`)을 고른 뒤 Code 의 Download ZIP 을 누른다. 주소로 받을 때는 저장소 주소 뒤에 `/archive/refs/tags/tcgen-v2.10.zip` 을 적는다.
- 압축 파일에는 그 시점의 저장소 전체가 들어 있다. v2 는 `tcgen_v2` 폴더, v1 은 `tcgen` 폴더만 쓴다.
- 이전 판으로 변경할 때는 그 판의 폴더로 다시 빌드하고(4절), 그 판의 A 블록을 점프 VM 에 다시 붙여넣는다. 생성기와 점프 VM 의 진행 스크립트는 판 번호가 같아야 한다.
- 데이터 폴더(`tcgen2_data`)는 v2 의 모든 판이 같이 쓴다. v2.8 부터 v2.13 까지는 데이터 형식이 같아, 서로 저장한 데이터를 값 변경 없이 읽고 저장한다(v2.12 와 그 앞의 판은 설정 파일의 Operations 값을 쓰지 않고 그대로 둔다). v2.7 과 그 앞의 판은 저장할 때 적용 체크한 케이스의 고정 값(모니터링 중지)을 지운다. v2.7 과 그 앞의 판을 쓰기 전에는 [설정 백업] 으로 데이터 폴더를 복사해 둔다.
- 같은 번호로 여러 번 올린 판(v1.0, v2.3, v2.5)의 태그는 그 번호의 마지막 상태에 있다.
- v2.12 에서 v2.11 과 그 앞의 판으로 돌아갈 때: 시작 시각의 `+간격` 은 그 판에서 같은 ESX 호스트의 앞 케이스 기준으로 계산된다. 설정 파일의 `설정 적용 N분 전`(30)은 그 판의 `시작 시각 준비` 값으로 읽힌다.

## 16. 개발 자료

구조, 설계 규칙, 고치는 절차는 `DEVELOPER.md` 에 있다. PC 가 점프 VM 에 넘기는 plan 의 형식은 `DEVELOPER.md` 5절에 있다.

- plan 은 줄 단위 글 파일이다. 첫 낱말이 종류(`CASE`, `SEG`, `START`, `MSTOP`, `VM`, `AH`, `AV`, `MS`, `JOB`, `MX`, `EMS`, `EMX`, `END` 등), 둘째 낱말이 케이스 번호다.
- 점프 VM 의 진행 스크립트는 plan 을 `grep`, `sed`, `cut` 으로만 읽는다. plan 의 글을 셸 명령으로 실행하지 않는다.
- `jump\tcrun.sh` 나 `jump\tcgen_apply.py` 를 고친 뒤에는 `python tools\make_payload.py` 를 실행하고, 점프 VM 에 A 블록을 다시 붙여넣는다.
